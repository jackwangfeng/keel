# 消息通知外发渠道接入（草案）

> **这是一份草案。** 本期一个真实外发渠道都没有接：微信订阅消息、短信、邮件都需要资质，
> 而这些资质本项目还没有。本文写的是「将来拿到资质后怎么接」，其中的环境变量名、模板映射方式
> 都**尚未实现**，落地时以当时的代码为准。已经实现、可以依赖的部分会明确标出。

站内消息（买家消息中心、后台铃铛）**不受本文影响**：它就是 `notifications` 表里那一行本身，
在订单 / 售后状态变化的同一个事务里就写好了，不经过任何外发渠道。设计见
[数据模型 §16](../电商系统-数据模型设计.md)。

---

## 已经就位的部分（已实现）

- **outbox**：每条通知写入时，同一个事务往 `jobs` 表入一条 `notification.deliver` 任务，
  payload 只有 `{"notification_id": …}`。
- **worker**：`internal/service/notification_delivery.go` 的 `NotificationDeliveryService`，
  随进程启动（`internal/app/app.go` 的 `Run`）。复用 `jobs` 队列的出队（每租户在途上限 + 兜底）、
  指数退避（2、4、8……秒）、五次后转死信、回收卡死任务、成功任务保留 7 天。
- **渠道接口** `service.NotificationChannel`：

  ```go
  type NotificationChannel interface {
      Name() string                                        // wechat_subscribe / sms / email
      Configured() bool                                    // false → 不调 Send，记「跳过」
      Send(ctx context.Context, m NotificationMessage) error
  }
  ```

  `NotificationMessage` 带着渲染好的标题正文、种类（`kind`）、收件人（买家 `UserID` 或门店 `StoreID`）、
  跳转目标（订单号 / 退款单号）与 `NotificationID`。
- **默认实现**：`DefaultNotificationChannels()` 返回三个「未配置」的渠道。**一个渠道都没配置时
  （本期默认），写入口（`emitNotification`）根本不产生 `notification.deliver` 任务**——不是
  「入队之后各记一行 status = 2 跳过」，压测（`docs/性能压测-2026-10.md` §5）量到旧行为高峰积压
  5 万多个待办之后改的。判据是 `anyChannelConfigured()`（`notification_delivery.go`），今天是
  进程级的，不是按商户 / 按渠道的。
- **投递记录** `notification_deliveries`：有渠道配置、任务真的入队时，每个渠道每一次尝试一行
  （1 已发出 / 2 跳过 / 3 失败）；没有任何渠道配置时这张表不会因为这条通知多一行。

## 接一个渠道要做的事

1. 在 `internal/service/`（或新建一个渠道包）实现 `NotificationChannel`：
   - `Name()` 返回三个名字之一（`00053` 的 `CHECK` 约束只收这三个；要加第四个渠道，先加迁移）；
   - `Configured()` 在凭据齐全时返回 `true`；
   - `Send` 自己按 `m.UserID` / `m.StoreID` 查收件人。**查不到收件人**（买家没授权订阅消息、
     没绑手机号）返回 `service.ErrNoRecipient` —— worker 记成「跳过」而不是失败，因为重试不会让它变好；
     渠道真的出错（超时、限流、签名错）返回普通错误 —— worker 记「失败」并退避重试。
2. 在 `app.Run` 里把 `NewNotificationDeliveryService` 的第二个参数从 `nil`（= 当前生效清单，默认
   三个未配置渠道）换成一份清单，**只替换已接入的那一项**，其余保留未配置的默认实现 —— 顺序就是
   投递顺序。**同时调一次 `service.SetNotificationChannels(同一份清单)`**——写入口
   `emitNotification` 判断「要不要入队」看的是这份全局清单，不是 `NewNotificationDeliveryService`
   这个服务实例自己持有的那份；只换掉后者会出现「worker 真的在发，写入口却仍然按旧清单觉得
   没渠道、连任务都不入队」这种两边各看各的漂移。
3. 写测试：替身渠道的写法见 `internal/handler/notification_test.go` 的 `fakeChannel`；测试里
   同理要先调 `service.SetNotificationChannels` 把替身注册成「已配置」，**且必须在触发通知的
   业务动作（下单、支付回调……）之前调**——是否入队在通知写入的那一刻就定了，之后才建的
   worker 改变不了这一点，用完记得 `t.Cleanup` 换回 `nil`（默认）。

worker 本身不用改。

## 建议的配置项（草案，未实现）

| 环境变量 | 用途 |
|---|---|
| `KEEL_NOTIFY_WECHAT_APPID` / `KEEL_NOTIFY_WECHAT_SECRET` | 小程序凭据，换 `access_token` 调 `subscribeMessage.send` |
| `KEEL_NOTIFY_WECHAT_TEMPLATES` | `kind=模板id` 的逗号分隔列表，例如 `order_shipped=AbC…,refund_succeeded=XyZ…` |
| `KEEL_NOTIFY_SMS_PROVIDER` | 短信服务商（`aliyun` / `tencent` …） |
| `KEEL_NOTIFY_SMS_KEY` / `KEEL_NOTIFY_SMS_SECRET` / `KEEL_NOTIFY_SMS_SIGN` | 凭据与报备过的签名 |
| `KEEL_NOTIFY_SMS_TEMPLATES` | `kind=模板CODE` 的逗号分隔列表 |
| `KEEL_NOTIFY_SMTP_ADDR` / `KEEL_NOTIFY_SMTP_USER` / `KEEL_NOTIFY_SMTP_PASSWORD` / `KEEL_NOTIFY_MAIL_FROM` | 发信服务器与发件人 |

原则：**缺任何一项就是「未配置」**（`Configured()` 返回 `false`），不要半配置地去发。
多租户部署里各商家可能有各自的小程序与短信签名，那时凭据应当挪到 `shop_settings.extra`
（与支付回调密钥 `payment_channels` 同一个位置），`Configured()` 按 `m.MerchantID` 判。

## 各渠道要准备的东西

### 微信订阅消息（只对买家）

- **资质**：已上线的小程序、在小程序后台申请的订阅消息模板（一次性订阅）。
- **收件人**：买家的 openid（`user_identities`，微信登录落地之后才有）+ 用户对**这个模板**的订阅授权。
  一次性订阅是「授权一次、发一条」，客户端要在合适的时机（下单成功页、申请售后后）调
  `wx.requestSubscribeMessage`。**今天缺**：微信登录（接口返回 501）、订阅授权的记录表。
- **模板映射**：每个 `NotificationKind` 对应一个模板 id 与字段映射（模板字段有长度与格式限制，
  `title` / `body` 要按模板拆字段，不能整段塞进去）。建议先只接 `order_shipped`、`refund_succeeded`、
  `refund_rejected` 三种。
- **商家侧通知**不走这条（员工不是小程序用户），`Send` 对 `m.StoreID != nil` 返回 `ErrNoRecipient`。

### 短信

- **资质**：短信签名与模板在服务商处报备通过（营销类与通知类分开，通知类才适合这里）。
- **收件人**：买家 `users.phone`；商家侧需要「这家门店的提醒发给谁」—— **今天缺**：员工手机号字段与
  「接收短信提醒」的开关。
- **模板映射**：`kind` → 模板 CODE，变量从通知参数取（订单号、金额、运单号）。短信按条计费，
  建议只接高价值的种类（发货、退款到账），不要全量开。

### 邮件

- **资质**：发信域名（SPF / DKIM）与 SMTP 凭据。
- **收件人**：主要是员工（`staff.email`）；买家没有邮箱字段。**今天缺**：员工「接收邮件提醒」的开关。
- 正文可以直接用 `title` / `body`，外加一个跳到后台对应页面的链接。

## 投递语义：至少一次

一次投递分三段：读通知（租户事务）→ 逐渠道发送（**事务外**）→ 记结果（租户事务）。
重试时已经有定论（发出 / 跳过）的渠道不再碰，所以「短信发出去了、邮件失败了」重试时只重发邮件。
但如果**发送成功之后、记结果之前**进程崩溃或数据库断开，整条任务会被回收重来，那一路会再发一次。
所以外发是「至少一次」：

- 渠道实现应当把 `NotificationID` 作为幂等键传给服务商（有此能力的话），或在自己这一侧去重；
- 不要为了「恰好一次」把网络调用放进数据库事务 —— 那会把订单行锁拖长，而且发出去的短信回滚不了。

## 失败、退避与死信

- 渠道返回普通错误 → 这一路记 `status = 3`，任务按 `1 秒 × 2^attempts` 退避后重来；
- 五次仍失败 → 任务转死信（`jobs.status = 3`，`last_error` 里是各渠道的错误），不再自动重试，
  要人看。复活一条死信：修好原因后把它的 `status` 改回 `0`、`attempts` 清零。
- 通知过了保留期（90 天）被删掉之后才轮到的任务，直接标成功（没有东西可投）。

## 怎么查投递记录

```sql
-- 某一单的通知各渠道投递情况（以管理员连接执行，或在租户事务里去掉 merchant_id 条件）
SELECT n.id, n.kind, n.title, d.channel, d.status, d.attempt, d.detail, d.created_at
  FROM notifications n
  LEFT JOIN notification_deliveries d ON d.notification_id = n.id
 WHERE n.merchant_id = 1 AND n.order_no = '20260927...'
 ORDER BY n.id, d.id;

-- 最近一天各渠道的结果分布
SELECT channel, status, count(*)
  FROM notification_deliveries
 WHERE created_at > now() - interval '1 day'
 GROUP BY 1, 2 ORDER BY 1, 2;

-- 卡在死信里的外发任务
SELECT id, merchant_id, job_key, attempts, last_error, updated_at
  FROM jobs WHERE queue = 'notification.deliver' AND status = 3
 ORDER BY updated_at DESC;
```

## 为什么不写假实现

一个「假装发了」的短信渠道会让投递记录里全是「已发出」，而用户一条都没收到 ——
「为什么没收到短信」从一句 SQL 就能回答的问题，变成要去翻代码才能发现渠道是假的。
所以本期三个渠道明写「未配置、跳过」，原因写在 `detail` 里；测试用的替身只存在于测试代码里。
