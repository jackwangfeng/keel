# 部署与配置

这篇讲怎么把 Keel 从「本机演示」变成「给真实客人用」：有哪些形态、每个环境变量管什么、
上线前哪些默认值必须改。

---

## 部署形态

| 形态 | 怎么起 | 租户怎么确定 |
|---|---|---|
| **单商家**（默认） | `docker compose up -d` | 所有请求都属于 `KEEL_DEFAULT_MERCHANT` 那一家，请求里不用带任何东西 |
| **多商家** | **`make multi-up`**（底层是 `scripts/multi-up.sh`；不建议手写那行 compose，理由见下） | 由请求的 `Host` 决定：`<商家code>.<KEEL_BASE_DOMAIN>`，或商家绑定的自有域名 |
| **带语义搜索** | 先 `./scripts/infero-up.sh`，再叠加 `-f compose.infero.yaml` | 同上，和前两种正交 |
| **拆分 B 档**（同一个 Postgres，库存独立 schema + 账号） | `docker compose -f compose.yaml -f compose.split-b.yaml up -d --build` | 同上 |
| **拆分 C 档**（core 与库存各一个进程、各一个库，事务协调器独立部署） | `KEEL_INTERNAL_SECRET=$(openssl rand -base64 48) KEEL_DTM_TOKEN=$(openssl rand -hex 24) docker compose -f compose.yaml -f compose.split.yaml up -d --build` | 同上 |

**单商家换多商家不用换架构。** 表结构、行级安全、接口都是同一套；区别只在
「从哪儿知道这个请求属于哪家店」。

多商家形态有自己的一组卷（`keel_pgdata_multi` 等；前缀是项目名，`-p` 换了就跟着换），和单商家的数据互不影响。拆分形态同理（`<项目名>_pgdata_split` 等），所以用不同 `-p` 起的几套栈各用各的卷。
它播的是 `db/seed/dev.sql`（多家演示店），不是单商家的 `single.sql`。

**起这一形态请用 `make multi-up`，不要手写那两行 compose。** 三条理由，都是踩过的：

- **项目名不能省，而且必须是新的。** 叠加层只给**卷**加了 `_multi` 后缀，**容器名仍由项目名派生**。
  用默认项目名（`keel`）叠上去不是「并存两套」，是把那一份单商家开发栈原地换掉。
  `scripts/multi-up.sh` 固定用 `keelmulti` 与宿主机端口 28185 / 28186，与演示栈、生产栈、CI 互不打扰；
  端口被占它会在 compose 报 `address already in use` 之前先停下来说清是哪一个（**这一栈自己在跑不算占**：
  `--build` 是原地升级这一栈的唯一路径，它必然打回这两个端口）。
- **它还会把签名密钥落在 `~/.config/keel/multi-auth-secret`（0600，不进仓库）。**
  不设 `KEEL_AUTH_SECRET` 时应用每次启动随机取一把，于是「重建一次这一栈」= 买家令牌与后台会话全部作废，
  而验收脚本缓存的平台会话也作废 —— 换不回来（引导 token 只在库里没有在岗平台管理员时才签，而这一栈已经有了），
  只剩 `--wipe` 一条路。换个项目名并起跑这一栈（`COMPOSE_PROJECT_NAME=xxx ...`）时可以用
  `KEEL_MULTI_AUTH_SECRET_FILE` 指到别的文件，否则两套栈共用一把密钥。
- **起完必须验收。** `docker compose up -d` 只等到容器启动，应用随后因启动自检不过而退出，它照样返回 0。
  `make multi-up` 起完自动跑 `scripts/multi-verify.sh`（102 项，判据是「必须等于某个具体值」）：
  Host 解析的十个分支、两家店的商品互不相交、同一个手机号在两家店是两个账号、
  **按 id 的跨租户点查与写入**（别家的商品 / 门店 id → 404，别家的 `store_id` → 422 而不是被忽略，
  别家的 sku 挂进本店活动 → 422 且 detail 点名那个 id；平台会话切进店之后同样挡住），
  **渠道回调的密钥按租户取**（拿 b 家的密钥签出的报文打到 a 家 → 401 且响应体是空的，
  而同一份报文用 a 家自己的密钥 → 200；这一对才是证据，单看 401 什么也证明不了），
  开店与幂等回放、商家级会话碰不到租户管理（403 且按 problem type 分）、
  `X-Keel-Merchant` 切店、停用后买家侧 404 而平台仍管得到、
  **自有域名登记的三态与三道闸门**（登记之后那个 Host 真的通到这家店；只改店名不动入口；
  落在平台基础域名之下 / 不像域名 / 已被别家占着，分别 422、422、409，而且抢失败之后
  那一家自己的入口还在；`domain: null` 摘掉之后旧域名 404 而子域名入口照常）。
  **一次性登录凭据走接口而不是日志**（开店的 201 带着新店第一个管理员的 `admin_login_token`
  与 `admin_staff_id`；拿它在新店自己的 Host 上换得到会话、第二次换 401；同一把幂等键的重放
  里没有凭据 —— 明文不进数据库，想回放也没有；而这串明文在 app 日志里搜不到）。
  检索那一路与 `jobs` 那张表**刻意没有断言**，理由写在脚本文件头（前者在本栈里恒为 0 条，
  0 条证明不了隔离；后者压根没有 HTTP 出口，是 `db/tenancy.json` 里明登记的不做 RLS 的队列类）。
  `make multi-verify` 单独跑，`multi-down` / `multi-wipe` / `multi-logs` / `multi-config` 是其余四个动作。
- **买家侧要带 Host 才解析得到**，`curl http://127.0.0.1:28185/api/v1/products` 直接打是 404，那不是坏了：
  `curl -H 'Host: shop-a.example.com' http://127.0.0.1:28185/api/v1/products`。
  商家后台在 `http://localhost:28186/admin/`，进去要平台级会话；
  首个平台管理员的一次性 token 只打在应用日志里（`make multi-logs`），本项目没接 SMTP。

### 启动自检

应用启动时会先做几项检查，**对不上就拒绝启动，不会猜**：

- 连数据库用的角色**不能**绕过行级安全（不能是超级用户，也不能有 `BYPASSRLS`）。
  compose 里应用用的是 `keel_app`，迁移用的是 `keel`，这是刻意分开的。
- 单商家形态下，`KEEL_DEFAULT_MERCHANT` 必须真的存在，而且库里只能有这一家活跃商家。
- `KEEL_DTM_DSN` 必须配置（见下文）。

## 拆分部署（B / C 档）

三档只差「库存数据放在哪、用哪个账号连」，代码一行不变（为什么这么拆见
[微服务拆分方案](../电商系统-微服务拆分方案.md)「部署档位」）。从单体迁过去都是同一件事：
建库存迁移 → `scripts/split-migrate.sh copy` → `cutover` → 改环境变量重启。

**切换要停写。** 先停 core 的公网入口与后台任务，等协调器里没有未完成的全局事务，再 copy。
脚本在目标四张表全空时才导入，目标已有数据就只核对、绝不覆盖；cutover 之后再跑两条都直接跳过。
两个连接串都用管理员角色（要绕过 RLS 读写全部商家）。

**B 档**（同一个 Postgres）：从零起一个 B 档栈就是上表那一条命令（`compose.split-b.yaml`，一个进程，自己的一套卷）。
把一个已有的单体库迁到 B 档：

```bash
export SRC_DSN='postgres://keel:<管理员口令>@<库>:5432/keel?sslmode=disable'
export DST_DSN="$SRC_DSN&options=-csearch_path%3Dinventory"
KEEL_INVENTORY_PASSWORD=<新口令> scripts/split-migrate.sh prepare-b   # 建 inventory schema 与 keel_inventory
KEEL_INVENTORY_ROLE=keel_inventory KEEL_INVENTORY_PASSWORD=<新口令> \
  make migrate-inventory INVENTORY_GOOSE_DBSTRING="$DST_DSN"
scripts/split-migrate.sh copy && scripts/split-migrate.sh cutover
```

然后应用（仍是一个进程，`KEEL_ROLE=all`）加一行
`KEEL_INVENTORY_DSN='postgres://keel_inventory:<新口令>@<库>:5432/keel?sslmode=disable&options=-csearch_path%3Dinventory'`，重启。
之后 `keel_app` 查 `inventory.*` 在权限检查这一步就被拒，`keel_inventory` 也读不到 core 的任何一张表。
想拆成两个进程：再起一个 `KEEL_ROLE=inventory` 的实例用同一个 `KEEL_INVENTORY_DSN`，core 改 `KEEL_ROLE=core` + `KEEL_INVENTORY_URL`。

**C 档**（另一个库）：`compose.split.yaml` 就是完整的样例 —— 它每次起新栈都用同一个脚本把种子里的库存搬进库存库。
把一个真实的单体库迁过去：在新库上 `KEEL_INVENTORY_ROLE=keel_inventory make migrate-inventory`，
`DST_DSN` 指向新库跑 `copy` / `cutover`，core 改 `KEEL_ROLE=core` + `KEEL_INVENTORY_URL` + `KEEL_INTERNAL_SECRET`，
库存进程 `KEEL_ROLE=inventory` + `KEEL_INVENTORY_DSN` + `KEEL_INTERNAL_ADDR` + 同一个 `KEEL_INTERNAL_SECRET`。
事务协调器（dtmrs）**独立部署**（`compose.split.yaml` 里的 `dtmrs` + `postgres-dtm`，[微服务部署方案](../电商系统-微服务部署方案.md)）：
core 与库存都配 `KEEL_DTM_SERVER` + `KEEL_DTM_TOKEN` + `KEEL_INTERNAL_ADDR` + `KEEL_SELF_URL`（本服务内网端口的服务地址，写服务名），
都**不**配 `KEEL_DTM_DSN`。库存把跨 0 通知发到主题、core 启动时订阅，库存不需要知道 core 的地址（`KEEL_CORE_URL` 已停用）。
**从旧的嵌入式切过来**：先停止接新单，等两个进程各自的 sqlite 协调器里没有未终结的事务（管理台或 `GET /api/dtmsvr/all`），再切配置——
在途事务不跨存储迁移。

**回滚**：刚切完、还没接流量时 `scripts/split-migrate.sh rollback`（把 `keel_app` 的权限还回源库）再改回单体配置。
接过流量之后，库存服务里的变化不在源库里，要先把目标四张表反向拷回（见脚本文件头）。

**库存服务不在时**（C 档实测，杀掉 inventory 容器下单）：`POST /orders` 等 15 秒后回 409 `idempotency-key-in-flight`，
订单已在买家列表里但**付不了**（409 `order-status-not-payable`，00085）；库存服务回来后，协调器在下一次重试时把 SAGA 推完
—— 重试按退避走，**最长约 5 分钟**才轮到下一次，不是回来就立刻推。

**对账**：core（`all` / `core`）每小时跑一轮库存对账，只读只报：孤儿库存行（SKU 或门店在 core 里已不存在）、
上线活动的配额行与 `promotion_skus` 的差集、进了死信的 `inventory.release` 任务。发现差异打 WARN 带明细。

## 环境变量

### 应用（`app` 服务）

| 变量 | 默认值 | 说明 |
|---|---|---|
| `KEEL_ADDR` | `:8080` | 监听地址 |
| `KEEL_SHUTDOWN_GRACE` | `20s` | 收到 SIGTERM / SIGINT 后的优雅停机宽限期（Go duration）：先停止接新请求、等在途请求做完，再停后台任务并等它们退出（各最多这么久），最后关事务协调器与连接池。超时的在途连接被强关。要比编排系统的强杀期限短（`docker stop` 默认 10 秒，compose 里可用 `stop_grace_period` 调长；k8s 默认 30 秒）。公网端口上 `/healthz` 只表示进程活着，`/readyz` 还要能 ping 通业务库 |
| `KEEL_BACKGROUND` | `on` | 本进程跑不跑后台任务：`on` / `off`，写错拒绝启动。`off` 时一个都不跑（超时补偿、自动确认收货、库存 outbox、通知投递等），**至少要有一个实例开着**。多实例都开着也可以：扫描 / 对账 / 刷新类任务（超时补偿、自动确认收货、退货超时关闭、孤儿文件回收、库存对账、有货标记刷新、多收款退回扫描、AI 员工提案过期与复盘、AI 员工事件扫描）靠 PostgreSQL 会话级咨询锁只在一个实例上跑（持锁实例停掉后约 15 秒内别的实例接手；持锁实例**冻住**（docker pause、宿主机卡死）或网络分区时，选主那条专用连接上设了 `idle_session_timeout = 45s`（ping 间隔 15 秒的 3 倍）与服务端 TCP keepalive（约 30 秒判死），服务端断开它的会话、锁随之释放，别的实例在一分钟内接手 —— `idle_session_timeout` 要 **PostgreSQL 14+**，更老的版本上设不上只告警，冻住的实例不会被接替；因此业务库连接**不能**经过 PgBouncer 的事务池模式），jobs 队列与 outbox 的消费者（库存 outbox、通知投递、AI 员工 webhook 投递、商品派生数据入库）各实例并行。任一后台任务 panic 只记 ERROR 并退避重启，不崩进程 |
| `KEEL_DEFAULT_MERCHANT` | compose 里是 `demo` | 单商家形态下那家店的 code。多商家形态必须留空 |
| `KEEL_BASE_DOMAIN` | — | 多商家形态的平台基础域名，`shop1.<它>` 解析到 code 为 `shop1` 的商家 |
| `KEEL_DTM_DSN` | 单体必须配（或改用 `KEEL_DTM_SERVER`） | **嵌入式**事务协调器的存储，只有单体（`KEEL_ROLE=all`）用。单机用 `sqlite:/var/lib/keel/dtm.db`（compose 已配好并挂了卷）；单体多实例要换成 Postgres / MySQL，并给它单独的数据库角色。与 `KEEL_DTM_SERVER` 只能配一个；`core` / `inventory` 配了拒绝启动 |
| `KEEL_DTM_SERVER` | 空（嵌入式） | **独立部署**的事务协调器（dtmrs 0.12+）地址，如 `http://dtmrs:36789`，写服务名。微服务形态（`KEEL_ROLE=core` / `inventory`）必须用它：服务只是客户端，下单 SAGA、二阶段消息都由它推进，它经内网回调各服务的分支。配了就必须同时配 `KEEL_DTM_TOKEN`、`KEEL_INTERNAL_ADDR`、`KEEL_SELF_URL` 与 `KEEL_INTERNAL_SECRET` |
| `KEEL_DTM_TOKEN` | — | 独立协调器的令牌（dtmrs 的 `DTMRS_AUTH_TOKEN`，`openssl rand -hex 24`）。Keel 拒绝连没开认证的协调器 |
| `KEEL_SELF_URL` | — | 本服务内网端口的**服务地址**（如 `http://app:8091`、`http://inventory:8090`），协调器回调本服务分支、订阅主题时登记的就是它。写经过负载均衡的服务名，不写实例 IP——多实例共用这一个地址 |
| `KEEL_AUTH_SECRET` | 留空则随机生成 | 买家令牌的签名密钥。**生产必须配**，见下文 |
| `KEEL_PAYMENT_SANDBOX` | 开 | 沙箱支付。**收钱的部署必须设为 `off`** |
| `KEEL_UPLOAD_ROOT` | compose 里是 `/var/lib/keel-uploads` | 上传文件（商品图、凭证）的本地目录。不配会落到临时目录，容器重建即丢。`KEEL_UPLOAD_DRIVER=s3` 时仍配着的话，磁盘上的旧文件照旧读得到（按行路由），存量搬完再撤 |
| `KEEL_UPLOAD_DRIVER` | `local` | 上传文件存哪：`local`（本地磁盘，单实例）/ `s3`（S3 兼容的对象存储：AWS S3、阿里云 OSS、腾讯云 COS、SeaweedFS…，多实例 / k8s / serverless 要它）。写错拒绝启动 |
| `KEEL_S3_ENDPOINT` / `KEEL_S3_BUCKET` | — | 对象存储地址（`http(s)://host[:port]`，协议决定是否 TLS）与桶名。`s3` 时必填；桶要事先建好（Keel 不替你建），连不上或桶不存在时拒绝启动 |
| `KEEL_S3_ACCESS_KEY` / `KEEL_S3_SECRET_KEY` | — | 对象存储的凭据。只需要这个桶的读、写、列、删权限 |
| `KEEL_S3_REGION` | `us-east-1` | 地域。OSS / COS 填对应地域（如 `oss-cn-shenzhen` 的地域名），SeaweedFS 等自建的不在乎 |
| `KEEL_S3_ADDRESS_STYLE` | `auto` | 桶怎么出现在地址里：`path`（`host/bucket/key`，SeaweedFS 等自建的要）/ `virtual`（`bucket.host/key`，OSS、COS 要）/ `auto`（按已知域名自动判） |
| `KEEL_S3_PREFIX` | 空 | 桶里的对象名前缀（如 `keel/`），几个部署共用一个桶时分开 |
| `KEEL_S3_PRESIGN_ENDPOINT` | 空（不直连） | 浏览器能访问到的对象存储地址。配了就让图片 302 直连对象存储的预签名地址（5 分钟），字节不经过应用；不配时图片由应用读出，桶可以完全私有 |
| `KEEL_EMBED_ENDPOINT` | — | 推理引擎地址。不配时搜索只走关键词那一路（正常降级，不是故障） |
| `KEEL_SYSTEMONE_ENDPOINT` | — | 判别模型引擎地址（`/v1/systemone`，Kev / Jev / infero 通用）。配了且 `KEEL_EMBED_ENDPOINT` 也在时，后台每小时给热词（7 天内搜过 ≥3 次）的向量路候选做相关度预判，检索命中预判就按它留或去、不再看余弦下限。不配时检索只按余弦下限（正常，不是故障） |
| `KEEL_CHANNELS` | 关 | 渠道适配层（Shopify / 美团闪购 / 饿了么零售……，`docs/superpowers/specs/2026-10-02-channel-adapter-design.md`）的进程开关：`on` / `off`，拼错拒绝启动。关着时没有任何渠道路由（后台不显示「渠道」菜单）、分支与后台任务，库存服务一次都不查 `channel_merchants` —— 不接渠道的部署与没有这一层时完全一样。开着时只有接了启用中销售渠道的商家会在可售数变化时多发一条 `stock.changed`。**拆分部署时 core 与库存服务要配同一个值** |
| `KEEL_CHANNEL_DEMO` | 关 | 演示站用的「演示外卖（模拟）」渠道（`demo_takeout`，`internal/channel/demotakeout`：背后没有真实平台，订单由演示站模拟器签名推进来）：`on` / `off`，拼错拒绝启动。关着时注册表里没有它，后台建不了这种账号、`/admin/channel-kinds` 不列它。只在 `KEEL_CHANNELS=on` 时有意义；正式部署不要开 |
| `KEEL_SYSTEMONE_TOKEN` | — | 判别模型引擎要的 Bearer 令牌（共享实例、Jev 云端要；本机引擎不用）。只走环境变量 |
| `KEEL_SEARCH_RATE_PER_SEC` | `12` | `/search` 每个 IP 每秒允许的请求数 |
| `KEEL_SEARCH_RATE_BURST` | `12` | `/search` 每个 IP 的瞬时额度 |
| `KEEL_DB_MAX_CONNS` | pgxpool 默认（max(4, CPU 核数)） | 业务连接池上限。多实例时与 `DTMRS_DB_POOL`（事务协调器的池，默认 32）一起按「实例数 × 两者之和 < max_connections」配 |
| `KEEL_DB_STATEMENT_TIMEOUT` | `15s` | 应用连接池（业务池、库存池，`keel-index` 也走同一个池）上单条语句的上限，作为连接启动参数发给服务端。`0` = 不发。连接串里自带 `statement_timeout` 时以连接串为准。迁移走 goose 自己的连接，不受影响。撞上它（57014）或撞上下面的 `KEEL_DB_LOCK_TIMEOUT`（55P03）的请求回 503 `busy` + `Retry-After: 3`（确定没生效，可原样重试；同一请求里更早的步骤已提交过的仍回 500），不再是 500 |

## 上线前必须改的

照着 `docker compose up` 起来的是一套**演示**配置。下面几项不改，就不要拿它服务真实客人：

1. **`KEEL_AUTH_SECRET`**：配一个足够长的随机值，并且所有实例用同一个。

   ```bash
   KEEL_AUTH_SECRET=$(openssl rand -base64 48)
   ```

   留空时应用会随机取一个并打 WARN。后果是每次重启所有买家被登出；多实例下各实例密钥不同，
   表现为「刷新几次页面就要重新登录」。compose **刻意不给默认值**：写在公开仓库里的默认密钥，
   等于任何人都能给任何一家店签出合法令牌。

2. **`KEEL_PAYMENT_SANDBOX=off`**：沙箱开着时，买家可以把自己的订单免费推成「已支付」。
   它默认开着是为了让演示能跑通，启动日志里会有一条 WARN 提醒你。
   只认 `off` / `false` / `0` 三种写法，写错（比如 `no`）会被当成**开**——这是刻意的，
   写错时宁可让你看到 WARN，也不要让你误以为已经关了。

3. **数据库口令**：改掉 `KEEL_ADMIN_PASSWORD` 和 `KEEL_APP_PASSWORD`。

4. **删掉种子买家**：单商家种子里有一个固定口令的买家（`13800000000` / `keel-demo-2026`），
   演示用的。生产库不要播种子，或者播完删掉这个账号。

5. **备份三个卷**：`pgdata`（业务数据）、`dtmdata`（未完成的分布式事务）、`uploads`（上传文件）。
   `dtmdata` 丢了的后果是：已经扣掉的库存、已经锁住的券，再也没人去回补。

   备份用 `pg_dump -Fc`，但**要当它不含授权**：实测导出的 `.dump` 里 `TABLE ACL` 条目为 0。
   如果这份备份的用途包含「重建 schema 后恢复」（迁移试跑、误删库后救回），
   恢复出来的表会对 `keel_app` 零授权，应用报 `permission denied for table xxx`。
   恢复后必须核对两条：

   ```bash
   docker exec <pg容器> psql -U keel -d <库> -tAc \
     "SELECT count(*) FROM information_schema.role_table_grants WHERE grantee='keel_app'"
   # 基线 318；恢复后偏低就是丢了
   docker exec <pg容器> psql -U keel -d <库> -tAc "SELECT count(*) FROM pg_default_acl"
   # 应为 2（建表四权 + 序列 + 00005 的收紧）；查出来 0 就是丢了
   ```

   丢了这样补（两条**分开执行**，写在同一个 heredoc 里顺序可能互相抵消）：

   ```sql
   -- 00003 与 00005 的默认权限
   ALTER DEFAULT PRIVILEGES FOR ROLE keel IN SCHEMA public
     GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO keel_app;
   ALTER DEFAULT PRIVILEGES FOR ROLE keel IN SCHEMA public
     GRANT USAGE, SELECT ON SEQUENCES TO keel_app;
   ALTER DEFAULT PRIVILEGES FOR ROLE keel IN SCHEMA public
     REVOKE INSERT, UPDATE, DELETE ON TABLES FROM keel_app;
   -- 存量表补齐
   GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO keel_app;
   ```

6. **后台引导 token**：第一次启动时打在日志里。用完即失效；如果你的日志会被收集到别处，
   记得在引导完成之后确认它已经被用掉。**除它以外没有别的凭据进日志** ——
   员工的登录 token 走 `POST /admin/staff/{id}/login-token` 的响应体，
   新店第一个管理员的走 `POST /admin/merchants` 的 201，日志里只剩「什么时候给谁签过」
   这条事实。反过来说：既然引导 token 一定会进日志，**app 的日志不要接到会被索引、
   会被很多方读到的地方**（第三方日志平台、集中检索、工单附件都算），
   或者接之前先在那一侧把 `bootstrap_token=` 那一行过滤掉。

这份清单是散文，靠人记。其中五条已经做成了机器强制（缺项在 compose 解析阶段就停），
见下一节。

## 生产部署（自助上线路径）

上面那六条是散文清单，人要自己记着逐条改。`compose.prod.yaml` 把其中五条做成了机器强制：
没配的项在 compose 解析阶段就停，沙箱与演示渠道直接关掉，演示数据不播。


### 两套栈同时跑时，配置别共用文件名

docker compose 会**自动读项目根的 `.env`**，裸 `docker compose up` 也不例外。所以同一个项目里
跑两套栈时，生产配置必须叫别的名字（本项目用 `.env.prod`，prod 栈用 `--env-file` 显式指定）。

踩过的症状：演示栈的 migrate 报 `password authentication failed`，而口令本身是对的——
它拿到的是另一套栈的口令。真因与症状指向完全相反，按「口令错了」去查会一无所获
（去 ALTER ROLE、去看卷、去看 compose，都找不到「这个文件是给谁用的」）。

给任何新的环境配置加文件名之前，先确认裸 compose 会不会自动读它。

### 为什么是 `.env.prod` 而不是 `.env`

docker compose 会**自动读项目根的 `.env`**，裸 `docker compose up`（演示栈）也不例外。
生产口令如果放在 `.env` 里，演示栈的 migrate 就会拿着生产口令去连演示库，报
`password authentication failed` —— 而真因是两个栈曾经共用这一个文件名，
症状完全指向「口令错了」。

所以生产配置叫 `.env.prod`，由 `make init` 生成、prod 栈用 `--env-file` 显式读它。
`make doctor` 会检查项目根有没有多余的 `.env` 并报出来。

```bash
make init      # 生成 .env.prod，三个密钥项自动填随机值
# 填 KEEL_DEFAULT_MERCHANT（商家 code）与 KEEL_MERCHANT_NAME（店名）
make doctor    # 自查：docker、必填项、compose 解析、端口占用、存量数据的坑
make prod-up   # 起栈（会先自动跑一遍 doctor）
```

三个 target 背后是 `compose.prod.yaml`。它**不改动 `compose.yaml`**，所以演示栈
（裸 `docker compose up`）行为一个字没变，两套栈用不同项目名与数据卷，可以同机并存。

它改了什么：

| 演示栈 | 生产栈 |
|---|---|
| 播 `single.sql`：商品、优惠券、订单，外加一个固定口令的演示买家 | 只跑 `deploy/bootstrap.sql`，建一家空店 |
| `KEEL_DEFAULT_MERCHANT: demo` 写死 | 从 `.env.prod` 读，与库里的商家对不上就拒绝启动 |
| 沙箱支付、演示外卖渠道都开着 | 都关 |
| 密钥与口令有开发默认值 | `${VAR:?}`，缺一个就起不来 |
| `app` 端口对所有网卡开放 | 只绑 `127.0.0.1`，对外交给宿主机上的反向代理 |

### 首个管理员

应用启动时 `EnsureBootstrapAdmin` 往 stdout 打一个**一次性** token：

```bash
make prod-logs    # bootstrap token 在里面
```

用它换第一个平台管理员。刻意不做成「默认账号 + 强制改密」——那种形式总会被自动化脚本吃掉，
而一次性 token 用完即失效、过期作废。

**之后加的人不再需要看日志。** 后台建员工时会当场显示那一串一次性 token（界面紧接着
调一次 `POST /admin/staff/{id}/login-token` 取的），开新店时它直接在 201 的响应体里
（`admin_login_token`，契约 `MerchantOpened`）。日志里只有签过的事实、没有明文，
`staff_tokens` 表里只有 sha256。这一条是刻意的设计，理由是日志的去向不由你控制。

### 四个只有部署的人才会踩的坑

**官方 Go module 代理在很多网络里连不上。** 生产栈默认本地构建，Dockerfile 第 4 步
`go mod download` 走的就是 `GOPROXY`。默认值 `proxy.golang.org` 在中国大陆与部分云网络里
超时，症状是构建失败在那一层，报错只有一行 `dial tcp ...:443: i/o timeout` ——
不知道的人会以为是 Dockerfile 写坏了。`.env.prod` 里设 `GOPROXY=https://goproxy.cn,direct` 即可
（`make doctor` 第 4 项会替你探这个地址）。

**`KEEL_ADMIN_PASSWORD` 在数据卷初始化之后就再也不生效了。** PostgreSQL 只在 initdb 时读一次
那个值。已经在跑的部署想换口令，要 `ALTER ROLE keel PASSWORD '...'` 然后同步改 `.env.prod`——
只改 `.env.prod` 的症状是 migrate 报「密码错误」，而真因是卷还是老的。`make doctor` 检测到
已存在的卷会主动提醒这一条。

**`KEEL_APP_PASSWORD` 只在 `keel_app` 角色首次创建时生效。** `db/migrations/00003` 刻意不写成
无条件 `ALTER ROLE`，理由写在那个迁移的文件头：角色是集群级对象而 GRANT 是单库的，无条件的话
给第二个库跑 `goose up` 就会把生产上已经设好的强口令静默重置回开发默认值，没有报错没有痕迹。
轮换口令要走单独的 `ALTER ROLE keel_app PASSWORD '...'`。

**商家 code 写错的表现是全站 404。** `tenant.Preflight` 核对 `KEEL_DEFAULT_MERCHANT` 指向的
商家存在且可服务，对不上直接拒绝启动。这个症状不会有人指向配置项，所以 doctor 单列了一条格式检查。

### 用预构建镜像

默认生产栈仍然是**本地构建**（`compose.yaml` 文件头有「不走 GHCR」的论证：仓库的测试基建不该
依赖仓库之外的可变产物）。要给客户机器装、或内网拉不到 GitHub 编 Rust 时，叠第三层：

```bash
KEEL_IMAGE_TAG=v0.7.0 docker compose -f compose.yaml -f compose.prod.yaml -f compose.release.yaml up -d
```

四个镜像分别是 `keel`（app）、`keel-migrate`、`keel-console`、`keel-postgres`，标签跟版本号走。

**拉镜像必须先 `docker login ghcr.io`，即使包是公开的。** 这一点反直觉：匿名 REST 请求能读到
manifest 和 blob，但 docker daemon 不发匿名 token，未登录直接报

```
Head "https://ghcr.io/v2/jackwangfeng/keel/manifests/v0.7.0": denied: denied
```

报错里一个字都没提登录，很容易被当成权限或网络问题去查错方向。令牌要带 `packages:read`
（`gh auth token` 给的 oauth 令牌**没有**这个 scope，要去 Settings → Developer settings
重新授权成 classic PAT，或另发一个）。`make doctor` 第 4 项会替你试拉一次。

配套的 Makefile 目标是 `make release-up`（自动先跑 doctor），它读 `.env.prod` 里的
`KEEL_IMAGE_TAG`。**实测 4.9 秒起完整套**，本地构建要几分钟——差别就在拉 module 编 Rust 那一步。

### 日常运维

```bash
make prod-logs     # 跟 app 日志
make prod-down     # 停掉，数据卷保留
make prod-config   # 打印合成后的完整配置（排查「我以为覆盖了」这类问题）
```

升级时先 `make prod-down`，换 `KEEL_VERSION` 或镜像标签，再 `make prod-up` —— 迁移由 `migrate`
服务按序自动跑完，**不要**用 `down -v`：那会连 `dtmdata` 一起删掉，而未完成的分布式事务
没人推进，已经扣掉的库存和已核销的券就再也不会回补。

## 反向代理

- 后台界面（`console`）内置 nginx，把 `/api` 同源反代给 `app`，所以**不需要配 CORS**。
  API 本身不发 CORS 头。H5 买家端也要和 API 同源部署。
- **`/search` 的限流按客户端 IP 计，但默认不信任客户端自报的来源**：不配 `KEEL_TRUSTED_PROXIES` 时只认直连 IP，
  `X-Forwarded-For` 一个字都不读，否则限流形同虚设。放在反向代理后面时**必须**把代理的地址配进去
  （例如宿主机上的网关经 docker 网桥连 `app`：`KEEL_TRUSTED_PROXIES=172.16.0.0/12`），
  否则所有访客都算在代理那一个 IP 上、共用一份额度——一个人刷搜索，所有人一起 429。
  代理要**覆写或追加** `X-Forwarded-For`（nginx：`proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`）；
  多层代理时每一层都要进名单，服务端从右往左跳过受信代理，取第一个不受信的地址。
- 多商家形态下，代理要把原始 `Host` 透传给 `app`，租户靠它确定。

## 多实例部署

**默认形态是单机单实例**（compose 就是这么起的）。多实例**可以**跑，但下面这些前提缺一条就会出只在多实例下复现的故障。
这一节不是推演：2026-09-27 在本机起了 3 个 `app` 实例 + nginx 轮询（不开 sticky）+ 一个共用的 Postgres，逐条打过。

### 必须满足的前提

| 前提 | 不满足时实测看到的 |
|---|---|
| 所有实例 `KEEL_AUTH_SECRET` 相同 | A 实例签的令牌 B 实例验不过，刷新几次页面就被登出 |
| `KEEL_DTM_DSN` 指向 **Postgres**（所有实例同一个库，给它单独的库 / 角色），不要用 sqlite | 用 Postgres 存储时 3 个实例轮询下单 180 笔全部成功；协调器存储自带租约（owner / lease_until），任一实例可以接手别的实例发起的事务。sqlite 共享文件的形态没有验证过，不要用 |
| 上传文件放在**所有实例共用的存储**上：推荐 `KEEL_UPLOAD_DRIVER=s3`（对象存储，见下文「上传文件换到对象存储」）；或所有实例的 `KEEL_UPLOAD_ROOT` 指向同一份存储（同机共用卷、跨机的共享文件系统） | 每个实例各用各的目录时：A 实例传的图，经轮询读取 6 次有 4 次 500（只有 A 自己读得到），孤儿回收也只删得到本机的文件 |
| 迁移**只跑一次**：部署流程里一个一次性的 migrate 任务，**不要**让每个实例启动时各跑一遍 | goose 不加锁：3 个 migrate 同时跑，1 个成功、2 个在 00001 上报错退出（每条迁移都在事务里，库不会坏，但那两个进程是失败的）。compose 的 migrate 本来就是一次性服务，应用进程自己不跑迁移 |
| **连接数算得过来**：`实例数 × (KEEL_DB_MAX_CONNS + DTMRS_DB_POOL) + 几条运维余量 < max_connections` | 默认一个实例最多 20（业务池，= CPU 核数）+ 32（协调器池）= 52 条；3 个实例共用默认 `max_connections = 100` 的 Postgres，压测时 7% 的读请求 500（`too many clients`）、下单 p95 近 1 秒。配成 20 + 8 之后同样的压力 0 错误：列表 6300 req/s、下单 650 单/s。实例再多就该在前面放 PgBouncer（事务模式；RLS 用的是 `set_config(…, true)` 事务级设置，兼容） |
| 负载均衡后面配 `KEEL_TRUSTED_PROXIES` | 所有访客算到负载均衡那一个 IP 上，共用一份限流额度 |

### 实测已经按多实例成立的

- **登录失败锁定**：计数在库里（`login_failures`，00065），3 个实例轮询下同一个号第 6 次就锁，重启所有实例之后仍然锁着。
  （最初放在进程内存里时，实测要错 15 次才锁、重启全部解锁 —— 所以挪进了库。）
- **refresh_token 轮换**：同一个令牌经 3 个实例并发刷新 5 次，恰好 1 次成功、4 次 401，胜出的新令牌可用。
  （修之前 5 次全成功、只有最后一个新令牌是活的 —— 单实例同样会出，多实例只是更容易撞上。）
- **后台定时任务**（超时关单、自动确认收货、退货超时关闭、孤儿上传回收、通知投递）**每个实例都跑，没有选主，也不需要**：
  150 笔同时超时的订单，3 个实例同一时刻开扫（`raced` 分别 74 / 113 / 98），结果每单恰好关一次、每行恰好回补一次、
  恰好一条通知，库存分毫不差。靠的是每一次处置都是「带状态谓词的原子 UPDATE，影响 1 行才算归我」，任务队列出队用
  `FOR UPDATE SKIP LOCKED`。代价是每个实例都扫一遍（N 倍的扫描查询），不是 N 倍的处置。
- **支付回调 / 退款审核重复打到不同实例**：同一个回调并发 10 次，全部 200、只有 1 行支付记录、订单只入账一次、1 条通知；
  同一张售后单 6 个并发审核（不同幂等键），1 个 200、5 个 409，只退一次款、只回补一次库存。
- **没有业务数据缓存**：改店铺设置、改价之后，经 3 个实例的下一次读取立刻是新值。唯一的进程内缓存是租户解析
  （域名 → 商家，30 秒 TTL）：停用一家商家后，各实例在各自缓存过期时停止服务（实测 10.7 秒），上限 30 秒，与单实例相同。

### 多实例下仍然不准的（知道就行，或在网关层补）

- **`/search` 限流是每个实例各一份**：60 个并发请求放过 36 个（3 × 12）。要全局准确的限额，在网关层限流
  （nginx `limit_req` 之类），或者把 `KEEL_SEARCH_RATE_PER_SEC` / `KEEL_SEARCH_RATE_BURST` 配成「目标值 ÷ 实例数」。
  做成跨实例精确计数需要一个共享计数器（Redis）；为这一个限流引入 Redis 不划算，今天不做。
- **类目推荐的向量缓存**在进程内，各算各的，代价只是冷启动时多几次推理调用，不影响正确性。

## 语义搜索与推理引擎

推理引擎是 [infero](https://github.com/jackwangfeng/infero)，跑在宿主机上，**不在 compose 里**。
默认（GPU 版）需要一块 NVIDIA GPU：

```bash
./scripts/infero-up.sh
docker compose -f compose.yaml -f compose.infero.yaml up -d
```

- 不跑任何引擎也能部署。不配 `KEEL_EMBED_ENDPOINT` 时 `/search` 只走关键词检索：
  返回 200，不报错，`explain: true` 会如实说明这次只跑了哪几段。
  少掉的是语义那一半：搜「夏天穿的显瘦一点的」这类和标题没有一个字重合的词，召回会明显变差。
- **没有 GPU 现在也可以选择跑 infero 的 CPU 版来获得语义检索**，见下面一节。
- 为什么不做成 compose 服务、GPU 版实测数字是多少，写在 `scripts/infero-up.sh` 的文件头。

### 没有 GPU：跑 infero 的 CPU 版

infero 2026-09-26 起有了 CPU 后端（`--features cpu`），首版单线程、单条约 5 秒，撑不起
Keel；infero `cb0ccbd`（2026-09-29，GEMM 换成并行化的 `gemm` crate、常驻 F32 权重缓存、
attention 按 (head, token) 并行）之后，本机（20 核，空闲，负载约 7）实测：单条短查询
117 ms 中位数 / 124 ms p90、60 字查询 359/384 ms、64 条一批 2.68 s 中位数——三条门槛
（250 ms / 430 ms / 5 s）全过，`make test-engine` 三条判据全过，向量与 GPU 版余弦
≥ 0.9999995、模型名相同。实测表见[总体架构](../电商系统-总体架构.md) §1「那个缺口」。

**负载会明显拖慢它**：同一版本在负载 17–30 时单条约 450–1,000 ms、60 字约
870 ms–1.9 s、64 条约 5.3–10.2 s，逼近甚至超过门槛。**CPU 形态需要给它留核**
（建议至少 4–8 核专用，核越多越快，批量查询最吃核），不要和别的 CPU 密集任务抢同一台
机器却不留余量。

编译（与 GPU 版区别只在 `--features`，编译期选择）：

```bash
cargo build --release -p infero-server --no-default-features --features cpu --target-dir target-cpu
```

启动参数与 GPU 版一致：

```bash
target-cpu/release/infero --model <Qwen3-Embedding-0.6B 的 safetensors 目录> \
    --host 0.0.0.0:18081 --ctx 2048 --max-seqs 32
```

`INFERO_CPU_THREADS=<n>` 限定线程数，缺省用全部逻辑核。常驻内存约 3.5 GB
（F16 权重 1.2 GB + 启动时转的 F32 缓存 2.3 GB，约为 F16 权重文件大小的 3 倍）。
起来之后跟 GPU 版一样，把 `KEEL_EMBED_ENDPOINT` 指过去：

```bash
KEEL_EMBED_ENDPOINT=http://127.0.0.1:18081 make test-engine
```

**用 compose 起（推荐）**：CPU 版没有显存问题，引擎可以直接作为 compose 里的一个服务，
从 infero 源码按它的 `Dockerfile.cpu`（infero `500ff62` 或更新）本地构建（infero 不发布镜像）：

```bash
KEEL_INFERO_SRC=../infero KEEL_INFERO_MODEL=/path/to/Qwen3-Embedding-0.6B \
  docker compose -f compose.yaml -f compose.infero-cpu.yaml up -d --build
```

app 会等引擎的 `/health/ready`（F32 缓存预热完才 200）再起，`KEEL_EMBED_ENDPOINT` 自动指向
`http://inference:8081`，引擎不对宿主机开端口。可选 `INFERO_CPU_THREADS` 限线程数。
**与 `compose.infero.yaml` 二选一**，不要同时 `-f`。

⚠️ 容器内的模型目录名就是引擎报的模型名（取第一个 `.` 之前）。叠加层默认挂成
`/models/Qwen3-Embedding-0.6B`，模型名 `Qwen3-Embedding-0`，与 GPU 版一致、互换不用重算向量；
换模型时 `KEEL_INFERO_MODEL` 与 `KEEL_INFERO_MODEL_DIR`（容器内目录名）一起换。
本机实测（2026-09-29）：容器 healthy 后向量与 GPU 版余弦 0.9999995，延迟与裸二进制同一量级。

## 版本与镜像

每个发布版本都会推一份镜像到 GitHub Container Registry：

```bash
docker pull ghcr.io/jackwangfeng/keel:v0.2.0            # API
docker pull ghcr.io/jackwangfeng/keel-migrate:v0.2.0    # goose + 迁移
docker pull ghcr.io/jackwangfeng/keel-postgres:v0.2.0   # PostgreSQL 16 + PostGIS + pgvector
docker pull ghcr.io/jackwangfeng/keel-console:v0.2.0    # 商家后台（nginx，把 /api 反代给 app）
```

v0.1.0 只发了 API 镜像；从 v0.2.0 起四个镜像随版本一起发，不从源码构建也能起一整套。
`docker compose build` 从源码构建照样可用。

镜像由 `.github/workflows/release.yml` 在打 vX.Y.Z 标签时自动构建推送（不是手动 buildx），
所以 tag 一推，四个镜像就都齐了。**拉取要 `docker login ghcr.io`** —— 包是公开的，但
docker daemon 不发匿名 token，未登录报 `denied: denied`；详见
[用预构建镜像](#用预构建镜像) 那节的坑。

确认跑的是哪一版：

```bash
curl -s http://localhost:8080/version
docker compose logs app | head -1      # 启动日志第一行就是版本号
```

升级：拉新代码或新镜像后 `docker compose up -d --build`。`migrate` 服务会先把库迁到新版本，
`app` 等它跑完才启动。

## 上传文件换到对象存储

多实例、k8s、serverless 部署要把上传文件（商品图、头像、退款凭证）放到所有实例共用的对象存储上（数据模型 §13）。
自建用 `compose.s3.yaml`（SeaweedFS，单容器起 S3 服务）；上云直接用阿里云 OSS / 腾讯云 COS / AWS S3，只配 `KEEL_S3_*`。

**全程不停服的切换**：

1. 准备桶与凭据。自建：
   ```bash
   export KEEL_S3_ACCESS_KEY=keel KEEL_S3_SECRET_KEY=$(openssl rand -hex 24)
   docker compose -f compose.yaml -f compose.s3.yaml up -d --build      # 拆分部署再叠 compose.split.yaml
   ```
   `seaweedfs-init` 会建好桶（已有就跳过）。OSS / COS 在控制台建桶，凭据给这个桶的读写列删权限。
2. 应用改成 `KEEL_UPLOAD_DRIVER=s3` 并**保留** `KEEL_UPLOAD_ROOT`（`compose.s3.yaml` 已经这样配）：新图进桶，磁盘上的老图照旧读得到。
3. 搬存量（工具随 app 镜像发）：
   ```bash
   docker compose ... exec app /keel-uploads migrate -dry-run      # 看有多少、源文件全不全
   docker compose ... exec app /keel-uploads migrate               # 搬：核过 sha256 与大小才改指，可中断重跑
   ```
   报告里「源文件缺失」「字节对不上」的那些没搬，行留在磁盘 driver 上，要人看（多半是之前手工删过文件）。
4. 观察几天没问题后，删掉磁盘上的旧文件与 `uploads` 卷，撤掉 `KEEL_UPLOAD_ROOT`。

**接新的对象存储之前**，先跑一遍兼容性测试（真打那个服务：读写、不存在、缩略图、预签名、删除）：

```bash
KEEL_TEST_S3_ENDPOINT=https://oss-cn-shenzhen.aliyuncs.com KEEL_TEST_S3_BUCKET=... KEEL_TEST_S3_ACCESS_KEY=... \
KEEL_TEST_S3_SECRET_KEY=... KEEL_TEST_S3_REGION=... go test ./internal/service/ -run TestS3StoreAgainstRealService
```

为什么自建不用 MinIO：它的社区版 2025 年 5 月去掉了管理控制台、10 月起不再发二进制与官方镜像、年底仓库进了维护模式
（[itsfoss](https://itsfoss.com/news/minio-moves-away-from-open-source/)）。SeaweedFS 是 Apache-2.0、仍在活跃维护，备选是 RustFS。
