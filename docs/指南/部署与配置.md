# 部署与配置

这篇讲怎么把 Keel 从「本机演示」变成「给真实客人用」：有哪些形态、每个环境变量管什么、
上线前哪些默认值必须改。

---

## 部署形态

| 形态 | 怎么起 | 租户怎么确定 |
|---|---|---|
| **单商家**（默认） | `docker compose up -d` | 所有请求都属于 `KEEL_DEFAULT_MERCHANT` 那一家，请求里不用带任何东西 |
| **多商家** | `docker compose -f compose.yaml -f compose.multi.yaml up -d` | 由请求的 `Host` 决定：`<商家code>.<KEEL_BASE_DOMAIN>`，或商家绑定的自有域名 |
| **带语义搜索** | 先 `./scripts/infero-up.sh`，再叠加 `-f compose.infero.yaml` | 同上，和前两种正交 |

**单商家换多商家不用换架构。** 表结构、行级安全、接口都是同一套；区别只在
「从哪儿知道这个请求属于哪家店」。

多商家形态有自己的一组卷（`keel_pgdata_multi` 等），和单商家的数据互不影响。
它播的是 `db/seed/dev.sql`（多家演示店），不是单商家的 `single.sql`。

### 启动自检

应用启动时会先做几项检查，**对不上就拒绝启动，不会猜**：

- 连数据库用的角色**不能**绕过行级安全（不能是超级用户，也不能有 `BYPASSRLS`）。
  compose 里应用用的是 `keel_app`，迁移用的是 `keel`，这是刻意分开的。
- 单商家形态下，`KEEL_DEFAULT_MERCHANT` 必须真的存在，而且库里只能有这一家活跃商家。
- `KEEL_DTM_DSN` 必须配置（见下文）。

## 环境变量

### 应用（`app` 服务）

| 变量 | 默认值 | 说明 |
|---|---|---|
| `KEEL_ADDR` | `:8080` | 监听地址 |
| `KEEL_DEFAULT_MERCHANT` | compose 里是 `demo` | 单商家形态下那家店的 code。多商家形态必须留空 |
| `KEEL_BASE_DOMAIN` | — | 多商家形态的平台基础域名，`shop1.<它>` 解析到 code 为 `shop1` 的商家 |
| `KEEL_DTM_DSN` | **无，必须配** | 事务协调器自己的存储。单机用 `sqlite:/var/lib/keel/dtm.db`（compose 已配好并挂了卷）；多实例必须换成 Postgres / MySQL，并给它单独的数据库角色 |
| `KEEL_AUTH_SECRET` | 留空则随机生成 | 买家令牌的签名密钥。**生产必须配**，见下文 |
| `KEEL_PAYMENT_SANDBOX` | 开 | 沙箱支付。**收钱的部署必须设为 `off`** |
| `KEEL_UPLOAD_ROOT` | compose 里是 `/var/lib/keel-uploads` | 上传文件（商品图、凭证）的本地目录。不配会落到临时目录，容器重建即丢 |
| `KEEL_EMBED_ENDPOINT` | — | 推理引擎地址。不配时搜索只走关键词那一路（正常降级，不是故障） |
| `KEEL_SEARCH_RATE_PER_SEC` | `12` | `/search` 每个 IP 每秒允许的请求数 |
| `KEEL_SEARCH_RATE_BURST` | `12` | `/search` 每个 IP 的瞬时额度 |
| `KEEL_TRUSTED_PROXIES` | 空（一个都不信） | 反向代理的地址名单，逗号分隔的 IP / CIDR。只有来自名单里的连接，`X-Forwarded-For` / `X-Real-IP` 才会被采信；写错一项拒绝启动。见下文「反向代理」 |
| `PGHOST` / `PGPORT` / `PGUSER` / `PGPASSWORD` / `PGDATABASE` | libpq 标准 | 业务库连接。`PGUSER` 必须是不能绕过行级安全的角色 |

### compose 层

| 变量 | 默认值 | 说明 |
|---|---|---|
| `KEEL_HTTP_PORT` | `8080` | API 映射到宿主机的端口 |
| `KEEL_CONSOLE_PORT` | `8081` | 商家后台映射到宿主机的端口 |
| `KEEL_ADMIN_PASSWORD` | `keel` | **数据库超级用户**的口令（迁移用），和后台界面无关 |
| `KEEL_APP_PASSWORD` | `keel_app` | 应用连库用的 `keel_app` 角色的口令 |
| `KEEL_VERSION` | `dev` | 构建时注入的版本号，`/version` 和启动日志第一行会显示 |

## 上线前必须改的

照着 `docker compose up` 起来的是一套**演示**配置。下面几项不改，就不要拿它服务真实客人：

1. **`KEEL_AUTH_SECRET`**：配一个足够长的随机值，并且所有实例用同一个。

   ```bash
   KEEL_AUTH_SECRET=$(openssl rand -base64 48)
   ```

   留空时应用会随机取一个并打 WARN。后果是每次重启所有买家被登出；多实例下各实例密钥不同，
   表现为「刷新几次页面就要重新登录」。compose **刻意不给默认值**：写在公开仓库里的默认密钥，
   等于任何人都能给任何一家店签出合法令牌。

2. **`KEEL_PAYMENT_SANDBOX=off`**：沙箱开着时，买家可以把自己的订单免费推成「已支付」。
   它默认开着是为了让演示能跑通，启动日志里会有一条 WARN 提醒你。
   只认 `off` / `false` / `0` 三种写法，写错（比如 `no`）会被当成**开**——这是刻意的，
   写错时宁可让你看到 WARN，也不要让你误以为已经关了。

3. **数据库口令**：改掉 `KEEL_ADMIN_PASSWORD` 和 `KEEL_APP_PASSWORD`。

4. **删掉种子买家**：单商家种子里有一个固定口令的买家（`13800000000` / `keel-demo-2026`），
   演示用的。生产库不要播种子，或者播完删掉这个账号。

5. **备份三个卷**：`pgdata`（业务数据）、`dtmdata`（未完成的分布式事务）、`uploads`（上传文件）。
   `dtmdata` 丢了的后果是：已经扣掉的库存、已经锁住的券，再也没人去回补。

6. **后台引导 token**：第一次启动时打在日志里。用完即失效；如果你的日志会被收集到别处，
   记得在引导完成之后确认它已经被用掉。

## 反向代理

- 后台界面（`console`）内置 nginx，把 `/api` 同源反代给 `app`，所以**不需要配 CORS**。
  API 本身不发 CORS 头。H5 买家端也要和 API 同源部署。
- **`/search` 的限流按客户端 IP 计，但默认不信任客户端自报的来源**：不配 `KEEL_TRUSTED_PROXIES` 时只认直连 IP，
  `X-Forwarded-For` 一个字都不读，否则限流形同虚设。放在反向代理后面时**必须**把代理的地址配进去
  （例如宿主机上的网关经 docker 网桥连 `app`：`KEEL_TRUSTED_PROXIES=172.16.0.0/12`），
  否则所有访客都算在代理那一个 IP 上、共用一份额度——一个人刷搜索，所有人一起 429。
  代理要**覆写或追加** `X-Forwarded-For`（nginx：`proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`）；
  多层代理时每一层都要进名单，服务端从右往左跳过受信代理，取第一个不受信的地址。
- 多商家形态下，代理要把原始 `Host` 透传给 `app`，租户靠它确定。

## 语义搜索与推理引擎

推理引擎是 [infero](https://github.com/jackwangfeng/infero)，跑在宿主机上，**不在 compose 里**，需要一块 NVIDIA GPU。

```bash
./scripts/infero-up.sh
docker compose -f compose.yaml -f compose.infero.yaml up -d
```

- 没有 GPU 也能部署。不配 `KEEL_EMBED_ENDPOINT` 时 `/search` 只走关键词检索：
  返回 200，不报错，`explain: true` 会如实说明这次只跑了哪几段。
  少掉的是语义那一半：搜「夏天穿的显瘦一点的」这类和标题没有一个字重合的词，召回会明显变差。
- infero 的 CPU 后端还在开发中。在它落地之前，没有 GPU 的部署只有关键词检索这一种形态。
- 为什么不做成 compose 服务、实测数字是多少，写在 `scripts/infero-up.sh` 的文件头。

## 版本与镜像

每个发布版本都会推一份镜像到 GitHub Container Registry：

```bash
docker pull ghcr.io/jackwangfeng/keel:v0.1.0
```

镜像只包含 API（`docker/Dockerfile` 的 `app` 阶段）。数据库镜像（PostGIS + pgvector）和后台界面
目前要从源码构建，`docker compose build` 会一起处理。

确认跑的是哪一版：

```bash
curl -s http://localhost:8080/version
docker compose logs app | head -1      # 启动日志第一行就是版本号
```

升级：拉新代码或新镜像后 `docker compose up -d --build`。`migrate` 服务会先把库迁到新版本，
`app` 等它跑完才启动。
