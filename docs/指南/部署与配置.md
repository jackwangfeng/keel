# 部署与配置

这篇讲怎么把 Keel 从「本机演示」变成「给真实客人用」：有哪些形态、每个环境变量管什么、
上线前哪些默认值必须改。

---

## 部署形态

| 形态 | 怎么起 | 租户怎么确定 |
|---|---|---|
| **单商家**（默认） | `docker compose up -d` | 所有请求都属于 `KEEL_DEFAULT_MERCHANT` 那一家，请求里不用带任何东西 |
| **多商家** | `docker compose -f compose.yaml -f compose.multi.yaml up -d` | 由请求的 `Host` 决定：`<商家code>.<KEEL_BASE_DOMAIN>`，或商家绑定的自有域名 |
| **带语义搜索** | 先 `./scripts/infero-up.sh`，再叠加 `-f compose.infero.yaml` | 同上，和前两种正交 |
| **拆分 B 档**（同一个 Postgres，库存独立 schema + 账号） | `docker compose -f compose.yaml -f compose.split-b.yaml up -d --build` | 同上 |
| **拆分 C 档**（core 与库存各一个进程、各一个库） | `KEEL_INTERNAL_SECRET=$(openssl rand -base64 48) docker compose -f compose.yaml -f compose.split.yaml up -d --build` | 同上 |

**单商家换多商家不用换架构。** 表结构、行级安全、接口都是同一套；区别只在
「从哪儿知道这个请求属于哪家店」。

多商家形态有自己的一组卷（`keel_pgdata_multi` 等），和单商家的数据互不影响。
它播的是 `db/seed/dev.sql`（多家演示店），不是单商家的 `single.sql`。

### 启动自检

应用启动时会先做几项检查，**对不上就拒绝启动，不会猜**：

- 连数据库用的角色**不能**绕过行级安全（不能是超级用户，也不能有 `BYPASSRLS`）。
  compose 里应用用的是 `keel_app`，迁移用的是 `keel`，这是刻意分开的。
- 单商家形态下，`KEEL_DEFAULT_MERCHANT` 必须真的存在，而且库里只能有这一家活跃商家。
- `KEEL_DTM_DSN` 必须配置（见下文）。

## 拆分部署（B / C 档）

三档只差「库存数据放在哪、用哪个账号连」，代码一行不变（为什么这么拆见
[微服务拆分方案](../电商系统-微服务拆分方案.md)「部署档位」）。从单体迁过去都是同一件事：
建库存迁移 → `scripts/split-migrate.sh copy` → `cutover` → 改环境变量重启。

**切换要停写。** 先停 core 的公网入口与后台任务，等协调器里没有未完成的全局事务，再 copy。
脚本在目标四张表全空时才导入，目标已有数据就只核对、绝不覆盖；cutover 之后再跑两条都直接跳过。
两个连接串都用管理员角色（要绕过 RLS 读写全部商家）。

**B 档**（同一个 Postgres）：从零起一个 B 档栈就是上表那一条命令（`compose.split-b.yaml`，一个进程，自己的一套卷）。
把一个已有的单体库迁到 B 档：

```bash
export SRC_DSN='postgres://keel:<管理员口令>@<库>:5432/keel?sslmode=disable'
export DST_DSN="$SRC_DSN&options=-csearch_path%3Dinventory"
KEEL_INVENTORY_PASSWORD=<新口令> scripts/split-migrate.sh prepare-b   # 建 inventory schema 与 keel_inventory
KEEL_INVENTORY_ROLE=keel_inventory KEEL_INVENTORY_PASSWORD=<新口令> \
  make migrate-inventory INVENTORY_GOOSE_DBSTRING="$DST_DSN"
scripts/split-migrate.sh copy && scripts/split-migrate.sh cutover
```

然后应用（仍是一个进程，`KEEL_ROLE=all`）加一行
`KEEL_INVENTORY_DSN='postgres://keel_inventory:<新口令>@<库>:5432/keel?sslmode=disable&options=-csearch_path%3Dinventory'`，重启。
之后 `keel_app` 查 `inventory.*` 在权限检查这一步就被拒，`keel_inventory` 也读不到 core 的任何一张表。
想拆成两个进程：再起一个 `KEEL_ROLE=inventory` 的实例用同一个 `KEEL_INVENTORY_DSN`，core 改 `KEEL_ROLE=core` + `KEEL_INVENTORY_URL`。

**C 档**（另一个库）：`compose.split.yaml` 就是完整的样例 —— 它每次起新栈都用同一个脚本把种子里的库存搬进库存库。
把一个真实的单体库迁过去：在新库上 `KEEL_INVENTORY_ROLE=keel_inventory make migrate-inventory`，
`DST_DSN` 指向新库跑 `copy` / `cutover`，core 改 `KEEL_ROLE=core` + `KEEL_INVENTORY_URL` + `KEEL_INTERNAL_SECRET`，
库存进程 `KEEL_ROLE=inventory` + `KEEL_INVENTORY_DSN` + `KEEL_INTERNAL_ADDR` + 同一个 `KEEL_INTERNAL_SECRET`。

**回滚**：刚切完、还没接流量时 `scripts/split-migrate.sh rollback`（把 `keel_app` 的权限还回源库）再改回单体配置。
接过流量之后，库存服务里的变化不在源库里，要先把目标四张表反向拷回（见脚本文件头）。

**库存服务不在时**（C 档实测，杀掉 inventory 容器下单）：`POST /orders` 等 15 秒后回 409 `idempotency-key-in-flight`，
订单已在买家列表里但**付不了**（409 `order-status-not-payable`，00085）；库存服务回来后，协调器在下一次重试时把 SAGA 推完
—— 重试按退避走，**最长约 5 分钟**才轮到下一次，不是回来就立刻推。

**对账**：core（`all` / `core`）每小时跑一轮库存对账，只读只报：孤儿库存行（SKU 或门店在 core 里已不存在）、
上线活动的配额行与 `promotion_skus` 的差集、进了死信的 `inventory.release` 任务。发现差异打 WARN 带明细。

## 环境变量

### 应用（`app` 服务）

| 变量 | 默认值 | 说明 |
|---|---|---|
| `KEEL_ADDR` | `:8080` | 监听地址 |
| `KEEL_DEFAULT_MERCHANT` | compose 里是 `demo` | 单商家形态下那家店的 code。多商家形态必须留空 |
| `KEEL_BASE_DOMAIN` | — | 多商家形态的平台基础域名，`shop1.<它>` 解析到 code 为 `shop1` 的商家 |
| `KEEL_DTM_DSN` | **无，必须配** | 事务协调器自己的存储。单机用 `sqlite:/var/lib/keel/dtm.db`（compose 已配好并挂了卷）；多实例必须换成 Postgres / MySQL，并给它单独的数据库角色 |
| `KEEL_AUTH_SECRET` | 留空则随机生成 | 买家令牌的签名密钥。**生产必须配**，见下文 |
| `KEEL_PAYMENT_SANDBOX` | 开 | 沙箱支付。**收钱的部署必须设为 `off`** |
| `KEEL_UPLOAD_ROOT` | compose 里是 `/var/lib/keel-uploads` | 上传文件（商品图、凭证）的本地目录。不配会落到临时目录，容器重建即丢 |
| `KEEL_EMBED_ENDPOINT` | — | 推理引擎地址。不配时搜索只走关键词那一路（正常降级，不是故障） |
| `KEEL_SEARCH_RATE_PER_SEC` | `12` | `/search` 每个 IP 每秒允许的请求数 |
| `KEEL_SEARCH_RATE_BURST` | `12` | `/search` 每个 IP 的瞬时额度 |
| `KEEL_DB_MAX_CONNS` | pgxpool 默认（max(4, CPU 核数)） | 业务连接池上限。多实例时与 `DTMRS_DB_POOL`（事务协调器的池，默认 32）一起按「实例数 × 两者之和 < max_connections」配 |
| `KEEL_LOGIN_LOCK_EXEMPT_PHONES` | 空 | 不参与口令失败锁定（同一号 15 分钟内错 5 次锁 15 分钟）的手机号，逗号分隔。只给把一个买家号公开给所有人用的演示环境；正式环境不要配 |
| `KEEL_TRUSTED_PROXIES` | 空（一个都不信） | 反向代理的地址名单，逗号分隔的 IP / CIDR。只有来自名单里的连接，`X-Forwarded-For` / `X-Real-IP` 才会被采信；写错一项拒绝启动。见下文「反向代理」 |
| `KEEL_STOCK_FLAG_INTERVAL` | `1m` | 商品列表「有货在前」排序标记的全量刷新间隔（Go duration）。后台改库存会立刻刷那件商品；下单扣减、关单回补靠这一轮，排序最多晚这么久。列表上显示的「无货」是实时的，不受它影响 |
| `KEEL_GEO_PROVIDER` / `KEEL_GEO_KEY` | 空（不启用） | 地图服务商与服务端 key（目前只有 `amap` 高德 Web 服务，key 绑服务器 IP 白名单，不下发给客户端）。启用后 `/geo/reverse`、`/geo/suggest` 可用（POI 选址）；不配时回 501，客户端退回手填 + 地图选点。高德个人认证额度很小（输入提示 5000 次/月），正式商用要企业认证。见 [POI 设计](../POI-设计.md) |
| `KEEL_MAP_TILES` / `KEEL_TIANDITU_KEY` / `KEEL_TIANDITU_REFERER` | 空（不显示地图） | 地图底图瓦片（买家端地图选点、后台门店坐标与围栏）。正式部署用 `tianditu` + 天地图**浏览器端**类型的 key（在 [天地图控制台](https://console.tianditu.gov.cn/) 申请，域名白名单填站点域名）+ 站点地址（如 `https://shop.example.com/`，代理取瓦片时带作 Referer）。**服务端类型的 key 取不了瓦片**（403「权限类型错误」）；不带 Referer 从服务端大量请求，浏览器端 key 会被禁用：有审图号、坐标 CGCS2000 与库里的 WGS-84 直接对得上。瓦片由 Keel 转发并缓存（进程内 64 MB、7 天），key 不下发给客户端。`osm` 只给开发自测（国内细节少、没有审图号、官方瓦片不许商用大流量）。选了 `tianditu` 没给 key 或站点地址、或写了不认识的名字，拒绝启动。见 [POI 设计](../POI-设计.md)「地图底图」 |
| `KEEL_TILE_RATE_PER_SEC` / `KEEL_TILE_RATE_BURST` | `60` / `300` | `/geo/tiles` 每个客户端 IP 的限流（一屏地图两层约六七十张瓦片，连续放大几级就是几百张）。`<= 0` 关闭 |
| `KEEL_TILE_UPSTREAM_PER_SEC` / `KEEL_TILE_UPSTREAM_BURST` | `20` / `400` | 瓦片**总闸**：全站不分 IP，每秒最多向瓦片服务商取多少张（只数缓存没命中的）。超过的请求回 503，不排队。防的是很多个 IP 一起刷、耗光天地图 key 的日调用量或被判滥用。`<= 0` 关闭 |
| `KEEL_ROLE` | `all` | 本进程在部署里的角色：`all`（单体）/ `core` / `inventory`，写错拒绝启动。拆分部署用：`core` 的库存读与后台改库存经 `KEEL_INVENTORY_URL` 调库存服务（**必须配**，否则拒绝启动）；`inventory` 只起内网端口，上面是 `/healthz`、`/version`、`/readyz`、`/internal/v1/inventory/...` 与下单 SAGA 的库存分支 `/internal/v1/saga/inventory_deduct`、`inventory_restore`（阶段 1b 起 core 与库存可以各用一个库；库存库用 `make migrate-inventory INVENTORY_GOOSE_DBSTRING=...` 建，单体库不必跑它）。见 [微服务拆分方案](../电商系统-微服务拆分方案.md) |
| `KEEL_INVENTORY_DSN` | 空（与业务库同一个池） | 库存库的完整连接串，必须是**不能绕过 RLS** 的角色（与业务库同一道自检）。拆分部署用，阶段 1 起生效。库存库只需要库存迁移目录（`db/migrations-inventory`，`make migrate-inventory`，版本表 `goose_db_version_inventory`），不需要 core 的任何一张表 |
| `KEEL_INTERNAL_ADDR` | 空（不监听） | 服务间内网端口（如 `:8090`），接口在 `/internal/v1` 下。只该在内网可达，**不要映射到公网**。`KEEL_ROLE=inventory` 时必须配 |
| `KEEL_INTERNAL_SECRET` | — | 服务间 HMAC 共享密钥，至少 32 字节，所有进程同一个值。配了 `KEEL_INTERNAL_ADDR` 或 `KEEL_INVENTORY_URL` 就必须配。**轮换请配合 `KEEL_INTERNAL_SECRET_PREVIOUS`（见下一行），不要直接改这个值再重启**：直接改会让已持久化的在途 SAGA 分支地址（带着旧密钥派生的令牌）永久 401 |
| `KEEL_INTERNAL_SECRET_PREVIOUS` | 空 | 轮换 `KEEL_INTERNAL_SECRET` 期间仍要接受的旧密钥。可选；逗号分隔可以给多个，每一项也要满足 32 字节下限。只影响验证：签名（内网请求的 HMAC、SAGA 分支地址里的 `?bt=` 令牌）永远只用 `KEEL_INTERNAL_SECRET` 当前值；验证时当前值与这里列的任意一个都算数。**安全的轮换顺序**（把新密钥记作 NEW，旧密钥记作 OLD）：<br>1. 全部进程：`KEEL_INTERNAL_SECRET` 不变（=OLD），`KEEL_INTERNAL_SECRET_PREVIOUS=NEW`，滚动部署。此时仍然只签 OLD，但验证方已经能认 NEW——这一步只是让「认」先于「用」，不改变任何签名行为，滚动过程中不会有 401。<br>2. 确认第 1 步已经**完整**覆盖所有进程后，翻转：`KEEL_INTERNAL_SECRET=NEW`，`KEEL_INTERNAL_SECRET_PREVIOUS=OLD`，滚动部署。还没翻转的进程签 OLD、认 {OLD, NEW}；已经翻转的签 NEW、认 {NEW, OLD}——两边都认对方在签的那个，滚动过程中同样不会有 401。<br>3. 等第 2 步之前持久化的在途 SAGA 事务（分支地址里带着 OLD 派生的令牌）都自然跑完——它们的地址不会更新，只能靠「仍然认 OLD」撑到结束。<br>4. 全部进程清空 `KEEL_INTERNAL_SECRET_PREVIOUS`，滚动部署。到此只认 NEW。<br>第 1、2 步顺序不能颠倒：先切当前值、再补发旧值当 PREVIOUS，滚动窗口内会出现「签 NEW 的请求打到还没学会认 NEW 的进程」，那正是这一机制要消灭的 401 |
| `KEEL_INVENTORY_URL` | 空（库存在进程内） | core 找库存服务的内网地址（如 `http://inventory:8090`）。`KEEL_ROLE=core` 时必填；`all` 时忽略（会打一条 WARN）。库存服务连不上时，取决于水位的接口回 503 `inventory-unavailable`，浏览与检索照常（见契约 `info.description`）；买家取消、超时关单、退款到账照常成功，放回库存的 outbox 任务（`jobs.queue = inventory.release`）重试到库存服务回来，约 16 小时后仍失败才进死信（有 Error 日志，需人工处理）。**升级到 00075 时若有秒杀在跑，先停旧实例再迁移**：滚动发布窗口里旧实例仍按 `promotion_skus.sold_qty` 计配额 |
| `PGHOST` / `PGPORT` / `PGUSER` / `PGPASSWORD` / `PGDATABASE` | libpq 标准 | 业务库连接。`PGUSER` 必须是不能绕过行级安全的角色 |

## 上线前必须改的

照着 `docker compose up` 起来的是一套**演示**配置。下面几项不改，就不要拿它服务真实客人：

1. **`KEEL_AUTH_SECRET`**：配一个足够长的随机值，并且所有实例用同一个。

   ```bash
   KEEL_AUTH_SECRET=$(openssl rand -base64 48)
   ```

   留空时应用会随机取一个并打 WARN。后果是每次重启所有买家被登出；多实例下各实例密钥不同，
   表现为「刷新几次页面就要重新登录」。compose **刻意不给默认值**：写在公开仓库里的默认密钥，
   等于任何人都能给任何一家店签出合法令牌。

2. **`KEEL_PAYMENT_SANDBOX=off`**：沙箱开着时，买家可以把自己的订单免费推成「已支付」。
   它默认开着是为了让演示能跑通，启动日志里会有一条 WARN 提醒你。
   只认 `off` / `false` / `0` 三种写法，写错（比如 `no`）会被当成**开**——这是刻意的，
   写错时宁可让你看到 WARN，也不要让你误以为已经关了。

3. **数据库口令**：改掉 `KEEL_ADMIN_PASSWORD` 和 `KEEL_APP_PASSWORD`。

4. **删掉种子买家**：单商家种子里有一个固定口令的买家（`13800000000` / `keel-demo-2026`），
   演示用的。生产库不要播种子，或者播完删掉这个账号。

5. **备份三个卷**：`pgdata`（业务数据）、`dtmdata`（未完成的分布式事务）、`uploads`（上传文件）。
   `dtmdata` 丢了的后果是：已经扣掉的库存、已经锁住的券，再也没人去回补。

6. **后台引导 token**：第一次启动时打在日志里。用完即失效；如果你的日志会被收集到别处，
   记得在引导完成之后确认它已经被用掉。

## 反向代理

- 后台界面（`console`）内置 nginx，把 `/api` 同源反代给 `app`，所以**不需要配 CORS**。
  API 本身不发 CORS 头。H5 买家端也要和 API 同源部署。
- **`/search` 的限流按客户端 IP 计，但默认不信任客户端自报的来源**：不配 `KEEL_TRUSTED_PROXIES` 时只认直连 IP，
  `X-Forwarded-For` 一个字都不读，否则限流形同虚设。放在反向代理后面时**必须**把代理的地址配进去
  （例如宿主机上的网关经 docker 网桥连 `app`：`KEEL_TRUSTED_PROXIES=172.16.0.0/12`），
  否则所有访客都算在代理那一个 IP 上、共用一份额度——一个人刷搜索，所有人一起 429。
  代理要**覆写或追加** `X-Forwarded-For`（nginx：`proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`）；
  多层代理时每一层都要进名单，服务端从右往左跳过受信代理，取第一个不受信的地址。
- 多商家形态下，代理要把原始 `Host` 透传给 `app`，租户靠它确定。

## 多实例部署

**默认形态是单机单实例**（compose 就是这么起的）。多实例**可以**跑，但下面这些前提缺一条就会出只在多实例下复现的故障。
这一节不是推演：2026-09-27 在本机起了 3 个 `app` 实例 + nginx 轮询（不开 sticky）+ 一个共用的 Postgres，逐条打过。

### 必须满足的前提

| 前提 | 不满足时实测看到的 |
|---|---|
| 所有实例 `KEEL_AUTH_SECRET` 相同 | A 实例签的令牌 B 实例验不过，刷新几次页面就被登出 |
| `KEEL_DTM_DSN` 指向 **Postgres**（所有实例同一个库，给它单独的库 / 角色），不要用 sqlite | 用 Postgres 存储时 3 个实例轮询下单 180 笔全部成功；协调器存储自带租约（owner / lease_until），任一实例可以接手别的实例发起的事务。sqlite 共享文件的形态没有验证过，不要用 |
| 所有实例的 `KEEL_UPLOAD_ROOT` 指向**同一份存储**（同机共用卷，或跨机的共享文件系统） | 每个实例各用各的目录时：A 实例传的图，经轮询读取 6 次有 4 次 500（只有 A 自己读得到），孤儿回收也只删得到本机的文件。S3 兼容 driver 预留了位置（`uploads.driver = 2`）但**还没实现** |
| 迁移**只跑一次**：部署流程里一个一次性的 migrate 任务，**不要**让每个实例启动时各跑一遍 | goose 不加锁：3 个 migrate 同时跑，1 个成功、2 个在 00001 上报错退出（每条迁移都在事务里，库不会坏，但那两个进程是失败的）。compose 的 migrate 本来就是一次性服务，应用进程自己不跑迁移 |
| **连接数算得过来**：`实例数 × (KEEL_DB_MAX_CONNS + DTMRS_DB_POOL) + 几条运维余量 < max_connections` | 默认一个实例最多 20（业务池，= CPU 核数）+ 32（协调器池）= 52 条；3 个实例共用默认 `max_connections = 100` 的 Postgres，压测时 7% 的读请求 500（`too many clients`）、下单 p95 近 1 秒。配成 20 + 8 之后同样的压力 0 错误：列表 6300 req/s、下单 650 单/s。实例再多就该在前面放 PgBouncer（事务模式；RLS 用的是 `set_config(…, true)` 事务级设置，兼容） |
| 负载均衡后面配 `KEEL_TRUSTED_PROXIES` | 所有访客算到负载均衡那一个 IP 上，共用一份限流额度 |

### 实测已经按多实例成立的

- **登录失败锁定**：计数在库里（`login_failures`，00065），3 个实例轮询下同一个号第 6 次就锁，重启所有实例之后仍然锁着。
  （最初放在进程内存里时，实测要错 15 次才锁、重启全部解锁 —— 所以挪进了库。）
- **refresh_token 轮换**：同一个令牌经 3 个实例并发刷新 5 次，恰好 1 次成功、4 次 401，胜出的新令牌可用。
  （修之前 5 次全成功、只有最后一个新令牌是活的 —— 单实例同样会出，多实例只是更容易撞上。）
- **后台定时任务**（超时关单、自动确认收货、退货超时关闭、孤儿上传回收、通知投递）**每个实例都跑，没有选主，也不需要**：
  150 笔同时超时的订单，3 个实例同一时刻开扫（`raced` 分别 74 / 113 / 98），结果每单恰好关一次、每行恰好回补一次、
  恰好一条通知，库存分毫不差。靠的是每一次处置都是「带状态谓词的原子 UPDATE，影响 1 行才算归我」，任务队列出队用
  `FOR UPDATE SKIP LOCKED`。代价是每个实例都扫一遍（N 倍的扫描查询），不是 N 倍的处置。
- **支付回调 / 退款审核重复打到不同实例**：同一个回调并发 10 次，全部 200、只有 1 行支付记录、订单只入账一次、1 条通知；
  同一张售后单 6 个并发审核（不同幂等键），1 个 200、5 个 409，只退一次款、只回补一次库存。
- **没有业务数据缓存**：改店铺设置、改价之后，经 3 个实例的下一次读取立刻是新值。唯一的进程内缓存是租户解析
  （域名 → 商家，30 秒 TTL）：停用一家商家后，各实例在各自缓存过期时停止服务（实测 10.7 秒），上限 30 秒，与单实例相同。

### 多实例下仍然不准的（知道就行，或在网关层补）

- **`/search` 限流是每个实例各一份**：60 个并发请求放过 36 个（3 × 12）。要全局准确的限额，在网关层限流
  （nginx `limit_req` 之类），或者把 `KEEL_SEARCH_RATE_PER_SEC` / `KEEL_SEARCH_RATE_BURST` 配成「目标值 ÷ 实例数」。
  做成跨实例精确计数需要一个共享计数器（Redis）；为这一个限流引入 Redis 不划算，今天不做。
- **类目推荐的向量缓存**在进程内，各算各的，代价只是冷启动时多几次推理调用，不影响正确性。

## 语义搜索与推理引擎

推理引擎是 [infero](https://github.com/jackwangfeng/infero)，跑在宿主机上，**不在 compose 里**。
默认（GPU 版）需要一块 NVIDIA GPU：

```bash
./scripts/infero-up.sh
docker compose -f compose.yaml -f compose.infero.yaml up -d
```

- 不跑任何引擎也能部署。不配 `KEEL_EMBED_ENDPOINT` 时 `/search` 只走关键词检索：
  返回 200，不报错，`explain: true` 会如实说明这次只跑了哪几段。
  少掉的是语义那一半：搜「夏天穿的显瘦一点的」这类和标题没有一个字重合的词，召回会明显变差。
- **没有 GPU 现在也可以选择跑 infero 的 CPU 版来获得语义检索**，见下面一节。
- 为什么不做成 compose 服务、GPU 版实测数字是多少，写在 `scripts/infero-up.sh` 的文件头。

### 没有 GPU：跑 infero 的 CPU 版

infero 2026-09-26 起有了 CPU 后端（`--features cpu`），首版单线程、单条约 5 秒，撑不起
Keel；infero `cb0ccbd`（2026-09-29，GEMM 换成并行化的 `gemm` crate、常驻 F32 权重缓存、
attention 按 (head, token) 并行）之后，本机（20 核，空闲，负载约 7）实测：单条短查询
117 ms 中位数 / 124 ms p90、60 字查询 359/384 ms、64 条一批 2.68 s 中位数——三条门槛
（250 ms / 430 ms / 5 s）全过，`make test-engine` 三条判据全过，向量与 GPU 版余弦
≥ 0.9999995、模型名相同。实测表见[总体架构](../电商系统-总体架构.md) §1「那个缺口」。

**负载会明显拖慢它**：同一版本在负载 17–30 时单条约 450–1,000 ms、60 字约
870 ms–1.9 s、64 条约 5.3–10.2 s，逼近甚至超过门槛。**CPU 形态需要给它留核**
（建议至少 4–8 核专用，核越多越快，批量查询最吃核），不要和别的 CPU 密集任务抢同一台
机器却不留余量。

编译（与 GPU 版区别只在 `--features`，编译期选择）：

```bash
cargo build --release -p infero-server --no-default-features --features cpu --target-dir target-cpu
```

启动参数与 GPU 版一致：

```bash
target-cpu/release/infero --model <Qwen3-Embedding-0.6B 的 safetensors 目录> \
    --host 0.0.0.0:18081 --ctx 2048 --max-seqs 32
```

`INFERO_CPU_THREADS=<n>` 限定线程数，缺省用全部逻辑核。常驻内存约 3.5 GB
（F16 权重 1.2 GB + 启动时转的 F32 缓存 2.3 GB，约为 F16 权重文件大小的 3 倍）。
起来之后跟 GPU 版一样，把 `KEEL_EMBED_ENDPOINT` 指过去：

```bash
KEEL_EMBED_ENDPOINT=http://127.0.0.1:18081 make test-engine
```

**用 compose 起（推荐）**：CPU 版没有显存问题，引擎可以直接作为 compose 里的一个服务，
从 infero 源码按它的 `Dockerfile.cpu`（infero `500ff62` 或更新）本地构建（infero 不发布镜像）：

```bash
KEEL_INFERO_SRC=../infero KEEL_INFERO_MODEL=/path/to/Qwen3-Embedding-0.6B \
  docker compose -f compose.yaml -f compose.infero-cpu.yaml up -d --build
```

app 会等引擎的 `/health/ready`（F32 缓存预热完才 200）再起，`KEEL_EMBED_ENDPOINT` 自动指向
`http://inference:8081`，引擎不对宿主机开端口。可选 `INFERO_CPU_THREADS` 限线程数。
**与 `compose.infero.yaml` 二选一**，不要同时 `-f`。

⚠️ 容器内的模型目录名就是引擎报的模型名（取第一个 `.` 之前）。叠加层默认挂成
`/models/Qwen3-Embedding-0.6B`，模型名 `Qwen3-Embedding-0`，与 GPU 版一致、互换不用重算向量；
换模型时 `KEEL_INFERO_MODEL` 与 `KEEL_INFERO_MODEL_DIR`（容器内目录名）一起换。
本机实测（2026-09-29）：容器 healthy 后向量与 GPU 版余弦 0.9999995，延迟与裸二进制同一量级。

## 版本与镜像

每个发布版本都会推一份镜像到 GitHub Container Registry：

```bash
docker pull ghcr.io/jackwangfeng/keel:v0.2.0            # API
docker pull ghcr.io/jackwangfeng/keel-migrate:v0.2.0    # goose + 迁移
docker pull ghcr.io/jackwangfeng/keel-postgres:v0.2.0   # PostgreSQL 16 + PostGIS + pgvector
docker pull ghcr.io/jackwangfeng/keel-console:v0.2.0    # 商家后台（nginx，把 /api 反代给 app）
```

v0.1.0 只发了 API 镜像；从 v0.2.0 起四个镜像随版本一起发，不从源码构建也能起一整套。
`docker compose build` 从源码构建照样可用。

确认跑的是哪一版：

```bash
curl -s http://localhost:8080/version
docker compose logs app | head -1      # 启动日志第一行就是版本号
```

升级：拉新代码或新镜像后 `docker compose up -d --build`。`migrate` 服务会先把库迁到新版本，
`app` 等它跑完才启动。
