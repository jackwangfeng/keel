# 大规模秒杀：方案备忘（未实施）

> 状态：**备忘，未排期**（2026-09-28 记）。今天的秒杀够中小流量用；等真有「几千人同时抢一个 SKU」的活动，
> 按这份方案改。动手前先做第一节的基线压测，拿数字决定做到哪一步。

## 今天的秒杀是什么样

秒杀是营销活动的一种（00058）：秒杀价 + 活动配额 + 每人限购。配额在库存服务的 `activity_stocks`，
门店库存在 `inventories`，都是 Postgres 里的行。每一单秒杀走完整下单链路：

```
POST /orders → 算价（选中秒杀报价）→ 建草稿单 → dtmrs SAGA（Postgres 存储、SQL 屏障）
  → 库存分支：锁 inventories 那一行 + 锁 activity_stocks 那一行 → 扣减 → 提交
```

正确性是有的：并发不超卖、每人限购不被绕过（2026-09-28 破坏性测试验过）。但**吞吐从来没量过**。
所有人抢同一个 SKU 时，所有请求都排在同一行（其实是两行）的行锁上 —— 这正是秒杀会出问题的地方。
唯一的实测是普通下单 650 单/秒（多 SKU 分散、同机压测，PROGRESS「多实例实测」）。

## dtmrs 已经为秒杀准备了什么（Keel 一样都还没用）

dtmrs（`third_party/dtmrs/.dtmrs-src`，上游 github.com/jackwangfeng/dtmrs）明确把秒杀当作重点场景：

| 能力 | 出处 | 要点 |
|---|---|---|
| Redis 存储后端（`redis` feature） | CHANGELOG「为秒杀那类流量尖峰而生」 | 端到端 13105 笔/秒（Postgres 4982）。**持久性弱一档**、终态记录按 TTL 过期、`list_recent` 只留最近 1000 笔 —— 用前读它的 README |
| Redis 版子事务屏障（`dtmrs-barrier` 的 `redis_barrier`） | Cargo.toml 注释 | 业务数据在 Redis 里时用：屏障判定与扣减在**同一个 Lua 脚本**里拿到原子性（没有 SQL 本地事务可加入） |
| 二阶段消息（msg）+ Redis | docs/benchmarks.md「秒杀场景」 | 1 个正向步骤 18213 笔/秒 |
| 选型论证 | docs/choosing-a-mode.md「秒杀该用哪个（以及为什么不是 TCC）」 | 见下 |

它的核心论点（摘要）：

- 秒杀库存**放 Redis 不放数据库**：单行更新扛不住几十万并发打同一行。
- **`DECR` 本身就是 Try**：扣掉的那一刻名额就预留给这个用户了，之后不用再动库存 —— 所以不要用 TCC
  （confirm 是空操作的 TCC 就是 SAGA，白多一倍往返，实测差 4.4 倍）。
- 下游**只会慢、不会被业务拒绝**（扣完发消息、消费者重试到建单成功）→ **msg**；
  下游**可能被业务拒绝**（券过期、风控拦截）→ **SAGA**，补偿把名额还回 Redis。
- 屏障键 TTL 必须长于事务最大生命周期（含重试退避），否则正向屏障键先过期、补偿后到，
  会被判成空回滚而**不执行补偿** —— 名额静默丢失。默认 7 天。

## 方案

### 0. 先量基线（不改代码，小半天）

私有栈（与演示站同一个 C 档拆分形态），一个配额 1000 件的秒杀 SKU，几千并发抢。量：
卖完用时、成功下单的每秒笔数、失败的错误分布（409 抢光 / 429 / 500 / 超时）、有没有超卖或少卖、
瓶颈在哪（应用 CPU、库存服务、PG 行锁等待 —— `pg_stat_activity` 的 `wait_event`）。
**有了数字再决定做到下面哪一步**；也许只要第 1 步就够了。

### 1. 准入：卖完即拒（改动小）

配额在内存 / Redis 里有一个「还剩多少」的近似值，归零后直接 409「已抢光」，
不让请求进下单链路。只挡流量、不改扣减语义（真正的扣减仍在 PG 行上），所以不会超卖；
代价是边界上可能「显示还有、实际没了」，那几单照常在库存分支被拒。

### 2. 配额分片（中等）

把一个 SKU 的 1 行配额拆成 N 行（`activity_stocks` 加 shard 列），下单随机落一片、片空了换片。
行锁热点被打散 N 倍。门店库存那一行也要一起处理：活动上线时把配额从门店库存**一次性划出来**
（下面第 3 步的「预留」），否则热点只是从配额行挪到库存行。

### 3. 预扣 + 异步建单（dtmrs 推荐的形状，改动大）

```
活动上线：从门店库存划出配额 → Redis（活动期间不再碰 inventories 那一行）
抢购入口：一个 Lua 脚本 —— 判时间窗、判每人限购、DECR 配额、写 Redis 屏障，原子完成
          拿不到 → 409 已抢光（绝大多数请求在这里结束，不碰数据库）
拿到名额 → SAGA（Keel 的建单可能被业务拒：地址超出围栏、券不可用 —— 按 dtmrs 的判据用 SAGA 不用 msg）
          正向：建单（core，Postgres）；补偿：把名额还回 Redis（Redis 屏障保证只还一次）
活动结束：没卖完的配额退回门店库存
```

协调器存储可以同时换成 dtmrs 的 Redis 后端（吞吐约 2.6 倍），但要接受它写明的持久性弱一档；
也可以只让秒杀这一条链路用 Redis 存储，普通下单仍在 Postgres。

### 必须想清楚的几处（设计评审的重点）

- **预留与回补**：划出去的配额与门店库存的账要对得上；活动提前下线、改配额、进程崩在划转中间时怎么办。
- **Redis 挂了**：降级成今天的 PG 路径（慢但正确），还是整场秒杀暂停。不能「Redis 不在就放行」。
- **对账**：定期核对 Redis 已卖名额 = 数据库里该活动的有效订单行数（含待支付），差额告警、不自动修
  （与库存对账任务同一个原则）。重点防名额静默丢失（屏障 TTL 那条坑）。
- **待支付超时**：秒杀单不付款会被关单，名额要回到 Redis 池子里（今天关单回补走库存 outbox，要加一支）。
- **部署**：演示栈与 compose 要加 Redis；拆分形态下 Redis 归库存服务管。
- **每人限购**：今天在 core 的 `promotion_purchases`（建单同事务），移到 Lua 里之后两边只能留一处真相。
