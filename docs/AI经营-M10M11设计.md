# AI 经营 M10 / M11 设计

> 2026-09-28。前置：[规划](./AI经营-规划.md)、[M9 设计](./AI经营-M9设计.md)、[AI 接口](./AI接口.md)。
> 迁移号段：M10 = `00120`–`00129`，M11 = `00130`–`00139`（开工时 main 最高 `00111`）。

M9 让 AI 员工「能接上」：读数据、算补货、提加库存提案、写简报。M10「能经营」把写操作扩到营销、商品与售后，
让 agent 被事件叫醒而不只是每天定时，并且量出每条提案执行之后到底有没有用。M11「能放手」让店长按类别、按上限
放开自动执行，给 agent 一个只读查数的口子，并把整套接入用第二个 harness 实测一遍。

原则不变：**Keel 不内置模型**；数字由 Keel 算；写操作默认是提案；执行复用后台接口同一个 service 函数，
以 AI 员工的身份、带幂等键；每一步可审计。

## M10 能经营

### 1. 提案种类（00120）

| kind | MCP 工具 | 执行（批准后，以 AI 员工身份） | 谁能提 / 批 |
|---|---|---|---|
| `inventory_adjust` | `propose_inventory_adjust` | 加库存（M9） | 门店操作范围 |
| `flash_price` | `propose_flash_price` | 建一个**限时折扣**活动（type 3）并上线：若干 SKU、活动价或折扣率、起止时间 | 全店范围（营销是全店的） |
| `coupon` | `propose_coupon` | 建一张券模板（满减 / 折扣 / 立减），可选进领券中心 | 全店范围 |
| `product_copy` | `propose_product_copy` | 改商品标题 / 副标题（过广告法违禁词检查） | 全店范围（商品是全店的） |
| `refund_decision` | `propose_refund_decision` | 审核售后：同意 / 驳回（驳回必须带理由） | 订单履约门店的操作范围 |

表结构：`agent_proposals.store_id` 改为可空（营销、商品是全店的），新增 `target_key TEXT`（去重键：
`store:1:sku:3`、`product:12`、`refund:RF…`、`flash:sku:3,5`、`coupon:<name>`），待处理唯一索引改成
`(merchant_id, kind, target_key)`。`kind` 的 CHECK 扩到五种。

**判权两道照旧**：提的时候按 AI 员工身份判一次（没权提的直接拒，免得人批了才发现执行不了）；批准时按人判
（全店类要全店范围，门店类按门店），执行时再按 AI 员工身份判一次。

**上限**（硬的，提案层就拒）：限时折扣最多 20 个 SKU、折扣率 ≥ 50%（即最多打五折）、时长 ≤ 14 天；
券面额 ≤ 100 元、总量 ≤ 10000；标题 ≤ 60 字。自动执行（M11）另有更紧的店长上限。

### 2. 计算工具

- `slow_movers`：高库存低周转。每个（门店，SKU）：可售、近 N 天销量、**库存周转天数** = 可售 ÷ 日均
  （日均按 restock_plan 同一口径，分母去断货天）、上架天数；按周转天数降序。给「滞销清仓」手册用。
- `promotion_review`：一个活动 / 一张券的复盘：活动期间与之前同长周期的销售额、单量、客单、
  参与 SKU 的销量；券的领取数、核销数、核销率、带来的销售额。给「活动复盘」手册用。
- 搜索缺口用已有的 `search_insights`（无结果词、低点击词）。

### 3. 事件（00121）

Keel 在这些时刻写一条 `agent_events`：

| type | 什么时候 | payload |
|---|---|---|
| `stock_low` | 一个（门店，SKU）的可售从预警线之上跌到预警线及以下（库存预警同一口径） | store_id, sku_id, available, threshold |
| `refund_created` | 买家提交售后申请 | refund_no, order_no, store_id, amount |
| `search_zero_spike` | 一个无结果词近 1 小时出现 ≥ 5 次（每词每天至多一条） | query, count |
| `proposal_decided` | 提案被批准 / 驳回 / 执行失败 / 过期 | proposal_id, status |

消费方式两种，都给：

- **拉**：MCP 工具 `list_events(after_id)` 与 `ack_events(up_to_id)`；每名 AI 员工有自己的游标
  （`agent_event_cursors`），事件按它的管辖范围过滤（门店管理员只看到自己店的）。
- **推**：后台给 AI 员工配一个 **webhook URL**（可选）。事件写入后由任务队列（jobs 表，已有）投递：
  `POST <url>`，JSON 体，`X-Keel-Signature: sha256=<hmac>`（密钥在配置 webhook 时生成、只显示一次），
  失败指数退避重试 6 次。接入方收到后自己拉起 agent —— 这就是「事件唤醒」，Keel 不管 agent 怎么跑。

演示站：运行器每 10 分钟 `list_events`，有新事件才拉起 Claude Code 处理（`agent/runner/claude-events.sh`）。

### 4. 执行后复盘（00122）

提案执行后 7 天（`flash_price`、`coupon` 为活动 / 券结束后 3 天，`inventory_adjust` 为 7 天），任务队列算一次
**结果**写进 `agent_proposals.outcome`（JSONB）：

- `inventory_adjust`：之后 7 天该 SKU 在该店的销量、断货天数（补了之后还断没断）；
- `flash_price`：活动期间 vs 之前同长周期的参与 SKU 销量与销售额；
- `coupon`：领取、核销、核销率、带来的销售额；
- `product_copy`：之后 7 天 vs 之前 7 天该商品的搜索点击与销量；
- `refund_decision`：不量（没有「效果」可言），只记执行结果。

每条结果带一个 `verdict`：`positive` / `neutral` / `negative`（规则写死、可解释：比如补货后 7 天没断货且卖出
≥ 补货量的 30% 为 positive；断货仍 ≥ 2 天为 negative）。

**「AI 员工成绩单」**：`GET /admin/agents/{staff_id}/scorecard`：按种类的提案数、批准率、执行成功率、
verdict 分布、最近 30 天的明细。后台 AI 员工页一个标签页。MCP 工具 `my_scorecard` 让 agent 自己也看得到
（手册要求它据此调整）。

### 5. 手册

`agent/skills/`：`滞销清仓.md`、`搜索缺口.md`、`售后审核.md`、`活动复盘.md`，与 `事件处理.md`（被事件唤醒时怎么分派）。
每本写清：看哪些工具、什么情况下提什么、上限、证据怎么写、什么时候只写简报不提案。

## M11 能放手

### 6. 自动执行策略（00130）

`agent_auto_policies`：每名 AI 员工 × 每种提案一行：`enabled`、单笔上限（按种类：加库存件数、活动最低折扣率、
券面额）、每日条数上限。提案写入时若命中策略且在上限内，**当场以 AI 员工身份执行**（与人批准走同一段执行代码），
状态直接到 20 / 40，`decided_by` 为空、`auto_approved = true`。超限的照常进待处理队列。
`refund_decision` 不允许自动执行（资金动作，策略写不进去，库里 CHECK 挡住）。
每日汇总进简报（手册要求）；后台提案列表可按「自动执行」筛。

### 7. 只读 SQL 工具（00131）

`query_sql(sql)`：给 agent 一个「大白话查数据」的口子，但只能读一组**专门的视图**：

- 视图在 schema `agent_ro` 里（`orders_v`、`order_items_v`、`products_v`、`skus_v`、`stores_v`、`refunds_v`、
  `search_logs_v`、`coupons_v`、`promotions_v`…），**不含**手机号、收货地址、口令哈希、令牌、密钥；
  每个视图的定义里显式 `WHERE merchant_id = current_merchant()`（视图以属主身份执行，不能指望 RLS）。
- 执行在单独的只读事务里：`SET LOCAL ROLE keel_agent_ro`（只对 `agent_ro` 有 SELECT，对 public 什么都没有）、
  `SET TRANSACTION READ ONLY`、`statement_timeout = 3s`、结果至多 500 行；只接受单条语句。
- 每次调用照常进审计（SQL 原文在参数里）。

### 8. 第二个 harness 与公开日志

- 用 Codex CLI（或本机可用的另一个 MCP 客户端）按 `docs/AI接口.md` 接一遍，把实测步骤与差异写进文档；
  本机没有就如实写「未实测」并给出配置。
- **AI 经营日志**：店铺设置里一个开关 `public_ai_log`（默认关）。开了之后 `GET /api/v1/ai-log`（买家侧、免登录）
  返回最近的简报标题与摘要、提案（种类、标题、状态、结果 verdict；不含证据全文里的数字以外的敏感信息 —— 证据
  本来就只有经营数字）。演示站打开它，页面 `/ai-log/`（静态页读这个接口）。

## 不做

- 让 agent 直接改价（基准价 / 门店价）：影响面太大，先用限时折扣表达「降价」。
- 让 agent 发站内消息给买家：M12 再说。
- 在 Keel 里跑模型：永远不做。
