# 微服务拆分方案：订单 / 优惠券 / 库存

> 状态：进行中（2026-09-27 立项）。这份文档是施工图，每完成一个阶段在文末「进度」里记一笔。

## 目标：一套代码，两种部署

**同一个二进制、同一套代码**，靠配置决定部署形态：

| 形态 | 进程 | 数据库 | 分支地址 |
|---|---|---|---|
| 单体（默认，今天的 `docker compose up`） | 1 个 `keel`，`KEEL_ROLE=all` | 1 个库 | `local://` |
| 拆分 | 3 个 `keel`：`KEEL_ROLE=core` / `coupon` / `inventory` | 3 个库 | `http://` |

「单体」不是拆分的降级模式，而是**同一套一致性协议跑在同一个进程里**：优惠券、库存的所有读写
在单体形态下也只经过它们各自的服务接口、只碰各自的表，只是接口的实现是进程内调用而不是 HTTP，
三个连接池指向同一个库。于是两种形态走的是同一条代码路径——单体上的全量测试同样覆盖拆分形态的
业务逻辑，拆分形态另有一组跨进程测试只验传输层。

不做的：把商品、用户、门店、营销等其余领域也拆出去。它们留在 `core`（订单服务是 core 的一部分）。

## 服务边界

| 服务 | 拥有的表 | 对外接口（进程内 = Go interface，拆分 = HTTP） |
|---|---|---|
| **inventory** | `inventories`、`inventory_logs`、`barrier` | 批量查水位；SAGA 扣减 / 回补分支；按单回补（幂等）；后台 CAS 设值 / 相对调整 / 建行；库存预警列表 |
| **coupon** | `coupon_templates`、`coupon_scopes`、`user_coupons`、`barrier` | 取券与规则；列可用券；SAGA 锁券 / 解锁分支；核销、退回（幂等）；领券、发券；模板与范围的后台读写；统计 |
| **core** | 其余全部（含 `orders`、`order_items`、`payments`、`refunds`、`promotion_*`、`products`、`skus`、`stores`……） | 现有全部对外 API |

**跨服务只传 id 与数值**，不传行、不共享表。core 调 inventory / coupon；inventory 与 coupon **不回调 core**
（没有环）。需要 core 数据的判断（SKU 在不在架、门店是否可售、券范围里的类目 / 商品 / 门店是否存在）
一律由 core 先判完再调下游。

## 要拆掉的耦合（逐项）

完整清单见审查记录；这里按处理方式归类。

### 1. 跨域外键 → 删掉，改由应用层 + 对账保证

| 外键 | 处理 |
|---|---|
| `inventories` / `inventory_logs` → `skus`、`stores`、`merchants` | 删。建 SKU 时 core 调 inventory 建行；删 SKU 是软删，库存行留着无害；对账任务报孤儿 |
| `orders.user_coupon_id` → `user_coupons`、`user_coupons.order_id` → `orders` | 删。两边只存 id；锁券 / 核销 / 退回都以 `order_no` 为幂等键 |
| `user_coupons.user_id` → `users` | 删。领券 / 发券由 core 校验用户存在后再调 |
| `promotions.gift_template_id` → `coupon_templates`、`promotion_gift_grants.user_coupon_id` → `user_coupons` | 删。core 写营销活动前调 coupon 校验模板存在 |

### 2. 跨域 JOIN → core 先取自己的，再批量问下游，在 Go 里合并

- 商品详情的 SKU 水位、列表与检索的 `in_stock`、购物车行水位、后台商品 / SKU 的总库存、门店 / 大区上架清单：
  一页一次 `inventory.Stock(storeID, skuIDs)` 批量调用。`in_stock_only` 过滤改成「core 召回 → 批量查水位 → 过滤」，
  分页按过滤后的结果截断（检索本来就是召回后排序，影响可控；商品列表不带这个过滤）。
- 库存预警报表：inventory 返回 `(sku_id, store_id, available, warning)`，core 补商品名 / 门店名。
- 券范围的显示名（类目 / 商品 / 门店名）：coupon 返回 `(scope_type, target_id)`，core 补名字。
- 下单扣减那条语句里对 `skus` / `stores` / 上下架覆盖的判断：挪到 core 的定价阶段（它本来就判了一遍），
  inventory 只做「这家店这个 SKU 够不够、够就扣」。

### 3. 跨域的单一本地事务 → SAGA 分支或 outbox 任务

今天有 5 处在**一个本地事务**里同时写订单与库存 / 券。拆开后每一处都要有明确的一致性协议：

| 今天的事务 | 拆分后 |
|---|---|
| 下单 SAGA 的库存分支（扣库存 + 流水 + 活动配额 + 预警通知） | 拆成两个分支：`inventory` 分支（扣库存 + 流水，屏障在库存库）、`core` 分支（活动配额）。预警通知：inventory 在响应里回「跌破预警线」，core 分支据此写通知 |
| 下单 SAGA 的锁券分支 | 本来就是独立分支，改成调 coupon（屏障在券库） |
| 超时关单 / 买家取消（关单 + 回补 + 放配额 + 解锁券 + 通知） | core 事务：关单 + 放配额 + 通知 + **入队 outbox 任务** `order.release`；worker 调 `inventory.RestoreForOrder`、`coupon.UnlockForOrder`，两者都以 `order_no` 幂等（库存按流水净值只补未补的部分） |
| 支付回调（入账 + 券 2→3 核销） | core 事务入账 + outbox 任务 `coupon.consume`；券核销以 `order_no` 幂等 |
| 退款到账（退款单 + 订单金额 + 回补 + 退券 + 通知） | core 事务写退款与订单 + outbox 任务 `refund.restock`、`coupon.return`；以 `refund_no` / `order_no` 幂等 |

outbox 用现有的 `jobs` 队列（与状态变化同事务入队、`FOR UPDATE SKIP LOCKED` 出队、指数退避、死信），
**单体形态下也走同一条路**。代价要说清楚：关单之后到库存回补完成之间有一个短窗口（毫秒到秒级，
下游不可用时更长），这段时间里库存看起来还被占着——方向是「少卖」不是「超卖」。

### 4. 服务间调用

- 进程内：直接调 Go 实现。
- HTTP：`/internal/v1/...`，只在内网监听端口上（与公网 API 分开的 `KEEL_INTERNAL_ADDR`），
  请求带 `X-Keel-Merchant-ID`（租户）与服务间 HMAC 签名（共享密钥 `KEEL_INTERNAL_SECRET`）。
  被调方按租户开事务（RLS 照旧）。
- SAGA 分支：库存、券分支的地址由配置决定（单体 `local://inventory_deduct`，拆分 `http://inventory:8090/internal/v1/saga/...`），
  分支体是同一个函数。屏障记在**分支所在服务自己的库**里。

## 数据库与迁移

- 迁移拆成三个目录：`db/migrations`（core，已有）、`db/migrations-inventory`、`db/migrations-coupon`。
  两个新目录的第一条迁移用 `CREATE TABLE IF NOT EXISTS` 建出与现在一致的表 —— 单体库里表已存在，是空操作；
  拆分部署的新库里真正建表。
- core 这边新增一条迁移删掉第 1 节列出的跨域外键。
- 从单体迁到拆分：提供 `scripts/split-migrate.sh`，把两组表导出、导入新库、校验行数，然后切配置。
