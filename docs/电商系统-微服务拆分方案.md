# 微服务拆分方案：库存服务（第一期）

> 状态：进行中（2026-09-27 立项）。这份文档是施工图，每完成一个阶段在文末「进度」里记一笔。
>
> **粒度的决定**（2026-09-27 与用户确认）：最初提的是「订单 / 优惠券 / 库存」三拆。评估之后改成
> **第一期只拆库存（含活动库存配额）**，理由见下面「为什么是这个粒度」。

## 目标：一套代码，两种部署

**同一个二进制、同一套代码**，靠配置决定部署形态：

| 形态 | 进程 | 数据库 | 分支地址 |
|---|---|---|---|
| 单体（默认，今天的 `docker compose up`） | 1 个 `keel`，`KEEL_ROLE=all` | 1 个库 | `local://` |
| 拆分 | 2 个 `keel`：`KEEL_ROLE=core` / `inventory` | 2 个库 | `http://` |

「单体」不是拆分的降级模式，而是**同一套一致性协议跑在同一个进程里**：库存的所有读写
在单体形态下也只经过库存服务的接口、只碰库存的表，只是接口的实现是进程内调用而不是 HTTP，
两个连接池指向同一个库。于是两种形态走的是同一条代码路径——单体上的全量测试同样覆盖拆分形态的
业务逻辑，拆分形态另有一组跨进程测试只验传输层。

不做的：把商品、用户、门店、营销、优惠券等其余领域也拆出去。它们留在 `core`。
机制（按角色启动、服务间调用、分支地址可配、outbox、分库迁移）按通用的方式建，以后拆下一个服务直接复用。

## 为什么是这个粒度

| 候选 | 结论 | 理由 |
|---|---|---|
| **库存（门店库存 + 活动库存配额）** | **拆** | 边界清楚（SKU × 门店的数量，逻辑只有扣 / 补 / 设值 / 预警）；下单扣减是最热的写路径，秒杀时热点压在单行上，有独立扩容的理由；业界「库存中心」就是这个边界。活动配额（秒杀 / 限时特价的 `stock_qty` / `sold_qty`）也是库存，必须一起划过来，否则同一个概念被切成两半 |
| 优惠券 | **不拆** | 用券门槛、适用范围、与营销活动叠加都算在 core 的定价里，拆出去券服务只剩存储；一单要跨服务 6 次（列可用券、取规则、锁、核销、解锁、退回），另有登录发新人礼、后台范围校验回调 core；负载很低，拆了省不下任何东西。真要拆也应该是「营销」（券 + 营销活动）整块 |
| 订单 / 支付 / 退款 | **不拆，留在 core** | 共用一个资金状态机，拆开是给自己造分布式事务 |
| 商品 / 检索（只读） | **下一期的候选** | 压测里真正的压力在读（列表 6300 req/s 吃掉 Postgres 约 10 核，下单 650 单/s 约 5.5 核）；读多写少、可配只读副本、与交易没有事务耦合 |

## 服务边界

| 服务 | 拥有的表 | 对外接口（进程内 = Go interface，拆分 = HTTP） |
|---|---|---|
| **inventory** | `inventories`、`inventory_logs`、`activity_stocks`（新：活动配额与已售，从 `promotion_skus` 拆出）、`barrier` | 批量查水位与活动余量；SAGA 扣减 / 回补分支（门店库存与活动配额同一个分支、同一个本地事务）；按单回补（幂等）；后台 CAS 设值 / 相对调整 / 建行 / 设活动配额；库存预警列表 |
| **core** | 其余全部（含 `orders`、`order_items`、`payments`、`refunds`、优惠券、`promotions` / `promotion_skus`（只剩价格配置与每人限购）/ `promotion_purchases`、`products`、`skus`、`stores`……） | 现有全部对外 API |

**跨服务只传 id 与数值**，不传行、不共享表。core 调 inventory；inventory **不回调 core**（没有环）。
需要 core 数据的判断（SKU 在不在架、门店是否可售、活动是否在进行中、每人限购）一律由 core 先判完再调下游。

## 要拆掉的耦合（逐项）

完整清单见审查记录；这里按处理方式归类。

### 1. 跨域外键 → 删掉，改由应用层 + 对账保证

| 外键 | 处理 |
|---|---|
| `inventories` / `inventory_logs` → `skus`、`stores`、`merchants` | 删。建 SKU 时 core 调 inventory 建行；删 SKU 是软删，库存行留着无害；对账任务报孤儿 |
| `promotion_skus.stock_qty / sold_qty` | 搬到 inventory 的 `activity_stocks(promotion_id, sku_id, quota, sold)`，不留外键；core 改活动商品时调 inventory 设配额，「已售出的 SKU 不能移除 / 配额不能低于已售」由 inventory 判 |

### 2. 跨域 JOIN → core 先取自己的，再批量问下游，在 Go 里合并

- 商品详情的 SKU 水位、列表与检索的 `in_stock`、购物车行水位、后台商品 / SKU 的总库存、门店 / 大区上架清单：
  一页一次 `inventory.Stock(storeID, skuIDs)` 批量调用。`in_stock_only` 过滤改成「core 召回 → 批量查水位 → 过滤」，
  分页按过滤后的结果截断（检索本来就是召回后排序，影响可控；商品列表不带这个过滤）。
- 库存预警报表：inventory 返回 `(sku_id, store_id, available, warning)`，core 补商品名 / 门店名。
- 商品列表 / 详情上的活动余量（秒杀「仅剩 N 件」）：同一次批量调用一起取回。
- 下单扣减那条语句里对 `skus` / `stores` / 上下架覆盖的判断：挪到 core 的定价阶段（它本来就判了一遍），
  inventory 只做「这家店这个 SKU 够不够、够就扣」。

### 3. 跨域的单一本地事务 → SAGA 分支或 outbox 任务

今天有 5 处在**一个本地事务**里同时写订单与库存 / 券。拆开后每一处都要有明确的一致性协议：

| 今天的事务 | 拆分后 |
|---|---|
| 下单 SAGA 的库存分支（扣门店库存 + 流水 + 活动配额 + 每人限购 + 预警通知） | 拆成两个分支：**inventory 分支**（扣门店库存 + 流水 + 活动配额，屏障在库存库，一个本地事务）、**core 分支**（每人限购 + 预警通知；预警由 inventory 在响应里回「跌破预警线的 SKU」）。每人限购放在库存分支之后：它失败时全局补偿会把库存与配额放回 |
| 下单 SAGA 的锁券分支 | 不变（券在 core） |
| 超时关单 / 买家取消（关单 + 回补 + 放配额 + 放限购 + 解锁券 + 通知） | core 事务：关单 + 放限购 + 解锁券 + 通知 + **入队 outbox 任务** `order.release`；worker 调 `inventory.ReleaseForOrder`，以 `order_no` 幂等（按流水净值只补未补的部分，配额同理） |
| 支付回调 | 不变（入账与券核销都在 core） |
| 退款到账（退款单 + 订单金额 + 回补 + 退券 + 通知） | core 事务写退款、订单、退券、通知 + outbox 任务 `refund.restock`；worker 调 `inventory.RestockForRefund`，以 `refund_no` 幂等 |

outbox 用现有的 `jobs` 队列（与状态变化同事务入队、`FOR UPDATE SKIP LOCKED` 出队、指数退避、死信），
**单体形态下也走同一条路**。代价要说清楚：关单之后到库存回补完成之间有一个短窗口（毫秒到秒级，
下游不可用时更长），这段时间里库存看起来还被占着——方向是「少卖」不是「超卖」。

### 4. 服务间调用

- 进程内：直接调 Go 实现。
- HTTP：`/internal/v1/...`，只在内网监听端口上（与公网 API 分开的 `KEEL_INTERNAL_ADDR`），
  请求带 `X-Keel-Merchant-ID`（租户）与服务间 HMAC 签名（共享密钥 `KEEL_INTERNAL_SECRET`）。
  被调方按租户开事务（RLS 照旧）。
- SAGA 分支：库存分支的地址由配置决定（单体 `local://inventory_deduct`，拆分 `http://inventory:8090/internal/v1/saga/...`），
  分支体是同一个函数。屏障记在**分支所在服务自己的库**里。

## 部署档位：逻辑上始终是分开的，物理上怎么放是部署的事

用户 2026-09-27 定的原则：**逻辑上就是分布式的，只是怎么部署而已。** 库存服务从代码层面只认自己的连接串
（`KEEL_INVENTORY_DSN`）、只碰自己的表；连接串指向哪里，决定了下面三档，代码一行不变：

| 档位 | 进程 | 库存数据放在 | 隔离强度 | 适合 |
|---|---|---|---|---|
| A 单体 | 1 个（`all`） | 同一个库、同一个 schema（今天的形态） | 靠代码约定（core 不直接碰库存表，阶段 1 之后由测试守住） | 本地开发、小店 |
| B 逻辑隔离 | 1 个或 2 个 | **同一个 Postgres**，独立的 schema `inventory` + 独立的数据库账号 `keel_inventory` | **靠权限**：`keel_inventory` 只能访问 `inventory` schema，core 的 `keel_app` 对它没有任何权限——跨模块 join 在数据库层面就过不去 | 想要边界、不想多一台库 |
| C 物理拆分 | 2 个（`core` + `inventory`） | 另一个库 / 另一台机器 | 物理隔离，故障、扩容、备份都独立 | 需要独立扩容或故障隔离 |

B 档的实现要点（阶段 2 做）：库存迁移目录建表时用连接串里的 `search_path`（`options=-csearch_path=inventory`）
落进 `inventory` schema；`keel_inventory` 账号只 GRANT 那个 schema；从 A 迁到 B 用同一个数据迁移脚本
（把 public 里的库存表搬进 `inventory` schema、校验行数、再切连接串）。A → B → C 都是「搬数据 + 改连接串」，
不改代码。

以后拆别的模块（下一期候选：商品与检索），同样按这三档走。

## 报表与分析（以后，不在这一期）

交易库（行存、点查、强一致）与分析库（列存、大范围扫描聚合）是两种东西，报表的演进按数据量分三步：

1. **现在**：报表跑在交易库上。数据量小、索引到位，毫秒级（商品排行 30 天 244ms）。
2. **中等规模**：专用只读副本跑报表，报表查询设语句超时；注意 Postgres 备库上的长查询会和复制回放冲突
   （要么被取消，要么打开 `hot_standby_feedback` 让主库膨胀），所以同时把常用口径做成预先汇总的宽表 / 物化视图，
   查询只读汇总结果，不在备库上临时大 join。
3. **大规模**：CDC 把各服务库的变更同步到列存库（ClickHouse / Doris / StarRocks 一类），报表改读那边。
   **这也是拆服务之后跨服务联合分析的标准做法**：交易侧严格隔离、不跨库 join，分析侧汇总所有服务的数据、随便 join。
