## 一、全局约定

这几条是「不山寨」的底线，所有表无条件遵守。

| 项目 | 约定 | 理由 |
|---|---|---|
| 金额 | `BIGINT`，单位**分** | 绝不用 float/double。字段名统一后缀 `_cents` |
| 时间 | `TIMESTAMPTZ`，存 UTC | 展示层转时区。禁用 `TIMESTAMP` |
| 主键 | `BIGINT GENERATED ALWAYS AS IDENTITY` | 内部主键；对外暴露另用业务编号 |
| 对外编号 | **仅**订单/支付/退款用不可枚举字符串（`order_no` / `payment_no` / `refund_no`） | 防止爬单量。其余对象对外用自增 `id` |
| 软删除 | `deleted_at TIMESTAMPTZ NULL` | 仅商品/分类等主数据使用；交易数据永不删除 |
| 枚举 | 用 `SMALLINT` + Go 常量，不用 PG ENUM | PG ENUM 改值要 DDL，迁移痛苦 |
| 审计 | 关键表带 `created_at` / `updated_at` | 由触发器统一维护 |

> **关于「对外编号」这条为什么收窄**
>
> 原先的写法是「对外一律用业务编号，不暴露自增主键」，一刀切。但这条规则的
> 真实理由只有一个——**防止竞对按 `order_no` 递增爬出你的日单量**。这个理由
> 只对订单、支付单、退款单成立，它们的编号密度直接等于经营数据。
>
> 商品 `id`、SKU `id` 本来就随列表页公开；地址、优惠券实例的 `id` 泄露出去也
> 推不出任何经营指标，它们真正要防的是**越权**——而越权的正解是服务端按
> `user_id` 强制过滤（见架构文档「安全」一节），不是把 id 换成随机串。
> 用不可枚举编号去防越权，属于把访问控制问题伪装成命名问题。
>
> 代价：对外标识符不统一，读 API 的人要记住「交易三兄弟用 no，其余用 id」。
> 换来的是不必为几十个接口各造一套编号生成与反查。

```sql
-- 通用 updated_at 触发器
CREATE OR REPLACE FUNCTION touch_updated_at() RETURNS trigger AS $$
BEGIN NEW.updated_at = now(); RETURN NEW; END;
$$ LANGUAGE plpgsql;
```

### 本文件的定位：业务表 DDL 的唯一真相源

**全部业务表的 `CREATE TABLE` / `ALTER TABLE ... ADD COLUMN` 只出现在本文件。**
其余设计文档（语义检索层、商品理解服务、总体架构）需要讲表结构时，用字段清单表格
或直接引用本文的章节号，不得自带 DDL。

两个例外：

- dtmrs 的 `barrier` 表是第三方组件 `migrate()` 的产物，不是本项目设计的表，
  但迁移脚本要知道它的存在，因此照抄在 §6。
- 推理引擎、检索服务之间的 HTTP 接口契约不属于表结构，仍留在各自文档。

> **为什么要立这条规矩**：本轮修订之前，三份文档各自定义了一套商品向量表——
> 一套叫 `product_embeddings` 且无 `model_version`，一套叫 `product_embeddings` 有，
> 还有一套叫 `product_vectors` 用 `(product_id, vector_type)` 复合主键，
> 而那一套的 `vector(1024)` 列根本装不下 768 维的图像向量。
> 同一段 DDL 抄在三处，不是「会不会漂移」的问题，是「什么时候被漂移咬到」的问题。
>
> 代价很实在：改一个字段要跨文档同步，看设计的人得在文档间跳转。
> 但比起线上才发现两份 schema 对不上，这个代价便宜太多。

## 二、多租户

一套部署承载多个商家。**每个商家有自己独立的店铺前台,订单永远不跨商家**——
这是 Shopify 那一类的多店模型,不是淘宝那类的集市模型。

> **为什么是多店而不是集市**
>
> 集市模型要拆主单子单、要跨店购物车、要分账结算、要入驻审核,
> 复杂度比多店高一个量级。而本项目的核心读者是「想拥有自己技术栈的商家」,
> 不是「想做一个淘宝」。
>
> 直接后果:**买家属于某个商家**。同一个人在 A 店和 B 店购物是两行 `users`,
> 订单、地址、优惠券互不相通,换店要重新登录。这不是缺陷,是多店模型的定义。
> 想要「一次登录逛所有店」,那就得是集市模型,整个订单域要重做。

**单机叙事不变。** 多租户是能力不是要求——小商家 `docker compose up`
起来就是租户数为 1 的部署,感知不到任何多租户的存在。

### merchants

```sql
CREATE TABLE merchants (
    id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    code         TEXT        NOT NULL UNIQUE,  -- 短标识,用于域名与路径路由
    name         TEXT        NOT NULL,
    status       SMALLINT    NOT NULL DEFAULT 1,  -- 1正常 2停用 3待审核
    deleted_at   TIMESTAMPTZ,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 商家的改名与停用 / 启用（迁移 00024）。**只追加**：当前名字与状态 = 最新一行，
-- 一行都没有时取 merchants 自己那一列。keel_app 在这里只有 SELECT + INSERT，
-- 在 merchants 上没有 UPDATE —— 给了就等于任何租户上下文都能改商家目录
-- （00005 实测过的「租户 1 的上下文里把租户 2 停用」）。
-- 写入由 RLS 钉在平台作用域：INSERT 的 WITH CHECK 是 platform_scope()；
-- 读侧放开，租户解析要在确定租户之前读它。
CREATE TABLE merchant_revisions (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id BIGINT      NOT NULL REFERENCES merchants(id),
    name        TEXT        NOT NULL,
    status      SMALLINT    NOT NULL,          -- 1正常 2停用（没有 3：审核流程本轮不存在）
    changed_by  BIGINT      NOT NULL,          -- 平台级操作员的 staff.id，审计用
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE shop_settings (
    merchant_id  BIGINT      PRIMARY KEY REFERENCES merchants(id),
    domain       TEXT        UNIQUE,           -- 自定义域名,空则走 /s/{code}
    logo_url     TEXT,
    currency     TEXT        NOT NULL DEFAULT 'CNY',
    timezone     TEXT        NOT NULL DEFAULT 'Asia/Shanghai',
    auto_confirm_days SMALLINT NOT NULL DEFAULT 7,  -- 发货后多少天自动确认收货
    extra        JSONB       NOT NULL DEFAULT '{}',
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### 三条无条件遵守的规矩

**一、每张业务表都带 `merchant_id`,不靠 join 推导。**

即使能从父表推出来也要冗余一列。理由是下面第二条要用它,
而且少一次 join 在热点路径上是实打实的收益。
`scripts/check_tenancy.py` 会机械检查这一条,豁免必须写明理由。

**二、父子关系用复合外键钉死,让「挂到别家租户」在物理上不可能。**

```sql
-- 父表额外开一个复合唯一键
ALTER TABLE orders ADD CONSTRAINT uk_orders_id_merchant UNIQUE (id, merchant_id);

-- 子表连 merchant_id 一起引用
CREATE TABLE order_items (
    order_id    BIGINT NOT NULL,
    merchant_id BIGINT NOT NULL,
    ...
    FOREIGN KEY (order_id, merchant_id) REFERENCES orders(id, merchant_id)
);
```

> 这是本节最要紧的一条。只靠「每个查询记得加 `WHERE merchant_id = ?`」
> 是守不住的——**漏一次就是跨租户数据泄露**,而这类 bug 在测试里几乎看不出来
> (单租户测试数据下,加不加那个条件结果完全一样)。
>
> 复合外键把它变成数据库层面的不可能:把 A 商家的订单项挂到 B 商家的订单上,
> 写入直接被拒。代价是每张父表多一个复合唯一索引、每张子表多一列。
> 跟金额恒等式写进 `CHECK` 是同一个路子——**能让数据库拒绝的,就别指望人记得**。

**三、唯一约束一律收进租户内。**

全局唯一的东西在多租户下几乎都是错的:两个商家各自有一个 `sku_code = "A001"`
是完全正常的。改动清单:

| 约束 | 原先 | 现在 |
|---|---|---|
| `skus.sku_code` | 全局唯一 | `(merchant_id, sku_code)` |
| `users.phone` / `users.email` | 全局唯一 | `(merchant_id, phone)` / `(merchant_id, email)` |
| `user_identities` | `(provider, external_id)` | `(merchant_id, provider, external_id)` |
| `staff.email` | 全局唯一 | `(merchant_id, email)` |
| `shipments` 运单号 | `(carrier_code, tracking_no)` | `(merchant_id, carrier_code, tracking_no)` |
| `payments` 渠道流水 | `(channel, channel_txn_id)` | `(merchant_id, channel, channel_txn_id)` |
| `refunds` 渠道流水 | `(channel, channel_refund_id)` | `(merchant_id, channel, channel_refund_id)` |
| `merchants.code` | — | 全局唯一(它就是租户标识) |
| `orders.order_no` | 全局唯一 | **保持全局唯一** |
| `payments.payment_no` / `refunds.refund_no` | 全局唯一 | **保持全局唯一** |
| `user_coupons.coupon_code` | 全局唯一 | **保持全局唯一** |

> 交易三兄弟的编号**刻意保持全局唯一**。它们要跟支付渠道对账,
> 而渠道那边只有一个商户号维度;客服查单时也不该先问「你是哪家店的」。
> 编号本身是随机不可枚举的,全局唯一不泄露任何东西。

> **全局与租户内的分界线,一句话说清**:
> **我们自己生成的不可枚举编号保持全局唯一,外部系统生成的标识一律收进租户内。**
> `order_no` / `payment_no` / `refund_no` / `coupon_code` 属前者——生成规则在我们手里,
> 全局不重复是我们能兑现的承诺。承运商的 `tracking_no`、支付渠道的 `channel_txn_id`
> 属后者——它们只在对方自己的商户号维度内保证不重复,
> **替别人做一个他没做的承诺,代价是后到的那一条被当成重复丢掉**。
> 物理资源(如 `uploads.storage_key` 指向的磁盘路径)是第三类,必须全局唯一,理由见 §13。

### 本轮同步：分表 DDL 补齐上面这三条

上面三条从一开始就写在本节里,但**本文件自己的分表 DDL 当时没有全部照做**。
欠账是成片的:`orders` 上建了 `uk_orders_id_merchant`,`categories` / `products` /
`users` / `payments` / `carts` 等父表全忘了建;`products.category_id`、`skus.product_id`、
`orders.user_id` 这一类父子引用还是单列外键;几乎所有索引都没带 `merchant_id` 前缀。

于是文档处在最坏的一种状态:**规矩写在正文里,约束不在 DDL 里**。
读到 §2 的人以为跨租户挂接已经被钉死,实际只有 `orders` 一条线被钉住,
其余每一处都仍然指望「写 SQL 的人记得加条件」——而本节自己刚说过那是守不住的。

本轮把分表 DDL 改成与总则一致。判断标准只有一条:
**改动必须能从上面三条直接推出来,推不出来的一律不动。**
因此本轮**没有**动任何设计决定——枚举取值、状态机、字段语义、冗余策略全部原样,
改的只是让 DDL 违反本节的那些结构。考虑过而判断不该改的地方,
都在它出现的那一节里写了理由(`inventories` 的豁免、GIN / HNSW 索引、
`jobs` 的出队索引、`staff` 相关的两个可空外键)。

**索引前缀这一条,是规矩一与 RLS 合起来的推论。** 规矩一让每张表都带 `merchant_id`,
下一节的行级安全又给每条业务查询注入 `merchant_id = current_merchant()`。
于是任何业务查询的真实谓词至少是 `merchant_id = ? AND <原条件>`——
索引不以 `merchant_id` 打头,就要扫过全部租户的行再逐行过滤,
选择性差一个量级,且租户越多差得越远。所以**业务索引一律以 `merchant_id` 开头**。
四类例外,每一类都有物理原因,写在各自出现的地方:
GIN / HNSW 索引(加不了 B-tree 前缀,除非引入 `btree_gin`)、
**GIST 索引**(同源,`stores` 的围栏索引 `idx_stores_fence`,要前缀得引入 `btree_gist`;
且门店行数以「几十」计,候选集偏大在这张表上没有量级 —— 见 §4)、
`jobs` 的出队索引(本来就是跨租户公平调度,且不走 RLS)、
以及首列已经是租户内标识的唯一索引(如 `(cart_id, sku_id)`,`cart_id` 已蕴含租户)。

> **为什么把这件事写下来,而不是悄悄改掉**
>
> 「总则写了、分表没照做」是文档类工程债里最难发现的一种:两边分开读都成立,
> 只有并排看才发现分歧。而复合外键这条尤其刺眼——
> 上一条规矩自己说的是「能让数据库拒绝的,就别指望人记得」,
> 结果本文件自己就指望了人记得。
>
> 更实际的理由是:下一个读者一定会撞上「本文件的 DDL 与更早的文档片段、
> 与凭记忆写出的 SQL 对不上」。对不上的原因不是设计变了,
> 是**文档原先没有遵守自己**。不写下来,他会以为是这一轮改了设计,
> 然后去「修正」回那个不自洽的版本。
>
> 代价说清楚,三笔:每张父表多一个复合唯一索引,写入要多维护一棵 B-tree;
> 每条父子引用的外键检查多比一列;索引加 `merchant_id` 前缀会让索引变宽,
> 且平台级 `BYPASSRLS` 的跨租户运维查询不再能吃到这些索引的前缀。
> 这三笔都是确定的、可度量的,换到的是「跨租户挂接在物理上不可能」——
> 按本节开头的论证,这笔交易划算。

### 隔离的兜底：行级安全

repository 层强制注入租户条件是第一道防线，但**它是人写的**。
PostgreSQL 的行级安全（RLS）做第二道。

以下写法经过实测（PostgreSQL 16，见下方「实测结论」），**三个元素缺一不可**：

```sql
-- ① 租户上下文取值函数：未设置时明确报错，而不是让调用方猜
--    STABLE 不是随手写的，标错就是跨租户泄露，见下方「坑三」
CREATE FUNCTION current_merchant() RETURNS BIGINT
LANGUAGE plpgsql STABLE AS $$
DECLARE v TEXT := nullif(current_setting('app.merchant_id', true), '');
BEGIN
    IF v IS NULL THEN
        RAISE EXCEPTION '租户上下文未设置：事务开始时必须 SET LOCAL app.merchant_id'
            USING ERRCODE = 'insufficient_privilege';
    END IF;
    RETURN v::BIGINT;
END $$;

-- ② ENABLE 之外必须再加 FORCE
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
ALTER TABLE orders FORCE  ROW LEVEL SECURITY;

-- ③ 策略
CREATE POLICY tenant ON orders USING (merchant_id = current_merchant());
```

每个事务开始时设置上下文：

```sql
BEGIN;
SET LOCAL app.merchant_id = '42';   -- 注意是 SET LOCAL，不是 SET
...
COMMIT;
```

#### 实测结论

以下每一条都在 PostgreSQL 16 上实际跑过，不是推断。

| 验证项 | 结果 |
|---|---|
| 跨租户读取被拦截 | ✅ 租户 1 只看得到自己的订单 |
| 跨租户写入被拦截 | ✅ `USING` 会同时作为 `WITH CHECK`，插入别家 `merchant_id` 被拒 |
| 复合外键拦截跨租户挂接 | ✅ 把订单项挂到别家订单上，外键直接报错 |
| `BYPASSRLS` 角色可跨租户 | ✅ 平台级运维走这条路径 |
| 上下文未设置 | ✅ **报错而非放行**——失败方向是安全的 |
| 事务内可切换租户 | ⚠️ 可以。RLS 不阻止应用中途改上下文，「事务开始时设一次」仍是纪律 |
| sqlc 生成的代码接事务 | ✅ `pgx.Tx` 满足 sqlc 的 `DBTX` 接口，无需改生成器 |
| 把连接池直接传给 sqlc（无事务） | ✅ 失败关闭并报出可读错误——但这是运行期而非编译期拦截，见下 |
| 单连接池下反复切换租户 20 轮 | ✅ 零串租户 |
| 60 并发、3 租户交错 | ✅ 零串租户 |

**两个必须知道的坑：**

> **坑一：表属主会绕过 RLS，`ENABLE` 不够，必须 `FORCE`。**
>
> 实测：一个**非超级用户**的表属主，在只 `ENABLE ROW LEVEL SECURITY` 的表上
> **照样读到全部租户的数据**。加上 `FORCE ROW LEVEL SECURITY` 之后才被正确过滤。
>
> 这为什么致命：**迁移工具通常用应用自己的数据库角色跑，那个角色于是成为表属主。**
> 于是最常见的部署形态下，RLS 静默失效——而你以为它在保护你。
> 比没有防护更糟，因为没人会再去检查。
>
> 超级用户则**永远**绕过，`FORCE` 对它也无效。应用绝不能用超级用户连库。

> **坑二：会话级 `SET` 会泄漏给下一个请求。**
>
> 实测：同一连接上，前一个事务用 `SET`（非 `LOCAL`）设了租户 1，
> 后一个事务什么都没设，**读到了租户 1 的数据**。
> 连接池会复用连接，所以这就是一次真实的跨租户泄露。
>
> 用 `SET LOCAL` 则在事务结束时自动复位，下一个事务落到「未设置」→ 报错。
>
> 附带一个细节：`SET LOCAL` 用过之后，该参数在会话里变为**空串**而不是消失。
> 若策略直接写 `current_setting('app.merchant_id')::BIGINT`，
> 下一个事务会报 `invalid input syntax for type bigint: ""`——
> 失败仍然是关闭的，但**没人能从这条信息想到是忘了设租户上下文**。
> 上面那个 `current_merchant()` 函数就是为了让这条错误说人话。

> **坑三：策略函数标成 `IMMUTABLE` 会把租户折进缓存的执行计划。**
>
> 实测对比，同一会话、同一条预编译语句、连续切换租户八轮：
>
> | 策略函数的 volatility | 依次设租户 1,2,3,1,2,3,1,2 的实际结果 |
> |---|---|
> | `STABLE`（本设计采用） | M1, M2, M3, M1, M2, M3, M1, M2 ✅ |
> | `IMMUTABLE` | **M1, M1, M1, M1, M1, M1, M1, M1** ❌ |
>
> `IMMUTABLE` 且无参数的函数，PostgreSQL 在**计划期**就把它折成常量。
> 于是第一次执行时的租户被烤进计划，后续所有租户都读到第一个租户的数据——
> **静默的跨租户泄露，没有任何报错**。
>
> 这个坑特别阴：`IMMUTABLE` 看起来「更优化」，而且单元测试里每个用例通常是
> 新连接、新计划，**根本复现不出来**。它只在长连接 + 预编译语句
> （也就是 pgx / sqlc 的默认行为）下才发作，而那正是生产形态。
>
> 规则：**策略函数必须是 `STABLE`。** 不是 `IMMUTABLE`（会被折叠），
> 也不用 `VOLATILE`（阻止合理的优化，且没有额外安全收益）。

#### sqlc 怎么配合

sqlc 生成的 `Queries` 接受一个 `DBTX` 接口，`pgx.Tx` 天然满足它。所以落地方式是
**把租户上下文和事务绑在一起**，业务代码拿不到「没设租户的 Queries」：

```go
func WithTenant(ctx context.Context, pool *pgxpool.Pool, merchantID int64,
                fn func(*db.Queries) error) error {
    tx, err := pool.Begin(ctx)
    if err != nil { return err }
    defer tx.Rollback(ctx)

    // SET LOCAL 不接受参数占位符，只能拼接。
    // merchantID 是 int64 且来自会话上下文，不是用户输入，没有注入面。
    if _, err := tx.Exec(ctx,
        fmt.Sprintf("SET LOCAL app.merchant_id = '%d'", merchantID)); err != nil {
        return err
    }
    if err := fn(db.New(tx)); err != nil { return err }
    return tx.Commit(ctx)
}
```

> **这里有个必须正视的缺口**：sqlc 的 `DBTX` 同时被 `*pgxpool.Pool` 满足，
> 所以 `db.New(pool)` 是**能编译过**的——而那条路径没有事务，也就没有 `SET LOCAL`。
>
> 实测的结果是它会被 RLS 拒绝并报出可读错误，**失败方向安全**。
> 但这是运行期拦截，不是编译期。真正干净的做法是在 repository 层不导出
> 接受 `Pool` 的构造函数，只导出 `WithTenant`——**让错误的写法写不出来**，
> 而不是让它跑起来才报错。
>
> 平台级操作（建商家、跨租户运维）用单独的 `BYPASSRLS` 连接池，
> 与业务池物理隔离，且该路径必须审计。

> **代价**：RLS 有性能开销，且让「为什么这条 SQL 查不到数据」更难排查。
> 接受这个代价，因为替代方案是把跨租户泄露的风险全押在代码审查上。

## 三、商品域

### categories（分类树）

用 `parent_id` + 物化路径 `path`，兼顾写简单和查高效。

```sql
CREATE TABLE categories (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id   BIGINT      NOT NULL DEFAULT current_merchant() REFERENCES merchants(id),
    parent_id   BIGINT,
    name        TEXT        NOT NULL,
    path        TEXT        NOT NULL,          -- '/1/23/456/'
    level       SMALLINT    NOT NULL DEFAULT 1,
    sort_order  INT         NOT NULL DEFAULT 0,
    status      SMALLINT    NOT NULL DEFAULT 1, -- 1启用 0停用
    deleted_at  TIMESTAMPTZ,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    -- 供 products 与本表自身的 parent_id 做复合外键
    UNIQUE (id, merchant_id),
    FOREIGN KEY (parent_id, merchant_id) REFERENCES categories(id, merchant_id)
);
CREATE INDEX idx_categories_path
    ON categories USING btree (merchant_id, path text_pattern_ops);
CREATE INDEX idx_categories_parent
    ON categories(merchant_id, parent_id) WHERE deleted_at IS NULL;
```

> **自引用的 `parent_id` 也走复合外键**,这是规矩二在同一张表内的应用:
> 分类树的父节点必须与子节点同属一个租户,否则一条 `path` 会横跨两家店,
> 而 `path` 正是分类查询的主索引——一旦跨了,前台目录树会直接长出别家的分类。
>
> 一个必须知道的 SQL 细节:复合外键默认是 `MATCH SIMPLE`,**任一列为 NULL 就不做检查**。
> 根分类的 `parent_id` 恰好是 NULL,于是天然放行,不需要额外写什么条件。
> 反过来说,这也意味着「`parent_id` 非空时才校验」是数据库给的语义,不是我们挑的。
>
> 代价:`categories` 多一个复合唯一索引;删除一个分类时,
> 外键检查要走 `(id, merchant_id)` 而不是主键,多一次索引查找。

### products（SPU）

```sql
CREATE TABLE products (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id   BIGINT      NOT NULL DEFAULT current_merchant() REFERENCES merchants(id),
    category_id   BIGINT      NOT NULL,
    brand_id      BIGINT,
    title         TEXT        NOT NULL,
    subtitle      TEXT,
    description   TEXT,
    -- 冗余字段：列表页只查 products，不 join skus
    -- min_price_cents / max_price_cents 在 M4 被删掉了（迁移 00019），见下面的设计说明
    total_stock   INT         NOT NULL DEFAULT 0,
    sales_count   INT         NOT NULL DEFAULT 0,
    status        SMALLINT    NOT NULL DEFAULT 0, -- 0草稿 1上架 2下架
    published_at  TIMESTAMPTZ,
    deleted_at    TIMESTAMPTZ,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    -- 供 skus / cart_items / 向量表 / 理解结果表做复合外键
    UNIQUE (id, merchant_id),
    FOREIGN KEY (category_id, merchant_id) REFERENCES categories(id, merchant_id)
);
CREATE INDEX idx_products_listing
    ON products(merchant_id, category_id, status, published_at DESC)
    WHERE deleted_at IS NULL;
```

> **`category_id` 改成复合外键**(规矩二)。这一条有实测:以租户 1 的身份
> 把一个 product 挂到租户 2 的 category 上,数据库直接拒绝——
> `violates foreign key constraint "products_category_id_merchant_id_fkey"`。
> 在只有单列外键的版本里,同一条写入是成功的。
>
> **列表页索引补 `merchant_id` 前缀**。这是全站最高频的查询,
> RLS 会给它注入 `merchant_id = current_merchant()`;
> 原先以 `category_id` 打头的索引在多租户下要扫过所有商家的同类目商品再逐行过滤。
> 代价是索引宽了 8 字节,以及单租户部署(租户数为 1)下这一列是纯冗余——
> 那正是「多租户是能力不是要求」要付的最小代价。

> **设计说明（M4 改写）**：原文是「`min_price_cents` / `total_stock` 是冗余字段，
> 由 SKU 变更时同步更新。电商列表页是最高频查询，join SKU 聚合会成为瓶颈。
> 一致性由应用层保证，并提供后台对账任务定期校正。」
>
> **`min_price_cents` / `max_price_cents` 两列已由迁移 00019 删除，改成按需现算**
> （读商品时 `LEFT JOIN LATERAL` 取未软删 SKU 的 `min/max(price_cents)`，
> 一个 SKU 都没有时 `COALESCE` 到 0）。三条理由：
>
> 1. **多门店 + 大区定稿之后它们不再是商品的属性。** 价格将有三层
>    （SKU 基准价 → 大区价 → 门店价），「这件商品多少钱」取决于本次请求
>    解析到哪一家门店 —— 一个挂在 `products` 行上的标量答不出这个问题。
> 2. **一个没人维护得住的冗余列会撒谎。** 同一张表上的 `total_stock` 已经是
>    这样：`db/queries/search.sql` 的文件头点名它是「一句永远不会被纠正的谎」，
>    而撒谎不报错、不变慢、不留痕迹。
> 3. **原文那句「join SKU 聚合会成为瓶颈」在这个 schema 下不成立。**
>    唯一覆盖 `products` 的列表索引是
>    `idx_products_listing(merchant_id, category_id, status, published_at DESC)`，
>    这两列不在其中，也不在任何别的索引里 —— 它们从来只省「取到行之后的一次
>    join」，不省「规划器要扫多少行」。列表页的 `ORDER BY` 只引用 `products`
>    的列，所以 `LIMIT` 仍然先生效，每页只多做 page_size 次 SKU 聚合。
>
> `total_stock` 那一列**仍然在表上**，但自 00019 起没有任何一处写它
> （维护它的 `RecalcProductAggregates` 与那两列一起删了）。后台读到的
> `AdminProduct.total_stock` 同样现算（`sum(inventories.available_qty)`）。
> 把这一列也删掉是下一轮的事 —— 它牵动 §8 那个「对账任务」的去留，
> 那是一次独立的决定，不该夹在价格这条里默默做掉。
>
> 契约里 `ProductSummary.min_price_cents` / `max_price_cents` 与
> `AdminProduct` 上那两个响应字段**都保留**：值的来源变了，客户端的类型不用改。
> 买家侧 `ProductSummary` 上它们的含义从此是**「按本次请求解析到的那家门店
> 算出来的区间」**（走 `sku_prices_by_store` 视图，三层定价见 §4）；
> `AdminProduct` 上是「SKU 基准价的区间」—— 后台不隶属于任何一家店。
>
> `sales_count` 留着，它是租户级的累计销量，不随门店变化。

`products` 还有 `search_text` / `search_vector` 两列用于关键词召回，与检索链路强相关，
定义放在 §8 一并说明。

### skus

```sql
CREATE TABLE skus (
    id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id   BIGINT      NOT NULL DEFAULT current_merchant() REFERENCES merchants(id),
    product_id   BIGINT      NOT NULL,
    sku_code     TEXT        NOT NULL,   -- 租户内唯一，见下方索引
    spec_values  JSONB       NOT NULL DEFAULT '{}', -- {"颜色":"黑","尺码":"XL"}
    price_cents  BIGINT      NOT NULL,
    cost_cents   BIGINT      NOT NULL DEFAULT 0,    -- 成本，用于业务重排
    weight_gram  INT         NOT NULL DEFAULT 0,
    image_url    TEXT,
    status       SMALLINT    NOT NULL DEFAULT 1,  -- 0停售 1在售
    deleted_at   TIMESTAMPTZ,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT chk_price_nonneg CHECK (price_cents >= 0),
    FOREIGN KEY (product_id, merchant_id) REFERENCES products(id, merchant_id)
);
CREATE INDEX idx_skus_product ON skus(merchant_id, product_id);
CREATE UNIQUE INDEX uk_skus_code
    ON skus(merchant_id, sku_code) WHERE deleted_at IS NULL;
-- 供子表做复合外键：让「挂到别家租户的商品上」在物理上不可能
CREATE UNIQUE INDEX uk_skus_id_merchant ON skus(id, merchant_id);
CREATE INDEX idx_skus_spec ON skus USING gin (spec_values);
```

> **`uk_skus_id_merchant` 原先就在,但一直没有子表用它**——本轮补上了
> `skus.product_id` 这一侧的复合外键,它才真正开始承重。
> 一个只建给别人用、却没人用的唯一索引,是「规矩写了没照做」最典型的痕迹。
>
> **`idx_skus_spec` 是本文件第一处「前缀加不上」的索引。** GIN 索引的每一列都要有
> GIN 操作符类,而 `merchant_id` 是 `BIGINT`,没有——想把它放进同一个 GIN 索引,
> 得先装 `btree_gin` 扩展。为一个规格筛选索引引入一个扩展不划算,
> 所以这里保持原样:GIN 先给出候选集,再由 RLS 的 `merchant_id = ...` 过滤。
> 代价是租户多了之后这个候选集会偏大,而**隔离性一点没少**——
> 被过滤掉是 RLS 在干活,漏出去才是问题。
> 同样情况的还有 §8 的 `idx_products_fts`(GIN)与两个 HNSW 向量索引。

> **`deleted_at` 与 `status` 是本轮（M4 任务 1）补的,两者不是一回事**
>
> 补它们的触发点是商家侧的写接口:`DELETE /admin/skus/{sku_id}` 要有语义。
> 而原先这张表**只有 `status`,还没写它是什么意思**——一个没有定义的
> `SMALLINT NOT NULL DEFAULT 1`,下一个人会按自己的理解用,那就是两套语义。
>
> · `status`:**0 停售 / 1 在售**。停售的规格仍出现在商品详情的规格矩阵里
>   (否则买家会以为规格表变了),但不可加购、不可下单。
> · `deleted_at`:软删。删掉的规格从所有视图里消失。
>
> **为什么必须是软删,而不是真的 DELETE 一行**:`order_items`、`cart_items`、
> `inventories`、`inventory_logs` 四张表都对 `skus` 有外键,一个卖过一次的 SKU
> 在数据库层面就删不掉。契约里若把 `DELETE` 写成硬删,那条接口对任何有过成交的
> SKU 都会以一个外键错误收场——而那是**设计阶段就能知道**的形状错误,
> 不该留到实现时才撞上。
>
> 连带的代价必须一起付:`uk_skus_code` 改成了 `WHERE deleted_at IS NULL` 的
> **部分唯一索引**。不改的话,一个被删掉的规格会永久占住一个货号,
> 而货号(`sku_code`)是商家自己的编码体系,不是我们发的 id——
> 「这个货号我不能再用了,因为三个月前我删过一个同名的」是说不通的。

### product_images（商品图与商品的关联）

```sql
CREATE TABLE product_images (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id BIGINT      NOT NULL DEFAULT current_merchant() REFERENCES merchants(id),
    product_id  BIGINT      NOT NULL,
    upload_id   BIGINT      NOT NULL,
    sort_order  INT         NOT NULL DEFAULT 0,   -- 0 即主图
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (merchant_id, product_id, upload_id),
    FOREIGN KEY (product_id, merchant_id) REFERENCES products(id, merchant_id),
    FOREIGN KEY (upload_id, merchant_id)  REFERENCES uploads(id, merchant_id)
);
CREATE INDEX idx_product_images_product
    ON product_images(merchant_id, product_id, sort_order);
```

> **这张表补的是 M2 验收记下的一笔账。**
>
> 契约里 `ProductSummary.image_url` 与 `ProductDetail.images` 从 M1 起就声明着,
> 而服务端从不填——因为 `products` 上根本没有图片列,§13 的 `uploads` 与商品
> 之间也没有任何关联。`internal/handler/contract_test.go` 里那两笔
> `NotYetImplementedResponse` 挂账写的就是这件事。缺口不在实现,在表结构。
>
> **为什么是一张关联表,而不是 `products` 上加一列**
>
> 加一列 `image_url TEXT` 解决不了多图与顺序;加一列 `images JSONB` 能存下顺序,
> 但会丢掉三样东西,而这三样恰恰是 §13 建 `uploads` 表的全部理由:
> 外键完整性(JSONB 里的 id 指向一个不存在的文件,数据库不会拒绝)、
> 归属校验(挂上别家租户的文件,没有任何约束拦得住)、
> 以及 `referenced` 能不能在**同一个事务里**置位。
> 有了复合外键 `(upload_id, merchant_id)`,「把别家的图挂到自己商品上」
> 在物理上不可能——这是规矩二在图片这一路的落地。
>
> 为此 §13 的 `uploads` 补了一条 `UNIQUE (id, merchant_id)`,
> 给这条复合外键当落点。那条索引按构造比主键更弱,是规矩三自动放行的那一类。
>
> **主图是 `sort_order` 最小的那一张,没有 `is_primary` 布尔。**
> 布尔允许「零张主图」和「两张主图」这两种业务上不存在的状态被表达出来
> (部分唯一索引只能挡住后者,挡不住前者);而顺序本来就要维护。
> 「设为主图」在客户端就是把那一项挪到第一位,与「调整顺序」是同一个动作——
> 多一个概念就要多一处保持一致。
>
> 写入面是整组替换(`PUT /admin/products/{product_id}/images`),不是增量。
> 顺序是一个整体:增量接口下,「把第 3 张挪到第 1 位」与「删掉第 2 张」
> 两个并发请求会互相踩出一个有空洞的顺序,而整组替换让顺序只有一个写入点。
>
> **不带 `deleted_at`**:这张表是纯关联,解除关联就是删行。
> 文件本身留在 `uploads` 里,由 §13 的孤儿回收负责——
> 只是那条回收一期只回收「传了没提交」的,不回收「引用后又解引用」的,
> 所以被换下来的旧图会永远停在 `referenced = TRUE`。这个已知缺口在 §15 记过。

> **本节四张表（`categories` / `products` / `skus` / `product_images`）的
> `merchant_id` 都带 `DEFAULT current_merchant()`。**
> 这是 M4 任务 2 落地商家写路径时补上的（迁移 `00018_catalog_write_path.sql`），
> 与 §5 那三张、§8 那四张、§12 的 `idempotency_keys` 是同一条理由：
> `scripts/check_query_tenancy.py` 不许 `db/queries/*.sql` 里出现 `merchant_id`
> 这个词——应用层再过滤一遍租户，「RLS 到底有没有生效」就变得测不出来了。
> 于是每条 INSERT 面临的选择是「把整条商品写路径塞进那个脚本的豁免清单」
> 还是「让数据库自己填」，选了后者。
>
> `DEFAULT` 只在**列被省略时**生效，所以迁移、种子、测试夹具里那些以管理员
> 身份显式带 `merchant_id` 的 INSERT 一条都不受影响；它们本来也不在租户
> 上下文里，`current_merchant()` 在那里会直接 RAISE。

## 四、门店、大区与库存域（下单 SAGA 的关键分支）

> **本节本轮改名了，从「库存域」变成「门店、大区与库存域」。**
>
> 原因是 §15 第 3 条被结清：库存从「一个商家一份」变成「一个商家的每家门店
> 各一份」，主键从 `sku_id` 变成 `(sku_id, store_id)`。门店一旦成为库存的
> 一个主键列，「门店是什么」就没法留在别的章节里说——读这一节的人要判断
> 一行库存归谁，必须在同一屏里看到 `stores`。大区跟着进来是因为它是门店的分组，
> 且它与门店合起来构成**两层覆盖**（见下）。
>
> 这一节现在回答同一个问题的四半：**这件商品在哪儿卖（`regions` / `stores`）、
> 这家店卖不卖它（两张 `*_product_overrides`）、卖多少钱（两张 `*_sku_prices`
> 与 `sku_prices_by_store` 视图）、还剩几件（`inventories`）**。
> 它们被同一条下单语句一起读，分开写会让语义各自漂。
>

### 三层模型，一句话

```
可见性：租户目录  −  大区排除  −  门店排除
价格：  SKU 基准价 →  大区价   →  门店价      （逐层覆盖，就近生效）
库存：                            门店
```

三行各自的粒度**不一样**，这一点决定了表的张数，值得先说清楚：

| 维度 | 粒度 | 为什么是这个粒度 |
|---|---|---|
| 可见性 | **商品（SPU）** | 运营说的是「这家店不卖这款」，不是「这家店不卖黑色 XL」 |
| 价格 | **SKU** | 同一款下不同规格的基准价本来就不同，大区价要能分别覆盖 |
| 库存 | **SKU** | 库存一直就是 SKU 粒度 |

所以可见性与价格**不能合并成一张表**——它们的主键列不一样。
这条在下面 `store_product_overrides` 那一段还会再用到一次。

### regions（大区）

```sql
CREATE TABLE regions (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id BIGINT      NOT NULL DEFAULT current_merchant() REFERENCES merchants(id),
    code        TEXT        NOT NULL,   -- 租户内的大区编号
    name        TEXT        NOT NULL,   -- 华北 / 华南 …
    status      SMALLINT    NOT NULL DEFAULT 1,   -- 0 停用 1 启用
    deleted_at  TIMESTAMPTZ,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX uk_regions_code ON regions(merchant_id, code)
    WHERE deleted_at IS NULL;
-- 供 stores / region_product_overrides / region_sku_prices / orders 做复合外键
CREATE UNIQUE INDEX uk_regions_id_merchant ON regions(id, merchant_id);
```

> **大区没有自己的几何，这是本轮最省事的一条决定，理由要写下来。**
>
> 一次地理解析已经存在：坐标 → 命中哪些门店围栏 → 门店。而门店属于某个大区，
> 于是**同一次解析同时给出两件事**：哪家店（库存、门店价）、哪个大区（大区价、
> 大区可见性）。
>
> 给大区再画一套边界，就要回答「门店围栏与大区边界不一致时听谁的」——
> 而那个问题**没有好答案**：按大区算价、按门店发货，会出现「A 大区的价格、
> B 大区的货」；按门店倒推大区，那大区的几何就是多余的。
> 两套几何还意味着两套 GIST 索引、两套 `ST_IsValid` 校验、两倍的运营画图工作量，
> 换来的是一个必须靠约定维持的一致性——而这个仓库的判据是「能让数据库拒绝的，
> 就别指望人记得」，这里恰恰让数据库拒绝不了。
>
> **所以大区是门店的分组，不是一块地。** `stores.region_id` 是它唯一的入口。

> **大区没有 `is_default`，默认大区就是默认门店所在的那个大区。**
>
> 「至多一个默认」这条规则在这份文档里已经有两处（§9 的默认地址、
> 下面的默认门店），每一处都要一条部分唯一索引、一条「先清旧再置新」的事务纪律、
> 和一段「为什么是至多一个不是恰好一个」的论证。**第三处能省则省。**
>
> 省得掉的判据是：回落链路的终点是**门店**（「回落到全国配送的默认门店」），
> 而门店必有大区（下面 `region_id` 是 `NOT NULL`），
> 所以「默认大区」是一个可以被推导出来的量，不是一个要存的量。
> 存一份推导得出的值，就是给它一次和事实不一致的机会。

### stores（门店与电子围栏）

```sql
CREATE TABLE stores (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id   BIGINT      NOT NULL DEFAULT current_merchant() REFERENCES merchants(id),
    region_id     BIGINT      NOT NULL,            -- 所属大区，决定大区价与大区可见性
    code          TEXT        NOT NULL,            -- 租户内的门店编号，后台与对账用
    name          TEXT        NOT NULL,
    phone         TEXT        NOT NULL DEFAULT '',
    province      TEXT        NOT NULL DEFAULT '',
    city          TEXT        NOT NULL DEFAULT '',
    district      TEXT        NOT NULL DEFAULT '',
    address       TEXT        NOT NULL DEFAULT '', -- 门牌号等
    location      GEOGRAPHY(POINT, 4326),          -- 门店自身坐标，「按距离排」按它算
    fence         GEOGRAPHY(POLYGON, 4326),        -- 电子围栏，多边形
    is_default    BOOLEAN     NOT NULL DEFAULT FALSE,  -- 全国配送的回落门店
    status        SMALLINT    NOT NULL DEFAULT 1,  -- 0 停业 1 营业
    deleted_at    TIMESTAMPTZ,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    -- 这里没有 CHECK (is_default OR fence IS NOT NULL)，理由见下面那段引言
    FOREIGN KEY (region_id, merchant_id) REFERENCES regions(id, merchant_id)
);
CREATE UNIQUE INDEX uk_stores_default ON stores(merchant_id)
    WHERE is_default AND deleted_at IS NULL;
CREATE UNIQUE INDEX uk_stores_code ON stores(merchant_id, code)
    WHERE deleted_at IS NULL;
-- 供 inventories / store_product_overrides / store_sku_prices / orders / inventory_logs
CREATE UNIQUE INDEX uk_stores_id_merchant ON stores(id, merchant_id);
CREATE INDEX idx_stores_listing ON stores(merchant_id, status)
    WHERE deleted_at IS NULL;
CREATE INDEX idx_stores_fence ON stores USING GIST (fence);
```

> **`region_id` 是 `NOT NULL`，不可空。**
>
> 可空意味着「这家店属于哪个大区」多出第三个答案（NULL），
> 而三层定价的 `COALESCE` 要为它写一条特判。那条特判只在「忘了配大区」时走到，
> 也就是**最不会被测到的那条分支**，而它算出来的是钱。
>
> 代价是建店前必须先有大区，于是建商家（`POST /admin/merchants`）
> 要在同一个事务里建出一个默认大区。这条代价是显式的、一次性的，
> 换掉的是一条永远在那儿的可空分支。

> **「至多一个默认店」照 §9 `user_addresses.is_default` 的形状做，不自己发明。**
>
> `uk_stores_default` 是一条部分唯一索引，它**就是那条规则本身**：不必在代码里写
> 「设置默认店前先把其他的置 false」再祈祷没人并发点两下——真并发了，第二个事务
> 会撞唯一冲突然后回滚，那正是想要的结果。切换默认店必须在同一个事务里
> 「先清旧、再置新」，顺序反了会自己撞自己。
>
> 差别只有一处：§9 的作用域是 `user_id`（每个用户至多一个默认地址），
> 这里是 `merchant_id`（每个商家至多一个默认门店）。于是这条索引的首列就是
> `merchant_id`，规矩三自动满足，不需要往 `unique_global_ok` 里加任何东西——
> 而 §9 那条因为首列是 `user_id`，是要写豁免理由的。
>
> **同样是「至多一个」而不是「恰好一个」，理由也和 §9 一样**：一个刚建出来、
> 还没配默认店的商家是合法状态，数据库不该逼着建店流程凭空造一条。
>
> 但这里的代价比地址簿那边**大得多，而且要写明**：没有默认店时，
> 「不在任何围栏内」与「没有位置」两条路径都无处可落，买家看到的是
> 「不在服务范围」。也就是说 **一个没配默认店的商家，它的店面对所有
> 未授权定位的访客都是空的**。这是规则的必然结果，不是 bug——
> 但它意味着「配一家默认店」几乎是开店的必做项。
> 契约在两处把这件事说出声（见 OpenAPI 的 `/admin/stores` 段头）：
> `GET /admin/stores` 的响应带一个必返的 `has_default` 布尔，
> 后台首页据此挂提示；`GET /stores/resolve` 的 `match_type = none`
> 把「这家店还没配默认店」和「你确实在服务范围外」收到同一个出口。
> **不把它做成建店时的强制项**，理由是建店与画围栏是两个人在两个时刻做的事，
> 强制会把第一步卡死在第二步上。

> **围栏是多边形，不是圆心加半径。这一条决定了要上 PostGIS。**
>
> 「圆」可以不用 PostGIS：存 `center_lat` / `center_lng` / `radius_m` 三列，
> 判定是一次 haversine，纯 SQL 写得出来。**多边形不行**——运营在地图上画出来的
> 范围是一串顶点，判定是「点在多边形内」，自己实现一个射线法 UDF 是在重写
> PostGIS 里被验证了二十年的那部分，而且没有空间索引，每次判定要全表扫门店。
>
> 所以这是一条**真依赖**，不是偏好。落地要求写在下面「数据库镜像」那一段。
>
> **为什么是 `GEOGRAPHY` 而不是 `GEOMETRY`。** `GEOMETRY(POLYGON, 4326)` 把经纬度
> 当平面直角坐标算，`ST_Distance` 返回的是「度」——在北京那个纬度上，
> 一度经度约 85 km、一度纬度约 111 km，**两个方向的尺子不一样长**。
> 于是「按距离排」会在东西向与南北向上给出系统性偏斜的名次，
> 而它看起来完全正常（数字是有的，顺序是稳定的，只是错的）。
> `GEOGRAPHY` 走球面计算，`ST_Distance` 直接返回米，`<->` 同样返回米。
> 代价是球面运算比平面慢，以及少数几个函数不支持 `GEOGRAPHY`——
> 本设计只用到 `ST_Intersects` / `ST_Distance` / `<->` / `ST_IsValid`，
> 前三个都支持，`ST_IsValid` 在写入校验时对 `GEOMETRY` 调用（见下）。
>
> 实测（本机，`postgis/postgis:16-3.4` 加装 pgvector 后的镜像，PostGIS 3.4.3）：
> 三个互相重叠的围栏 + 一家无围栏的默认店，点落在其中两个围栏内时
> `ST_Intersects` 返回那两家，`ORDER BY location <-> $point` 给出以米为单位的名次；
> 点落在全部围栏外时返回 0 行。`SRID 4326` 两处都要写死——
> 混进一个别的 SRID，`ST_Intersects` 会直接报错而不是静默算错，这是好事。

> **「一家非默认店没有围栏就是一家永远接不到单的店」——这条判断对，
> 而把它做成写入约束错了。**
>
> 判定链路是「点在哪个围栏内 → 都不在则回落默认店」。一家 `fence IS NULL`
> 的非默认门店在这条链路上**不可达**：它不会被任何坐标命中，也不是回落目标。
> 后台会把它列出来、能给它配库存、能给它上下架商品、能给它定价，而它一单也接不到——
> 这是那种「配置完成了，但什么都没发生」的故障，症状与真因之间没有任何线索。
>
> 本轮契约先行的那一版据此写了
> `CONSTRAINT chk_store_fence_or_default CHECK (is_default OR fence IS NOT NULL)`。
> 落地时对着真库跑了一遍，**它让两条契约明写的主路径直接不可能**：
>
> - `POST /admin/stores` 按契约**不收围栏**（建店是表单、画围栏是地图，
>   后台的两个界面）。于是它建不出任何一家非默认门店。
>   实测：`INSERT ... (is_default = false, fence = NULL)` → 23514。
> - `PUT /admin/stores/{id}/default` 的第一步是清掉旧的那家默认店。而上面那段
>   回填给**每一个**已有商家造出的正是「默认店 + 无围栏」。
>   实测：`UPDATE stores SET is_default = FALSE WHERE is_default` → 23514，
>   报错指着被清掉标记的那一行。也就是说这条 CHECK 在每一个迁移过的库上
>   都让「换一家默认店」这个动作失败。
>
> 所以 `CHECK` 删掉，规则退成**一条路径上的服务端判定**：
> `PUT .../fence` 传 `null` 时，如果这家店不是默认店，返回 409
> `store-fence-required`（`repository.SetStoreFence`）。
>
> 退让了什么，说清楚：这个状态**现在是可达的**，数据库不再挡它。
> 而契约本来就把它定义成一个正常的中间态——`AdminStore.fence` 为 `null`
> 且 `is_default = false` ⇒ 后台列表挂「未完成」提示。可达不是本轮新出现的
> 问题；从前那条 `CHECK` 只是在同时宣称「它不可达」与「它是一个要显示的状态」，
> 而两句话不能都对。

> **`idx_stores_fence` 是本文件第四类「加不上 `merchant_id` 前缀」的索引。**
>
> §2 列了三类物理原因（GIN / HNSW、`jobs` 的出队索引、首列已是租户内标识的唯一索引），
> GIST 是第四类，原因与 GIN 同源：`merchant_id` 是 `BIGINT`，没有 GIST 操作符类，
> 要把它放进同一个索引得先装 `btree_gist`。为一个门店表的空间索引引入一个扩展不划算——
> **门店的行数以「几十」计，不是以「十万」计**，候选集偏大这件事在这张表上没有量级。
> 所以保持原样：GIST 先给出候选，再由 RLS 的 `merchant_id = current_merchant()` 过滤。
> §2 的例外清单本轮已随这一条一起补上 GIST。
>
> 实测规划器确实走得到它：`SET enable_seqscan = off` 下
> `WHERE ST_Intersects(fence, $point)` 的计划是
> `Index Scan using idx_stores_fence`，`Index Cond: (fence && $point)`。

> **围栏的写入校验：`ST_IsValid`，在服务端，不在客户端。**
>
> 运营在地图上画出来的环可以自交（「8 字形」）、可以不闭合。自交的多边形在
> `ST_Intersects` 下的行为是**未定义**的——不是报错，是给一个谁也说不清的答案。
> 所以 `PUT /admin/stores/{store_id}/fence` 落库前必须过一次
> `ST_IsValid(ST_GeomFromGeoJSON($1))`，假则 422。
> 实测：`[[0,0],[1,1],[1,0],[0,1],[0,0]]`（领结形）→ `ST_IsValid` 为 `f`，
> 并附 `NOTICE: Self-intersection at or near point 0.5 0.5`，那句话可以直接进
> Problem 的 `detail`。
>
> 契约里围栏的表示是 **GeoJSON Polygon**，实测 `ST_GeomFromGeoJSON` 能直接吃下去。
> 有一条要在契约和实现里都写死：**GeoJSON 的坐标序是 `[经度, 纬度]`**，
> 和中文口语里的「纬度、经度」相反。写反了不会报错——它会得到一个在地球另一侧的
> 合法多边形，而所有判定都「正常工作」。这是这一整块里最便宜也最常见的一个错。

### 数据库镜像：PostGIS 与 pgvector 要在同一个镜像里

`CREATE EXTENSION postgis` 要求镜像里真有它，这与 `00016` 文件头记的 pgvector
是同一件事的第二次。现在的镜像 `pgvector/pgvector:pg16` **没有 PostGIS**，
而 PostGIS 的官方镜像 `postgis/postgis:16-3.4` **没有 pgvector**。

**方案：自建一个两行的 Dockerfile，`FROM postgis/postgis:16-3.4` 再从 PGDG 源
装 `postgresql-16-pgvector`。** 这与 `compose.yaml` 顶部「为什么用官方 pgvector
镜像而不是自己 build」那段论证**方向相反**，所以要把账重算一遍：

| 判据 | 当时（只要 pgvector） | 现在（要 PostGIS + pgvector） |
|---|---|---|
| 有没有现成的官方镜像 | 有，`pgvector/pgvector:pg16` | **没有**。两个上游各发各的，没有一个官方镜像同时带两者 |
| 体积 | 438 MB，比官方 `postgres:16`（451 MB）还小 | 794 MB（实测 `docker images`）。多出来的约 350 MB 是 GEOS / PROJ / GDAL |
| 可信度 | 上游自己发的，与扩展同一个发布流程 | 底座仍是 PostGIS 上游自己发的；pgvector 来自 **PGDG 官方 apt 源**（`apt.postgresql.org`），同样是 pgvector 的官方分发渠道之一 |
| 构建代价 | 不需要 build | 一次 `docker build`，实测 **90 秒**（拉基础镜像 19 s + apt 68 s），之后是层缓存 |

实测证据（本机，`docker build` 后起容器再建扩展）：

```
 extname          | extversion
------------------+------------
 postgis          | 3.4.3
 postgis_topology | 3.4.3
 fuzzystrmatch    | 1.2
 vector           | 0.8.6

 PostgreSQL 16.15 (Debian 16.15-1.pgdg11+2)
```

**最要紧的一行是 `16.15` 与 `0.8.6`：和现在 `pgvector/pgvector:pg16` 上实测到的
PostgreSQL 与 vector 版本一模一样。** 换镜像不改变 M3 依赖的任何东西——
`hnsw.iterative_scan` 要求的 vector ≥ 0.8 仍然满足（`00016` 文件头把它列为
多租户下向量召回可用的前提）。

三条落地时必须一起做的事，**本轮只写方案，不改文件**（`compose*.yaml`、
`.github/workflows/ci.yml`、`docker/` 归实现任务，且主线上正有任务在动它们）：

1. `docker/postgres/Dockerfile` 新建，两行；`compose.yaml` 的两处 `image:` 与
   `compose.multi.yaml` 改成 `build:` 或指向一个预先 push 的标签。
   **倾向后者**：`compose.yaml` 顶部那段论证里「CI 与开发机都得先 build 一次才能起库」
   这条代价是真的，把镜像 push 到仓库的 GHCR 之后它就消失了，而可信度不变
   （构建脚本在仓库里，可复现）。
2. `.github/workflows/ci.yml` 的 `services.postgres.image` 同步。
   CI 上若走 build，`docker build` 那 90 秒每个 job 都要付一次；走 GHCR 是一次 pull。
3. `CONTRIBUTING.md` 里两条冷库 `docker run` 命令、以及依赖表里 PostgreSQL 那一行，
   都写着 `pgvector/pgvector:pg16`。**这三处在 PostGIS 迁移落地之前是正确的**，
   所以本轮不动——提前改会让文档描述一个还不存在的状态，那正是
   `scripts/check_promises.py` 存在的理由要防的东西。

> **考虑过而否掉的两条**
>
> · `supabase/postgres` / `timescale/timescaledb-ha`：都同时带 PostGIS 与 pgvector，
>   但它们各自还带一大堆本项目不用的扩展与角色约定，体积 1 GB 起。
>   用一个「顺便带了我要的两样」的发行版当基线，等于把别人的产品决策接进来。
> · 反过来做，`FROM pgvector/pgvector:pg16` 再 `apt install postgresql-16-postgis-3`：
>   也走得通，但 PostGIS 那侧的 apt 包要拉 GEOS / PROJ / GDAL 一整套，
>   而 `postgis/postgis` 镜像的上游把这套的版本搭配、以及初始化脚本
>   （它在 initdb 阶段就把 `postgis` / `postgis_topology` 建好）都调好了。
>   把复杂的那一半交给上游、自己只补简单的那一半，是更稳的分工。
>
> 注意 `postgis/postgis:16-3.4` 的底座是 Debian **bullseye**（实测
> `16.15-1.pgdg11+2`），而 `pgvector/pgvector:pg16` 是 bookworm。这不影响
> 本项目（应用不在这个镜像里跑），但它是换镜像时唯一一处基座差异，记在这里。
>
> **更正（M4 合并后重建演示栈时撞上的）：上面那句「这不影响本项目」推错了，
> 底座随后换成了官方 `postgres:16-bookworm`。** 原话保留在上面，因为错在哪里

>

> 上面「考虑过而否掉」的第二条（反过来装 postgis）随之被**重新采纳**，但它

> （实测 `16-3.4` 与 `16-3.5` 都是 bullseye），所以不是换个 tag 能解决的。
>
> 现在的实测：PostgreSQL 16.15 / vector 0.8.6 / postgis **3.6.4** / glibc

### 产品规则与它们各自的执行者

「按距离排」「不在围栏内回落默认店」「没有默认店就报不在服务范围」
「开店即营业」「大区价格统一、门店可覆盖」——这些都是产品规则。
这个仓库的经验是：**写在文档里而没有执行者的规则会漂**
（`scripts/check_tenancy.py`、`internal/handler/contract_test.go` 都是为这件事建的）。
所以每一条都要配一个机械检查，实现任务照着做：

| 规则 | 执行者 | 它在什么时候红 |
|---|---|---|
| 至多一个默认店 | `uk_stores_default` 部分唯一索引 | 插入第二个默认店时，数据库拒绝（已实测） |
| 非默认店不许**清空**围栏 | `repository.SetStoreFence` 里的显式判定（409 `store-fence-required`） | handler 测试给一家非默认店 `PUT .../fence {"fence":null}`，断言 409。**不是数据库约束**——那一版实测挡死了建普通店与切换默认店两条主路径，论证见上面那段引言 |
| 围栏必须是合法多边形 | 写入前 `ST_IsValid`，假则 422 | handler 测试喂一个领结形多边形，断言 422 |
| 每家门店必属于一个大区 | `stores.region_id NOT NULL` + 复合外键 | 建店不给大区、或给了别家的大区，数据库拒绝 |
| 按距离排 | 契约里 `StoreMatch.distance_m` 必返（进 `check_openapi.py` 的 `REQUIRED_FIELDS`）+ handler 测试：三个重叠围栏，断言返回序列按 `distance_m` 非降序 | 有人把排序去掉、或把字段删了 |
| 回落默认店 | 契约里 `StoreResolveResult.match_type` 必返且枚举为 `[fence, fallback_default, none]`（同样进 `REQUIRED_FIELDS`）+ handler 测试：坐标落在全部围栏外 → `match_type = fallback_default` 且返回的正是 `is_default` 那家 | 有人把回落改成「返回最近的店」 |
| 没有默认店 → 不在服务范围 | handler 测试：租户下没有默认店、坐标在围栏外 → `200` + `match_type = none` + `stores` 为空数组 | 有人把它改成 404，或改成「随便给一家」 |
| 无位置 ≡ 不在围栏内（同一条路径） | handler 测试：不带 `lat`/`lng` 的 `/stores/resolve` 与一个落在围栏外的坐标，**两次响应的 `match_type` 与 `stores` 必须逐字段相等** | 有人给「没有位置」单开一条分支 |
| 开店即营业，卖全部商品 | 两张排除表的 `CHECK (status = 0)`——它们**在结构上表达不了**「只卖这几件」+ handler 测试：建店后不写任何一行，`GET /products?store_id=新店` 的条数等于租户级在售商品数 | 有人把默认值改成「默认不卖」——那要先改 DDL，是一次迁移，不是改一行注释 |
| 就近生效只有一份实现 | `sku_prices_by_store` 视图是唯一一处 `COALESCE(门店价, 大区价, 基准价)`；新增一条检查：**`store_sku_prices` / `region_sku_prices` 这两个表名在 `db/queries/*.sql` 里一次都不许出现**（与 `check_query_tenancy.py` 同一路子） | 有人在列表那边另写一套聚合——那正是「列表价与下单价分叉」的来源 |
| 试算与下单共用同一份定价 | M2 已有的纪律：`internal/service/pricing.go` 的 `priceOrder`。本轮把它的取价口改成走上面那个视图 | 有人绕过 `priceOrder` 自己算钱 |
| 视图不许泄露跨租户行 | `internal/db/migrate_test.go` 新增一条：`pg_class` 里 `relkind = 'v'` 的每张视图，`reloptions` 必须含 `security_invoker=true` | 有人建了一张忘了加那个选项的视图（实测这就是一个真洞，见下） |

> **夹具里必须有反例，否则这些断言恒真。** M3 验收刚记过同一件事
> （检索的 `status` / `deleted_at` 过滤此前没有执行者，夹具里一件反例都没有）。
> 具体到这里，门店夹具至少要有：一家无围栏的默认店、两家围栏互相重叠的普通店、
> 一个落在全部围栏外的坐标、一件「在 A 店下架、在 B 店在售」的商品、
> 一件「大区排除了、门店没排除」的商品（证明两层是**与**不是**或**）、
> 一个 SKU 的三层价各一份（基准 / 大区 / 门店），
> 以及一家**没有**默认店的商家。少任何一样，对应那行断言都是在检查空集。

### store_product_overrides / region_product_overrides（可见性的两层排除）

商品目录是**租户级**的（`products` 不动）。大区与门店各自只决定「我不卖哪些」。

```sql
CREATE TABLE region_product_overrides (
    region_id   BIGINT      NOT NULL,
    product_id  BIGINT      NOT NULL,
    merchant_id BIGINT      NOT NULL DEFAULT current_merchant() REFERENCES merchants(id),
    status      SMALLINT    NOT NULL,   -- 只有 0 下架；见下方 CHECK
    updated_by  BIGINT      REFERENCES staff(id),   -- 谁下的架
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (region_id, product_id),
    CONSTRAINT chk_region_override_status CHECK (status = 0),
    FOREIGN KEY (region_id, merchant_id)  REFERENCES regions(id, merchant_id),
    FOREIGN KEY (product_id, merchant_id) REFERENCES products(id, merchant_id)
);
CREATE INDEX idx_region_overrides_product ON region_product_overrides(merchant_id, product_id);

CREATE TABLE store_product_overrides (
    store_id    BIGINT      NOT NULL,
    product_id  BIGINT      NOT NULL,
    merchant_id BIGINT      NOT NULL DEFAULT current_merchant() REFERENCES merchants(id),
    status      SMALLINT    NOT NULL,
    updated_by  BIGINT      REFERENCES staff(id),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (store_id, product_id),
    CONSTRAINT chk_store_override_status CHECK (status = 0),
    FOREIGN KEY (store_id, merchant_id)   REFERENCES stores(id, merchant_id),
    FOREIGN KEY (product_id, merchant_id) REFERENCES products(id, merchant_id)
);
CREATE INDEX idx_store_overrides_product ON store_product_overrides(merchant_id, product_id);
```

> **这是两张排除表，不是清单表。缺一行的意思是「在售」，不是「不卖」。**
>
> 产品定下的默认语义是「**门店开店即营业，卖全部商品，手动下架不卖的**」。
> 这个默认值直接决定表的形状，两种做法在运营上是**完全不同的产品**：
>
> · **包含表**（记「这家店卖哪些」）：10 家店 × 10,000 件商品 = 十万行，
>   每一行都在说「是」。更要命的是**新品**：上架一件新商品之后，
>   它在所有门店默认**不卖**，直到有人往每家店插一行。
>   那与「开店即营业」正面冲突——建店流程要在事务里插一万行，
>   而上新流程要在事务里插十行，两处都在维护同一个「默认是卖的」的假象。
> · **排除表**（记「这家店不卖哪些」）：只记真正下架的那几件，通常是个位数到几十行。
>   新品自动在所有门店在售，不需要任何写入。建店是插一行 `stores`，没有第二步。
>
> 选排除表。**没选的那个的代价上面写了，选中的这个的代价在这里，一并写明：**
>
> 一、**「这家店卖哪些」变成两次 `NOT EXISTS`**，要拼进 `/products` 与 `/search`
>    的现有查询：
>
>    ```sql
>    AND NOT EXISTS (SELECT 1 FROM region_product_overrides o
>                     WHERE o.region_id = @region_id AND o.product_id = p.id
>                       AND o.status = 0)
>    AND NOT EXISTS (SELECT 1 FROM store_product_overrides o
>                     WHERE o.store_id = @store_id AND o.product_id = p.id
>                       AND o.status = 0)
>    ```
>
>    各是一次按主键的点查，每个候选商品两次。`/search` 那条已经有
>    「三层 filters + 一个 `in_stock` 的 EXISTS」，再加两个 anti-join 不改变量级。
>    **反过来说，包含表在这里更贵**：semi-join 的候选集是「这家店的上架清单」，
>    那才是十万行的那张表。
>
>    两条是**与**不是**或**：大区排掉的，门店不能自己捞回来。这是产品语义
>    （「大区不卖」是更上层的决定），也要有反例夹具钉住。
>
> 二、**post-filter 陷阱在这里比包含表轻，这一点值得单独记。** `00016` 文件头
>    第三节讲过：HNSW 是近似索引，过滤条件命中率低时最终返回远少于 `size` 条。
>    排除表的过滤条件命中率**接近 1**（绝大多数商品没被任何大区或门店下架），
>    所以它几乎不吃掉召回结果；包含表的命中率是「这家店上架了多少比例的商品」，
>    一家只上架了 1% 商品的门店会让向量召回基本返回空。
>
> 三、**价格不进这两张表。** 上面「三层模型」那张表已经说了原因：
>    可见性是 SPU 粒度、价格是 SKU 粒度，主键列都不一样。
>    把它们塞进一张表只有两条路——要么价格降级成「整款一个价」（表达不了
>    「黑色 XL 贵 20 块」），要么可见性升级成 SKU 粒度（运营要逐个规格点下架）。
>    两条都是为了省一张表而改坏产品。所以是两组表，四张。
>
> 四、**将来要做「按门店的排序位」** 这类同样是 SPU 粒度的东西，
>    往这两张表加列即可（`sort_order`，`NULL` 即继承）。届时
>    `chk_*_override_status` 要放宽成 `status IN (0, 1)`，
>    让「显式在售但改了排序位」也能有一行。表名叫 `overrides` 而不是
>    `exclusions`，留的就是这个口子。
>
> **`chk_*_override_status CHECK (status = 0)` 是「开店即营业」这条产品规则
> 在数据库里的执行者。** 有了它，这两张表在结构上表达不出「这家店只卖这几件」——
> 想把默认值改成「默认不卖」，必须先改 DDL，而那是一次迁移、一次评审。
> 没有它，同一个改动只需要改一行注释和一个 `WHERE`，不会有任何东西变红。
>
> `updated_by` 指向 `staff`，是单列外键，与 `shipments(created_by)` 同一条豁免
> （`staff.merchant_id` 可空，复合外键在 `NULL` 下 `MATCH SIMPLE` 直接跳过检查，
> 平台级操作员那一路会写不进去）。理由与清单在 `db/tenancy.json` 的
> `fk_single_column_ok` 里。留这一列的收益很具体：运营最常问的问题是
> 「这件商品在这家店为什么不卖了」，而一张只有主键两列的表回答不了它。
>
> **重新上架就是删掉那一行，不加 `deleted_at`。** 给一张排除表再加一个软删标记，
> 等于让「不卖」有两种写法，而查询要同时认得两种。

### region_sku_prices / store_sku_prices（价格的两层覆盖）

```sql
CREATE TABLE region_sku_prices (
    region_id   BIGINT      NOT NULL,
    sku_id      BIGINT      NOT NULL,
    merchant_id BIGINT      NOT NULL DEFAULT current_merchant() REFERENCES merchants(id),
    price_cents BIGINT      NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (region_id, sku_id),
    CONSTRAINT chk_region_price_nonneg CHECK (price_cents >= 0),
    FOREIGN KEY (region_id, merchant_id) REFERENCES regions(id, merchant_id),
    FOREIGN KEY (sku_id, merchant_id)    REFERENCES skus(id, merchant_id)
);

CREATE TABLE store_sku_prices (
    store_id    BIGINT      NOT NULL,
    sku_id      BIGINT      NOT NULL,
    merchant_id BIGINT      NOT NULL DEFAULT current_merchant() REFERENCES merchants(id),
    price_cents BIGINT      NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (store_id, sku_id),
    CONSTRAINT chk_store_price_nonneg CHECK (price_cents >= 0),
    FOREIGN KEY (store_id, merchant_id) REFERENCES stores(id, merchant_id),
    FOREIGN KEY (sku_id, merchant_id)   REFERENCES skus(id, merchant_id)
);
```

> **同样是覆盖表：缺一行的意思是「用上一层的价」，不是「免费」或「不卖」。**
>
> 「大区价格统一，但是每个门店可以自己调整价格」这句产品原话，
> 翻成结构就是这两张表加下面那条 `COALESCE`。绝大多数 SKU 在绝大多数大区、
> 门店上一行都没有——它们用的是 `skus.price_cents`。
>
> **没有 `is_active` / `effective_from` 这类字段。** 定时调价、促销价是另一个产品
> （它要活动、要时间窗、要与优惠券的叠加顺序对齐，见 §7），
> 不该混进「这家店这个 SKU 卖多少钱」这个最底层的事实里。
> 一期改价就是 upsert 一行、撤销就是删一行。

### sku_prices_by_store（「就近生效」的唯一一份实现）

```sql
CREATE VIEW sku_prices_by_store WITH (security_invoker = true) AS
SELECT st.id        AS store_id,
       st.region_id AS region_id,
       s.id         AS sku_id,
       s.product_id AS product_id,
       COALESCE(ssp.price_cents, rsp.price_cents, s.price_cents) AS price_cents,
       CASE WHEN ssp.price_cents IS NOT NULL THEN 3   -- 门店价
            WHEN rsp.price_cents IS NOT NULL THEN 2   -- 大区价
            ELSE 1 END                                 -- 基准价
                    AS price_source
  FROM stores st
  JOIN skus   s   ON s.merchant_id = st.merchant_id
  LEFT JOIN store_sku_prices  ssp ON ssp.store_id  = st.id        AND ssp.sku_id = s.id
  LEFT JOIN region_sku_prices rsp ON rsp.region_id = st.region_id AND rsp.sku_id = s.id
 WHERE st.deleted_at IS NULL AND s.deleted_at IS NULL;
```

> **这是全仓库唯一一处写 `COALESCE(门店价, 大区价, 基准价)` 的地方，这一点是有执行者的。**
>
> M2 立过一条硬纪律：试算与下单**共用同一份定价实现**
> （`internal/service/pricing.go` 的 `priceOrder`），理由是「试算和真下单算出不同的钱
> 是这条链路最严重的一类 bug」。三层定价让这条纪律的**边界变大了**：现在
> 商品列表、商品详情、检索结果也都在展示价格，而它们走的是 SQL 聚合、
> 不走 `priceOrder`。如果列表那边另写一套 `COALESCE`，**列表显示的价与下单
> 算出的价会分叉，而那种 bug 只在特定门店 + 特定商品上出现**——
> 也就是最不可能被夹具覆盖到的那种。
>
> 所以把「就近生效」下沉成一张视图，四条读路径全部经过它：
>
> | 读路径 | 怎么用 |
> |---|---|
> | `GET /products` 列表的价格区间 | `JOIN sku_prices_by_store v ON v.store_id = @store_id AND v.product_id = p.id` 后 `min/max(v.price_cents) GROUP BY p.id` |
> | `GET /products/{id}` 的每个 SKU 价 | 同上，不聚合 |
> | `POST /search` 两路召回的价格区间与价格过滤 | 同上，两条召回查询**逐字一致**（那个文件头的老要求） |
> | `priceOrder`（试算与下单） | 取价口从 `skus.price_cents` 改成 `sku_prices_by_store`，其余不动 |
>
> 机械执行者：**`store_sku_prices` 与 `region_sku_prices` 这两个表名，
> 在 `db/queries/*.sql` 里一次都不许出现**（写路径除外，见下）。
> 这与 `scripts/check_query_tenancy.py` 禁 `merchant_id` 是同一个路子：
> 把「必须走那一条」从约定变成检查。写价格的那两条 upsert 是唯一的例外，
> 按文件名豁免（`db/queries/prices.sql`），豁免要写理由。

> **`WITH (security_invoker = true)` 不是可选项。少了它就是一个跨租户读取的洞，已实测。**
>
> PostgreSQL 的视图默认以**视图属主**的权限求值，于是底层表的 RLS 策略
> 按属主判定——而迁移工具跑出来的属主通常就是应用自己（§2 已经为
> `FORCE ROW LEVEL SECURITY` 记过同一个坑的另一面）。
>
> 实测（本机 PostgreSQL 16.15，两个商家、各一个大区一家店、各自的 SKU，
> `keel_app` 同款的受限角色，`SET LOCAL app.merchant_id = '1'`）：
>
> | 视图 | 商家 1 读到的行数 | 应该是 |
> |---|---|---|
> | `WITH (security_invoker = true)` | **4** | 4（自己的 2 店 × 2 SKU） |
> | 默认（属主权限） | **5** | —— 多出来的那一行是**商家 2 的店 × 商家 2 的 SKU** |
>
> 一行。不是报错，不是空集，是安静地多出一行别人的价格。
> 这正是 §2 开头那句「这类 bug 在单租户测试数据下完全看不出来」的又一个实例——
> 只有两个商家、且刻意去数行数，才看得见。
>
> 所以上面那张执行者表里加了一条 `internal/db/migrate_test.go` 的新检查：
> **`relkind = 'v'` 的每张视图，`reloptions` 必须含 `security_invoker=true`**。
> 注意现有的 Go 侧租户检查全部写着 `relkind = 'r'`（实测，七处），
> 视图**一张都不在它们的视野里**——不补这一条，这个洞连「有没有被检查过」
> 这个问题都不会被问到。

> **查这张视图必须带 `store_id`。** 它的 `FROM` 是 `stores × skus`，
> 不带门店条件就是一次笛卡儿积。所有 sqlc 查询都要有
> `WHERE v.store_id = @store_id`，规划器会把它推到 `stores` 上，
> 之后两条 `LEFT JOIN` 都是主键点查。
>
> 实测就近生效（同一个 SKU、基准价 10000）：
> 北京店（华北大区价 9000，门店价 8500）→ `8500 / price_source = 3`；
> 广州店（华南大区价 9500，无门店价）→ `9500 / price_source = 2`；
> 没定任何覆盖的 SKU → 基准价 / `price_source = 1`。
>
> `price_source` 不是调试字段，它有两个真实读者：后台价格页要显示
> 「这个价来自哪一层」，以及 `order_items` 要把它快照下来（见 §5）——
> 否则事后对账说不清「这个价是怎么来的」。

### products 的 `min_price_cents` / `max_price_cents` 本轮删掉了

它们在 §3 的 DDL 里是两列冗余字段（「由 SKU 变更时同步更新」），
而 `/products` 列表与 `/search` 结果**直接拿它们展示价格区间**。
三层定价之后，「这件商品多少钱」取决于解析到哪家店——**那两列不再是商品的属性**。

三条路都想过：

| | 做法 | 判决 |
|---|---|---|
| (a) | 删掉，每次请求按解析出的门店现算 | **选这条** |
| (b) | 按门店物化一张 `store_product_prices` | 否。行数是 门店数 × 商品数，正是上面刚否掉「包含表」的那个量级；而且改基准价要扇出到每家店，一次上新要写一万行 |
| (c) | 保留为「租户参考价」，只在无位置时用 | 否。无位置已经定死回落到默认门店，那时**同样有确定的大区与门店**，参考价没有使用时机 |

选 (a)，理由有三条，第二条是决定性的：

一、**这两列在三层定价下会变成一句谎话**，而这个仓库已经有一个现成的反面教材：
   `products.total_stock`。`db/queries/search.sql` 的注释里写着「那一列是冗余汇总，
   全仓库没有任何一处在维护它（grep 一下只剩建表与种子），拿它当『有没有货』
   等于对用户撒一个永远不会被纠正的谎」。同一节还删过 `inventories.reserved_qty`，
   理由一字不差：「留一个永远为 0 的字段，代价不是那 4 个字节，
   是后面接手的人一定会误用它」。**保留一个只对『恰好用基准价的那些店』
   正确的价格区间，是同一类债的第三次。**

二、**价格过滤今天本来就没有索引可走，所以 (a) 不损失任何执行计划。**
   这一点是核过的：`products` 上唯一的列表索引是
   `idx_products_listing ON products(merchant_id, category_id, status, published_at DESC)`，
   **`min_price_cents` / `max_price_cents` 不在任何索引里**。
   于是 `min_price_cents <= @max` 今天就是一条堆上的过滤条件，
   (a) 只是把「读一列」换成「读一个已经 JOIN 好的聚合值」，
   改变的是每行常数，不是计划的类别。
   `/search` 那条向量召回同理——00016 文件头第三节讲的 post-filter 陷阱
   在这两种写法下**程度相同**，因为价格条件两边都不在 HNSW 索引里。

三、**契约几乎不动。** `ProductSummary.min_price_cents` / `max_price_cents`
   两个响应字段原样保留，只是它们的值从「一列冗余字段」变成
   「按当前门店算出来的区间」，并且响应里会同时回显 `store` 上下文
   （见 OpenAPI 的 `StoreContext`）。客户端的类型一个字都不用改。
   后台的 `AdminProduct` 上这两个字段的含义改成**基准价区间**
   （由 `skus.price_cents` 聚合，不含任何覆盖），并在 schema 描述里写明——
   后台是租户视角，那里没有「当前门店」。

> **代价诚实说两笔。** 一、列表页每页要多一次对 `sku_prices_by_store` 的聚合，
> 候选是当页 20 条商品的 SKU；检索侧是召回条数（`size` ≤ 100）的 SKU。
> 两者都是主键点查的量级，但它们**确实不是零**，且会随「一个商品有多少 SKU」
> 线性增长。二、`products.total_stock` 在多门店之后是同一类谎话
> （它连「哪家店」都没有），本轮**没有**一起删——它不在这次的改动面上，
> 而主线有任务正在动商品域。记进 §15。

### inventories（按门店分，§15 第 3 条在这里结清）

```sql
CREATE TABLE inventories (
    sku_id        BIGINT      NOT NULL,
    store_id      BIGINT      NOT NULL,
    merchant_id   BIGINT      NOT NULL DEFAULT current_merchant() REFERENCES merchants(id),
    available_qty INT         NOT NULL DEFAULT 0,  -- 可售
    warning_qty   INT         NOT NULL DEFAULT 0,
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (sku_id, store_id),
    CONSTRAINT chk_qty_nonneg CHECK (available_qty >= 0),
    FOREIGN KEY (sku_id, merchant_id)   REFERENCES skus(id, merchant_id),
    FOREIGN KEY (store_id, merchant_id) REFERENCES stores(id, merchant_id)
);
CREATE INDEX idx_inventories_store ON inventories(merchant_id, store_id)
    WHERE available_qty > 0;
```

> **本轮补上了 `merchant_id`，这张表从 `parent-scoped` 变成 `tenant` 类。**
>
> §4 原先的豁免注里写着后路：「将来若要做多仓（见 §15 第 3 条，主键会变成
> `(sku_id, warehouse_id)`），**可以顺手把 `merchant_id` 一起补上，届时策略可简化为
> 直接的列比较**」。现在正是那一天，而且不是「顺手」——是**必须**：
>
> · 主键多了 `store_id` 之后，「这一行的租户归属由主键唯一决定」这条判据不再成立。
>   原先一行库存只对应一个 SKU、那个 SKU 只属于一个商家，所以**错挂之后没有第二个
>   真相可以对不上**。现在有了：这一行可以说它属于 A 店的 SKU、而那家店属于 B 商家。
>   这正是 `order_items` 那种「两个真相对不上」的形状，规矩二为它而存在。
> · 两条复合外键（`(sku_id, merchant_id)` → `skus`、`(store_id, merchant_id)` → `stores`）
>   要求本表有 `merchant_id` 那一列，没有它复合外键拼不出来。
>   而这两条外键合起来钉死的恰恰是新的越权形状：**把 A 店的库存挂到 B 商家的 SKU 上**。
>
> 于是原先那条豁免的**两个理由本轮都失效了**，逐条记下：
>
> | 原豁免理由 | 现在 |
> |---|---|
> | 「主键就是 `sku_id`，租户归属由 `skus` 决定」 | 主键是 `(sku_id, store_id)`，有两个父表，两条归属链要对齐 |
> | 「热点表，多一列索引成本不划算」 | 这一列不是为索引加的，是为复合外键加的。索引成本仍在（主键索引宽了 8 字节），但换到的是两条外键与一条**便宜的** RLS 策略 |
>
> 策略随之从对父表的 `EXISTS` 子查询简化成直接的列比较：
>
> ```sql
> ALTER TABLE inventories ENABLE ROW LEVEL SECURITY;
> ALTER TABLE inventories FORCE ROW LEVEL SECURITY;
> CREATE POLICY tenant ON inventories
>   USING      (merchant_id = current_merchant())
>   WITH CHECK (merchant_id = current_merchant());
> ```
>
> **这是净收益，不是平手**：旧策略在每次扣减上外加两次 `skus_pkey` 查找
> （`USING` 与 `WITH CHECK` 各一，上一轮实测过）；新策略是一次列比较。
> 下单扣减是全站最热的写路径，这一笔省得值。
>
> `DEFAULT current_merchant()` 与 `orders` / `order_items` / `inventory_logs` /
> `idempotency_keys` 同一条路子（第六次）：`scripts/check_query_tenancy.py`
> 不许 `db/queries/*.sql` 里出现 `merchant_id` 这个词，让数据库自己填是唯一
> 不进豁免清单的走法。默认值同时是一道形状约束——生成的 Go 函数签名里
> 根本没有 `merchant_id`。
>
> 本轮新建的另外五张表（`regions` / `stores` / 两张 overrides / 两张 prices）
> 全部照这一条办，不再逐张重复理由。

> **上一轮那张 RLS 实测表仍然成立，只有最后一行换了内容。**
>
> 实测（10 万行 `skus` / 5 万行 `inventories`，`keel_app` 角色，旧策略）：
>
> | 场景 | 无策略 | 有策略 |
> |---|---|---|
> | 商家 A 改商家 B 的库存 | `UPDATE 1` —— 得手 | `UPDATE 0` |
> | 商家 A 读商家 B 的库存水位 | 读得到 | 读不到 |
> | 往别家 SKU 上插库存行 | 成功 | `ERROR: new row violates row-level security policy` |
> | 忘了 `SET LOCAL` | 全表可读可写 | **报错 42501**（失败关闭） |
> | 扣减一行 | 一次主键查找 | 旧策略外加两次 `skus_pkey` 查找；**新策略只多一次列比较** |
>
> 「忘了 `SET LOCAL`」那一行的结论不变，它对新旧策略都成立、且都很要紧：
> 真实的 `current_merchant()`（§2 ①）在未设上下文时是 `RAISE EXCEPTION`，
> 不是返回 NULL，语句以 **`42501 insufficient_privilege`** 失败，
> 根本走不到「可见 0 行」。
>
> ```
> BEGIN;  -- 没有 SET LOCAL
>   UPDATE inventories SET available_qty = available_qty - 1
>    WHERE sku_id = 1 AND available_qty >= 1;
> ERROR:  租户上下文未设置：事务开始时必须 SET LOCAL app.merchant_id
> CONTEXT:  PL/pgSQL function current_merchant() line 5 at RAISE
> ```
>
> 这个区别在扣减路径上是有代价的：下一节那条正向分支按 `rows_affected = 0`
> 分支，而漏设租户上下文走的是异常路径。混为一谈，SAGA 会把一次**配置错误**
> 当成一次**库存不足**来补偿——补偿是幂等的、日志是正常的，
> 于是「所有下单都失败」会表现为「所有商品都缺货」。
>
> 上一轮写错这一条的原因值得留着，它是方法问题：当时是在探针库里**重新实现了**
> 一个返回 NULL 的 `current_merchant()`，而不是用仓库里真正的那个。
> 探针一旦复刻被测对象，测的就是复刻件。
>
> 视图那一段刚记下的 `security_invoker` 是同一类坑的第三个面：
> **默认值在多租户下是不安全的那一侧，而它不报错。**

> **主键的列序是 `(sku_id, store_id)`，不是 `(store_id, sku_id)`。**
>
> 两种写法在「扣某店某 SKU」这个点查上完全一样。分歧在别处：
>
> · `sku_id` 打头：商品详情页要算「这家店这件商品有没有货」，
>   谓词是「这个商品的这批 SKU × 这一家店」——按 `sku_id` 逐个探。
>   下单扣减同样按 `sku_id` 进入。**这两条是热路径。**
> · `store_id` 打头：后台的「这家店的库存清单」一次范围扫描就出来。
>   **这条是后台的低频页面**，给它一条 `idx_inventories_store` 就够了，
>   而且那条索引还能带上 `WHERE available_qty > 0`（缺货行不进索引）。
>
> 另外 §15 第 3 条当时的原话就是「主键会变成 `(sku_id, warehouse_id)`」，
> 保持同一个列序，让结清这一条时不需要额外解释一次为什么反过来了。

> **一行库存不存在，等于「可售 0」，不等于「这家店不卖」。这一条必须写死。**
>
> 两件事在库里长得很像（都是 `WHERE sku_id = ? AND store_id = ?` 查不到行），
> 但语义相反，而且**判错的方向是不对称的**：
>
> · 判成「不卖」：一家刚开的店在录入库存之前，每一个 SKU 都没有库存行，
>   于是**新店什么都不卖**——和「开店即营业」正面冲突。
> · 判成「可售 0」：新店开张即全目录在售，只是都显示缺货，等运营录库存。
>   这正是产品要的形态。
>
> 而且这不是新规矩，是**既有语义**：`db/queries/products.sql` 的
> `ListSKUsForDetail` 用的就是 `LEFT JOIN inventories`，注释里写着种子里的
> `SKU-NOSTOCKROW` 是一个「有 SKU、没有库存行」的真实状态，
> 用 `JOIN` 的话这类 SKU 会整个从详情里消失。
> 「缺行 ≡ 可售 0」在多门店之前就已经是这个仓库的答案，本轮只是把它写进正文。
>
> **「这家店不卖」由两张 `*_product_overrides` 表达，那是另外的表。**
> 下一节的五种 `rows_affected = 0` 就建立在这条分界线上。

### 扣减库存时，`rows_affected = 0` 有五种成因

上一轮分出了两种（`ErrInsufficientStock` / `ErrSKUNotInTenant`），按门店与大区分之后
变成五种。判据仍然是那一条，而且它现在有了名字——**M4 契约在
`PUT /admin/skus/{sku_id}/inventory` 上把它写成了一句话：
「把『不是你的 SKU』也报成 409 会让调用方以为重读一次再试就能成功，
而那个循环永远不会结束」**。同一条判据在这里展开成一张表：

| # | 成因 | sentinel | 重试有用吗 | 契约 | SAGA 与告警 |
|---|---|---|---|---|---|
| ① | 这个 SKU 在本租户不可见（别家的，或已软删） | `ErrSKUNotInTenant`（既有） | 无用，且不该有人重试 | `422` + `.../invalid-request` | 分支失败 → 全局补偿；**告警**，这是 bug 或攻击 |
| ② | 这个门店在本租户不可见（别家的，或已软删） | `ErrStoreNotInTenant`（新） | 同上 | `422` + `.../invalid-request` | 同上 |
| ③ | 这家店不卖这件商品（门店排除、**大区排除**、或门店已停业） | `ErrSKUNotSoldInStore`（新） | **无用。客户端该换一家店，不是重试** | `422` + `.../sku-not-sold-in-store`，响应体带 `store_id` 与冲突的 `sku_id` 列表 | 分支失败 → 全局补偿；**不告警**，这是运营随时会做的动作与下单之间的正常竞态 |
| ④ | 库存不足，**含「这家店根本没有这一行」** | `ErrInsufficientStock`（既有） | 有用——补货之后会成功 | `409` + `.../insufficient-stock` | 分支失败 → 全局补偿；埋点算缺货 |
| ⑤ | 完全没设租户上下文 | 不是 sentinel，是 `42501` 异常原样上浮 | —— | `500` | **不是**库存的任何一种状态，是配置错误 |

> **⑤ 一直都在**（`internal/repository/inventory.go` 的注释叫它「第四条出路」），
> 列进来是因为这张表现在是这条路径的完整清单，缺一行就会有人以为它只有四支。

> **为什么「没有那一行」归进 ④ 而不是 ③。** 上一段刚论证过「缺行 ≡ 可售 0」。
> 归进 ③ 会让新开的门店在录库存之前对每一件商品都回「本店不卖」，
> 而那是产品明确不要的形态。**这是本设计里唯一一处和任务书字面不同的地方**，
> 理由写在这里，证据是 `db/queries/products.sql` 里已经存在的
> `SKU-NOSTOCKROW` 那一路。
>
> **为什么 ③ 是 422 而不是 404。** M4 在 `PUT /admin/skus/{sku_id}/inventory` 上
> 用的是 404，因为那里 `sku_id` 是**路径参数**——「这个 URI 下没有这个资源」
> 是 404 的本义。`POST /orders` 的路径是 `/orders`，报 404 会被客户端读成
> 「下单接口不存在」。分界线因此写死一条：
> **路径里指名的资源不存在 → 404；请求体里指名的东西不存在或不可用 → 422。**
> 两者的共同点才是要紧的：都**不是** 409，因为 409 在本契约里被客户端读成
> 「重读一次再试」（`Retry-After`、`InventoryConflict.current` 都在教它这么读）。
> 门店维度那条后台接口（`PUT /admin/stores/{store_id}/skus/{sku_id}/inventory`）
> 两个 id 都在路径里，所以它仍然用 404，与 M4 的先例一致。
>
> **为什么 ① 和 ② 合用一个 problem type。** 对外它们是同一句话「你的请求里
> 有一个服务端不认识的 id」，分开告诉调用方等于替攻击者做区分。
> 对内它们是两个不同的 sentinel，日志与告警分得开——
> 这与 §2「查不到即 404，不是 403」是同一个路子。
>
> **大区排除为什么也归进 ③ 而不是单开一支。** 对调用方而言，「大区不卖」
> 与「门店不卖」的处置完全一样：换一家店（换到别的大区的店去）。
> 分成两个 sentinel 只会让 SAGA 分支多一个没人分支的判断。
> 对内要分得清的那一面由 `store_product_overrides` / `region_product_overrides`
> 两张表自己承担——运营页面查得到是哪一层排掉的。

> **五种成因要在同一条语句、同一个 MVCC 快照里分别回传，不许拆成先 SELECT 再 UPDATE。**
>
> 这是 `db/queries/inventories.sql` 现有写法的延续（它今天已经用两个 CTE
> 回传 `visible_rows` / `deducted_rows`）。形状变成三个判定 CTE + 一个更新 CTE：
>
> ```sql
> WITH sku_visible AS (
>     SELECT s.id FROM skus s WHERE s.id = $1 AND s.deleted_at IS NULL
> ), store_visible AS (
>     SELECT st.id FROM stores st WHERE st.id = $2 AND st.deleted_at IS NULL
> ), sellable AS (
>     SELECT 1 FROM stores st JOIN skus s ON s.id = $1
>      WHERE st.id = $2 AND st.status = 1
>        AND NOT EXISTS (SELECT 1 FROM store_product_overrides o
>                         WHERE o.store_id = st.id AND o.product_id = s.product_id
>                           AND o.status = 0)
>        AND NOT EXISTS (SELECT 1 FROM region_product_overrides o
>                         WHERE o.region_id = st.region_id AND o.product_id = s.product_id
>                           AND o.status = 0)
> ), deducted AS (
>     UPDATE inventories upd
>        SET available_qty = upd.available_qty - $3, updated_at = now()
>      WHERE upd.sku_id = $1 AND upd.store_id = $2 AND upd.available_qty >= $3
>     RETURNING upd.available_qty AS left_qty
> )
> SELECT ... 三个计数 + deducted 的计数 + d.left_qty ...
> ```
>
> 注意 `sku_visible` 的来源本轮从 `inventories` 改成了 `skus`。
> 今天那条 CTE 读的是 `inventories`，于是「别家的 SKU」与「没有库存行」
> **本来就是混在一起**的——`internal/repository/inventory.go` 的注释自己写着
> 「要么这个 `sku_id` 属于别的商家……要么它根本没有库存行」。
> 按门店分之后「没有库存行」会从罕见变成常态（新店、新品、缺货清零都会缺行），
> 那个混淆不能带进来。所以这次不只是加三种，**同时拆开了已经混着的那一对**。
>
> 判定顺序是 ① → ② → ③ → ④，不能反。一件被下架的商品通常同时也没库存行，
> 先判 ④ 会报「缺货」，而用户会一直等一个永远不会来的补货。
>
> 三处 sqlc 的将就照旧（两个 CTE 里的表各带别名、末尾的
> `FROM (SELECT 1) a LEFT JOIN deducted d ON true`、注释里不许有反引号），
> 理由写在那个文件的头上，不再重复。

> **`RestoreInventory`（补偿回补）也要带 `store_id`。**
> 它现在是 `WHERE sku_id = $1`，加上门店之后是 `WHERE sku_id = $1 AND store_id = $2`。
> 这条语句没有「数量不够」那一支，所以零行仍然只有一种含义，
> 仍然用 `:one` 让它变成 `pgx.ErrNoRows`——补偿路径是最容易直接攥着 `sku_id`
> 回滚的地方（那正是 RLS 在这张表上要挡的动作），不能是一次静默的
> `rows_affected = 0`。**补偿要用的 `store_id` 从 `orders` 读**，
> 不从 gid 解析，理由见下一段。
>
> 有一处不对称要写明：补偿**不**重新判 ③。一件在下单后被运营下架的商品，
> 它的回补必须照样执行——补的是一件已经扣掉的货，
> 「现在还卖不卖」与「当时扣没扣」是两个问题。

### SAGA 分支怎么知道该扣哪家店的库存

`BranchFunc func(gid, branchID, op string) int` —— 分支只拿到三个字符串，
而且它跑在任何 HTTP 请求之外（崩溃重启后由 TC 重放，进程对原请求毫无记忆）。

**结论：`store_id` 落在 `orders` 上就够，不必改 gid 的文法。这一条是核过的。**

论证链条已经在 `internal/service/order.go` 的文件头里了，这里只确认它对
`store_id` 同样成立：

1. 订单**必须**先落库、再提交 SAGA。这不是偏好，是被这个签名逼出来的顺序——
   「扣哪些 SKU、各扣几件」从 gid 里推不出来（gid 只有租户与订单号），
   只能落库。`00013` 的文件头与 `order.go` 的文件头都有这段论证，原话是
   「分支需要的一切必须能从 gid 推出来，或者已经落在库里」。
2. 于是 `order_items` 在分支执行时**一定已经在库里**。`store_id` 是订单级的
   一个标量，和 `user_id`、`receiver_snapshot` 一样落在 `orders` 那一行上，
   跟 `order_items` 在同一个事务里提交。
3. 分支从 gid 解析出 `merchant_id` + `order_no`（`internal/dtm/gid.go`），
   `SET LOCAL app.merchant_id`，按 `order_no` 读回订单行，
   于是它同时拿到 `store_id` 与全部明细。**补偿分支走同一条路**，
   所以回补一定回补到当初扣减的那家店。

**不改 gid 的三条理由：**

· gid 是屏障幂等的键（`barrier` 主键的第一列），改它的文法等于改那把钥匙的形状。
  正在途中的事务在部署切换的瞬间会拿旧文法写、新文法读，
  屏障判定当场失效——而屏障失效的表现是业务被执行两遍，不是报错。
· gid 有 128 字节上限（dtmrs 的 `Backend::ID_MAX`）。塞得下一个 `store_id`，
  但「能塞下」不是理由：一旦开了这个口子，下一个需要的字段也会想挤进去。
· `store_id` 已经必须落在 `orders` 上（订单要按门店做报表与对账，见 §5），
  把它同时编进 gid 是让同一个事实有两个真相源，而它们可以不一致。

> **一个必须一起定的边界：`store_id` 与 `region_id` 在 `orders` 上都是 `NOT NULL`。**
> 分支读回订单行拿到一个 `NULL` 的 `store_id` 时无路可走——它既不能猜默认店
> （那会把单扣到另一家店去），也不能失败（订单已经落库了）。
> 所以这两列不可空，而那意味着**迁移必须给每个已有商家建出一个默认大区、
> 一家默认门店，并回填历史订单**。这条写进 §15 的待确认里，因为它是实现任务的
> 第一步，也是唯一一处不能靠「新数据走新路」绕过去的地方。
### 为什么不用 version 乐观锁

用**条件原子更新**，不是「读-改-写 + version」：

```sql
-- 正向：扣减库存
UPDATE inventories SET available_qty = available_qty - $3
WHERE sku_id = $1 AND store_id = $2 AND available_qty >= $3;

-- 补偿：回补库存
UPDATE inventories SET available_qty = available_qty + $3
WHERE sku_id = $1 AND store_id = $2;
```

单条 UPDATE 在 PG 中是原子的，行锁自动生效，高并发下不会像乐观锁那样反复重试失败。
`CHECK` 约束是最后一道防线——即使代码写错，数据库也不允许负库存。

> **上面这两句**不是可以照抄进代码的形态，本轮把原先跟在第一句后面的那行注释
> （`rows_affected = 0 ⇒ 库存不足，分支失败，触发全局补偿`）删掉了：它和本节
> 上方那段实测结论**直接冲突**。上方刚记下「设了租户、但 SKU 是别家的，
> 结果也是 `UPDATE 0`，信号和库存不足完全一样」，而这行注释就写在同一节里，
> 是一句可以直接复制进 SAGA 分支的、错的代码。两者并存时，人会照抄代码那一份。
>
> 真正执行的形态在 `db/queries/inventories.sql`：把「这一行在本租户可见吗」
> 与「扣成功了吗」压进同一条语句、同一个 MVCC 快照，分别回传。
> repository 层把它们映射成不同的 sentinel 错误，
> `internal/repository/inventory_test.go` 用两家商家的真实数据证明它们分得开。
>
> **本轮那条语句要从两个判定扩成四个**（上一节那张五种成因的表）：
> `ErrSKUNotInTenant` / `ErrStoreNotInTenant` / `ErrSKUNotSoldInStore` /
> `ErrInsufficientStock`。两条 `WHERE` 也都多了 `store_id` ——
> 少写这一条的后果不是报错，是**扣到别的门店头上**：没有 `store_id` 的
> `WHERE sku_id = $1` 在多门店之后会匹配到该 SKU 在**所有**门店的行，
> `UPDATE` 会把它们一起改掉。这是本轮改动里最容易漏、后果最重的一处，
> 所以两句示例 SQL 都在这里一起改了。

### inventory_logs（流水，用于对账）

```sql
CREATE TABLE inventory_logs (
    id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id   BIGINT      NOT NULL DEFAULT current_merchant() REFERENCES merchants(id),
    sku_id     BIGINT      NOT NULL,
    store_id   BIGINT      NOT NULL,
    change_qty INT         NOT NULL,   -- 正负
    biz_type   SMALLINT    NOT NULL,   -- 1下单扣减 2SAGA补偿回补 3超时关单释放 4退款回补 5手工调整
    biz_id     TEXT        NOT NULL,   -- 订单号等
    before_available INT   NOT NULL,
    after_available  INT   NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    FOREIGN KEY (sku_id, merchant_id)   REFERENCES skus(id, merchant_id),
    FOREIGN KEY (store_id, merchant_id) REFERENCES stores(id, merchant_id)
);
CREATE INDEX idx_inv_logs_biz ON inventory_logs(merchant_id, biz_id);
CREATE INDEX idx_inv_logs_sku_time
    ON inventory_logs(merchant_id, store_id, sku_id, created_at DESC);
```

> **`store_id` 是本轮补的，它不是可选的冗余。**
> 流水的唯一用途是对账，而对账的口径从「这个商家这个 SKU 扣了多少」
> 变成了「这家店这个 SKU 扣了多少」——`before_available` / `after_available`
> 这两列现在记的是**某一家门店**的水位，不写下是哪一家，同一个 SKU 在五家店的
> 流水会交织成一条谁也对不平的序列。
>
> `idx_inv_logs_sku_time` 因此把 `store_id` 插在 `sku_id` 前面：
> 盘点页是「这家店、这个 SKU、按时间倒序」，门店是更外层的筛选。

> **`sku_id` 本轮补成了复合外键,推翻了上一轮「保持无外键」的结论。**
> 上一轮的理由是「规矩二管的是已有的父子引用要连租户一起钉,不是凡是 id 列都要建外键」。
> 这个划界让规矩二在最要紧的地方失效:**把外键降级成单列会被闸门抓住,
> 把外键整个删掉反而全绿**——违规做得更彻底反而绕过了检查。
> 于是判断标准改成「列名形如 `<x>_id`、能解析到一张父表,就要么有外键、
> 要么写明为什么不该有」,清单在 `db/tenancy.json` 的 `fk_missing_ok` 里。
>
> 对本表而言不补的代价是:库存流水可以记在别家的 SKU 上,而对账正是按
> `merchant_id + sku_id` 跑的——错挂的那一行会静默地算进另一家的账。
>
> 两个索引则照规矩加了 `merchant_id` 前缀:对账按商家跑,
> `biz_id`(订单号)与 `sku_id` 在 RLS 注入之后都不是最有选择性的首列。

## 五、交易域

### orders

```sql
CREATE TABLE orders (
    id                BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id   BIGINT      NOT NULL DEFAULT current_merchant() REFERENCES merchants(id),
    order_no          TEXT        NOT NULL UNIQUE,   -- 对外编号
    user_id           BIGINT      NOT NULL,
    store_id          BIGINT      NOT NULL,          -- 履约门店，见 §4
    region_id         BIGINT      NOT NULL,          -- 下单时该门店所属大区，定价口径
    status            SMALLINT    NOT NULL DEFAULT 10,   -- 履约维度，见状态机
    refund_status     SMALLINT    NOT NULL DEFAULT 0,    -- 资金维度：0无退款 1退款中 2部分退款完成 3全额退款完成
    -- 金额拆分，每一项都可追溯
    goods_amount_cents    BIGINT  NOT NULL,          -- 商品总额
    freight_cents         BIGINT  NOT NULL DEFAULT 0,
    discount_cents        BIGINT  NOT NULL DEFAULT 0,
    payable_cents         BIGINT  NOT NULL,          -- 应付 = 商品+运费-优惠
    paid_cents            BIGINT  NOT NULL DEFAULT 0,
    refunded_cents        BIGINT  NOT NULL DEFAULT 0,
    receiver_snapshot JSONB       NOT NULL,          -- 收货信息快照
    store_snapshot    JSONB       NOT NULL,          -- 门店与大区的展示字段快照，见下
    remark            TEXT,
    expire_at         TIMESTAMPTZ NOT NULL,          -- 超时关单时间
    paid_at           TIMESTAMPTZ,
    shipped_at        TIMESTAMPTZ,
    finished_at       TIMESTAMPTZ,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT chk_amount CHECK (
        payable_cents = goods_amount_cents + freight_cents - discount_cents
        AND paid_cents >= 0 AND refunded_cents <= paid_cents
    ),
    CONSTRAINT chk_refund_status CHECK (
        (refund_status = 0 AND refunded_cents = 0) OR
        (refund_status = 1) OR
        (refund_status = 2 AND refunded_cents > 0 AND refunded_cents < paid_cents) OR
        (refund_status = 3 AND refunded_cents = paid_cents AND paid_cents > 0)
    ),
    FOREIGN KEY (user_id, merchant_id)   REFERENCES users(id, merchant_id),
    FOREIGN KEY (store_id, merchant_id)  REFERENCES stores(id, merchant_id),
    FOREIGN KEY (region_id, merchant_id) REFERENCES regions(id, merchant_id)
);
CREATE INDEX idx_orders_user ON orders(merchant_id, user_id, created_at DESC);
CREATE INDEX idx_orders_store ON orders(merchant_id, store_id, created_at DESC);
CREATE INDEX idx_orders_status_expire ON orders(merchant_id, status, expire_at)
    WHERE status = 10;  -- 待支付，给超时关单任务用
-- 供 order_items / shipments / payments / refunds 做复合外键
CREATE UNIQUE INDEX uk_orders_id_merchant ON orders(id, merchant_id);
CREATE INDEX idx_orders_refunding ON orders(merchant_id, refund_status, updated_at DESC)
    WHERE refund_status = 1;  -- 售后进行中，给客服看板与重试任务用
```

> **`store_id` / `region_id` 是外键，`store_snapshot` 是快照。两样都要，不是二选一。**
>
> §9 论证过「地址与订单的关系是快照，不是外键」，所以 `orders` 里没有 `address_id`。
> 门店**反过来**，理由是那段论证的前提在这里不成立：
>
> · 地址是**买家的**私有数据，数量无上限，用户随时自己删；按它做聚合没有意义，
>   所以只留一份拍扁的 JSONB 就够了。
> · 门店与大区是**租户的运营主数据**，几十行，软删，而且**第一需求就是按它聚合**——
>   「这家店这个月卖了多少」「华北大区的客单价」是开多门店的全部动机。
>   `GROUP BY` 一个 JSONB 里的字符串是做不了的，字段名改一次全部报表就断。
>   所以 `store_id` / `region_id` 必须是真正的列与真正的外键。
>
> 那为什么还要 `store_snapshot`：**门店会改名、会搬家、会换大区**。
> 三个月前那单的详情页要显示「朝阳门店 · 朝阳区 xx 路 1 号」，
> 而不是它今天改成的新名字——这和 `order_items` 存 `title_snapshot` 是同一条道理
> （§6：「快照只在下单那一瞬间产生」）。
> 快照里只放**展示用**的字段（门店名、地址、电话、大区名），不放 id，
> 也不放任何会被拿去做聚合的东西——放了就会有人去 `GROUP BY` 它。
>
> **`region_id` 冗余在 `orders` 上，不靠 `stores.region_id` 推。** 门店可以被调到
> 另一个大区去，而这一单的价格是按**当时那个大区**算的。要能事后回答
> 「这个价是怎么来的」，就不能让它取决于一张随后会变的表。
>
> 两列都是 `NOT NULL`，理由在 §4 末尾：SAGA 分支读回订单行拿到 `NULL` 时无路可走。

> **这三张表（`orders` / `order_items` / `inventory_logs`）以及 §12 的
> `idempotency_keys`，`merchant_id` 都带 `DEFAULT current_merchant()`。**
> 这是 M2 任务 4/5 落地下单写路径时补上的（迁移 `00013_order_write_path.sql`），
> 不是省事：`scripts/check_query_tenancy.py` 不许 `db/queries/*.sql` 里出现
> `merchant_id` 这个词 —— 应用层再过滤一遍租户，「RLS 到底有没有生效」就变得
> 测不出来了。于是每条 INSERT 面临的选择是「把整条下单写路径塞进那个脚本的
> 豁免清单」还是「让数据库自己填」，选了后者。
>
> 默认值同时是一道形状约束：生成的 Go 函数签名里根本没有 `merchant_id`，
> 所以「拿 A 店的上下文往 B 店名下建单」连编译都编不出来。RLS 的 `WITH CHECK`
> 仍是第二道 —— 默认值只在没写这一列时生效，真写了别家的值，策略会当场拒绝。
> §9 的 `user_tokens` 用的是同一条路子。

> **`user_id` 改成复合外键**(规矩二)。买家属于某个商家是 §2 开头就定下的事实,
> 订单挂到别家的买家身上在多店模型里没有任何合法解释,
> 所以它该由数据库拒绝,而不是靠下单代码记得校验。
>
> `uk_orders_id_merchant` 原先就在——它是本文件里**唯一**照规矩二做了的父表,
> 本轮把其余父表补齐,并给三个业务索引加上 `merchant_id` 前缀。

> **设计说明**：`CHECK` 里把金额恒等式写死。这是「懂业务」最直接的体现——
> 任何计算错误在写入瞬间就会被数据库拒绝，而不是在对账时才发现。
>
> `chk_refund_status` 是同一思路的延伸：`refund_status` 与 `refunded_cents`
> 是同一件事的两种表示，让它们互相校验。这里也顺手定死了两条容易含糊的边界——
> **「全额退款」是资金口径**（退到 `refunded_cents = paid_cents`），
> 只退货款不退运费的，状态是 `2 部分退款完成` 而不是 3；
> `1 退款中` 不约束金额，因为多笔退款并行时中间态什么金额都可能出现。

### 订单状态机（显式定义，不散在 if-else 里）

订单有**两个互相正交的状态维度**：`status` 管履约走到哪儿，`refund_status` 管资金退到哪儿。

**履约维度 `status`：**

```
 0 创建中 ──建单分支正向──► 10 待支付 ──支付成功──► 20 已支付 ──发货──► 30 已发货 ──确认收货──► 40 已完成
   │                          │                        │
   │全局补偿                   │超时/取消                │未发货整单退
   ▼                          ▼                        ▼
90 已关闭 ◄──────────────── 90 已关闭                 50 退款中 ──退款到账──► 60 已退款
                                                         │
                                                         └──审核驳回──► 回到 20
```

> **`0 创建中` 是 M2 任务 5 加进来的，它是一个用户永远看不到的状态。**
>
> 下单 SAGA 的分支只拿到 `(gid, branch_id, op)` 三个字符串，「扣哪些 SKU、
> 各扣几件」推不出来，所以订单与订单项**必须先落库、再提交 SAGA**。而「已落库」
> 不等于「已成交」：一笔 SAGA 还没跑完的订单如果就是 `10 待支付`，那么在库存
> 分支失败与补偿跑完之间，它对用户是一笔可支付的订单，而它背后一件库存都没扣。
>
> 所以落库时的状态是 `0`，由建单分支把它推到 `10`。契约的 `OrderStatus` 枚举
> 不含 `0` —— 这正是要的效果：状态 `0` 的订单要么被推到 `10` 再返回，
> 要么被补偿关到 `90`，它不会出现在任何响应里。
>
> 两条出边 `(0,10)` 与 `(0,90)` 登记进了 `order_status_transitions`（见下），
> 而不是让它游离在状态机之外 —— 那张表是状态机的唯一真相源，一个不在表里的
> 状态就是一个没人知道存在的状态。没有 `(0,20)`：一笔还没建成的订单不可能
> 先被支付。
>
> 代价说清楚：进程若在「订单落库提交」与「SAGA 提交」之间死掉，库里会留下一行
> `status = 0` 的孤儿订单 —— 不可见、不可支付、不占库存，**但也没人来关它**。
> 清理它属于超时关单任务（M2 任务 6）的范围。

```sql
CREATE TABLE order_status_transitions (
    from_status SMALLINT NOT NULL,
    to_status   SMALLINT NOT NULL,
    PRIMARY KEY (from_status, to_status)
);
INSERT INTO order_status_transitions VALUES
 (0,10),(0,90),
 (10,20),(10,90),(20,30),(20,50),(30,40),(50,60),(50,20);
```

**资金维度 `refund_status`：** `0 无退款 → 1 退款中 → 2 部分退款完成 / 3 全额退款完成`，
由 §11 的退款单驱动，`2` 与 `1` 之间可以来回（退完一笔又申请下一笔）。

> **为什么要拆成两个维度**
>
> 原设计只有 `status` 一列，`50 退款中` / `60 已退款` 承担全部售后语义。
> 用户买三件退一件，订单就得整单变成「退款中」——那么剩下两件还发不发货？
> 已经发出去的还能不能确认收货？这些问题在单维度模型里**无解**，
> 只能靠代码里堆特判，而特判一定会漏。
>
> 拆开之后规则很干净：
>
> | 场景 | `status` | `refund_status` |
> |---|---|---|
> | 未发货整单退 | `20 → 50 → 60` | `0 → 1 → 3` |
> | 买三退一（已发货） | 不变，继续 `30 → 40` | `0 → 1 → 2` |
> | 已完成后全部退回 | 停在 `40 已完成` | `1 → 3` |
> | 退款被驳回 | 未发货的从 `50` 回 `20`；已发货的本就没动过 | 回到 `0` 或 `2` |
>
> 一句话：**`status` 说货到哪儿了，`refund_status` 说钱退了多少。**
> 这也是真实电商平台的做法。
>
> **`50` / `60` 只留给未发货的整单退款**，这是本轮定下的收窄规则。原状态机里
> `30 已发货 → 50 退款中` 那条边已经删掉了，理由是：`50` 是个中间态，
> 从 `30` 进去之后如果审核驳回，要回到 `30` 还是 `20`？为了答这一问就得再存一列
> 「进入退款前的原状态」。而已发货订单的退款本来就该走资金维度——
> 货已经在路上了，履约进度不该被售后流程抹掉。
>
> 代价：查「所有有售后的订单」要带上 `refund_status`，不能只看 `status`；
> 前端订单列表的标签要由两列组合渲染。这是把复杂度从代码特判挪到了展示层，
> 挪得值。
### order_items（下单即快照）

```sql
CREATE TABLE order_items (
    id             BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id   BIGINT      NOT NULL DEFAULT current_merchant() REFERENCES merchants(id),
    order_id       BIGINT      NOT NULL,
    sku_id         BIGINT      NOT NULL,
    product_id     BIGINT      NOT NULL,
    -- 快照：商品改价改名不影响历史订单
    title_snapshot TEXT        NOT NULL,
    spec_snapshot  JSONB       NOT NULL,
    image_snapshot TEXT,
    price_cents    BIGINT      NOT NULL,
    price_source   SMALLINT    NOT NULL DEFAULT 1,   -- 1 基准价 2 大区价 3 门店价，见 §4
    quantity       INT         NOT NULL CHECK (quantity > 0),
    amount_cents   BIGINT      NOT NULL,
    discount_cents BIGINT      NOT NULL DEFAULT 0,   -- 该行分摊到的优惠，见 §7
    refunded_qty   INT         NOT NULL DEFAULT 0,   -- 已退件数，流水见 §11 refund_items
    refunded_cents BIGINT      NOT NULL DEFAULT 0,   -- 该行已退金额
    CONSTRAINT chk_item_refund CHECK (
        refunded_qty >= 0 AND refunded_qty <= quantity
        AND refunded_cents >= 0 AND refunded_cents <= amount_cents - discount_cents
    ),
    -- 供 refund_items 做复合外键
    UNIQUE (id, merchant_id),
    FOREIGN KEY (order_id, merchant_id)   REFERENCES orders(id, merchant_id),
    FOREIGN KEY (sku_id, merchant_id)     REFERENCES skus(id, merchant_id),
    FOREIGN KEY (product_id, merchant_id) REFERENCES products(id, merchant_id)
);
CREATE INDEX idx_order_items_order ON order_items(merchant_id, order_id);
```

> **`price_source` 是本轮补的一列，它是三层定价的对账入口。**
> `price_cents` 已经是快照，但它只说「多少钱」，说不出「凭什么」。
> 三层定价之后，同一个 SKU 在同一天的两笔单上可以是两个价——
> 一笔走了门店价、一笔走了大区价。没有这一列，事后只能拿三张表的**当前值**
> 去反推，而那三张表随时在改。取值与 `sku_prices_by_store.price_source` 同源
> （§4），下单时由 `priceOrder` 一起写下来。
>
> `DEFAULT 1` 是给迁移用的：历史订单一律是基准价，那是它们当时的唯一真相。

> `order_id` 的复合外键正是 §2 规矩二那段示意代码所演示的写法——
> **示意归示意,本表原先并没有照做**。这是本轮同步的起点。
>
> **`sku_id` / `product_id` 本轮也补成了复合外键,推翻了上一轮「保持无外键」的结论。**
> 上一轮的理由是「它们是快照行上的溯源字段,商品删了订单项也要留着」。
> 那个理由站不住:本文档里 `products` 走的是 `deleted_at` 软删除、`skus` 根本没有
> 删除路径(§1「交易数据永不删除」同时也意味着被交易引用过的商品不会被物理删除),
> 所以外键从来不会挡住任何一次实际发生的删除。
>
> 而不补的代价是具体的:A 商家的订单行可以引用 B 商家的 SKU,**数据库不拒**。
> 这一条还特别难发现——订单行带着价格与规格快照,错挂之后展示、对账、退款
> 看起来全都正常,只有拿 `sku_id` 回查库存时才会露馅,而那正是 M2 下单 SAGA
> 的主链路。规矩二自己说的是「能让数据库拒绝的,就别指望人记得」。

> `chk_item_refund` 是「超退」的最后一道防线：退款件数不能超过购买件数，
> 退款金额不能超过该行的实付净额（金额 − 分摊优惠）。退款流程本身也会用条件更新
> 做一次判定（§11），但那是代码，这一条是数据库。两道都要有。

### shipments（发货包裹）

```sql
CREATE TABLE shipments (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id   BIGINT      NOT NULL REFERENCES merchants(id),
    order_id      BIGINT      NOT NULL,
    carrier_code  TEXT        NOT NULL,   -- 'sf' / 'jd' / 'yto' 等
    tracking_no   TEXT        NOT NULL,
    status        SMALLINT    NOT NULL DEFAULT 1,  -- 1已发出 2已签收 3异常
    shipped_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    delivered_at  TIMESTAMPTZ,
    created_by    BIGINT      REFERENCES staff(id),
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    FOREIGN KEY (order_id, merchant_id) REFERENCES orders(id, merchant_id)
);
CREATE INDEX idx_shipments_order ON shipments(merchant_id, order_id);
-- 同一承运商的运单号在**本店内**不会重复；重复提交同一个单号是录入错误，不是新包裹
CREATE UNIQUE INDEX uk_shipments_tracking
    ON shipments(merchant_id, carrier_code, tracking_no);
```

> **`created_by` 刻意保持单列外键**,这是规矩二的一处真例外,理由在 §14:
> `staff.merchant_id` 可以为 NULL(平台级操作员),
> 而 `FOREIGN KEY (created_by, merchant_id) REFERENCES staff(id, merchant_id)`
> 会把「平台级操作员替某家店发货」直接拒掉——那是合法场景,不是越权。
> 代价是这一列的跨租户挂接只能靠应用层挡;它是审计字段而非业务主线,可以接受。
> `staff.created_by`(§14)与 `uploads.staff_id`(§14)同理,不再重复。
>
> **运单号唯一键收进租户内**(规矩三)。承运商的运单号由承运商生成,
> 只在它自己的商户账号维度内保证不重复。全局唯一会让 A 店录过的单号在 B 店录入时撞冲突,
> 而且撞出来的错误本身就泄露了「别家用过这个号」。
> 代价:同一个物理包裹若被两家店各录一次,数据库不再拦——但那在多店模型里
> 本来就不是同一个包裹(两家店各自发货),拦住才是错的。

> **物流信息为什么不放在 `orders` 上**
>
> 一期每单只发一个包裹，把 `carrier_code` / `tracking_no` 直接塞进 `orders`
> 会更省事。但支持多包裹时就得把这两列搬走并回填历史数据——**那是真迁移**。
>
> 放在独立表里，一期每单一行，将来多包裹只是多插几行；
> 再加一张 `shipment_items` 记录「哪几件在哪个包裹」是**纯增量，不动已有结构**。
>
> 这和优惠券 `stackable` 那种「留个字段先不启用」不一样——`shipments`
> 从第一天就真的在用。§4 删掉 `reserved_qty` 的理由（永远为 0 的字段一定会被误用）
> 在这里不适用。

**一期只允许整单发货**，所以 `orders.status` 走 `20 → 30` 即可，不需要新状态。

> **将来开部分发货时不要加「25 部分发货」。** 按本文档已有的正交模式，
> 加一列 `orders.ship_status`（0 未发货 / 1 部分发货 / 2 全部发货），
> `status = 30` 的含义收窄为「全部发货」——与 `refund_status` 完全同构。
> 把发货进度压进 `status` 会重演「部分退款该不该改订单状态」那个死结。
> 这条现在只写进设计，不建列。

### 发货的三条规则

**一、不动库存。** 下单 SAGA 的正向阶段已经扣过了（见 §4），发货只是履约动作。
写在这里是因为这是最容易重复扣减的地方。

**二、存在未完结的整单退款申请时拒绝发货。** 部分退款不阻断——
理由与确认收货那条一致：部分退款不该冻结整个履约流程。

**三、自动确认收货挂在 `jobs` 上。** 定时扫
`status = 30 AND shipped_at < now() - <N> days`，推进 `30 → 40`。
`N` 是店铺配置（`shop_settings.auto_confirm_days`），不硬编码——
不同品类的合理收货期差别很大。

**物流轨迹查询一期不做。** 只存承运商与运单号，前端自己拼快递公司的查询链接。
接聚合物流 API 是独立的事，而且要花钱。

### payments（支付单，与订单分离）

一个订单可能有多次支付尝试，必须分表。

```sql
CREATE TABLE payments (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id   BIGINT      NOT NULL DEFAULT current_merchant() REFERENCES merchants(id),
    payment_no    TEXT        NOT NULL UNIQUE,
    order_id      BIGINT      NOT NULL,
    channel       SMALLINT    NOT NULL,   -- 1微信 2支付宝 3余额
    amount_cents  BIGINT      NOT NULL,
    status        SMALLINT    NOT NULL DEFAULT 0, -- 0待支付 1成功 2失败 3已关闭
    channel_txn_id TEXT,                  -- 渠道流水号，用于对账
    notify_payload JSONB,                 -- 原始回调报文，永久保留
    paid_at       TIMESTAMPTZ,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    -- 供 refunds 做复合外键
    UNIQUE (id, merchant_id),
    FOREIGN KEY (order_id, merchant_id) REFERENCES orders(id, merchant_id)
);
CREATE UNIQUE INDEX uk_payments_channel_txn
    ON payments(merchant_id, channel, channel_txn_id) WHERE channel_txn_id IS NOT NULL;
```

> **幂等关键**：`(merchant_id, channel, channel_txn_id)` 唯一索引是支付回调幂等的
> 最后一道锁。渠道重复回调时，第二次写入会触发唯一冲突，直接返回成功即可。
>
> **本轮把它收进了租户内**(规矩三)。`channel_txn_id` 是支付渠道生成的,
> 渠道只保证在单个商户号维度内不重复。全局唯一等于替渠道做了一个它没做的承诺,
> 而承诺落空的后果是:两家店的流水号一旦相同,**后到的那一笔回调会被静默当成重复丢弃**,
> 也就是一笔真实到账没有入库。收进租户内之后幂等语义完全不变
> (回调本来就路由到某个商家),冲突面从全局缩到店内。
>
> `payment_no` 仍然全局唯一——它是我们自己生成的不可枚举编号,属于 §2 那条分界线的另一侧。
>
> **`merchant_id` 的 `DEFAULT current_merchant()` 是 M2 任务 7 补上的**，与
> `user_tokens`(§9) / `idempotency_keys`(§12) / `orders`(§5) 是同一条路子：
> `scripts/check_query_tenancy.py` 不许 `db/queries` 里出现 `merchant_id` 这个词
> （应用层再过滤一遍租户，「RLS 到底有没有生效」就变得测不出来了），
> 而支付回调那条 INSERT 必须写得出来。让数据库自己填之后，生成的 Go 函数签名里
> 根本没有这个参数，调用方**没有那个参数可以传错**。
>
> **这条唯一索引同时约束了回调那条 INSERT 的形状：它不许带 `ON CONFLICT`。**
> 不带冲突目标的 `DO NOTHING` 会把任何唯一冲突都吞掉，包括 `payment_no` 撞车 ——
> 而那是熵源坏了或者生成逻辑被改坏了，必须炸出来，不能被伪装成一次「重复回调」。
> 带冲突目标又写不出来（目标里要出现 `merchant_id`）。所以回调发的是一条光秃秃的
> `INSERT`，由应用侧按约束名 `uk_payments_channel_txn` 把「重复回调」这一种冲突
> 挑出来，其余 `23505` 原样上浮。**索引名因此是接口的一部分。**

## 六、dtmrs 集成

### barrier 表（必须与业务表同库）

以下为 dtmrs 源码 `crates/dtmrs-barrier/src/lib.rs` 中 `BranchBarrier::migrate()` 的
实际产物（Postgres 方言）。**通常不需要手写——调用 `migrate()` 会自动建表**，
此处列出仅为让 DBA 和迁移脚本知情。

```sql
CREATE TABLE IF NOT EXISTS barrier (
    trans_type  TEXT   NOT NULL,
    gid         TEXT   NOT NULL,
    branch_id   TEXT   NOT NULL,
    op          TEXT   NOT NULL,
    barrier_id  TEXT   NOT NULL,
    reason      TEXT   NOT NULL,
    create_time BIGINT NOT NULL,          -- Unix 时间戳，非 TIMESTAMPTZ
    PRIMARY KEY (gid, branch_id, op, barrier_id)
);
```

几点值得注意：

- **表名默认 `barrier`**，可通过 builder 的 `.table()` 改名。若与业务表命名规范冲突，
  建议统一改为 `dtm_barrier`。
- **故意没有自增 id 列**。作者的注释写明：`AUTOINCREMENT` / `BIGSERIAL` /
  `AUTO_INCREMENT` 是最难移植的方言点，而屏障算法只依赖那个唯一约束，
  去掉它换来一套 DDL 跑三种库。
- MySQL 下列类型为 `VARCHAR(128)` / `VARCHAR(45)`，因为 MySQL 不能对 TEXT 建索引。
- `create_time` 是 BIGINT 而非 TIMESTAMPTZ——与本项目「时间统一 TIMESTAMPTZ」的
  约定不一致，但这是第三方组件的表，不强求统一。

### 屏障的三种判定

`decide()` 返回三种结果，业务方必须正确处理：

| Decision | 含义 | 业务方应做 |
|---|---|---|
| `Execute` | 该干活 | 在**同一事务**内执行业务 SQL |
| `NullCompensation` | 空回滚：正向分支从未执行 | **什么都不做，返回成功** |
| `Duplicated` | 重复请求或悬挂 | **什么都不做，返回成功** |

> **最容易踩的坑**：`NullCompensation` 和 `Duplicated` 都是**正常路径**，
> 必须返回成功。若返回失败，TC 会误判分支出错并无限重试。

算法本身（读源码所得）：补偿类操作先以「正向分支」的身份插一行，
插进去了说明正向分支从没来过 → 空回滚；再以自己身份插一行，插不进去说明已处理过 → 重复。

### 下单流程的 SAGA 编排

```
Global TX: order-{order_no}   (SAGA)
├─ Branch 1  库存
│   正向  : available_qty -= n   （条件更新，不足则失败）
│   补偿  : available_qty += n
├─ Branch 2  优惠券
│   正向  : status 1 未使用 → 3 已使用
│   补偿  : status 3 → 1
└─ Branch 3  订单
    正向  : 创建订单，status = 10 待支付
    补偿  : status → 90 已关闭
```

> **为什么是 SAGA 而不是 TCC**
>
> TCC 的预留阶段能提供隔离性——库存从「可售」转为「预占」，总量不变。
> 但在下单场景里这个收益很小：用户看到缺货本来就是正确的，因为确实有人在买。
>
> 代价却是实打实的：每个分支三个方法而非两个，加上预留量的维护、
> 超时清理与一致性校验。
>
> 另需澄清：「支付回调与超时关单竞态」在两种模式下都由子事务屏障处理——
> 先到的补偿会占掉正向的位置，后到者被判定为 `Duplicated`。这不构成 TCC 的优势。
>
> **TCC 留给真正需要预留语义的场景**：预售定金、多仓调拨、需要向供应商
> 区分「锁定量」与「真实销量」。届时再引入——注意 `inventories` 里那个
> 「预留」字段已经在本轮删掉了（见 §4 的说明），真要用时新加一列即可，
> 这比在表里供着一个永远为 0 的字段安全得多。

支付回调用**二阶段消息**：支付成功 → 消息投递 → 订单状态流转 + 券核销确认 + 积分发放。
退款用 **SAGA** 补偿链。超时关单用 **SAGA**。

## 七、营销域（优惠券）

设计取向：**常用规则用固定字段，复杂规则留 JSONB 扩展位**。
纯 JSONB 规则引擎太早了（要写解释器、难索引、难调试）；纯固定字段又不通用。
先支持四种最常见的券型，扩展位留好。

### coupon_templates（券模板 / 批次）

```sql
CREATE TABLE coupon_templates (
    id              BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id   BIGINT      NOT NULL REFERENCES merchants(id),
    name            TEXT        NOT NULL,
    coupon_type     SMALLINT    NOT NULL,  -- 1满减 2折扣 3立减 4包邮
    -- 门槛与优惠额
    threshold_cents BIGINT      NOT NULL DEFAULT 0,  -- 满多少可用，0 表示无门槛
    discount_cents  BIGINT      NOT NULL DEFAULT 0,  -- 满减/立减的减免额
    discount_rate   SMALLINT    NOT NULL DEFAULT 0,  -- 折扣，千分比：850 = 8.5折
    max_discount_cents BIGINT   NOT NULL DEFAULT 0,  -- 折扣封顶，0 = 不封顶
    -- 有效期：两种模式二选一
    valid_mode      SMALLINT    NOT NULL DEFAULT 1,  -- 1绝对时间 2领取后N天
    valid_start_at  TIMESTAMPTZ,
    valid_end_at    TIMESTAMPTZ,
    valid_days      INT         NOT NULL DEFAULT 0,
    -- 发放控制
    total_count     INT         NOT NULL DEFAULT 0,  -- 总量，0 = 不限
    issued_count    INT         NOT NULL DEFAULT 0,
    per_user_limit  INT         NOT NULL DEFAULT 1,
    -- 叠加策略
    stackable       BOOLEAN     NOT NULL DEFAULT FALSE, -- 能否与其他券叠加
    priority        SMALLINT    NOT NULL DEFAULT 0,     -- 多券计算顺序，大的先算
    -- 扩展位：新规则先放这里，稳定后再提为正式字段
    extra_rules     JSONB       NOT NULL DEFAULT '{}',
    status          SMALLINT    NOT NULL DEFAULT 1,     -- 1启用 0停用
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT chk_coupon_rule CHECK (
        (coupon_type = 1 AND discount_cents > 0 AND threshold_cents >= discount_cents) OR
        (coupon_type = 2 AND discount_rate BETWEEN 1 AND 999) OR
        (coupon_type = 3 AND discount_cents > 0) OR
        (coupon_type = 4)
    ),
    -- 供 coupon_scopes / user_coupons 做复合外键
    UNIQUE (id, merchant_id)
);
```

> **CHECK 约束的价值**：满减券的减免额必须小于等于门槛（「满 100 减 200」是配置错误，
> 会被数据库直接拒绝）；折扣率必须在合法区间。运营在后台配错券的成本极高——
> 上线几分钟就能造成不可挽回的资损，这道约束是最便宜的保险。

### coupon_scopes（适用范围）

一张券可以有多条范围规则，`include` 为真是白名单，为假是黑名单。

```sql
CREATE TABLE coupon_scopes (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id   BIGINT      NOT NULL REFERENCES merchants(id),
    template_id BIGINT   NOT NULL,
    scope_type  SMALLINT NOT NULL,  -- 1全场 2分类 3商品 4品牌
    target_id   BIGINT,             -- 对应 category_id / product_id / brand_id
    include     BOOLEAN  NOT NULL DEFAULT TRUE,
    FOREIGN KEY (template_id, merchant_id) REFERENCES coupon_templates(id, merchant_id)
);
CREATE INDEX idx_coupon_scopes_tpl ON coupon_scopes(merchant_id, template_id);
```

> **`target_id` 是多态列,进不了外键,更进不了复合外键。** 它按 `scope_type`
> 分别指向 `category_id` / `product_id` / `brand_id`,这是本表既有的设计,本轮不动。
> 但要写明后果:**规矩二在这一列上失效**,「把别家的商品配进本店券的适用范围」
> 数据库拦不住,只能由后台配置接口在应用层校验。
> §14 讲 `uploads` 归属时用两个可空外键换掉多态,正是为了避开这种失效;
> 这里没有跟着改,是因为 `scope_type` 有四种取值且还会增加,
> 拆成四个可空外键列的代价明显高于收益——**这是一条知道自己有缺口的设计,不是疏忽**。

### user_coupons（券实例）

```sql
CREATE TABLE user_coupons (
    id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id   BIGINT      NOT NULL REFERENCES merchants(id),
    coupon_code  TEXT        NOT NULL UNIQUE,
    template_id  BIGINT      NOT NULL,
    user_id      BIGINT      NOT NULL,
    status       SMALLINT    NOT NULL DEFAULT 1,  -- 1未使用 2锁定 3已使用 4已过期
    order_id     BIGINT,                          -- 使用时回填
    valid_start_at TIMESTAMPTZ NOT NULL,
    valid_end_at   TIMESTAMPTZ NOT NULL,
    locked_at    TIMESTAMPTZ,
    used_at      TIMESTAMPTZ,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    FOREIGN KEY (template_id, merchant_id) REFERENCES coupon_templates(id, merchant_id),
    FOREIGN KEY (user_id, merchant_id)     REFERENCES users(id, merchant_id),
    FOREIGN KEY (order_id, merchant_id)    REFERENCES orders(id, merchant_id)
);
CREATE INDEX idx_user_coupons_avail
    ON user_coupons(merchant_id, user_id, status, valid_end_at) WHERE status = 1;
CREATE UNIQUE INDEX uk_user_coupons_order
    ON user_coupons(order_id) WHERE order_id IS NOT NULL;
```

> **这个索引原先是空转的**：写法是 `(order_id, id)`，而 `id` 是自增主键，
> 任意包含 `id` 的组合天然唯一——索引建了，但一个约束也没施加，
> 同一个订单照样能挂上五张券。
>
> 去掉 `id` 之后它才真正生效：**一个 `order_id` 在本表最多出现一次**，
> 也就是本节末尾那条「第一期同一订单只允许用一张券」的落地处。

> **`order_id` 本轮补上了复合外键。** 它可空（使用时才回填），而复合外键在
> `MATCH SIMPLE` 下任一列为 NULL 即跳过检查，所以「还没用掉的券」自动不受约束，
> 正是想要的语义——待遇与 §14 `uploads.user_id` 完全一样。
> 不补的代价是：本店的券可以核销到**别家店的订单**上，而券的核销直接影响
> 订单实付金额与退款分摊（§11），是资金链路上的一条边。
> 规则写在文档里不算数，写进约束才算数。
>
> 代价：将来要开券叠加时，这个索引必须先删。到那时「一单几张券」会变成
> 券模板的 `stackable` 与优先级共同决定的运行时规则，数据库层管不了——
> 这也是为什么现在能管的时候要管住。
>
> **`uk_user_coupons_order` 本轮没有加 `merchant_id` 前缀**：`order_id` 已经蕴含租户
> (`orders` 那边的复合外键钉死了这一点),加前缀既不多防一分,还会把约束从
> 「一个订单全局最多一张券」放宽成「一个订单在本店最多一张券」——后者是同一件事,
> 但首列换成低基数列会让这个唯一索引的写入定位变差。
> 规矩三针对的是**全局作用域**的唯一约束;首列已经是租户内标识的,不在其列。
> 同类的还有 `uk_user_addresses_default(user_id)`、`uk_cart_items(cart_id, sku_id)`、
> `uk_refund_items(refund_id, order_item_id)`、`idempotency_keys` 的主键。

### 券的状态机 —— 对应 SAGA 正向与补偿

```
1 未使用 ──正向──► 3 已使用
    ▲                │
    └──── 补偿 ──────┘
    └──────── 退款回补（可选策略）────────┘
                              4 已过期（定时任务）
```

```sql
-- 正向：核销。条件更新，抢不到说明已被使用或已过期
UPDATE user_coupons SET status = 3, used_at = now(), order_id = $3
WHERE id = $1 AND user_id = $2 AND status = 1 AND valid_end_at > now();

-- 补偿：释放
UPDATE user_coupons SET status = 1, used_at = NULL, order_id = NULL
WHERE id = $1 AND status = 3 AND order_id = $2;
```

> 状态 2（锁定）保留在枚举中不启用，供将来引入 TCC 预留语义时使用。

与库存完全同构：条件原子更新 + rows_affected 判定，不用乐观锁。

### 优惠计算顺序（最容易出错的地方）

多种优惠并存时，**计算顺序直接影响最终金额**，必须固定下来写进文档：

```
1. 单品级优惠（限时折扣、会员价）      → 得到每个 item 的实付单价
2. 店铺级满减（按 priority 降序）
3. 平台券
4. 运费券
```

### 优惠分摊 —— 部分退款的前提

优惠必须**按比例分摊到每个 order_item**，结果写入 `order_items.discount_cents`。

原因：用户买了三件用了一张满 300 减 50 的券，只退其中一件时，
退多少钱？必须按该件商品分摊到的优惠倒算，否则会多退或少退。

```
item 分摊额 = 券面额 × (item 金额 / 参与优惠的商品总额)
```

**分摊余数处理**：整数分相除必有余数，规则是「余数全部给金额最大的那一项」，
保证 `SUM(item.discount_cents) == order.discount_cents` 恒等。
这一条不写清楚，对账必然对不平。

### 第一期先实现

只做四种券型 + 三类范围（全场 / 分类 / 商品），且**同一订单只允许用一张券**
（`stackable` 字段先留着不启用）。叠加规则是复杂度爆炸的起点，
等核心链路跑通再开。

### 向量表：按模态拆成两张

```sql
CREATE EXTENSION IF NOT EXISTS vector;

-- 文本向量
CREATE TABLE product_text_vectors (
    product_id    BIGINT       PRIMARY KEY,
    merchant_id   BIGINT       NOT NULL DEFAULT current_merchant() REFERENCES merchants(id),
    content       TEXT         NOT NULL,       -- 实际送入模型的拼接文本，留作调试与精排输入
    embedding     vector(1024) NOT NULL,       -- BGE-M3 / Qwen3-Embedding
    model_name    TEXT         NOT NULL,
    model_version TEXT         NOT NULL,
    updated_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
    FOREIGN KEY (product_id, merchant_id)
        REFERENCES products(id, merchant_id) ON DELETE CASCADE
);
CREATE INDEX idx_ptv_hnsw ON product_text_vectors
    USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);

-- 图像向量（主图）
CREATE TABLE product_image_vectors (
    product_id    BIGINT       PRIMARY KEY,
    merchant_id   BIGINT       NOT NULL DEFAULT current_merchant() REFERENCES merchants(id),
    image_url     TEXT         NOT NULL,       -- 当前已嵌入的主图，换图即重算
    embedding     vector(768)  NOT NULL,       -- clip-vit-l
    model_name    TEXT         NOT NULL,
    model_version TEXT         NOT NULL,
    updated_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
    FOREIGN KEY (product_id, merchant_id)
        REFERENCES products(id, merchant_id) ON DELETE CASCADE
);
CREATE INDEX idx_piv_hnsw ON product_image_vectors
    USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);
```

> **两张向量表的 `product_id` 改成复合外键**(规矩二),`ON DELETE CASCADE` 原样保留:
> 复合外键一样支持级联,删商品照旧带走它的向量。
>
> **两个 HNSW 索引没有 `merchant_id` 前缀,而且加不了。** HNSW 是单列向量索引,
> 不接受前置的 B-tree 列。于是多租户下的向量召回是「先近似搜、再被 RLS 过滤」:
> 取 top-100 时可能有一部分属于别的租户、被过滤掉,实际到手不足 100。
> 这是 pgvector 在共享 schema 下的已知形态,**不是这一轮能改的东西**——
> 真要改只有两条路:按 `merchant_id` 做表分区,或把租户编进向量空间做前置过滤,
> 两者都远超一期成本。
>
> ~~一期的应对很朴素:召回时把 `LIMIT` 放大(例如取 top-300 再截到 100)。~~
> **这句话是错的,M3 Task 1 落地时更正。** 它把 app-side 过滤的直觉搬到了
> RLS-side 过滤上:不带迭代扫描时,HNSW 索引扫描一共只吐 `hnsw.ef_search` 条
> 候选(pgvector 0.8.6 默认 40),吐完就结束。这 40 条里一条都不属于当前租户时,
> **把 `LIMIT` 从 100 放大到 500 一行也多不出来** —— `LIMIT` 限的是
> 「过滤后要几行」,限不住索引愿意吐几行。真正的一期方案是
> `hnsw.iterative_scan`(pgvector 0.8+,会话级 GUC,设在检索连接上),
> 论证与实验在语义检索层 §2.4 与 M3 计划第一条;
> 按 `merchant_id` 分区为什么在这个仓库里不成立(它会逼着主键变成
> `(product_id, merchant_id)`),写在 `db/migrations/00016_semantic_layer.sql` 的文件头。
>
> **隔离性没有任何损失**——被过滤掉是 RLS 在干活,漏出去才是问题;
> 受影响的只是召回率,而且它在单库租户多时是功能直接失效,不只是「召回率低一点」。

> **四张表的 `merchant_id` 都带 `DEFAULT current_merchant()`**,与 `user_tokens`
> (§9)、`idempotency_keys`(§12)、`payments`(§5) 同一条路子。
> 没有默认值的话,写入语句里就必须出现 `merchant_id` 这个词,而
> `scripts/check_query_tenancy.py` 不许 `db/queries` 里出现它 ——
> 应用层再过滤一遍租户,「RLS 到底有没有生效」就变得测不出来了。
> 默认值同时是一道形状约束:生成的 Go 函数签名里根本没有 `merchant_id`。

> **为什么拆表，而不是一张表加 `vector_type` 做复合主键**
>
> 因为 **pgvector 的维度是列级固定的**。文本模型输出 1024 维，图像模型
> （clip-vit-l）输出 768 维，768 维的向量根本插不进 `vector(1024)` 列——
> 这不是风格问题，是插入直接报错。想塞进一张表只剩两条路：补零对齐（污染余弦距离），
> 或者把 embedding 存成 `float4[]` 放弃 HNSW 索引（放弃了用 pgvector 的全部理由）。
>
> 拆开之后还白拿一个好处：两种模态的召回质量与数据分布不同，HNSW 的
> `m` / `ef_construction` / `ef_search` 可以分别调，互不牵连。
>
> 代价，诚实地说三条：
> 1. 多一张表、多一套写入与回填链路；
> 2. 跨模态检索（图文混合召回、同款归并）要自己写 UNION 再融合，
>    没法一条 SQL 带走——但那一步本来就要做 RRF 融合，多一个 UNION 不算负担；
> 3. `model_name` / `model_version` 在两张表各存一份，换模型时要分别灰度。
>    这其实也是好事：换文本模型不该逼着图像向量一起重算。
>
> **一期只嵌入主图**，所以主键就是 `product_id`。多图检索（同一商品多张图各出一个向量）
> 是后续扩展，届时主键改为 `(product_id, image_url)`，`ON DELETE CASCADE` 不变。
>
> 旧表名 `product_embeddings` 与 `product_vectors` 一并废弃，不再作为表名出现在任何文档里。

### 商品理解的状态与结果

商品理解服务（见 [商品理解服务设计](./电商系统-商品理解服务设计.md)）把商品加工成
可被机器消费的对象。加工**状态**与**非向量结果**落在这张表，向量落在上面两张表。

```sql
CREATE TABLE product_understanding (
    product_id       BIGINT      PRIMARY KEY,
    merchant_id   BIGINT       NOT NULL DEFAULT current_merchant() REFERENCES merchants(id),
    status           SMALLINT    NOT NULL DEFAULT 0,  -- 0待处理 1部分完成 2完成 3失败
    -- 各 processor 的输入指纹，按能力分别记录：
    -- {"text_embedding":"ab12..","image_embedding":"cd34..","attribute_extract":"ef56.."}
    input_hashes     JSONB       NOT NULL DEFAULT '{}',
    -- 非向量类结果：标准化属性、卖点、类目预测、质量分、合规结论
    results          JSONB       NOT NULL DEFAULT '{}',
    pipeline_version TEXT        NOT NULL,
    last_error       TEXT,                            -- 最近一次失败原因，供后台排查
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    FOREIGN KEY (product_id, merchant_id)
        REFERENCES products(id, merchant_id) ON DELETE CASCADE
);
-- 后台「待处理 / 部分完成 / 失败」列表与重跑扫描
CREATE INDEX idx_pu_unfinished
    ON product_understanding(merchant_id, status, updated_at)
    WHERE status IN (0, 1, 3);
```

> **为什么向量不进 `results`**：JSONB 里的数组建不了 HNSW 索引。向量必须是
> `vector(N)` 列才能被近似检索用上，所以单独成表——这是物理约束，不是洁癖。
>
> **这里没有 `retry_count`**。重试次数是队列的账，记在 `jobs.attempts`（见 §12）。
> 而且一个商品的理解由多个 processor 各自入队，「这个商品重试了几次」本身就是个
> 界定不清的问题——是文本向量重试了 3 次，还是合规检查重试了 3 次？
> 按上一节刚立的规矩：同一件事只记一处。
>
> `last_error` 留下了，它和重试计数不是一回事——后台要能一眼看到「这个商品卡在哪」，
> 不必跳到队列表去翻。代价是它只保留最近一次，完整失败历史要查 `jobs`。

### 同款簇

```sql
CREATE TABLE product_clusters (
    product_id BIGINT      PRIMARY KEY,
    merchant_id   BIGINT       NOT NULL DEFAULT current_merchant() REFERENCES merchants(id),
    cluster_id BIGINT      NOT NULL,
    confidence REAL        NOT NULL,
    method     SMALLINT    NOT NULL,   -- 1自动 2人工确认 3人工拆分
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT chk_cluster_conf CHECK (confidence >= 0 AND confidence <= 1),
    FOREIGN KEY (product_id, merchant_id)
        REFERENCES products(id, merchant_id) ON DELETE CASCADE
);
CREATE INDEX idx_pc_cluster ON product_clusters(merchant_id, cluster_id);
-- 人工判定不得被自动逻辑覆盖，扫描自动簇时按此索引取
CREATE INDEX idx_pc_auto
    ON product_clusters(merchant_id, cluster_id) WHERE method = 1;
```

> **`cluster_id` 加了 `merchant_id` 前缀,顺带把一件事挑明:同款簇不跨租户。**
> 「A 店的商品与 B 店的商品是同款」在多店模型里没有消费方——
> 前台同款推荐只能推本店的货。索引前缀让这一点在物理布局上也成立。
> 代价:将来若要做跨店比价(那已经是集市模型了,见 §2),这两个索引要重建。

> **`method` 不只是审计字段，它是写入权限**。商品理解服务设计 §6 的原则是
> 「错误合并的代价远高于漏合并」，因此人工的「确认 / 拆分」（`method = 2 / 3`）
> 优先级最高，自动聚类不得覆盖。落地方式是自动写入时带上 `WHERE method = 1`
> 条件更新——与库存、优惠券用的是同一套条件原子更新手法。
>
> `confidence < 0.95` 的自动合并不直接生效、进人工审核队列，这条规则的判据就是本表的
> `confidence`；审核任务本身走 §12 的 `jobs`。

### 增量重算的指纹：只认一处

向量表**不带 `content_hash`**。「这个 processor 的输入变没变」这件事，
唯一真相源是上一节 `product_understanding` 的 `input_hashes` 列：

```sql
-- 判断文本向量是否需要重算
SELECT input_hashes ->> 'text_embedding' FROM product_understanding WHERE product_id = $1;
```

> **为什么不在向量表里也存一份**：早先的设计里 `product_embeddings.content_hash`
> 和 `product_understanding.input_hashes` 记的是同一件事。同一件事两处写，
> 迟早漂移——而漂移的表现形式是「向量悄悄过期了但系统认为它是新的」，
> 这种 bug 在检索结果里几乎看不出来，只会表现为「搜索效果慢慢变差」。
>
> 归口到 `input_hashes` 还顺带更严格：那边是**按 processor 分别记指纹**的。
> 换一张主图不该触发文本向量重算，只在向量表放一个 `content_hash` 做不到这种粒度。
>
> 全量重算 10 万商品的 embedding 成本很高，增量是必需的——只是这个「增量」的判据
> 应该只有一个出处。

### 关键词召回

```sql
ALTER TABLE products ADD COLUMN search_text TEXT;   -- 应用层写入 bigram 串
ALTER TABLE products ADD COLUMN search_vector tsvector
    GENERATED ALWAYS AS (to_tsvector('simple', coalesce(search_text, ''))) STORED;
CREATE INDEX idx_products_fts ON products USING gin(search_vector);
```

> **为什么是 `search_text` 而不是直接对 `title` 做**：`to_tsvector('simple', ...)`
> 对中文等于不分词——「羊毛衫」整个被当成一个词，用户搜「毛衫」一条也召不回。
> 所以 `search_text` 由应用层写入**二元切分（bigram）串**：
> 「羊毛衫」→「羊毛 毛衫」，这样 `simple` 配置就能按空格切出可检索的词。
> 切分算法、方案对比与「为什么一期选 bigram 而不是 pg_jieba / zhparser」的论证
> 见《语义检索层设计》§4，那边不再重复表结构。
>
> 代价：`search_text` 是应用层维护的派生列，标题改了忘记重写就会索引过期。
> ~~所以它跟 `min_price_cents` 一样，归在同一个对账任务里校正。~~
> **M3 Task 3 落地时改了这个安排**：它与文本向量归在**同一个** processor 流水线里
> （`internal/service/index.go`），而不是价格库存那个对账任务里。理由是两者的判据
> 不同源——`min_price_cents` 的真相在 `skus`，一次聚合就能校正；而 `search_text`
> 与 `text_embedding` 共用同一个触发点（`products.updated_at`）和同一张指纹表
> （本节下面的 `input_hashes`），分到两个任务里意味着「商品变更时哪些派生数据要重算」
> 这份清单存在两处，而散在两处的清单迟早只更新一处。
> 两者仍然是**两个 processor、两格指纹**：`search_text` 的输入只有标题与副标题，
> 换一次类目只重算向量、不重写 bigram 串。
> 拿一个非生成列换了「不依赖任何第三方分词扩展就能部署」，这笔交易在一期是划算的。

### search_logs（第一天就要埋）

```sql
CREATE TABLE search_logs (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id   BIGINT      NOT NULL REFERENCES merchants(id),
    user_id       BIGINT,
    session_id    TEXT,
    query         TEXT        NOT NULL,
    parsed_intent JSONB,                  -- LLM 解析出的结构化意图
    recall_ids    BIGINT[],               -- 召回结果
    ranked_ids    BIGINT[],               -- 最终排序
    clicked_id    BIGINT,
    carted_id     BIGINT,                 -- 加购回传，算「搜索→加购率」
    ordered_id    BIGINT,
    latency_ms    INT,
    trace_id      TEXT        NOT NULL,   -- 与 /search 响应回传给客户端的同一个值
    -- 归因三件套：没有这三列，排序策略与模型升级的效果都无法回溯
    strategy      TEXT        NOT NULL DEFAULT 'default',  -- 本次实际使用的排序策略
    model_name    TEXT,                                    -- embedding / reranker 实际版本
    model_version TEXT,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_search_logs_strategy
    ON search_logs(merchant_id, strategy, created_at DESC);
-- 行为回传按 trace_id 定位，必须唯一且可索引
CREATE UNIQUE INDEX uk_search_logs_trace ON search_logs(trace_id);
```

> **`uk_search_logs_trace` 保持全局唯一**:`trace_id` 是链路追踪标识,
> 全局唯一是它的定义——日志、指标、APM 三处都按它对齐,按租户切会让跨系统排查失去锚点。
> 它也符合 §2 那条分界线:**我们自己生成的不可枚举标识保持全局唯一**,
> 与 `order_no` 同类。行为回传 `UPDATE ... WHERE trace_id = $1` 是一次点查,
> 不靠前缀取选择性。
>
> `user_id` 保持无外键:搜索日志要能记录未登录访客(该列可空),
> 且日志表不该因为用户注销而被外键卡住删除顺序。

> 没有这张表，后续无法做效果评测和排序调优。埋点成本极低，补埋成本极高。

> **`trace_id` 是行为回传的落点**。`/search` 把它回给客户端，客户端在
> 点击 / 加购 / 下单时通过 `POST /search/events` 带回来，服务端据此
> `UPDATE ... WHERE trace_id = $1`。没有这一列，那个接口拿到 id 也无处可写。
>
> 三个行为列与语义检索层设计 §10.2 的在线指标一一对应：
> `clicked_id` → CTR@10，`carted_id` → 搜索→加购率，`ordered_id` → 搜索→下单转化率。
> **少一列就少一个指标**——早先只有点击与下单两列，而「搜索→加购率」是三个里
> 最灵敏的一个：加购比下单频繁得多，又比点击更能反映真实意图。

### 检索流水线

```
用户 query
  ├─► 向量召回  top-100   (pgvector HNSW, cosine)
  └─► 关键词召回 top-100  (tsvector / Meilisearch)
           ↓
      RRF 融合  → top-50
           ↓
      Reranker (bge-reranker-v2-m3, 本地推理) → top-20
           ↓
      业务重排：库存状态 × 活动有效性 × 毛利 × 销量 × 评分
           ↓
        最终 top-10
```

**业务重排是本系统区别于通用向量检索的核心**。缺货商品、已结束活动、
负毛利商品不应出现在前列，无论语义相似度多高。

## 九、用户域

`orders.user_id`、`user_coupons.user_id` 一直在引用一张不存在的表。补上，
并把这两处的外键补齐。**章节顺序不是迁移顺序**——`users` 必须先于 `orders`、
`user_coupons`、`carts` 建立。

### users

```sql
CREATE TABLE users (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id   BIGINT      NOT NULL REFERENCES merchants(id),
    phone         TEXT,                             -- 国内电商主登录态
    email         TEXT,
    password_hash TEXT,                             -- 可空：允许仅第三方登录
    nickname      TEXT        NOT NULL DEFAULT '',
    avatar_url    TEXT,
    gender        SMALLINT    NOT NULL DEFAULT 0,   -- 0未知 1男 2女
    status        SMALLINT    NOT NULL DEFAULT 1,   -- 1正常 2封禁 3已注销
    last_login_at TIMESTAMPTZ,
    deleted_at    TIMESTAMPTZ,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    -- 供 orders / user_coupons / user_identities / user_addresses / carts / uploads
    -- 做复合外键：买家属于某个商家，订单与地址不得挂到别家的买家身上
    UNIQUE (id, merchant_id)
);

> **这里没有 `user_no`**。早先给 users 也留了一个不可枚举对外编号，本轮删掉了——
> 它与 §1 收窄后的编号约定冲突，而且解决的是一个不存在的问题：
> 用户只能通过 `/me` 取到自己，接口层面**根本没有可枚举的入口**；
> 后台管理是已认证的内部人员，用自增 `id` 没有额外风险。
> 真正要防的是越权，那靠服务端按 `user_id` 强制过滤，不靠编号难猜。
>
> 如果将来出现「用户主页可被他人访问」这类场景，再加列不迟——
> 那时才真正出现了可枚举面。
CREATE UNIQUE INDEX uk_users_phone ON users(merchant_id, phone)
    WHERE phone IS NOT NULL AND deleted_at IS NULL;
CREATE UNIQUE INDEX uk_users_email ON users(merchant_id, email)
    WHERE email IS NOT NULL AND deleted_at IS NULL;
```

> **`password_hash` 为什么可空**：国内电商的主登录态是手机验证码和微信授权，
> 密码是可选项而不是必需项。硬性要求 `NOT NULL` 只会逼出一堆存着随机串的假密码。
>
> **手机号唯一索引为什么带 `deleted_at IS NULL`**：号码是会被运营商回收再放号的，
> 注销用户占着一个手机号，新主人就永远注册不了。带上软删条件后号码可以复用，
> 而历史订单仍然挂在旧的 `user_id` 上——**交易数据的归属永不改写**，
> 这跟 §1 里「交易数据永不删除」是同一条原则的两面。
>
> 有一条约束**没有**写进数据库，得说明白：「每个账号至少要有一种可登录的凭据」
> 跨了 `users` 和 `user_identities` 两张表，CHECK 做不到，触发器代价又太大，
> 只能由注册流程保证。这是本节唯一一条靠代码兜的规则。

### user_identities（第三方身份）

```sql
CREATE TABLE user_identities (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id   BIGINT      NOT NULL REFERENCES merchants(id),
    user_id     BIGINT      NOT NULL,
    provider    SMALLINT    NOT NULL,   -- 1微信小程序 2微信公众号 3微信开放平台 4支付宝 5Apple
    external_id TEXT        NOT NULL,   -- openid：同一个人在不同 appid 下不同
    union_id    TEXT,                   -- 微信 unionid：跨应用识别同一个人
    credential  JSONB       NOT NULL DEFAULT '{}',  -- session_key 等，密文存放
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    FOREIGN KEY (user_id, merchant_id) REFERENCES users(id, merchant_id)
);
CREATE UNIQUE INDEX uk_user_identities
    ON user_identities(merchant_id, provider, external_id);
CREATE INDEX idx_user_identities_user ON user_identities(merchant_id, user_id);
CREATE INDEX idx_user_identities_union
    ON user_identities(merchant_id, union_id) WHERE union_id IS NOT NULL;
```

> **为什么单独一张表而不是在 `users` 上加 `openid` 列**：微信的 openid 是
> **按 appid 隔离**的——同一个人在小程序、公众号、App 里拿到三个不同的 openid，
> 只有 unionid 能把他们认成一个人。一个用户对多条身份是本来就存在的事实，
> 拿列去表达迟早要加 `openid_mp`、`openid_app`、`openid_web` 这种字段。
>
> `UNIQUE (provider, external_id)` 说的是：**一条第三方身份只能挂在一个账号上**。
> 小程序静默登录拿到 openid 后照这个索引查，查到就是老用户，查不到就建号。
>
> 边界要写明：小程序先授权后绑手机号时，可能绑到一个已经存在的手机号账号上，
> 这时会出现「同一个人有两个 user」。**一期不做自动合并**，直接提示用户换绑。
> 账号合并要迁订单、迁券、迁余额、还要处理两边都有默认地址这类冲突，
> 是个能单独做一个迭代的活儿，塞进登录流程里只会做成半吊子。
>
> `credential` 存的是凭据，**明文落库不可接受**，字段里放的应是应用层加密后的密文；
> access_token 这类短期票据根本不该进数据库，放进程内缓存即可。

### user_addresses（收货地址）

```sql
CREATE TABLE user_addresses (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id   BIGINT      NOT NULL REFERENCES merchants(id),
    user_id       BIGINT      NOT NULL,
    receiver_name TEXT        NOT NULL,
    phone         TEXT        NOT NULL,
    province      TEXT        NOT NULL,
    city          TEXT        NOT NULL,
    district      TEXT        NOT NULL,
    street        TEXT        NOT NULL DEFAULT '',
    detail        TEXT        NOT NULL,          -- 门牌号等
    region_code   TEXT,                          -- 行政区划码，用于运费与配送范围计算
    postal_code   TEXT,
    tag           SMALLINT    NOT NULL DEFAULT 0, -- 0无 1家 2公司 3学校
    is_default    BOOLEAN     NOT NULL DEFAULT FALSE,
    deleted_at    TIMESTAMPTZ,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    FOREIGN KEY (user_id, merchant_id) REFERENCES users(id, merchant_id)
);
CREATE UNIQUE INDEX uk_user_addresses_default ON user_addresses(user_id)
    WHERE is_default AND deleted_at IS NULL;
CREATE INDEX idx_user_addresses_user ON user_addresses(merchant_id, user_id)
    WHERE deleted_at IS NULL;
```

> **部分唯一索引就是「每个用户至多一个默认地址」这条规则本身。**
> 不用在代码里写「设置默认前先把其他的置 false」再祈祷没人并发点两下——
> 真并发了，第二个事务会撞唯一冲突然后回滚，这正是想要的结果。
> 切换默认地址必须在同一个事务里「先清旧、再置新」，顺序反了会自己撞自己。
>
> 注意是「至多一个」不是「恰好一个」：新用户零个地址是合法状态，
> 数据库不该逼着注册流程凭空造一条。
>
> **地址与订单的关系是快照，不是外键**：下单时把这一行拍扁成 JSONB 写进
> `orders.receiver_snapshot`，之后用户改地址、删地址都不影响历史订单。
> 所以 `orders` 里没有 `address_id`——道理跟 `order_items` 存商品快照完全一样，
> 只是这里快照的是买家信息。地址用 `deleted_at` 软删，也是因为它算主数据。
>
> `region_code`（行政区划码）比省市区三个字符串更可靠：字符串会有「内蒙古」
> 和「内蒙古自治区」这种写法差异，而运费模板、偏远地区判定都要按区划做匹配。

### 买家会话

```sql
CREATE TABLE user_tokens (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id BIGINT      NOT NULL DEFAULT current_merchant() REFERENCES merchants(id),
    user_id     BIGINT      NOT NULL,
    token_hash  BYTEA       NOT NULL,   -- sha256(refresh_token 明文)
    expire_at   TIMESTAMPTZ NOT NULL,
    revoked_at  TIMESTAMPTZ,            -- 非空即已吊销（logout / 轮换后的旧值）
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    FOREIGN KEY (user_id, merchant_id) REFERENCES users(id, merchant_id)
);
CREATE UNIQUE INDEX uk_user_tokens_hash ON user_tokens(merchant_id, token_hash);
CREATE INDEX idx_user_tokens_live ON user_tokens(merchant_id, user_id, expire_at)
    WHERE revoked_at IS NULL;
```

> **这张表原本不在本文里，是实现时被契约逼出来的。**
>
> OpenAPI 的 `/auth/logout` 写着「服务端吊销当前 `refresh_token`」，而本节此前
> 只有 `users` / `user_identities` / `user_addresses`——买家侧没有任何会话表
> （§14 只给后台建了 `staff_tokens`）。**吊销必须有服务端状态**：无状态令牌
> 能做的只有「等它过期」，那在共用设备上就是退不掉登录。
>
> 两条路二选一，这里选了补表而不是把 logout 降级成「客户端丢弃令牌」：
> 降级会把一个真实的安全问题写进契约当成既定行为。
>
> **存的是 `sha256(明文)` 而不是明文**：库被读走时，拿到哈希换不出可用的刷新
> 令牌。唯一索引建在 `(merchant_id, token_hash)` 而不是单列——规矩三，而且它
> 顺带让「同一串哈希在两家店各有一行」成为合法状态。
>
> `access_token` 刻意是**无状态**的（签名里带租户，不落库），代价写明：封禁一个
> 账号之后，他手上那串 access_token 在过期前仍然可用（窗口 2 小时），而 refresh
> 会立刻失败。要做到即时封禁就得让每个请求查库，那是另一笔账。
>
> 过期行只增不减，清理任务归运维面（和超时关单是同一类定时任务）。

## 十、购物车

```sql
CREATE TABLE carts (
    id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id   BIGINT      NOT NULL REFERENCES merchants(id),
    user_id    BIGINT      NOT NULL UNIQUE,        -- 用户已隐含租户
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    -- 供 cart_items 做复合外键
    UNIQUE (id, merchant_id),
    FOREIGN KEY (user_id, merchant_id) REFERENCES users(id, merchant_id)
);

CREATE TABLE cart_items (
    id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id   BIGINT      NOT NULL REFERENCES merchants(id),
    cart_id    BIGINT      NOT NULL,
    sku_id     BIGINT      NOT NULL,
    product_id BIGINT      NOT NULL,
    quantity   INT         NOT NULL CHECK (quantity > 0),
    selected   BOOLEAN     NOT NULL DEFAULT TRUE,   -- 结算勾选态
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    FOREIGN KEY (cart_id, merchant_id)
        REFERENCES carts(id, merchant_id) ON DELETE CASCADE,
    FOREIGN KEY (sku_id, merchant_id)     REFERENCES skus(id, merchant_id),
    FOREIGN KEY (product_id, merchant_id) REFERENCES products(id, merchant_id)
);
CREATE UNIQUE INDEX uk_cart_items ON cart_items(cart_id, sku_id);
CREATE INDEX idx_cart_items_cart ON cart_items(merchant_id, cart_id);
```

> **购物车是规矩二收益最直观的一处**:`cart_items` 同时引用 `carts`、`skus`、
> `products` 三张父表,三条都改成了复合外键。
> 加购接口一旦把别家的 `sku_id` 放进本店的车,写入直接被拒——
> 而这条路径的入参恰恰**完全由客户端提供**,是最容易被构造越权请求的地方。
>
> `carts.user_id` 的 `UNIQUE` 保持原样(不加 `merchant_id` 前缀):
> `user_id` 已经蕴含租户,「一个用户一辆车」是全局成立的事实,
> 加前缀会把它弱化成「一个用户在本店一辆车」——两者在多店模型里等价,
> 但前者更强,没有理由主动放弃。
>
> `uk_cart_items` 同理保持 `(cart_id, sku_id)`:首列已是租户内标识,
> 而且下面那条 upsert 的 `ON CONFLICT (cart_id, sku_id)` 依赖它——
> 加前缀要连着改 SQL,却不多防一分。

`UNIQUE (cart_id, sku_id)` 让「加购」变成一条 upsert，不用先查再判：

```sql
INSERT INTO cart_items (cart_id, sku_id, product_id, quantity)
VALUES ($1, $2, $3, $4)
ON CONFLICT (cart_id, sku_id) DO UPDATE
    SET quantity = cart_items.quantity + EXCLUDED.quantity,
        updated_at = now();
```

### 购物车不存价格快照

这是刻意决策，不是漏了。

> 购物车是**意图清单**，不是报价单。一旦在 `cart_items` 里存下加购时的价格，
> 马上要回答一串没有好答案的问题：商品降价了，展示哪个价？涨价了，按哪个结算？
> 存了三个月的车，价格还算数吗？
>
> 而这些问题的正确答案永远只有一个——**以结算时的价格为准**。
> 既然如此，存下来的那个价格从第一天起就是个只会制造矛盾的冗余字段。
>
> 所以价格链路是：购物车只记 `sku_id` 与数量 → `/orders/preview` 时实时取
> `skus.price_cents` 并算优惠 → **快照只在下单那一瞬间产生**，写进 `order_items`。
> 从「无快照」到「有快照」的切换点，就是订单创建这一下。
>
> 代价有两处，都不大：
> 1. 购物车列表要 join `skus` / `products` 取当前价与状态。购物车行数天然很少
>    （几十行到头了），这个 join 不构成问题。
> 2. 用户看到的价格可能在他点「提交」那一刻刚变。解决办法是 `preview` 返回
>    `payable_cents`，提交时把它带回来做二次比对，不一致就中断让用户确认——
>    **宁可多一次确认，也不能在用户不知情的情况下按新价扣款。**
>
> 下架、删除的商品不从购物车里清掉，查询时标记为失效让用户自己处理。
> 替用户默默删东西，比让他看到一条划掉的商品更讨人嫌。

`carts` 这张只有 `user_id` 的表看着多余，留着是为了给「游客购物车」留位置——
未登录时车挂在设备标识上，登录后把 `cart_items` 整体改挂到用户的车上，
是个只动一个 `cart_id` 的操作。如果确定不做游客车，这张表可以砍掉，
把 `user_id` 直接放进 `cart_items`。

## 十一、退款与售后

`POST /orders/{order_no}/refunds` 在 OpenAPI 里已经定义、`Refund` schema 已经存在，
但一直没有表可落。这是本轮补得最要紧的一块。

### refunds（退款单）

```sql
CREATE TABLE refunds (
    id                 BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id   BIGINT      NOT NULL REFERENCES merchants(id),
    refund_no          TEXT        NOT NULL UNIQUE,   -- 对外编号，不可枚举
    order_id           BIGINT      NOT NULL,
    payment_id         BIGINT      NOT NULL,          -- 原路退回：退哪一笔
    user_id            BIGINT      NOT NULL,
    refund_type        SMALLINT    NOT NULL,   -- 1仅退款 2退货退款
    reason_code        SMALLINT    NOT NULL,   -- 1不想要了 2少发漏发 3商品损坏 4描述不符 5其他
    reason_text        TEXT,
    evidence_urls      TEXT[]      NOT NULL DEFAULT '{}',
    goods_amount_cents BIGINT      NOT NULL DEFAULT 0,  -- 退的货款，已按 §7 分摊倒算
    freight_cents      BIGINT      NOT NULL DEFAULT 0,  -- 退的运费
    amount_cents       BIGINT      NOT NULL,            -- 实退总额
    status             SMALLINT    NOT NULL DEFAULT 10,
    channel            SMALLINT    NOT NULL,            -- 冗余自 payments，对账用
    channel_refund_id  TEXT,                            -- 渠道退款流水号
    notify_payload     JSONB,                           -- 原始回调报文，永久保留
    reject_reason      TEXT,
    audited_at         TIMESTAMPTZ,
    refunded_at        TIMESTAMPTZ,
    created_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT chk_refund_amount CHECK (
        amount_cents = goods_amount_cents + freight_cents
        AND goods_amount_cents >= 0 AND freight_cents >= 0 AND amount_cents > 0
    ),
    -- 供 refund_items 做复合外键
    UNIQUE (id, merchant_id),
    FOREIGN KEY (order_id, merchant_id)   REFERENCES orders(id, merchant_id),
    FOREIGN KEY (payment_id, merchant_id) REFERENCES payments(id, merchant_id),
    FOREIGN KEY (user_id, merchant_id)    REFERENCES users(id, merchant_id)
);
CREATE UNIQUE INDEX uk_refunds_channel_txn
    ON refunds(merchant_id, channel, channel_refund_id)
    WHERE channel_refund_id IS NOT NULL;
CREATE INDEX idx_refunds_order ON refunds(merchant_id, order_id);
CREATE INDEX idx_refunds_user ON refunds(merchant_id, user_id, created_at DESC);
CREATE INDEX idx_refunds_pending ON refunds(merchant_id, status, updated_at)
    WHERE status IN (10, 30);   -- 待审核 / 退款中，给工单与重试任务用
```

> **为什么必须关联到具体某一笔 `payments`**：退款走的是原路退回，
> 渠道要求带上原支付的流水号。一个订单可能有多次支付尝试（这正是 §5 把
> `payments` 单独成表的理由），只挂 `order_id` 就答不出「退到哪张卡」。
>
> `uk_refunds_channel_txn` 与支付回调的 `uk_payments_channel_txn` **完全同构**：
> 渠道重复推送退款结果时，第二次写入撞唯一冲突，直接返回成功。
> 退款回调的重复率比支付回调只高不低——退款到账往往延迟数小时，渠道会反复推。
> 两者**同构到底**：本轮一起收进了租户内(`(merchant_id, channel, channel_refund_id)`)，
> 理由见 §5 payments 那段——渠道流水号只在单个商户号维度内保证不重复，
> 全局唯一会让另一家店的同号回调被静默丢掉，而丢掉的是一笔真实的退款到账。
>
> 三条父子引用(`order_id` / `payment_id` / `user_id`)本轮一并改成复合外键(规矩二)。
> 退款是全系统资金风险最高的写入路径，「退别家订单的钱」必须由数据库拒绝，
> 而不是靠审核流程记得核对。
>
> `channel` 是从 `payments` 冗余过来的。理由只有一个：对账是按渠道跑的，
> 每次都 join 回 `payments` 才能知道该找微信还是支付宝，不值当。

### refund_items（退款明细）

```sql
CREATE TABLE refund_items (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id   BIGINT      NOT NULL REFERENCES merchants(id),
    refund_id     BIGINT NOT NULL,
    order_item_id BIGINT NOT NULL,
    quantity      INT    NOT NULL CHECK (quantity > 0),
    amount_cents  BIGINT NOT NULL CHECK (amount_cents >= 0), -- 该行实退，已扣分摊优惠
    FOREIGN KEY (refund_id, merchant_id)
        REFERENCES refunds(id, merchant_id) ON DELETE CASCADE,
    FOREIGN KEY (order_item_id, merchant_id)
        REFERENCES order_items(id, merchant_id)
);
CREATE UNIQUE INDEX uk_refund_items ON refund_items(refund_id, order_item_id);
CREATE INDEX idx_refund_items_order_item ON refund_items(merchant_id, order_item_id);
```

> 这两条复合外键把「拿本店的退款单去退别家的订单项」钉死在数据库层。
> 它和上面那条 `chk_item_refund`(§5)是配套的:一个管「退的是不是自己的货」,
> 一个管「退的件数金额有没有超」。**两个问题都不该由业务代码独自回答。**
>
> `uk_refund_items` 保持 `(refund_id, order_item_id)` 不加前缀:首列已是租户内标识。

`refund_items` 是 `order_items.refunded_qty` / `refunded_cents` 的**流水来源**，
后者是前者的汇总。回写用条件更新，和库存扣减同构：

```sql
UPDATE order_items
   SET refunded_qty   = refunded_qty + $2,
       refunded_cents = refunded_cents + $3
 WHERE id = $1
   AND refunded_qty + $2 <= quantity
   AND refunded_cents + $3 <= amount_cents - discount_cents;
-- rows_affected = 0 ⇒ 超退，整个退款事务回滚
```

> **`refunding_qty`：契约里有，表里没有，它是算出来的**
>
> OpenAPI 的 `OrderItem` 暴露了 `refunding_qty`，客户端据此算「本行还可退几件」：
>
> ```
> 还可退 = quantity - refunded_qty - refunding_qty
> ```
>
> 它**不是持久化列**，而是在途退款的占用量，定义式为：
>
> ```sql
> SELECT COALESCE(SUM(ri.quantity), 0)
>   FROM refund_items ri
>   JOIN refunds r ON r.id = ri.refund_id
>  WHERE ri.order_item_id = $1
>    AND r.status IN (10, 20, 30);   -- 待审核 / 待买家退货 / 退款中
> ```
>
> **注意上面那条回写 SQL 的条件里不含它**：数据库只拦「已退 + 本次 > 总数」，
> 拦不住「已退 + 在途 + 本次 > 总数」。也就是说**数据库会放行契约算式禁止的超退**。
>
> 这是有意为之——把在途量写成持久化列，就要在退款单的每一次状态流转里维护它，
> 而那正是 `reserved_qty` 被删掉的原因（见 §4）。代价是这道校验只能在业务层做：
> 申请退款时必须在同一事务内跑上面那个 SELECT 并比对，不能只依赖 CHECK 兜底。
> **这条不写清楚，就会有人以为数据库已经拦住了。**

### 退款金额怎么算：§7 那句话的兑现

§7 说过「优惠必须按比例分摊到每个 order_item，否则部分退款算不出金额」。
这里就是它的兑现处。

设某行 `order_items` 的**实付净额** `net = amount_cents - discount_cents`，
购买 `quantity` 件，本次退 `k` 件：

```
若 refunded_qty + k < quantity ：本次退款额 = floor(net × k / quantity)
若 refunded_qty + k = quantity ：本次退款额 = net - refunded_cents（退干净剩下的）
```

> **余数为什么落在最后一笔**：整数分相除必有余数。买 3 件用了满 300 减 50 的券，
> 每件净额除不尽，如果每次都 `floor`，退完三件会比实付少几分钱——
> 而用户的感知是「我退完了，钱没退全」，客服工单就来了。
>
> 让最后一次退款吃掉全部余数，就保证了 **`SUM(refund_items.amount_cents) = net` 恒等**。
> 这和 §7「分摊余数全部给金额最大的那一项」是同一条思路：
> 余数必须有一个确定的归属，随便丢给谁都行，但不能没人管。
>
> 有一条恒等式**进不了 CHECK**，必须承认：
> `SUM(refund_items.amount_cents) = refunds.goods_amount_cents` 是跨行聚合，
> PG 的 CHECK 管不了。选择是在创建退款单的同一个事务里校验，加上对账任务兜底。
> 不用触发器，是因为触发器里做聚合会在售后高峰期把锁竞争放大到整张表。
> 这是本节唯一一条靠代码保证的恒等式，其余全部写进了约束。

**运费退不退，一期的规则**：未发货整单退，运费全退；部分退款不退运费
（运费是按整单算的，没有可分摊的口径）；退货退款的运费责任由客服在审核时
手工填 `freight_cents`。把这条写死在文档里，比让每个客服自己发挥强。

### 退款单状态机

```
10 待审核 ─通过(退货退款)─► 20 待买家退货 ─商家收货─► 30 退款中 ─渠道成功─► 40 已退款
   │                                                   ▲
   ├─通过(仅退款)───────────────────────────────────────┘
   │
   ├─驳回──► 50 已拒绝
   └─撤销──► 60 已取消      （20 待买家退货 超时未寄回 / 买家撤销，同样进 60）
```

```sql
CREATE TABLE refund_status_transitions (
    from_status SMALLINT NOT NULL,
    to_status   SMALLINT NOT NULL,
    PRIMARY KEY (from_status, to_status)
);
INSERT INTO refund_status_transitions VALUES
 (10,20),(10,30),(10,50),(10,60),(20,30),(20,60),(30,40);
```

注意 `30 退款中` **没有通向失败态的边**：渠道调用失败是重试，不是终态。
退款失败的钱不会凭空消失，只会是「还没退到」，最终要么成功、要么人工介入，
不存在「系统判定这笔钱不退了」这种状态。真需要人工中止时，走的是对账与工单，
不是状态机。

### 退款与订单状态的联动

退款单进入 `40 已退款` 时，在同一个事务里：

1. 回写 `refund_items` 对应的 `order_items.refunded_qty` / `refunded_cents`；
2. 累加 `orders.refunded_cents`；
3. 重算 `orders.refund_status`——退满 `paid_cents` 置 `3`，否则置 `2`；
4. 只有**未发货整单退**这一种情形，才顺带推进 `orders.status` 到 `60 已退款`
   （见 §5 的两维度说明）。

退款本身用 SAGA 编排（§6）：渠道退款、库存回补、订单金额回写三个分支。
其中渠道退款分支**没有补偿**——钱退出去了收不回来，所以它必须排在最后一个正向分支，
前面任何一步失败都还来得及整体回滚。这是编排顺序上的硬约束，不是可选优化。

券要不要回补，一期的规则是：整单退款回补（券回到 `1 未使用`，
若已过期则不回补，由客服补发），部分退款不回补——
券是整单门槛的产物，退一件之后原订单可能已经够不上门槛了，
回补等于让用户白拿一次优惠。

## 十二、幂等与异步任务

这两张表都不属于任何业务域，是整个系统的地基。

### idempotency_keys（接口幂等）

架构文档 §10 写了「重复下单强制 `Idempotency-Key`」，但没说这个键存在哪儿。存这儿。

```sql
CREATE TABLE idempotency_keys (
    scope         TEXT        NOT NULL,            -- 接口标识，如 'orders.create'
    merchant_id   BIGINT      NOT NULL DEFAULT current_merchant() REFERENCES merchants(id),
    subject_kind  SMALLINT    NOT NULL,            -- 1 买家(users.id) 2 后台操作员(staff.id)
    subject_id    BIGINT      NOT NULL,            -- 这把钥匙属于谁
    idem_key      TEXT        NOT NULL,            -- 客户端传来的 Idempotency-Key
    request_hash  TEXT        NOT NULL,            -- sha256(规范化后的请求体)
    status        SMALLINT    NOT NULL DEFAULT 0,  -- 0处理中 1成功 2失败
    response_code INT,
    response_body JSONB,
    expire_at     TIMESTAMPTZ NOT NULL,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (scope, subject_kind, subject_id, idem_key),
    CONSTRAINT chk_idem_subject CHECK (subject_kind IN (1, 2))
);
CREATE INDEX idx_idem_expire ON idempotency_keys(merchant_id, expire_at);
```

**主键就是那把锁**。并发同键时，先以「处理中」抢占插入：

```sql
INSERT INTO idempotency_keys (scope, subject_kind, subject_id, idem_key, request_hash, expire_at)
VALUES ($1, $2, $3, $4, $5, now() + interval '24 hours')
ON CONFLICT (scope, subject_kind, subject_id, idem_key) DO NOTHING;
-- rows_affected = 1 ⇒ 抢到了，执行业务，完事把 status / response_* 写回
-- rows_affected = 0 ⇒ 已存在，读出那一行，按下表处理
```

| 已存行 `status` | `request_hash` 相同 | `request_hash` 不同 |
|---|---|---|
| 0 处理中 | `409` 正在处理，让客户端稍后重试 | `422` 幂等键被复用 |
| 1 成功 | 回放 `response_code` / `response_body` | `422` 幂等键被复用 |
| 2 失败 | 回放当时的失败响应 | `422` 幂等键被复用 |

> **`request_hash` 是这张表里最容易被省掉、也最不能省的一列。**
> 没有它，客户端拿同一个键配不同的请求体，第二次会被当成重放**静默吞掉**——
> 用户以为下单成功了，实际什么都没发生。这类 bug 在测试环境几乎必然测不出来，
> 因为没人会故意复用幂等键；而线上客户端一个「重试时忘了换键」的 bug 就能触发。
> 宁可返回 422 让客户端显式失败，也不要假装成功。
>
> **主体进主键**，是因为幂等键由客户端生成，不能让 A 的键影响到 B；
> 顺带也堵掉了猜键探测别人订单的路。
>
> **主体是 `(subject_kind, subject_id)` 两列，不是一个 `user_id`**（迁移 00023）。
> 这张表原先只有 `user_id`，而后台那条路（M4 那 5 条 `/admin/` POST）要往里放的是
> `staff.id` —— `staff.id` 与 `users.id` 来自同一种自增序列（§14），
> 「把 staff_id 当成 user_id 用」会让 7 号员工与 7 号买家落在同一行上，
> 后果是其中一个人拿到另一个人的存档响应，而它不报错。
> 加一列之后那件事按构造不可能发生，代价是 2 个字节。
> `CHECK (subject_kind IN (1, 2))` 钉住取值：没有它，一个拼错的 `3`
> 会安静地开出第三个键空间。
> Go 侧的对应物是 `repository.IdempotencySubject`，只能由 `BuyerSubject` /
> `StaffSubject` 造出来 —— 「这把钥匙是谁的」于是成了一件拼错就编译不过的事。
>
> **三态里的 `0 处理中` 不能省**：没有它，第一次请求执行到一半时来的第二次请求
> 会查不到记录然后重复执行。抢占式插入 + 409 的组合，把「同时」变成了「先后」。
>
> 边界：`status = 2 失败` 是否允许换个请求重试？一期的选择是**失败也回放**，
> 最保守，绝不会重复扣款；确实要重试的场景，让客户端换一个新键。
>
> 代价：每个写接口多一次插入和一次更新；`response_body` 落库会让表长得很快，
> 靠 `expire_at` + 定时清理压住（24 小时足够覆盖客户端的重试窗口）。
>
> **主键里没有 `merchant_id`**：`subject_id` 已经蕴含租户（`users` 与 `staff` 都自带 `merchant_id`），
> 加一列只会让主键变宽，而抢占插入本来就是一次点查，谈不上选择性。
> 规矩三要收的是「跨租户会撞车的全局唯一」，这一条不属于。
> `idx_idem_expire` 则加了前缀——清理任务是按租户入队的 `jobs`，走 RLS，
> 注入的 `merchant_id = ...` 需要它打头。
>
> `subject_id` 按定义挂不了外键：它指向哪张表取决于 `subject_kind`。
> （换列之前那条「`user_id` 无外键」的豁免因此从 `db/tenancy.json` 的
> `fk_missing_ok` 里删掉了 —— `subject_id` 解析不到任何一张 `subjects` 表，
> 那条豁免留着两侧闸门都会报「该清理了」。）
> 这张表本来也是纯基础设施、随 `expire_at` 过期即删，
> 给它挂外键只会让清理任务和用户注销互相牵制。

> **平台作用域那一半还没有落点。** `merchant_id` 的默认值是 `current_merchant()`，
> 而平台级操作员（`staff.merchant_id IS NULL`）的会话里那个函数是 `RAISE` 不是 `NULL`，
> 所以 `POST /admin/merchants` 与 `POST /admin/staff` 这两条**可能跑在平台作用域**
> 的接口今天用不了这张表。它们的暴露面由各自的唯一约束兜住（重发第二次是 409，
> 不是一次重放的 201），挂账记在 `internal/handler/contract_test.go` 的
> `NotYetImplementedHeader` 上，靶子是 `TestPlatformScopedWritesAreNotYetIdempotent`。
> 把它做对要的是另一次 schema 决定（`merchant_id` 可空 + RLS 策略跟着改），
> 不在 00023 的范围里。

### jobs（任务队列就是一张表）

README 明确宣称「不需要 Redis、不需要 RabbitMQ，任务队列是一张表」。
兑现它。

```sql
CREATE TABLE jobs (
    id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id  BIGINT      NOT NULL DEFAULT current_merchant() REFERENCES merchants(id),
    queue        TEXT        NOT NULL,            -- 'product.understanding' / 'vector.text' ...
    job_key      TEXT        NOT NULL,            -- 业务幂等键，如 'product:12345'
    payload      JSONB       NOT NULL DEFAULT '{}',
    priority     SMALLINT    NOT NULL DEFAULT 0,  -- 大的先出队，**仅在租户内有意义**
    status       SMALLINT    NOT NULL DEFAULT 0,  -- 0待执行 1执行中 2已成功 3死信
    attempts     INT         NOT NULL DEFAULT 0,
    max_attempts INT         NOT NULL DEFAULT 5,
    run_after    TIMESTAMPTZ NOT NULL DEFAULT now(),  -- 退避后的可执行时间
    locked_by    TEXT,                            -- worker 标识，排查卡死用
    locked_at    TIMESTAMPTZ,
    last_error   TEXT,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT chk_jobs_attempts CHECK (attempts >= 0 AND attempts <= max_attempts)
);
CREATE UNIQUE INDEX uk_jobs_pending
    ON jobs(merchant_id, queue, job_key) WHERE status IN (0, 1);
-- 出队扫描。带上 merchant_id 是为了让公平调度的过滤在索引上完成，不回表
CREATE INDEX idx_jobs_dequeue ON jobs(queue, priority DESC, id)
    INCLUDE (merchant_id) WHERE status = 0;
-- 统计各租户在途数，集合很小（上限是 worker 数）
CREATE INDEX idx_jobs_inflight ON jobs(queue, merchant_id) WHERE status = 1;
CREATE INDEX idx_jobs_dead ON jobs(queue, updated_at DESC) WHERE status = 3;

-- 表膨胀的对策。队列表是高频 UPDATE + DELETE 的表，默认 scale_factor = 0.2
-- 意味着要等死元组堆到表的 20% 才清理，而一张常驻几百行、每天翻几十万次的表
-- 等于永远不触发相对及时的清理。症状是出队越来越慢，不报错。
ALTER TABLE jobs SET (
    autovacuum_vacuum_scale_factor  = 0.01,
    autovacuum_analyze_scale_factor = 0.01
);
```

> **`merchant_id` 带 `DEFAULT current_merchant()`**，与 `user_tokens`（§9）、
> `idempotency_keys`（§12）、`payments`（§5）、§8 那四张表同一条路子：
> 入队语句里因此不必出现 `merchant_id`，而 `scripts/check_query_tenancy.py`
> 不许 `db/queries` 里出现它。
>
> 在这张表上它还多一层意思。**`jobs` 是全库唯一一张「有 `merchant_id`、
> 那一列有真实语义、却刻意不挂租户策略」的表**（出队是跨租户的，见下面两条
> 出队语句；挂上策略之后 `busy` 那个 CTE 永远只看得见一家店，公平调度整个蒸发，
> 而且不报错）。于是「入队时的 `merchant_id` 只能是当前租户」这件事没有
> RLS 的 `WITH CHECK` 兜底，**全靠这个默认值**。
> 类别登记在 `db/tenancy.json` 的 `cross-tenant-queue`，完整论证在
> `db/migrations/00022_jobs.sql` 的文件头。
>
> `job_key` 的例子从 `'text_embedding:12345'` 改成了 `'product:12345'`：
> 一期落地的两个 processor（`text_embedding` / `search_text`）共用同一次判定、
> 同一个写回事务、同一格水位线（`MarkProductIndexed` 一次写两格指纹），
> 拆成两条任务会把一个事务拆成两个、把同一次乐观校验做两遍。
> 等 `image_embedding` 落地（输入是主图，与文本无关，失败也不该连累文本），
> 那时再按 processor 拆队列。

**出队语句**——「一张表当队列」能不能成立，全在这两条。

第一条是公平路径：**跳过在途任务已达上限的租户**。

```sql
WITH busy AS (
    SELECT merchant_id
      FROM jobs
     WHERE queue = $1 AND status = 1
     GROUP BY merchant_id
    HAVING count(*) >= $3          -- 每租户在途上限
)
SELECT * FROM jobs
 WHERE queue = $1 AND status = 0 AND run_after <= now()
   AND merchant_id NOT IN (SELECT merchant_id FROM busy)
 ORDER BY priority DESC, id
   FOR UPDATE SKIP LOCKED
 LIMIT $2;
```

第二条是兜底：**上面一条没取到、但确实还有待办时，去掉租户限制再取一次。**

```sql
SELECT * FROM jobs
 WHERE queue = $1 AND status = 0 AND run_after <= now()
 ORDER BY priority DESC, id
   FOR UPDATE SKIP LOCKED
 LIMIT $2;
```

> **为什么必须有第二条**：只有第一条的话，系统里只剩一个租户有任务时，
> 他会被自己的上限卡住，而 worker 全都空转。
> **公平的目的是防饿死，不是让机器闲着。**

> **为什么不做严格轮转**
>
> 严格的按租户轮转要么需要额外的游标状态，要么需要在
> `ORDER BY` 里放一个算出来的「在途数」——后者让排序无法走索引，
> 十万条待办时每次出队都要排序十万行。
>
> 「上限 + 兜底」这个组合是**可索引的**：`ORDER BY priority DESC, id` 不变，
> 多出来的只是对一个极小集合（`busy` 的行数上限就是 worker 数）做 `NOT IN` 过滤，
> 而且 `merchant_id` 在索引的 `INCLUDE` 里，过滤不回表。
>
> 代价诚实说一条：**极端倾斜下仍有额外扫描**——某个租户的十万条待办排在索引前面
> 且他正好 busy 时，索引扫描要走过这些行才能找到别人的。
> 真撞上了再按 `queue` 拆分区索引，或者到那个量级本来也该换专门的消息队列了。

> **`jobs` 的三个索引刻意不以 `merchant_id` 打头**，这是本文件里唯一一组
> 主动不守「索引前缀」的索引，理由就在上面那两条出队语句里：
> 出队是**跨租户**的公平调度，`ORDER BY priority DESC, id` 必须由索引直接给出顺序，
> 把 `merchant_id` 提到首列会把这个顺序碎成每租户一段，公平调度反而做不成。
> 所以 `merchant_id` 放在 `INCLUDE` 里（过滤不回表）或作为第二列。
>
> 前提也不一样：worker 出队以平台身份执行，不走 RLS 注入，
> 「每条查询都带 `merchant_id = ?`」这个推论的前提在这条路径上不成立。
> 唯一键 `uk_jobs_pending` 则是照规矩三收进租户内的，没有例外。

> **跨租户的 `priority` 没有意义。** A 商家标「紧急」的任务，
> 不说明它比 B 商家的普通任务更该先跑。加了公平调度之后，
> `priority` 的语义**收窄为租户内排序**——这一点要写清楚，
> 否则运营会拿它当全局插队用。

同一事务内紧接着把取到的行置为执行中：

```sql
UPDATE jobs SET status = 1, attempts = attempts + 1,
       locked_by = $1, locked_at = now(), updated_at = now()
WHERE id = ANY($2);
```

失败后按指数退避放回队列，次数耗尽转死信：

```sql
UPDATE jobs
   SET status     = CASE WHEN attempts >= max_attempts THEN 3 ELSE 0 END,
       run_after  = now() + (interval '1 second' * pow(2, attempts)),
       last_error = $2,
       locked_by  = NULL, locked_at = NULL, updated_at = now()
 WHERE id = $1;
```

> **`SKIP LOCKED` 是整个方案的胜负手。** 没有它，多个 worker 的
> `FOR UPDATE` 会排在同一批行上互相等待，队列直接退化成全局串行——
> 起十个 worker 和起一个一样快。加上它，被别人锁住的行直接跳过，
> 十个 worker 各取各的。这个子句是 PG 9.5 就有的东西，但它是
> 「用数据库当队列」从玩具变成可用方案的那个分界线。
>
> **`UNIQUE (queue, job_key) WHERE status IN (0, 1)`**：同一个任务在未完成时
> 不会重复入队。条件里必须包含 `1 执行中`，否则任务刚被取走就能再入一条。
> 而成功和死信的行不在索引里，所以同一个商品可以被反复重新嵌入——
> 重试中的任务回到 `0` 而不是新状态，也是为了让这个索引持续有效。
>
> **`idx_jobs_dequeue` 为什么不把 `run_after` 放在前面**：绝大多数待执行任务的
> `run_after` 早已到期，处在退避中的是少数。按 `(queue, priority DESC, id)` 组织，
> 让索引直接给出出队顺序、`run_after` 作为过滤条件回表判断，
> 比让索引先按时间排、再在内存里重排 `priority` 划算。如果哪天退避任务占比很高，
> 这个结论要重新测。
>
> **`priority` 的用处**：§9 的冷启动回填要「按销量降序、低优先级、不影响线上」——
> 回填任务入队时 `priority = -10`，线上实时任务是 `0`，
> 于是十万条回填任务永远排在新商品的理解任务后面，不需要单独起一个队列。
>
> **这套方案的上限，说实话**：单机 PG 大概能撑到每秒数千次出队，
> 万级 QPS 以下够用。但先撞上的往往不是吞吐，而是**表膨胀**——
> 队列表是高频 `UPDATE` + `DELETE` 的表，死元组堆积会让出队索引扫描越来越慢，
> 必须单独给它调 autovacuum 阈值（`autovacuum_vacuum_scale_factor` 调到 0.01 一类）。
> 成功的任务保留 7 天便于排查，之后由清理任务删除；死信永久保留。
> 真到了持续万级 QPS、或者需要跨机房投递的时候，再上专门的消息队列不迟——
> 到那天，业务量已经足够养得起一个 MQ 的运维成本了。

## 十三、文件存储

商品图、用户头像、退款凭证都需要落地。这一节定义存储的抽象与元数据表。

### Storage 接口抽象

三个方法即可覆盖全部需求：写入（返回 `storage_key`）、删除、生成访问 URL。
一期只实现本地磁盘 driver，S3 driver 留位置不实现。

> **为什么不直接上 MinIO**：README 的核心卖点之一是「只有一个数据库，
> 不需要 Redis / RabbitMQ / ES」。加对象存储要么破坏这句话，要么逼着改写卖点。
> 本地磁盘 driver 不是新增组件——它就是容器的一个卷。
>
> 更重要的是这与 dtmrs 那套「部署形态是配置，不是重写」**同构**：
> 形态 A 用本地磁盘，形态 B/C 换 S3，业务代码不改。
> 架构主张应当在每一处都成立，而不只在事务层成立。
>
> 代价诚实说两条：形态 A 多实例部署时要共享卷；换 S3 时确实会多一个组件。

### uploads

```sql
CREATE TABLE uploads (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    merchant_id   BIGINT      NOT NULL DEFAULT current_merchant() REFERENCES merchants(id),
    -- 上传者二选一，见 §14「uploads 的归属」：C 端用户或后台操作员
    user_id       BIGINT,
    staff_id      BIGINT      REFERENCES staff(id),
    purpose       SMALLINT    NOT NULL,   -- 1商品图 2头像 3退款凭证
    driver        SMALLINT    NOT NULL DEFAULT 1,  -- 1本地磁盘 2S3兼容
    storage_key   TEXT        NOT NULL,   -- driver 内部路径，不对外暴露
    content_type  TEXT        NOT NULL,
    size_bytes    BIGINT      NOT NULL,
    sha256        TEXT        NOT NULL,   -- 完整性校验与将来去重的预留，一期不做秒传
    referenced    BOOLEAN     NOT NULL DEFAULT FALSE,  -- 是否已被业务对象引用
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT chk_upload_size CHECK (size_bytes > 0),
    CONSTRAINT chk_upload_owner CHECK (
        (user_id IS NOT NULL) <> (staff_id IS NOT NULL)
    ),
    -- 供 product_images 做复合外键：让「把别家租户的文件挂到自己商品上」在物理上不可能
    UNIQUE (id, merchant_id),
    FOREIGN KEY (user_id, merchant_id) REFERENCES users(id, merchant_id)
);
CREATE UNIQUE INDEX uk_uploads_key ON uploads(driver, storage_key);
-- storage_key 里应包含 merchant_id 前缀，换 S3 driver 时按前缀分桶最省事
-- 孤儿回收任务扫描：创建超过 24 小时仍未被引用的文件
CREATE INDEX idx_uploads_orphan
    ON uploads(merchant_id, created_at) WHERE NOT referenced;
```

> **`uk_uploads_key` 刻意保持全局唯一**，它是 §2 那条分界线的第三类：
> `storage_key` 是磁盘或对象存储里的**物理路径**，两个租户写到同一个路径
> 就是真的互相覆盖文件——物理资源的唯一性不能按租户切，
> 与「`merchants.code` 全局唯一」同类。
> 上面那行注释本来就要求 `storage_key` 自带 `merchant_id` 前缀，所以现实里也不会撞；
> 但约束必须按「撞了会怎样」来定，不能按「大概不会撞」来定。
>
> `idx_uploads_orphan` 则加了前缀：孤儿回收挂在 §12 的 `jobs` 上，
> 而 `jobs` 是按租户入队的，扫描走 RLS。

> **`merchant_id` 带 `DEFAULT current_merchant()`**，与 §3 商品域那四张表同理
> （迁移 `00018_catalog_write_path.sql`）。
>
> **这张表由 `00018` 建出来，而它引用 `staff(id)`，所以它必须排在建 `staff` 的
> `00017` 之后。** 这不是凑巧的编号顺序：`db/tenancy.json` 的
> `fk_single_column_ok` 里登记着 `uploads(staff_id)`，Go 侧的过期检查一旦看到
> `uploads` 已在库中、而这条豁免没有对应的外键，就会报「该清理了」——
> 也就是说「`uploads` 已存在、`staff` 还没有」是闸门不接受的中间态。

> **为什么建表而不是只写磁盘返回 URL**
>
> 三个理由，每个单独都不够，合起来是充分的：
>
> 1. **归属校验**。退款凭证是隐私内容。只写磁盘意味着任何人拿到 URL
>    就能看别人的退货照片——而 URL 是会被转发、被日志记录、被截图的。
>    必须能查「这个文件属于谁」。
> 2. **孤儿回收**。用户上传了凭证但没提交退款申请，文件就永远躺在磁盘上。
> 3. **迁移能力**。将来换 S3 driver 要批量搬运存量文件，没有清单就搬不了。
>
> **孤儿回收的安全条件**：`referenced` 必须在**引用它的业务对象落库的同一个事务内**
> 置为 TRUE，而不是靠事后扫描反查。否则存在这样的窗口——退款申请刚提交、
> 清理任务恰好扫到、凭证被删，而用户界面上那条申请还带着一个 404 的图片链接。
> 清理任务只删 `NOT referenced AND created_at < now() - interval '24 hours'`，
> 24 小时是给「上传了但还没点提交」的用户留的余量。
>
> 清理任务挂在 §12 已有的 `jobs` 表上，不引入新机制。

> **一期只回收「传了没提交」的文件，不回收「引用后又解引用」的。**
> `referenced` 是单向布尔，没有置回 FALSE 的机制——退款申请被撤销、
> 商品主图被替换、头像被换掉之后，旧文件会永远停在 `referenced = TRUE`，
> 永远不被回收。
>
> 这是个已知缺口，不是疏忽。做解引用要在每处「替换/撤销」的业务逻辑里
> 精确地减引用，而一个文件可能被多处引用（同一张图既是主图又在详情里），
> 真正的解法是引用计数或反向扫描，两者都比一期该付的成本高。
> 代价是磁盘会缓慢增长——按一期的量级，这个增长速度远慢于「攒够数据再做」
> 所需的时间。列入 §14 待确认事项。

> **`purpose = 1 商品图` 的上传者是谁 —— 本轮（M4 任务 1）结清了。**
> 这条原先写着「取决于后台身份体系，而它还不存在」，并留了一个权宜：
> 后台账号先复用 `users`、在应用层标记。那句话现在是假的 —— §14 的 `staff`
> 与 `staff_tokens` 早已落地，本表的上传者也已经是 `user_id` / `staff_id`
> 二选一，由 `chk_upload_owner` 钉死。**那个权宜从来没有被执行过，
> 把它留在纸上只会让下一个人照着一个不存在的方案去写。**
>
> 结论：`purpose = 1 商品图` 走 `staff_id`，由 `POST /admin/uploads` 写入；
> `2 头像` 与 `3 退款凭证` 走 `user_id`，由 `POST /uploads` 写入。
> **两个路径，不是一个路径的两种用法** —— 哪一列被填上取决于这次调用带的是
> 买家 token 还是 staff 会话 token，而 OpenAPI 文件头约定 6（后台接口一律挂在
> `/admin/` 前缀下）存在的全部理由就是「按路径前缀挂鉴权中间件」。
> 同一个路径同时接受两种身份，等于把「这次是谁传的」变成一个要在 handler 里
> 靠 token 形状猜的东西 —— 而猜错的代价正是这条注一开始就在防的那种烂账。

> **限制写进契约，不要只写在代码里**：单文件上限 10 MB，允许的 `content_type` 为
> `image/jpeg` / `image/png` / `image/webp`。这两条必须出现在 OpenAPI 的接口描述里——
> 否则客户端只能靠试到 413 / 415 才知道边界。

## 十四、后台身份

后台操作员与 C 端用户是**两套身份**，不共表。

> **为什么不在 `users` 上加一个 role 列**
>
> 两者几乎没有共同点：认证方式不同（C 端是微信 openid / 手机号，后台是 token）、
> 生命周期不同、PII 暴露面不同。混在一张表里，意味着**每一个 C 端查询都要记得
> 过滤掉 staff**，而漏掉一次就是越权。`users` 加 role 是电商系统里很经典的一类
> 认证 bug 来源。
>
> 代价：多两张表，以及 `uploads` 的归属要能指向两种主体（见下）。

### staff

```sql
CREATE TABLE staff (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    -- NULL = 平台级（能建商家、跨租户运维）；非空 = 属于某个商家
    merchant_id   BIGINT      DEFAULT staff_scope_merchant() REFERENCES merchants(id),
    email         TEXT        NOT NULL,          -- 唯一标识，也是找回通道
    name          TEXT        NOT NULL DEFAULT '',
    role          SMALLINT    NOT NULL DEFAULT 2, -- 1管理员 2操作员
    status        SMALLINT    NOT NULL DEFAULT 1, -- 1正常 2停用
    created_by    BIGINT      REFERENCES staff(id), -- 谁加的；引导账号为 NULL
    last_login_at TIMESTAMPTZ,
    deleted_at    TIMESTAMPTZ,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX uk_staff_email
    ON staff(merchant_id, email) WHERE deleted_at IS NULL;
-- 平台级那一半：上面那条索引对它**不生效**（部分唯一索引里 NULL 彼此相异，
-- (NULL, 'ops@x.com') 能存在两行）。而邮箱是这套认证唯一的信任根，
-- 两个平台管理员共用一个邮箱意味着一封找回信能开出两把钥匙。
CREATE UNIQUE INDEX uk_staff_email_platform
    ON staff(email) WHERE merchant_id IS NULL AND deleted_at IS NULL;
```

> **`merchant_id` 上那个 `DEFAULT staff_scope_merchant()` 与两条策略函数**
>
> 下面认证流程 ④ 写着「新员工的 `merchant_id` 继承自调用者，**不接受前端传入**」。
> 这个 DEFAULT 是那句话的落点：省略这一列时它取当前作用域的租户，
> 于是 `db/queries/staff.sql` 里一个 `merchant_id` 都不必写，
> **调用方没有那个参数可以传错**——生成的 Go 函数签名里根本没有它。
> 理由与 §9 的 `user_tokens.merchant_id DEFAULT current_merchant()` 一字不差。
>
> 它取的不是 `current_merchant()` 而是 `staff_scope_merchant()`，因为这张表的
> 那一列**可空**，而 `current_merchant()` 永远不返回 NULL：
>
> ```sql
> -- 本事务是不是平台级作用域。没设 / 设成别的值一律为假 —— 默认必须是假。
> CREATE FUNCTION platform_scope() RETURNS BOOLEAN
> LANGUAGE plpgsql STABLE AS $$
> BEGIN
>     RETURN coalesce(nullif(current_setting('app.platform_scope', true), ''), 'off') = 'on';
> END $$;
>
> -- 本作用域属于哪个租户，**可以是 NULL**（平台级）。
> CREATE FUNCTION staff_scope_merchant() RETURNS BIGINT
> LANGUAGE plpgsql STABLE AS $$
> BEGIN
>     IF platform_scope() THEN RETURN NULL; END IF;
>     RETURN current_merchant();
> END $$;
> ```
>
> 两张表的租户策略都用它，而不是 §2 那条标准的列比较：
>
> ```sql
> CREATE POLICY tenant ON staff
>   USING      (merchant_id IS NOT DISTINCT FROM staff_scope_merchant())
>   WITH CHECK (merchant_id IS NOT DISTINCT FROM staff_scope_merchant());
> ```
>
> 为什么不能写成 `merchant_id = current_merchant() OR merchant_id IS NULL`：
> `USING` 在没有单独 `WITH CHECK` 时同时充当写谓词（§2 的实测表格里就有这一条），
> 于是那个 `OR` 在写侧的意思是「任何商家级管理员都能插入一行 `merchant_id` 为
> NULL 的 staff」——**给自己造一个平台管理员**。一条为了让平台级看得见自己而加的
> `OR`，把两级身份模型接成了一个提权入口，而且不会有任何报错。
>
> `IS NOT DISTINCT FROM` 则在租户作用域下逐行等价于标准策略
> （`NULL IS NOT DISTINCT FROM 42` 是假），在平台作用域下只解锁
> `merchant_id IS NULL` 那一抽屉——比 `BYPASSRLS` 窄得多，那正是想要的。
>
> 平台作用域**刻意不设** `app.merchant_id`：平台事务里误读别的租户表时，
> 那些表的策略会调 `current_merchant()` 而当场报错（§2），
> 而不是安静地返回零行。失败方向是关闭的，且看得见。

> **`staff` 是全文唯一一张 `merchant_id` 可空的表，规矩二在它身上必然失效。**
> 复合外键要求父子两边的 `merchant_id` 相等，而平台级操作员的那一列是 NULL：
> 一条 `FOREIGN KEY (created_by, merchant_id) REFERENCES staff(id, merchant_id)`
> 会让「平台管理员创建某家店的管理员」写不进去——而那恰好是 §14 认证流程 ② 的主路径。
>
> 所以 `created_by` 保持单列自引用外键。指向 `staff` 的另外两处
> （§5 `shipments.created_by`、§14 `uploads.staff_id`）同理。
> 代价写明白：**这三处的跨租户挂接数据库拦不住**，只能靠「`merchant_id` 从会话
> 上下文取、绝不从请求体取」那条纪律（见下方认证流程 ④）。
> 三处都是审计/归属字段，不在资金与库存的主链路上——这是接受它的全部理由。

**注意这张表没有 `password_hash`。** 整个后台不存在密码——认证走 token，
找回走邮箱，见下。少一个密码就少一整类问题：不用定密码策略、不用防撞库、
不用处理「密码写进日志」。

> **两级身份**：`merchant_id IS NULL` 是平台级操作员——他建商家、做跨租户运维，
> 数据库角色带 `BYPASSRLS`（见 §2）。`merchant_id` 非空则属于某个商家，
> 只能看见自己那一份数据。
>
> 这一层是多店模型必须有的：**部署者和商家不是同一拨人**。
> 单机自托管时两者恰好是同一个人，但那是巧合，不该固化进数据模型。
>
> `role` 在各自的层级内生效：平台级的 `role=1` 能加平台操作员，
> 商家级的 `role=1` 只能加自己店的员工。

> **一条进不了数据库的约束**：系统里必须至少有一个平台级管理员
> （`merchant_id IS NULL AND role = 1 AND status = 1`），且每个商家至少有一个
> 自己的管理员。这是跨行约束，`CHECK` 表达不了，只能在停用 / 降级 / 删除的业务逻辑里拦。
> 与 §11 那条 `SUM(refund_items...)` 恒等式一样，属于「知道它进不了约束，
> 所以必须写下来」的那一类。

### staff_tokens

```sql
CREATE TABLE staff_tokens (
    id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    staff_id     BIGINT      NOT NULL REFERENCES staff(id) ON DELETE CASCADE,
    token_hash   TEXT        NOT NULL UNIQUE,   -- sha256(明文)
    kind         SMALLINT    NOT NULL,          -- 1引导 2邮件登录链接 3会话
    expire_at    TIMESTAMPTZ NOT NULL,
    used_at      TIMESTAMPTZ,                   -- 一次性 token 用掉即失效
    revoked_at   TIMESTAMPTZ,
    last_seen_at TIMESTAMPTZ,
    created_ip   INET,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- 校验会话：按 hash 命中且未过期未撤销
CREATE INDEX idx_staff_tokens_live ON staff_tokens(staff_id, expire_at)
    WHERE used_at IS NULL AND revoked_at IS NULL;
```

> **本表按规矩一的豁免条款不带 `merchant_id`**（`scripts/check_tenancy.py` 的豁免清单
> 里写着理由：跟随 `staff`，租户归属由 `staff.merchant_id` 决定），
> 于是规矩二与索引前缀在它身上都无从谈起——没有那一列，复合外键拼不出来，
> 索引也没有前缀可加。`staff_id` 保持单列外键。
>
> 这个豁免比 `inventories` 那个更站得住：`staff.merchant_id` 本来就可空，
> 就算复制一份下来也表达不了「平台级 token」属于谁。
> 校验会话是按 `token_hash` 的点查，本来也不需要租户前缀来取选择性。

> **只存 hash，明文只在签发的那一瞬间存在。** 后台 token 能读全部订单与客户手机号、
> 能改价、能发起退款——它和支付密钥是同一个量级的东西。数据库被拖走时，
> 存明文意味着攻击者直接拿到全部后台权限。
>
> `kind = 1 / 2` 是一次性的（`used_at` 一置就作废），`kind = 3` 会话在过期或
> 撤销前可反复使用。三种共表是因为校验逻辑完全一样，分表只会让「查一个 hash」
> 变成查三次。

### 认证流程

**没有密码，也没有注册。** 三条路径：

```
① 首次启动（库里一个 staff 都没有）
   └─ 建平台级管理员（merchant_id = NULL, role = 1）+ kind=1 一次性 token
      └─ 明文打印到容器 stdout，24 小时有效
      └─ 用它换会话，并补上自己的邮箱

② 平台管理员开店
   └─ POST /admin/merchants {code, name, admin_email}
      └─ 建 merchant + 该店的 role=1 管理员
         └─ 给这个邮箱发 kind=2 链接，商家点开即完成首次登录

③ 日常登录（两级通用）
   └─ POST /admin/auth/email-link {email}
      └─ kind=2 一次性 token，15 分钟有效
         └─ 点开换成 kind=3 会话 token

④ 商家管理员加自己的员工
   └─ POST /admin/staff {email, role}
      └─ 新员工的 merchant_id 继承自调用者，**不接受前端传入**
```

> ④ 那条注释是关键：`merchant_id` 从会话上下文取，绝不从请求体取。
> 允许前端指定租户等于把越权做成了一个入参。

> **② 那一步是全系统唯一一次「一个事务里换两个作用域」**（落地于
> `repository.WithNewTenant`，迁移 `00021_open_shop.sql`）。
>
> 它不能拆成两步。先建店提交、再开一个事务建管理员，两者之间崩一次留下的是
> 一家**谁也进不去**的店：没有 `staff` 就没有后台会话，而应用角色在
> `merchants` 上没有 `DELETE`，连收拾都收拾不了。
>
> 两个作用域的顺序也是硬的：
>
> 1. **平台作用域**建 `merchants` 那一行。这一段里碰任何业务表都是 42501
>    （它们的策略要调 `current_merchant()`，而此时未设 → RAISE）。
> 2. **切到新店的租户作用域**再建那个管理员。这一步必须把
>    `app.platform_scope` 显式关掉 —— 不关的话 `staff_scope_merchant()`
>    仍然返回 NULL，于是「新店的第一个管理员」会被建成一行 `merchant_id`
>    为 NULL 的 `staff`，也就是一个**平台级管理员**。
>
> 第 2 步那个失败方向不报错、也没有任何约束拦得住：`staff.merchant_id` 本来
> 就可空，而 RLS 的写谓词 `merchant_id IS NOT DISTINCT FROM
> staff_scope_merchant()` 在平台作用域下对 NULL 行恰好为真。接口照样回 201，
> 响应体一个字都不会变（契约 201 的 schema 是 `Merchant`，里面没有 staff）。
> 所以它的执行者只能是一条**去库里看那一列**的测试。
>
> 与之配套的一次 GRANT 面取舍：`merchants` 是 tenant-root 类（没有 RLS，
> 防护全压在 GRANT 面上），`00005` 把它的写权限收成了零，而开店必须由应用
> 角色执行。`00021` 只把 `INSERT` 还回去，判据是 `00005` 记下的那三条实测
> 越权（改别家 `domain`、停用别家店、无租户上下文改 `merchants`）**全部需要
> `UPDATE`，一条都不需要 `INSERT`**。`shop_settings` 一并不给：开店不写它，
> 而 `domain` 恰恰是那三条里最贵的一条。完整论证与另外三条被否掉的路
> （管理员连接池、`SECURITY DEFINER` 函数、给 `merchants` 挂 RLS）
> 写在 `00021` 的文件头。

> **引导 token 为什么打印到 stdout 而不是发邮件**
>
> 全新部署时 SMTP 大概率还没配。如果登录的唯一入口是邮件，
> **操作员第一次就进不去后台**——而本项目的卖点是 `docker compose up` 一条命令。
>
> 打印到 stdout（Jupyter、Gitea 都这么做）让 SMTP 从「核心依赖」降级为
> 「可选功能」：不配邮箱也能用，只是找回麻烦。单机叙事因此保住。
>
> 代价：容器日志里会短暂出现一个高权限凭据。所以它 24 小时过期、用掉即失效，
> 并且只在库里一个 staff 都没有时才生成。

> **邮箱才是真正的信任根**
>
> 既然 token 丢了能用邮箱重发，那么**能收这个邮箱的人就拥有后台全权**，
> token 只是会话产物。承认这一点之后，设计就该按「短期会话」来做，
> 而不是「长期 token + 丢了重发」——两者安全强度完全一样（都取决于邮箱），
> 但后者要人保管一个长期有效的高权限字符串，它迟早会出现在便签、
> 聊天记录、截图和 shell history 里。
>
> 会话默认 7 天，可撤销。一次性链接 15 分钟。

### uploads 的归属：两种主体二选一

§13 的 `uploads` 原先只能指向 `users`，而商品图是后台操作员传的。改为：

```sql
    user_id  BIGINT,                          -- 原先是 BIGINT NOT NULL
    staff_id BIGINT REFERENCES staff(id),     -- 新增
    FOREIGN KEY (user_id, merchant_id) REFERENCES users(id, merchant_id),
    CONSTRAINT chk_upload_owner CHECK (
        (user_id IS NOT NULL) <> (staff_id IS NOT NULL)
    )
```

> **这段改动本轮已经落进 §13 的 `CREATE TABLE` 正文里了，这里只留说明。**
> 原先它是一段「替换原先的……」的补丁式片段，而 §1 说本文件是业务表 DDL 的
> 唯一真相源——补丁式片段让这句话对 `uploads` 不成立：机械检查读的是
> `CREATE TABLE` 那一块，看不见几百行之后的这段散文，于是
> `uploads.staff_id` 那条「知道自己拦不住跨租户挂接」的单列外键
> 既不在闸门视野里，也没法进豁免清单。**补丁只能存在于人的眼睛里，
> 而规矩二已经说过那是守不住的。**

> 用两个可空外键加一条互斥 `CHECK`，而不是 `owner_type + owner_id` 多态。
> 多态更灵活，但会丢掉外键完整性——删掉一个 staff 之后，
> 那些 upload 行会静默指向一个不存在的主体，而且数据库不会阻止。
>
> 这条 `CHECK` 把「上传者只能是其中一种、且必须是一种」写进了约束本身，
> 与本文档一贯的取向一致。
>
> **`user_id` 走复合外键，`staff_id` 走单列外键**，两者待遇不同不是笔误：
> `user_id` 变成可空之后复合外键仍然成立——`MATCH SIMPLE` 下任一列为 NULL 即跳过检查，
> 所以「这一行的主体是 staff」时它自动不生效，正是想要的语义。
> `staff_id` 则因为 `staff.merchant_id` 可空（平台级操作员）而配不出复合外键，
> 理由与 §5 `shipments.created_by` 完全一样。

对应到 §13 的用途表：`purpose = 1 商品图` 走 `staff_id`，
`2 头像` 与 `3 退款凭证` 走 `user_id`。

### 本轮（多门店 + 电子围栏 + 大区）新产生的待确认事项

14. **回填迁移是这一整块唯一不能靠「新数据走新路」绕过去的地方。**
    `orders.store_id` / `orders.region_id` / `inventories.store_id` /
    `inventory_logs.store_id` 全是 `NOT NULL`，所以迁移必须：
    给每个已有商家建出**一个默认大区 + 一家默认门店**（`is_default = TRUE`，
    `fence` 为 `NULL`），
    把现有 `inventories` 全部挂到那家店上，回填历史订单的两列与
    `store_snapshot`。**这一步跑失败的后果是整条迁移链断在这里**，
    而它依赖「每个商家都能推出一个门店名」这件没人定过的事——
    一期先用商家名，产品侧需要给一个正式口径。
15. **围栏的重叠与空洞没有任何检查。** 运营可以画出两个完全重合的围栏
    （命中两家，按距离排，这是产品明确要的），也可以在两个围栏之间留一条
    缝（落在缝里的用户静默回落到默认店）。后者是**看不见的**故障：
    没有人会去点那条缝。要做的话是一次 `ST_Union` + `ST_Difference` 的覆盖率
    报表，属于后台的运营工具，不是闸门。一期不做。
16. **改价没有历史。** `region_sku_prices` / `store_sku_prices` 只有当前值
    加 `updated_at`，改回去就查不到改过。`order_items.price_source` 能回答
    「这单走了哪一层」，回答不了「那一层当时是多少」——后者只能靠
    `order_items.price_cents` 这个快照倒推。真要做是一张价格变更流水表，
    与 `inventory_logs` 同构。一期不做，理由是价格变更的频率与库存不在一个量级。
17. **`products.total_stock` 在多门店之后是第三个 `reserved_qty`。**
    它是一个没有任何一处在维护的冗余汇总（`db/queries/search.sql` 的注释
    已经指出这一点），而现在它连「哪家店」都没有。该删，
    本轮没删的原因是它不在这次的改动面上、且主线有任务正在动商品域。
18. **门店维度的「相对调整」与第 12 条是同一个洞的放大。**
    按门店分之后，「给这家店进 100 件」这个动作的频率会乘以门店数，
    而现在仍然只有比较并设置（409 重试）。相对调整（`delta`）的优先级
    因此比第 12 条写下时更高。
19. **跨店履约没有设计。** 现在一单只能挂一家店（`orders.store_id` 是标量）。
    「这家店缺货、隔壁店有」要么让用户自己换店，要么把一单拆成两单——
    后者会牵动支付、退款、发货三条链路，是一个独立的产品，不是增量。
20. **`OrderPreview.items` 是内联 schema，于是它加不了字段。**
    本轮想给试算的每一行加一个 `price_source`（这一行的单价来自哪一层），
    加不进去：内联 schema 生成的是**匿名 struct**，而
    `internal/handler/order.go:92` 有一处按字段拼出来的 `[]struct{...}` 字面量，
    匿名类型多一个字段就不再可赋值（实测报错见契约里那一段）。
    这是「请求体不要用内联 schema」那条规矩的**响应侧同一个毛病**——
    内联类型没有名字，它的每一次演进都是一次破坏性变更。
    要做的是提成具名的 `OrderPreviewItem` 并同时改 handler，
    一个 commit 的事，但那属于实现任务。
    **在它落地之前，试算页回答不了「为什么这件在这家店便宜 20 块」**，
    只有订单落库之后（`order_items.price_source`）才说得清。

21. **自提与到店核销没有设计。** 有了门店与坐标之后，「到店自提」是最自然的
    下一个需求，而它要的是核销码、核销记录、以及 `orders` 上的一个履约方式维度。
    一期只做「按位置决定由哪家店发货」，不做自提。
