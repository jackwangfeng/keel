## 一、P0：SAGA 超时后幂等键永久锁死 → 重复下单 + 重复收款

### 根因回顾（一句话）

SAGA 超过 `sagaWaitTimeout = 15s` 时请求已经带着 `409 idempotency-key-in-flight` 返回了，
而 SAGA 之后**可能成功**；但没有任何地方记录「这把钥匙对应哪一单」，那个成功再没人回填 →
同一把钥匙恒定 409 → 客户端换新钥匙 → 第二单。**换钥匙正是幂等协议要它别做的事。**

### 改法：记录草稿单号，重试方按订单终态自愈

不去等那个已经返回的请求，而是**让下一次重试自己查库定论**。

| 层 | 改动 |
|---|---|
| `db/queries/orders.sql` | `ClaimIdempotencyKey` 的 `ON CONFLICT` 从 `DO NOTHING` 改为带条件的 `DO UPDATE`：**只回收**「`status = 0` 且 `expire_at` 已过」那一行 |
| 同上 | 新增 `MarkIdempotencyInFlightOrder`：`status` 仍是 0，把草稿 `order_no` 暂存进 `response_body` |
| 同上 | `GetIdempotencyKey` 多取一列 `expire_at` |
| `internal/repository/order.go` | `IdempotencyRecord` 加 `ExpireAt`；新增 `PendingOrderNo() string`；`OrderTx` 加 `MarkIdempotencyInFlightOrder` |
| `internal/service/order.go` | 落草稿的**同一个事务**里调 `MarkIdempotencyInFlightOrder` |
| 同上 | `replay()` 的 in-flight 分支从「只返回 409」改为按订单状态分派 |

### `replay()` 现在的分派逻辑

```
读到 status = 0（处理中）
├── 没有暂存单号  → 409 处理中（真在跑，或抢到键就崩了，等同现状）
├── 单号查不到     → 释放这把钥匙，报 409（客户端下次重试是全新尝试）
├── 订单 status = 0 → 409 处理中（SAGA 真在推动这一单）
├── 订单 status = 90 → 存失败存档，报业务失败（不再是 409）
└── 订单 status = 10/20 → 补成功存档并回放该订单（Idempotency-Replayed: true）
```

关键点在最后一条：**补上成功存档，这把钥匙才真正回到「成功」档**，从此同键重试走回放，
重复下单的路径被堵死。而且这个办法**不依赖当时那个请求还活着**——进程崩了、SAGA 还在跑、
客户端隔天才重试，都能自愈。

### 两个实现上的坑

1. **`archiveSuccessTx` / `archiveFailureTx`：不能在事务里再开事务。**
   `replay()` 跑在 `Create` 第一段那个事务里，而原来的 `archiveSuccess` 走
   `finishKey → s.repo.WithTenant`，后者会**再开一个事务**——同一个连接上嵌套开事务会
   **死锁自己**，实测 panic `reportSecondConn`。所以凡是已在事务里的调用点都必须用 Tx 版。

2. **`archivedBizErrFor`：失败原因本来就查不到，这是常态不是异常。**
   `branchNotes` 是进程内 map，原始请求返回时的 `defer s.notes.drop(gid)` 就把它删了，
   而自愈发生在之后（进程也可能重启过）。所以查不到时**不编业务原因**，落
   `ErrArchivedReasonUnknown`。

## 二、P1：协调器不可达返回裸 500 → 503 + Retry-After

停掉 `dtmrs` 后原本返回：

```json
{"status":500,"title":"服务内部错误","type":"https://keel.dev/problems/internal"}
```

**没有 `Retry-After`。** 500 的 type 是 `internal`，客户端读作「服务端写错了代码，重试也不会好」，
而协调器挂掉会自己恢复——退避后原样重试才是对的处置。同一故障域里库存服务不可用回的是
`409`/`503`，两种可自愈的依赖给出互斥语义，客户端没法用一套逻辑处理。

### 改法

| 层 | 改动 |
|---|---|
| `internal/dtm/remote.go` | 新增 `ErrUnavailable` sentinel；新增 `IsUnavailable(error) bool`；`do()` 在网络失败那条路上 `%w` 包上 sentinel |
| `internal/service/order.go` | 新增 `ErrCoordinatorUnavailable`；`SubmitSaga` 与 `WaitFinal` **两条路径**都先判不可达 |
| `internal/handler/order.go` | `coordinator-unavailable` → `503` + `Retry-After: 10` |
| `internal/problem/problem.go` | 新增 `TypeCoordinatorUnavailable` |

**`Retry-After` 是 10 秒，不是 in-flight 那档的 2 秒。** 协调器重启通常要十几秒，
客户端拿到钥匙重试时还会先撞一次「处理中」，退太快只是白跑一趟。

**503 的 detail 刻意不保证「这笔一定没下」**：协调器可能落库之后才断的连接。
detail 里写明「用同一个 `Idempotency-Key` 原样重试即可，服务端保证重试不会重复下单」。
让客户端以为「这次一定没下」而换新钥匙，那才是重复下单。

**`IsUnavailable` 故意不解析错误字符串**——那是重构时最容易静默失效的做法。
判据只有三类：`errors.Is(err, ErrUnavailable)`、`errors.As(err, &netErr)`、
`errors.Is(err, context.DeadlineExceeded)`。

## 三、顺带处理：`ErrOrderSagaFailed` 落 500 的老问题

`ErrOrderSagaFailed` 映射到 500 本身**是设计**（分支把失败原因弄丢了 = 服务端状态异常）。
真正的问题是：**自愈路径误用它来表示一次正常的补偿失败**。那一单被库存不足的补偿正常关掉了，
却因为原因查不到而报成 500。

现在新增 `ErrArchivedReasonUnknown` → **`503 order-outcome-unknown`**，语义是：
「结果确定不成功（商品没卖出去、库存已回补、没有重复下单），但原因暂时无法查证」。
不发 500（那读作「服务端写错了」），也不编业务原因（那会让客户端显示一条它无法处理的错误）。

配套：`replayableFailures` 加了 `outcome_unknown` 条目——**不加会被兜底写成 `saga_failed`，
回放时又变回 500**。

  （可参考库存侧 `inventory_logs.reason` 是跨进程持久化的）。这属于设计取舍，本次不动。
- **没加后台 reconciler。** 定期扫 `status = 0` 的行与 `trans_global` 比对修正。
  自愈已经覆盖了「客户端重试」这条主路径；没有客户端重试的遗留行要靠它兜。
  代价是引入一个新的后台任务与它自己的并发判据，本次先不做。
