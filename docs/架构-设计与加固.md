# Keel 架构：设计原则与一次系统性加固

> 这份文档讲两件事：Keel 的架构**凭什么**称得上扎实，以及 2026-09-30 做的一次全面架构审查翻出了什么、怎么修的、
> 怎么证明修好了。数字全部来自仓库与实测，可以复现。细节设计见[总体架构](./电商系统-总体架构.md)、
> [数据模型](./电商系统-数据模型设计.md)、[微服务拆分方案](./电商系统-微服务拆分方案.md)。

## 一、设计原则：让错误写不出来，而不是靠人记得

好的架构不是「没有 bug」，而是**把最容易犯、后果最重的那几类错误，从结构上变得写不出来**，
再用机械检查把剩下的挡在合并之前。Keel 的几根主梁都是这个思路：

| 容易出的错 | 常见做法 | Keel 的做法 |
|---|---|---|
| 前后端字段对不上 | 靠人同步、靠联调发现 | 一份 OpenAPI 契约（141 个接口、197 个数据结构）生成 Go / TypeScript / Dart / UTS 四端类型；CI 把生成物重新生成到临时目录逐字比对 |
| A 店看到 B 店的数据 | 每条 SQL 记得加 `WHERE merchant_id` | 每张业务表带 `merchant_id`，父子关系用 `(id, merchant_id)` 复合外键钉死，PostgreSQL 行级安全兜底；三道检查分别核对建表语句、真实库的系统目录，并**禁止**查询里手写租户过滤（否则行级安全有没有生效永远测不出来） |
| 下单扣了库存却没建单 | 一个大本地事务，或外挂协调器 | 内嵌 Rust 分布式事务协调器 dtmrs，下单是 SAGA（扣库存、核销券、建单，失败逐一补偿），子事务屏障挡住重复与乱序 |
| 单体长大后要重写 | 一开始就上微服务，或者长大了推倒重来 | 同一段编排代码在单进程与微服务两种形态下只差一行地址（`local://` ↔ `http://`）；库存已拆成独立进程、独立库，演示站就这么跑 |
| AI 乱动数据 | 不让 AI 碰写操作，或者直接放权 | AI 是有角色、有管辖范围的员工账号；每次写操作都是带证据的提案，人批准后才以它的身份幂等执行，全程留痕 |

这些约束都有测试或脚本守着，写错了 CI 当场报错。仓库里 Go 业务代码约 9 万行，测试代码约 5 万行（840 个测试函数），
另有 178 条 Flutter 测试、100 条后台测试、14 道提交前检查。

## 二、一次系统性审查（2026-09-30）

功能暂停堆砌之后，按三个方向做了一次只读的架构审查：后端分层与装配、数据层与服务拆分、客户端与工程体系。
每条发现都要求附代码位置作证据，关键几条再单独实测核实。结论是**骨架扎实**（分层单向依赖、无循环；
多租户在连接复用下安全；对外调用全在数据库事务之外；拆分边界有测试双向核对），但有一批「每一步看着都对、
合起来有坑」的问题，在低并发的测试与演示环境里永远碰不到，一上量就会出事。

下面是修掉的部分，按「会不会出事」排序。

### 2.1 会出事的

**事务里又向连接池要第二条连接 → 池耗尽自锁。** 退款审核、收货、多收款退回在事务里读支付回调密钥时，
没用当前事务的连接，而是从池里另取一条。连接池默认约 4 条：4 个退款同时处理，各自占住一条等第二条，全体卡死到超时，
期间整个服务都拿不到连接。
- 修：密钥改走本事务读取。
- **防线**：`internal/repository/txguard.go`。开事务期间记下「本 goroutine 在这个池上开着事务」，所有直接用池的方法都经过检查；
  测试里一旦在事务中再向池取连接就直接 panic（带方法名），生产里记错误日志。这道防线在全量测试里又抓出一处同类问题（AI 提案效果复盘），一并修掉。
- **证明**：回归测试把池设为 2 条，并发 8 个退款审核 / 收货，全部成功；修复前这条测试超时失败。

**停机被硬掐断，HTTP 没有超时。** 进程不处理 SIGTERM，重启时后台任务与内嵌协调器被直接杀掉；HTTP 服务没有读请求头超时，慢速连接能一直占着连接。
- 修：收到信号后按序收尾——停止接新请求 → 等在途请求完成 → 停后台任务并等它们退出 → 关协调器 → 关连接池（宽限期默认 20 秒）；
  加请求头读取超时与空闲超时（刻意不设整体写超时：商品导入、报表导出、上传是正当的长请求）；公网新增 `/readyz`（检查数据库）。

**数据库没有任何超时兜底。** 一个卡住的扣库存事务会锁住那件商品，同一 SKU 的所有下单排队、各占一条连接，直到池耗尽——秒杀时会被放大。
- 修：连接启动参数默认 `statement_timeout` 15 秒、`idle_in_transaction_session_timeout` 30 秒；扣减与 SAGA 分支的事务里 `lock_timeout` 3 秒，
  排队超时的那一笔失败并由协调器重试，而不是整站陪着一行锁一起等。

**公开仓库的 PR 会在服务器上执行代码。** 仓库公开、CI 跑在自托管 runner（同机有演示站与其他项目），而原先只有首次贡献者需要审批。
- 修：所有外部贡献者的 PR 都需维护者批准；每个 CI 任务加判断，来自 fork 的 PR 一律不在自托管 runner 上跑。

**后台任务崩一个，整个进程陪葬；多实例时每个实例各跑一份。**
- 修：新包 `internal/worker` 统一管理 15 个后台任务：panic 只重启该任务（退避 1 秒到 1 分钟），停机时等待退出；
  扫描、对账、刷新这类 10 个任务用 PostgreSQL advisory lock 选主，只在一个实例上跑；投递、索引这类消费者多实例并行（本来就用 `SKIP LOCKED` 出队）。

**调用库存服务没有熔断。** 库存服务卡住（而不是拒绝连接）时，商品列表、试算、购物车每个请求都要多等满 5 秒才降级。
- 修：读请求超时 0.8 秒；连续失败 5 次熔断，10 秒后放一个探测请求；写操作与下单 SAGA 不受影响。连接复用上限从默认的 2 提到 64。

### 2.2 数据量上来会变慢的

**行级安全让索引失效。** PostgreSQL 在有行级安全的表上，只会把 leakproof 的条件下推成索引条件；全文检索的 `@@`、JSON 取值 `->>`、`LIKE` 都不是。
结果是关键词搜索、按手机号查订单都只能先扫出整家店的行、再逐行过滤。这一条最隐蔽：不开行级安全测，一切正常。
- 修：手机号冗余成普通列（触发器维护）加索引；类目前缀匹配改成区间比较（leakproof）；关键词召回放进一个 SECURITY DEFINER 函数，
  函数内显式按当前商户过滤、只返回命中 id，外层回表仍受行级安全约束；执行它的角色权限压到最小（只读商品表 3 列、不能登录、没有成员），
  并有「A 店搜不到 B 店商品」的测试。
- 以应用角色（不能绕过行级安全）实测，每店 4 万行：

| 查询 | 改前 | 改后 |
|---|---|---|
| 商品列表第一页（有货在前） | 713 ms | 0.08 ms |
| 按收货手机号查订单 | 38 ms | 0.29 ms |
| 关键词搜索召回 | 30 ms | 1.0 ms |
| 后台订单按单号 / 手机号（通用执行计划） | 7.7–14.6 ms | 0.03–0.05 ms |

每一处都有以应用角色跑 EXPLAIN、断言用到了对应索引的测试。

**派生数据用定时全量刷新。** 商品列表「有货在前」依赖主库里一份「门店 × 商品 → 有没有货」的冗余标记（库存在另一个库，联不了表），
原来每分钟把所有门店、所有 SKU 全量刷一遍，开销是门店数 × SKU 数 × 实例数。
- 修：库存服务在扣减 / 回补 / 调整的同一个本地事务里，只在可售数**跨过 0** 时登记一条 dtmrs 二阶段消息；主服务收到后不信消息内容，
  回库存服务读最新数量再算。消息与库存改动原子提交（改了就一定通知到），乱序、重复都不影响结果；全量刷新降为每小时一次的兜底。
- 同一套办法用在**活动配额同步**上：原来是先调库存服务、再写活动表，中间失败两边就不一致。现在活动与消息同事务提交，库存服务暂时不在也能保存，恢复后自动对上。
- 演示站实测：把一个 SKU 从 27 扣到 0 再加回，两次跨 0 各一条消息，接收方各执行一次，标记先变无货、再变有货。

**只增不删的表。** 幂等键、检索日志、AI 工具调用记录、库存流水都没有保留期。
- 修：按表设保留期分批清理（每批 5000 行、每轮有上限，不开长事务），单实例运行；上线第一轮删掉 2080 条过期幂等记录。

**迁移会锁表。** 旧迁移里有大表建索引不用 `CONCURRENTLY`、在锁表状态下全表更新的写法。已上线的不改，但定了规矩并机械化：
`CONTRIBUTING.md`「迁移怎么写」（先扩后收、大表索引不锁表、回填不进 DDL 事务），`scripts/check_migrations.py` 在 CI 里检查新迁移。

## 三、沉淀下来的约定

审查的价值不只是修掉这些问题，更在于把它们变成**以后不会再犯**的约定：

1. **派生数据同步**（写进[总体架构](./电商系统-总体架构.md)「七、一致性策略」）：跨服务或跨库的派生数据，默认用二阶段消息同步。
   三条前提：接收方把消息当「去查一下」、回源读最新状态；只在有意义的变化时发；保留低频对账兜底。按时间触发的任务、同库同事务能改完的、发给外部系统的，不适用。
2. **适当冗余，但每份数据只有一个主人**：冗余只给读和排序用，扣库存、付款、退款这类要紧判断一律回到源头、在锁住的行上做；冗余随时可以整张删掉重建。
3. **事务里不向池要第二条连接**：有防线，测试里违反即失败。
4. **迁移规矩**：有检查脚本，违反即失败。
5. **后台任务**：统一注册到 `internal/worker`，扫描类默认选主。

## 四、诚实地说：还没做的

- dtmrs 屏障表的清理（要先从协调器拿到已结束事务的清单，否则删错会让补偿被误判成空回滚）；
- 拆分部署下库存流水的清理（库存进程目前不跑后台任务；保留期 180 天，量不急）；
- 关键词搜索的 SECURITY DEFINER 角色需要超级用户才能建，托管数据库上可能要换方案；
- 维护成本类：演示站部署脚本收进仓库、配置集中与启动校验、请求 ID / 访问日志 / 指标等可观测性、数据访问接口按领域收窄。
  （已冻结的 uni-app x 客户端已于 2026-09-30 下线，最后状态见 tag `uniapp-final`。）

这些都记在 [PROGRESS](../PROGRESS.md)。
