## 一、这个项目为什么存在

开源电商系统已经很多（mall、Saleor、Medusa、Shopware）。做第五十个没有意义。
本项目的存在理由是三条别人没有的东西：

**1. 自带分布式事务内核**
交易一致性由自研的 [dtmrs](https://github.com/jackwangfeng/dtmrs) 保障——
Rust 实现，支持 SAGA / TCC / 二阶段消息 / XA / workflow。
其他开源商城要么回避分布式事务（单体大事务），要么依赖外部 Seata / DTM。

**2. AI 贯穿经营全链路，且全部本地推理**
进货（商品结构化、同款归并、合规检查）、卖货（语义检索、对话导购、拍照搜同款）、
经营（销量预测、补货建议、自然语言查数据）、反馈（评价归因、退货归因）——
每个环节都有，全部本地推理。**embedding 这一半已经跑在自研推理引擎
[infero](https://github.com/jackwangfeng/infero) 上。**
**零外部 API 调用，商品数据与客户信息不出网，无按量计费。**

> **「全部跑在自研推理引擎上」这句话，embedding 这一半从 M4 起是真的了。**
>
> 这条注的上一版（`1eec464`）说 infero 接不上 Keel，缺两样：没有 embedding 出口、
> 没有 CPU 后端，所以路线是「M3–M6 用 Python 那个，M7 起接 infero」。
> **第一个缺口补上了，而且不等 M7 就换过来了；第二个 infero 2026-09-26 也补上了，但速度还不够 Keel 用（见下面「那个缺口」）。**
> 下面逐条说清今天的事实。
>
> **已经换过去的：`/v1/embed` → infero 的 `/v1/embeddings`。**
> 索引侧与查询侧的向量现在都由 infero 算，模型是 Qwen/Qwen3-Embedding-0.6B
> （safetensors，非量化 F16），跑在一块 RTX A4000 上。
> M3 那个 Python 服务（FastAPI + torch CPU + BGE-M3）就此退役 ——
> **这个系统只维护一个推理引擎实现**。CPU 那条路不靠第二个引擎补，
> 靠给 infero 加 CPU 后端 —— 它已经有了、数值与 GPU 一致，但单线程、单条 5 秒，今天还切不过去（见下面「那个缺口」）。
>
> **DDL 一行没动。** Qwen3-Embedding-0.6B 原生 1024 维，正好对上
> `product_text_vectors.embedding vector(1024)`。pgvector 的维度写在列类型上，
> 换模型通常等于新建表 + 双写 + 原子切换（语义检索层 §2.2 的影子表方案）——
> 这次那一步免了，是这轮切换最大的一笔便宜。
>
> **延迟：那笔算错过三次的账，第一次算平了。** §8 给 query embedding 的预算是
> 15 ms。本机实测（RTX A4000，warm，中位数）：
>
> | | 单条 | 批 32 | 批 64 |
> |---|---|---|---|
> | Python + BGE-M3 + CPU | 62 ms | 33.0 ms/条 | 31.3 ms/条 |
> | infero + Qwen3-Embedding-0.6B + GPU | **7.0 ms** | **1.60 ms/条** | **1.56 ms/条** |
>
> 单条 7 ms 是第一次真的落在 15 ms 预算之内（此前 CPU 上是 62 ms，
> 也就是「这套配置能用于索引，不适合直接挡在搜索请求前面」）。
> 批量吞吐差 20 倍。
>
> **语义质量：margin 从 +0.19 涨到 +0.29。** 判据见 keel-integration.md 第二条
> （两条相近、一条无关，余弦差要 > 0.10）。BGE-M3 实测 +0.19，
> Qwen3-Embedding-0.6B 实测 **+0.2917**。
>
> **rerank 那一半还没换，所以卖点只能说一半。** `/v1/rerank` infero 已经实现了
> （用 Qwen3-Reranker-0.6B，解码器架构的官方打分配方，不是 bge-reranker 那种
> cross-encoder），但 Keel 这边 M5 才用得上它，现在接进来就是一段没人调用、
> 也没有闸门守着的代码。所以 §1 那句卖点现在写的是「embedding 这一半」，
> 等 M5 把 rerank 接上再说「全部」。
>
> **那个缺口：CPU 后端 —— 有了，但还不够 Keel 用。** infero 2026-09-26 加上了 CPU 后端
> （infero `0bcd714`，编译开关 `--features cpu`，只覆盖 Qwen2 / Qwen3 这类稠密解码器，F32 / F16 / Q8_0）。
> 2026-09-29 在本机（20 核）用 Keel 的同一份权重 Qwen3-Embedding-0.6B 实测：
>
> | | GPU（CUDA，RTX A4000） | CPU 首版（单线程） | CPU 当前（infero 2026-09-29 四轮优化，**未提交**） |
> |---|---|---|---|
> | 向量与 GPU 的余弦 | — | ≥ 0.999999 | **0.9999995–0.9999997** |
> | `model` / `model_version` | `Qwen3-Embedding-0` | 相同 | 相同（已存的向量不会被判为过期） |
> | 单条短查询 | ~8 ms | ~5,000 ms | **450–1,000 ms**（机器负载 20–30；单线程 CPU 时间 0.87 s） |
> | 60 字查询 | — | — | 1.0–1.9 s |
> | 64 条一批（索引侧的批大小） | 正常 | ~239 s | 5.9–10.2 s |
> | Keel `make test-engine` 三条判据 | 通过 | 归一化过、其余两条 60 s 超时 | **全部通过** |
> | 启动 / 常驻内存 | — | ~1.4 s / 1.3 GB | ~2.5 s / 3.5 GB（F16 权重启动时转 F32 常驻） |
>
> 四轮优化（infero 会话做，Keel 这边验收）：推理核并行化 → 消除重复解码 → 换 `gemm` crate 做矩阵乘 →
> F32 权重启动时预转常驻。本机一直被别的任务占着（负载 20–30），读数随负载翻倍波动，**250 ms / 430 ms / 5 s
> 三条线还没在空闲时段验收过**。
>
> **正确性达标，端到端判据全过**：按 infero docs/keel-integration.md §4 Keel 定的那条线，它不是「另一个模型」，是同一个模型的
> 另一个后端。**速度还没验收达标**（下面是首版时的分析，当前版已快了 10–40 倍，差距缩到 2–4 倍、且受负载影响）：查询侧预算 250 ms（`DefaultQueryEmbedTimeout`），CPU 版每一次都超时 →
> `/search` 全部走关键词降级；索引侧一批 64 条要 4 分钟，远超 5 秒的单次超时。那条线当时写的是「速度不作要求，
> 62 ms 那个量级就行」—— 5 秒差了两个数量级，瓶颈是单线程。**所以今天 Keel 仍然按「没有 CPU 后端」部署**：
> 下面三条后果照旧成立。等 infero 的 CPU 后端提速（已请 infero 那边定位）后重测这张表，达标了再切。
> （起 CPU 版时 `--max-seqs` 要与 GPU 版一样给 32：给 8 时 64 条一批会 500「24 sequences want logits, the limit is 16」，
> 那是启动参数，不是后端的限制。）
> 复现：`cargo build --release -p infero-server --no-default-features --features cpu --target-dir target-cpu`，
> 起在另一个端口，`KEEL_EMBED_ENDPOINT=http://127.0.0.1:<端口> make test-engine`。
>
> - **CI 里再没有任何东西在跑真引擎。** GitHub 托管 runner 没有 GPU，原来那个
>   `inference` job 已经删掉（`.github/workflows/ci.yml` 文件头「没有覆盖到的」
>   第一条记着这件事）。三条判据现在只有人在 GPU 机器上手动跑。
> - **`docker compose up` 不再能一条命令起全栈。** infero 跑在 compose 之外的
>   宿主机进程里（`scripts/infero-up.sh`），理由是显存账：一块卡同时只装得下
>   一份引擎，而容器化换来的只有那一条命令。叠加层
>   `compose.infero.yaml` 只负责把 app 的 `KEEL_EMBED_ENDPOINT` 指过去。
> - **无 GPU 的部署今天没有语义检索 —— 但它跑得起来。** 这两句要一起读，
>   漏掉后半句就会以为没有卡就用不了这个系统。
>
>   没有 GPU 的机器照样 `docker compose up`、照样能下单能搜索：不配
>   `KEEL_EMBED_ENDPOINT` 时 `/search` 走 §8 的纯关键词降级链（bigram 召回 +
>   业务重排），返回 200，`explain: true` 如实列出这一次真正跑过的阶段。
>   **那是一条设计好的、有执行者的路径，不是故障。** 缺的是语义那一路：
>   搜「显瘦的裙子」这种和商品标题没有字面重合的词，召回会明显变差。
>
>   **而且今天只有这一种形态，没有第二种。** §6 形态 A 原本写着「无 GPU 时降级为
>   小模型 CPU 推理，搜索仍可用」—— 那句话描述的是已经退役的 Python 服务，
>   现在已经改掉。让没有卡的机器也有语义检索，正解是 infero 的 CPU 后端 ——
>   **它 2026-09-26 有了，数值与 GPU 一致，但单线程、单条 5 秒，今天还用不上**（见上面那张表）。
>
> **换引擎时发现的那个 bug，记在这里因为它是判据存在的理由。**
> infero 的 tokenizer 不执行 checkpoint 自带的 `post_processor`，
> 而 Qwen3-Embedding 的 last-token pooling 要取的正是那条规则追加的
> `<|endoftext|>` 那一行。不补这个 token，本机实测 margin 只有 **+0.0960**，
> 低于 0.10 的下限 —— 而维度对、L2 范数对到小数点后 9 位、model 名对、HTTP 200，
> **形状断言一条都不会红**。这正是 keel-integration.md 拿「哈希伪引擎 margin
> −0.05」立那条判据要防的东西，这次它真的抓到了一个。
> Keel 这边的临时绕法是在 `internal/inference` 那唯一的耦合点上补这个 token
> （索引侧与查询侧共用同一次拼接，结构上不可能分叉）；正确的修法在 infero，
> 已经如实报过去了。
>
> （注：本节写于 2026-09-26 路线图重排之前，下文与上文的 M7 / M9 / M10 是**旧编号**，
> 分别指对话导购、generate 接口、Text-to-SQL——三者现在都在「远期」，见第十三节。）
>
> **infero 真正的位置仍然在 M7 之后。** 它是 LLM 解码器引擎，而 M3–M6 要的
> embedding / rerank 本来就是编码器的活。从 M7 起换了方向：对话导购（M7）、
> generate 接口与属性抽取 / 评价归因 / 退货归因（M9）、Text-to-SQL（M10）
> 全都要 LLM 生成。尤其 M9 那个「generate 接口（**schema 约束**）」就是受约束
> 解码 —— infero 已经实现了（`response_format: json_schema`，逐 token 拒绝任何
> 会让输出不再是合法前缀的 token），那恰恰是手写推理引擎能做好、而套现成服务
> 反而受限的东西。提前换 embedding 的收益是：那条路径上的运维（起进程、配显存、
> 接监控）先踩一遍，M7 接 LLM 时不用同时踩两件事。

> **竞品现状（2026 年 9 月核实）**
> Medusa 已内置语义检索，但托管在 Medusa Cloud 上——自托管仍需自行接入
> MeiliSearch 或 Algolia。Saleor 是被第三方用作 AI 导购的后端，非内置能力。
> Shopware、Bagisto 的 AI 走插件，多为 OpenAI 接口封装。
>
> 因此「语义检索」本身**不再是独有卖点**，不应作为首要差异点宣传。
> 真正独有的是三条：本地推理、供给侧与经营侧的 AI（全行业空白）、以及覆盖面的完整性。

**3. 一套代码，从单机长到分布式**
借助 dtmrs 的嵌入式协调器，事务编排代码在单进程与多服务形态下完全一致。
小商家一台机器 `docker compose up` 即可跑通全流程；规模增长后拆分服务，
**业务代码不改**。

传统开源商城逼你在「单体好部署但难扩展」与「微服务能扩展但部署地狱」之间二选一。
本项目不需要选。

## 三、多租户：一套部署，多个商家

一套部署承载多个商家，**每个商家有自己独立的店铺前台，订单永远不跨商家**——
Shopify 那一类的多店模型，不是淘宝那类的集市模型。

**单机叙事不变。** 多租户是能力不是要求：小商家 `docker compose up` 起来就是
租户数为 1 的部署，感知不到任何多租户的存在；需要开第二家店时不用换架构。

三条硬规矩（细节见[数据模型](./电商系统-数据模型设计.md) §2）：

1. **每张业务表都带 `merchant_id`**，不靠 join 推导。`scripts/check_tenancy.py`
   机械检查这一条，新加表却忘了租户列会在提交前被拦下。
2. **父子关系用复合外键钉死**。把 A 商家的订单项挂到 B 商家的订单上，
   数据库直接拒绝——不是靠代码记得过滤。
3. **行级安全兜底**。repository 层强制注入租户条件是第一道防线，但它是人写的；
   PostgreSQL 的 RLS 是第二道——注意必须 `FORCE ROW LEVEL SECURITY`，
   只 `ENABLE` 的话表属主会绕过去，而迁移工具跑出来的表属主通常就是应用自己
   （已实测，见数据模型 §2）。

> **为什么值得付这个代价**：共享 schema 的多租户里，跨租户泄露不是「小概率 bug」，
> 而是「漏一次就是事故」——更麻烦的是，这类 bug 在单租户测试数据下**完全看不出来**，
> 加不加那个 `WHERE` 条件结果一模一样。所以必须把它从「记得写」变成「写不错」。

> **买家属于商家**。同一个人在 A 店和 B 店购物是两行 `users`，订单、地址、
> 优惠券互不相通。这是多店模型的定义，不是缺陷。想要「一次登录逛所有店」
> 就得是集市模型，整个订单域要重做。

### 3.1 一个请求怎么找到它的租户

上面三条讲的是**隔离**——租户定了之后不许串。这一节讲**解析**：租户是怎么定下来的。
它是整条链路的第一跳，定错了，后面三道防线全都在忠实地保护一个错的答案。

**租户只有两个来源，都不可由客户端伪造：**

| 部署形态 | 租户来自 | 配置 |
|---|---|---|
| 单商家（`docker compose up` 的默认形态） | 配置里的默认商家，**Host 完全不参与** | `KEEL_DEFAULT_MERCHANT` |
| 多商家 | Host 头 | `KEEL_BASE_DOMAIN` |

两个变量互斥，同时配上会被拒绝启动。

**刻意不支持用请求头指定租户。** 公开接口没有鉴权，那等于让调用方自己声明它是哪家店。
本地开发的便利由默认商家提供，不需要为它开一个生产环境也在的口子。

多商家形态下，一家店的入口只有两个:`shop_settings` 里登记过的域名，或者
`{code}.{KEEL_BASE_DOMAIN}`。后者**必须锚定在基础域名上**——不锚定的话，
`shop-b.attacker.example.org` 也会解析到 shop-b，谁把自己的 DNS 指过来，
就能在自己控制的 origin 上提供任意一家店的店面，cookie、CSP、钓鱼全跟着走。
基础域名下的一级名字（`www`、`api`、`admin`、`mail`…）保留给平台，不发给商家：
判据是「这个名字被商家占走之后，平台还能不能正常运转」，不是敏感词过滤。

**误配在启动时拒绝，不在每个请求里猜。**

这是本节唯一一条需要解释的设计选择，因为它推翻过一版。早先的规则是让解析器
在**每个请求**里判断「这个 Host 算不算平台自己的」，结果同时太松和太紧：
`shop-a.<任意后缀>` 能通过，而 apex 和 `www` 因为 `shop_settings` 的主键是
`merchant_id` 而**根本无法配置**，k8s 的 FQDN、PaaS 给的域名则会让整站 404。
每个请求都在重新回答一个本该在启动时回答一次的问题，而且答不对。

现在改成:启动时一次性把配置的自洽性查清楚，之后解析只做查表。`Preflight` 拒绝启动的情形：

- 两个变量同时配了（形态自相矛盾）
- 配了默认商家，但库里不止一家活跃商家 —— **典型误配**：单商家起步，后来加了第二家店却忘了取消 `KEEL_DEFAULT_MERCHANT`。没有这道检查，它不报错不报警，只是所有人都看到同一家店的数据
- 配了默认商家，但那家店不存在或不可访问
- 基础域名写法不合法 —— 一个字符的手滑会**静默**关掉整条子域名规则，例如写成 `.example.com`（想表达「通配」时很自然）之后没有任何 Host 会以 `..example.com` 结尾，而 Preflight 若只看它非空就会以为入口天然存在
- 有活跃商家**谁也访问不到**（既没登记域名，`{code}` 也不是合法 DNS 标签，或者压根没配基础域名）—— 症状是「某几家店全站 404」，而真因在 404 里看不出一丝痕迹
- 有商家占用了保留名

判据是**让故障在它还叫「配置错误」的时候暴露**。上面每一条，放到运行期都会
表现成一个和真因毫无关系的症状：全站 404、所有人看到同一家店、某家店时好时坏。

## 四、模块边界

| 模块 | 职责 | 不负责 |
|---|---|---|
| handler | 参数校验、鉴权、响应封装 | 业务逻辑、SQL、事务 |
| service | 业务规则、事务编排、调用 AI 层 | 直接拼 SQL |
| repository | 数据访问（**手写领域层**，sqlc 产物被关在它下面的 `internal/db/`） | 业务判断 |
| dtmrs | 跨分支一致性 | 业务语义 |
| 商品理解服务 | 商品的语义化 | 交易 |
| 推理引擎 | 模型推理 | 业务逻辑 |

**分层纪律**：handler 里出现 SQL 或事务，即为架构违规。
守住这条，将来换框架或拆服务只需改最外层。

> **repository 那一行刻意不是「sqlc 生成」。** sqlc 的产物在
> `internal/repository/internal/db/`——Go 的 `internal/` 路径规则让它在
> repository 包之外**引用不到**，`db.New(pool)` 在 handler 或 service 里是
> 编译错误。外面只能走 `repository.WithTenant(ctx, fn)`，而那个函数负责
> `SET LOCAL app.merchant_id`。
>
> 这层封装本身就是安全设计的载体：绕过它就等于绕过租户上下文，
> 而症状会是线上偶发的 42501，不是本地跑不起来。把它描述成「生成的代码」
> 会让人以为可以直接用，那正是这条边界要防的事。

## 五、核心链路：下单的端到端

```
① 用户点「提交订单」
       │
② POST /orders/preview  ── 试算金额与优惠分摊（无副作用）
       │                    前端展示应付金额
③ POST /orders  (Idempotency-Key + expected_payable_cents)
       │
④ service 层校验：幂等键、金额一致性、地址有效性
       │
⑤ 发起 dtmrs 全局事务  gid = order-{merchant_id}-{order_no}  (SAGA)
       │
   ┌───┴────────────────────────────────────────┐
   │ 正向阶段（任一失败则已执行分支全部补偿）      │
   │  ├ 库存：available_qty -= n                 │
   │  ├ 优惠券：status 1 未使用 → 3 已使用        │
   │  └ 订单：建单 status=10 待支付               │
   └───┬────────────────────────────────────────┘
       │ 全部成功
⑥ 返回订单号 + 应付金额 → 前端跳支付
       │
⑦ 用户支付 → 渠道异步回调 POST /webhooks/payments/{channel}
       │      幂等由 (channel, channel_txn_id) 唯一索引兜底
       │
⑧ 二阶段消息：订单 10→20 · 支付单落库 · 积分发放 · 触发履约
       │      库存与券在此步无动作（见下）
       │
⑨ 若超时未支付 → 定时任务扫 status=10 AND expire_at<now
       │           发起 SAGA 补偿：库存 available_qty += n
       │                          · 券 status 3 已使用 → 1 未使用 · 关单
```

> ### 这张图画的是终局，代码今天走到哪一步（M2 任务 4/5 落地时写下）
>
> **图上是三个正向分支，代码里是两个：库存、建单。优惠券那一支还没有。**
>
> 券的三张表（`coupon_templates` / `user_coupons` / `coupon_scopes`）一张都还没
> 建，它和当初的 `users` 一样是隐藏前置。判据是 M2 的产出标志「能下单能支付」：
> 一笔没有用券的订单是完整的订单；而 SAGA 本身要验的东西（正向、补偿、屏障
> 幂等、崩溃重放）两个分支就已经全都走到了，第三个分支是重复同一种结构，
> 不是多验一件事。
>
> **没有实现不等于可以静默忽略。** `POST /orders` 与 `POST /orders/preview`
> 收到 `user_coupon_id` 时返回一个明确的 501，而不是当作没看见 ——
> 传了券却被忽略，用户以为用了券、实际按原价成交，那是钱的问题，而且客户端
> 没有任何办法发现。这笔账挂在 `internal/handler/contract_test.go` 的
> `NotYetImplementedBody` 里，接上券的那天忘了删这一行，测试会红。
>
> 同一段里还有三处「图与代码不一致」，一并写明：
>
> 1. **第 ⑤ 步的两个分支，代码里的顺序是「建单 → 库存」，与图上相反。**
>    理由是补偿只对**真的执行过**的分支生效（子事务屏障的空回滚保护）：
>    库存排在前面时，一次库存不足会让建单分支的补偿变成一次空回滚，
>    那笔已经落库的订单就永远没人关。建单排在前面，一次失败一定会把订单
>    关到 `90`，而且是 SAGA 自己关的，不靠 HTTP 那一侧的善后代码
>    （那段代码在进程崩溃时不会跑）。换来的窗口是「订单已待支付、库存还没扣」
>    的那一瞬间 —— 本期没有支付回调（任务 7），窗口里没有人能对它做什么；
>    接上支付之后这里要重新算一遍账。
>
> 2. **第 ③ 步与第 ⑤ 步之间多了一个状态。** 订单必须先落库才能提交 SAGA
>    （分支只拿到三个字符串，扣减意图推不出来），所以落库时的状态是
>    `0 创建中` 而不是 `10 待支付`，由建单分支推到 `10`。
>    见数据模型 §5 的状态机。
>
> 3. **第 ⑤ 步之前的运费（00056 起）。** 运费模板落地之前这条链路没有算过运费：
>    库里 `orders.freight_cents` 恒为 `0`、响应里整个不出现（「没算」不等于「包邮」）。
>    00056 起运费是计价顺序的最后一段（原价 → 营销活动 → 券 → 运费 → 包邮券），
>    试算与建单共用 `service/freight_calc.go` 同一份实现，按收货地址、履约门店、
>    每行商品挂的模板算好写进订单，连同规则快照 `orders.freight_snapshot`；
>    `contract_test.go` 里那笔 `NotYetImplementedResponse` 挂账随之划掉（数据模型 §7）。
>
> ### 第 ⑦ ⑧ ⑨ 步（任务 6 / 7 落地时写下）
>
> 三步都实现了，但 ⑧ 与 ⑨ 的**形态都和图上不一样**，逐条说清楚。
>
> 4. **第 ⑧ 步没有走二阶段消息，而二阶段消息是存在的。**
>
>    先说实测结论，因为任务书是照着一个错误的前提写的：`dtmrs` v0.11.0 的
>    C ABI **导出了二阶段消息**——`dtmrs_msg_prepare(tc, gid, actions_json,
>    query_prepared, grace_secs)` 加上与 TCC/XA 共用的 `dtmrs_submit` /
>    `dtmrs_abort`。它不叫 `submit_msg`，所以按那个名字去找会找不到。
>    核实方式是 `nm -D` 读**编译出来的 libdtmrs.so** 的导出面（22 个符号），
>    不是读头文件——头文件可以领先于实现。
>
>    没有用它，理由是**它要送的两件事一件都还不存在**。二阶段消息的语义是
>    「本地事务 + 消息表 + 定时回查」，它解决的问题是：本地事务提交了，
>    但下游还没收到通知。而图上第 ⑧ 步的四件事里，
>    「订单 10→20」与「支付单落库」是**同一个库里的两行**——它们在一个本地
>    事务里就是原子的，那正是二阶段消息里「本地事务」的那一半；剩下两件
>    「积分发放」与「触发履约」是它要投递的收件人，而积分表与履约都还没有。
>
>    于是 `actions_json` 会是一个空数组。一个没有 action 的二阶段消息不是
>    「先接上、以后再填」，它是纯粹的开销：多一次 prepare、多一行协调器状态、
>    多一个必须写对的回查 handler（`query_prepared`，答错了会让已提交的本地
>    事务被作废），换来零次投递。所以本期第 ⑧ 步是**一个本地事务**：
>    支付单落库 + 订单 10 → 20，中间没有协调器。
>
>    接上积分或履约的那一天，这里换成 `msg_prepare → 本地事务 → submit`，
>    业务这一段不用动——**而那时它是必需的，不是可选的**：一笔钱到账了、
>    订单也推到已支付了，而积分没发出去，靠重试是补不回来的（没人知道该重试谁）。
>    `internal/dtm` 本轮**刻意没有**为它加符号绑定，理由写在那个包的文件头：
>    internal/ 里一个没人调的导出 API 没有任何闸门守着，上游改了 C ABI 它会
>    安静地烂掉。要用的那天加，成本是十几行。
>
> 5. **第 ⑨ 步没有走 SAGA，它是一个本地事务。** §7 的表里「超时关单 → SAGA」，
>    那对形态 C（库存与订单各自独立服务、各自独立库）是对的。在形态 A 下，
>    关单与库存回补是**同一个库里的事**，一个本地事务比 SAGA 严格更强：
>    原子，而不是最终一致。为它开一个全局事务换不来任何东西，还要多回答一个
>    问题——那个 SAGA 的 gid 长什么样？沿用下单那一笔的 `order-{m}-{no}` 会
>    和它的屏障记录撞车（同一个 gid 在协调器里就是同一笔事务），另起一个前缀
>    则要动 `internal/dtm` 的 gid 文法，而那是 M2 刻意冻住的东西。
>
>    竞态因此不是靠编排解决的，是靠**两条带条件的 UPDATE 撞在同一行上**：
>    关单发 `... WHERE order_no = $1 AND status = 10`，支付回调发
>    `... WHERE order_no = $1 AND status = 10`，行锁让它们排队，
>    **恰好一个的 rows_affected 是 1**。输掉的那一边什么都不做：
>    补偿任务整个事务回滚（一件货都没回补），或者支付回调把支付单落库、
>    订单不动、留一条 Error 日志（钱到了而订单已关，要人工退款）。
>
> 6. **第 ⑨ 步还扫第二类行：`status = 0` 的孤儿草稿。** 图上没有它，
>    因为它是「订单先落库、再提交 SAGA」这个顺序的副产物（见上面第 2 条）。
>    处置和第一类**不一样**：只关单，**不回补库存**——它从没进过 SAGA，
>    一件库存都没扣。回补一次的后果是凭空多出来的库存，而且会留下一行
>    看起来完全正常的流水。
>
> 7. **定时任务怎么拿到租户。** 它跑在任何 HTTP 请求之外：没有 Host，
>    所以 `tenant.Resolver` 用不上；没有 gid，`dtm.TenantContextFromGID` 也用不上。
>    答案是**枚举 `merchants`**，再一家一家进 `WithTenant`——这条路走得通是
>    因为 `merchants` 是 tenant-root 类，**没有 RLS**，而且刻意没有（租户解析
>    本来就要在 `SET LOCAL` 之前读它）。于是不需要任何 RLS 豁免，也不需要给
>    应用一份能绕过 RLS 的凭据（那是 `db.NewPool` 的自检明确拒绝的东西）。
>
>    代价是扫描被切成每租户一段，没有跨租户的全局顺序，**公平调度因此落在
>    应用层**：形状照数据模型 §12 的「上限 + 兜底」，差别逐条写在
>    `internal/service/sweep.go` 的文件头。这同时是与 §12 的一处冲突——
>    §12 说「worker 出队以平台身份执行，不走 RLS 注入」，本仓库没有那个身份。
>
> 8. **第 ⑤ 步那个窗口重新算过了，结论是维持。** 上面第 1 条留了一笔账：
>    「建单在前、库存在后」换来的窗口是「订单已是 10 待支付、库存还没扣」，
>    而本期之前没有支付回调，窗口里没人能做什么。现在有了，所以重算：
>
>    窗口**仍然不可达**，因为 `order_no` 是 72 bit 随机不可枚举，而它
>    **只在 SAGA 到达终态之后才对外返回**（`Create` 的第三段：WaitFinal 成功、
>    重新读库确认 status = 10，才把单号交出去）。支付回调必须带着订单号才找得到
>    订单，所以窗口里没有任何人知道该付哪一单。
>
>    而**换成「库存在前」的代价比这个窗口大**：那样一来，`order_create_undo`
>    这个补偿分支在每一条失败路径上都退化成空回滚（建单排在最后，它失败时
>    自己的补偿是空回滚；它成功时整笔 SAGA 就成功了），于是下单主链路上
>    「补偿到底跑没跑」这件事再也测不出来——而那正是 SAGA 最需要能被证伪的性质。
>    顺带地，最常见的失败（库存不足）会从「SAGA 自己把订单关到 90」退化成
>    「留一行 status = 0 等 30 分钟后被扫」。
>
>    维持的同时补了一道：建单分支的补偿（`closeOrder`）在**关不掉**时不再静默
>    成功——它要能区分「已经是 90 了」（幂等重放，正常）与「已经被付掉了」
>    （窗口真的发生了），后者留一条 Error 日志。不可达不等于不存在，
>    而一个不可达的洞一旦被别的改动打开，要有声音。

> **gid 为什么要带 `merchant_id`？**
> 因为分支只能从 gid 知道自己是谁。`SubmitSaga(gid, steps)` 的 steps 里只有
> `{"action","compensate"}` 两个地址，**不带业务载荷**；分支签名是
> `(gid, branch_id, op)` 三个字符串；分支跑在任何 HTTP 请求之外，崩溃重启后由
> 协调器重放，进程对原请求毫无记忆。而分支要写库就得 `SET LOCAL app.merchant_id`。
> 想「按 order_no 查表反查租户」是死循环——那张表本身在 RLS 之下，
> 而 RLS 正需要租户。也不为此开一张 RLS 豁免表：一张能无租户按 order_no 查出
> merchant_id 的表，就是一条绕过 RLS 的合法路径，它会比它解决的问题活得久。
> 解析在 `internal/dtm`（`OrderGID` / `ParseOrderGID`），**刻意严格**：
> 前导零、`+12`、`0`、别的业务前缀一律拒绝，出错时返回的租户是 0 而不是半个结果——
> 这个返回值会被直接塞进 `SET LOCAL`，之后 RLS 就按它放行，不会再复核一遍。

> **第 ⑧ 步为什么没有「库存 Confirm」「券 Confirm」？**
> 因为下单走的是 SAGA，不是 TCC。库存在第 ⑤ 步的正向阶段就已经真实扣减、
> 优惠券也已真实核销——没有中间的预留态，自然也没有需要确认的东西。
> 支付成功只是让这些既成事实**不再可能被补偿掉**。
> 这正是 §7 所说「SAGA 比 TCC 少一半方法数」的具体体现：
> 库存分支只需写 `扣减` 与 `回补` 两个方法，而不是 `Try / Confirm / Cancel` 三个。
>
> 代价也要说清楚：SAGA 在正向阶段就改了「可售量」这个对外可见的量，
> 因此第 ⑤ 步到第 ⑦ 步之间，超卖风险为零、但**少卖风险存在**——
> 用户下单未付、订单关闭前，这批库存对其他人不可售。这是刻意接受的取舍，
> 换来的是少一半的方法数与少一个永远为 0 的预留字段。

每个分支内部用 `BranchBarrier::decide()` 保证幂等：

| Decision | 业务方动作 |
|---|---|
| `Execute` | 在**同一事务**内执行业务 SQL |
| `NullCompensation` | 什么都不做，**返回成功** |
| `Duplicated` | 什么都不做，**返回成功** |

> 最易踩的坑：后两者是正常路径。返回失败会让 TC 误判并无限重试。

## 六、部署演进：一套代码三种形态

### 形态 A · 单机（默认，面向小商家与演示）

```
docker compose up                    # 没有 GPU 的机器：到此为止，搜索走关键词那一路
  ├ app        (Go, 含 dtmrs 协调器)
  └ postgres   (业务表 + barrier + pgvector)

./scripts/infero-up.sh               # 有 NVIDIA GPU 时再加这两步，语义检索才有
docker compose -f compose.yaml -f compose.infero.yaml up -d
  └ infero     (自研推理引擎, 宿主机进程, **不在 compose 里**)
```

> **`docker compose up` 起的就是上面那两个服务。** dtmrs 已在 M2 接入，
> pgvector 在 M3 Task 1 进了盒子（镜像换成 `pgvector/pgvector:pg16`，
> `db/migrations/00016` 建扩展与四张向量 / 理解表）。
>
> **推理引擎刻意不是一个 compose 服务。** M4 起它是自研的 infero：GPU-only，
> 而一块卡同时只装得下一份 —— 容器化换来的只有「一条命令起全栈」，代价是
> 2–3 GB 的 CUDA 基础镜像、GPU 透传，以及把它 dlopen 的那套 CUDA 用户态库
> 也一起挂进去。完整的显存账写在 `scripts/infero-up.sh` 的文件头。叠加层
> `compose.infero.yaml` 因此只做一件事：把 app 的 `KEEL_EMBED_ENDPOINT`
> 指到宿主机上那个进程。两份 README 的「还没在盒子里的」一节列的就是这个差集。
>
> **`barrier` 不是 dtmrs 建的**（原先这里写「随它一起建」，那句是错的）。
> dtmrs 自己的 `migrate()` 建的是 `trans_global` / `trans_branch_op` / `auth_token`
> 三张——**协调器自己的状态**，而 `barrier` 由 `dtmrs-barrier` 那个 crate 建，
> C ABI 根本不依赖它（`dtmrs-ffi` 的依赖表与符号表里都没有）。所以 `barrier`
> 由本项目自己的迁移建出来，登记在 `db/tenancy.json` 里。
>
> 这也决定了上面那张图里**协调器的状态不在业务库里**：dtmrs 启动时要建自己那三张表，
> 需要建表权限。用 `keel_app` 去做实测报 `permission denied for schema public`；
> 换管理员角色能建出来，但那三张表就落进业务库的 `public` 下，
> `db/tenancy.json` 的四道闸门当场全红，而且应用从此握着能绕过 RLS 的凭据。
> 所以它是一份独立的存储，由 `KEEL_DTM_DSN` 指定：单机形态是挂在卷上的 sqlite，
> 多实例形态必须换成 Postgres/MySQL/Redis 并给它自己的角色。

- 事务分支为进程内函数调用（`local://`），无网络开销
- 单机目标容量：商品 10 万、日订单 1 万、搜索 QPS 50
- **无 GPU 时搜索仍可用，但只剩关键词那一路。**

  这一条原来写的是「无 GPU 时降级为小模型 CPU 推理，搜索仍可用」。那句话描述的是
  M3 那个跑 BGE-M3 的 Python 服务，它已经退役，所以改成今天的事实：

  | | 有 NVIDIA GPU | 没有 GPU |
  |---|---|---|
  | 起法 | `./scripts/infero-up.sh` + `-f compose.infero.yaml` | `docker compose up`，不用加任何东西 |
  | `KEEL_EMBED_ENDPOINT` | 指到 infero | **不配** |
  | `/search` | 向量召回 + 关键词召回，RRF 融合 + 业务重排（M5；精排未实现） | 纯关键词召回 + 业务重排（§8 的降级链） |
  | 实际表现 | — | 返回 200，不报错；`explain: true` 如实列出跑过的阶段；字面不重合的查询召回明显变差 |
  | 派生数据索引任务 | 维护向量表与 bigram 串 | 不启动，启动日志里有一条 WARN 把后果说清楚 |

  **没有 GPU 不等于跑不起来，等于搜索退化成关键词。** 之所以只有这一种形态：
  infero 只有 CUDA / Metal 后端，而这个系统不再维护第二个推理引擎实现。
  让没有卡的机器也有语义检索，正解是给 infero 加 CPU 后端 —— **今天还没有**，
  所以这里不写成「支持」，只记成打算。

### 形态 B · 读写分离

应用多实例无状态化；Postgres 主从；推理引擎独立部署到 GPU 机器。
事务编排代码不变。

### 形态 C · 服务拆分

按 dtmrs 的事务边界拆分：商品 / 库存 / 订单 / 支付各自独立服务与数据库。

**迁移工作量**：分支地址由 `local://deduct_stock` 改为
`http://inventory-svc/deduct`，dtmrs 转独立 TC 部署。
**业务逻辑代码零改动。** 每个服务的库各自建 `barrier` 表（各自的迁移里建，见形态 A 的说明）。

```
形态 A:  tc.saga(gid).step("local://deduct_stock", "local://restore_stock").submit()
形态 C:  tc.saga(gid).step("http://inv/deduct",    "http://inv/restore").submit()
                     ↑ 只有这一行变了
```

这是本项目最核心的架构主张——**部署形态是配置，不是重写**。

## 七、一致性策略：什么用 dtmrs，什么不用

| 场景 | 方案 | 理由 |
|---|---|---|
| 下单（库存+券+订单） | **SAGA** | 操作天然可逆，无需预留阶段；比 TCC 少一半方法数（无 Confirm 分支） |
| 支付回调 | **二阶段消息** | 外部单向触发，只需保证最终一致 |
| 退款 | **SAGA** | 补偿链清晰，无需预占；部分退款只推进 `orders.refund_status`，不动 `orders.status` |
| 超时关单 | **SAGA** | 同上 |
| 预售 / 多仓调拨（未来） | **TCC** | 需要区分「锁定量」与「真实销量」时才引入 |
| 商品理解 | **普通任务队列** | 幂等可重试的异步任务，不需要分布式事务；落地就是 `jobs` 表 + `FOR UPDATE SKIP LOCKED` 出队 |
| 搜索索引更新 | **普通任务队列** | 同上，与商品理解共用 `jobs` 表，靠 `queue` 字段分流 |
| 购物车操作 | **单库事务** | 不跨服务 |

> **克制原则**：分布式事务是有成本的（额外表、额外往返、更复杂的失败路径）。
> 只在真正跨资源且需要回滚的地方使用。为了展示而滥用，是架构上的减分项。

> **SAGA 的连带决定**：既然下单不走 TCC，库存表里就**不保留预留量字段**——
> 「可售量」即全部真相。等真正做预售定金或多仓调拨时再加列，加一列很便宜；
> 而一个永远为 0 的预留字段留在表里，后面接手的人一定会误用它。字段清单见数据模型文档。

> **退款为什么要两个维度**：订单状态管履约，售后状态管资金。买三件退一件时，
> 订单该继续走它的履约流程（已发货的照发），只有资金侧发生了变化。
> `orders.status` 的 `50 退款中` / `60 已退款` 因此收窄为**仅整单退款**，
> 部分退款由正交的 `orders.refund_status` 表达。压进一个字段的话，
> 「部分退款后订单还能不能确认收货」这类问题会无解。状态机见数据模型文档。

## 八、架构决策记录（ADR）

开源项目必须回答「为什么这么做」，否则每个贡献者都会重问一遍。

| # | 决策 | 理由 | 代价 |
|---|---|---|---|
| 1 | 后端用 Go 而非 Rust | 支付/短信/物流 SDK 生态成熟；迭代快；贡献者基数大十倍 | 失去 `CGO_ENABLED=0` 静态编译；需自建多平台预编译流水线（见下） |
| 2 | 不用 `{code,message,data}` 信封 | 信封让所有响应都是 200，破坏 HTTP 语义；codegen 客户端需手写拆包。改用 RFC 9457 | 与国内惯例不同，需在文档说明 |
| 3 | 金额用 `BIGINT` 存分 | 浮点在金额计算中必然产生舍入误差 | 展示层需除 100 |
| 4 | 向量用 pgvector，不引入专用向量库 | 少一个组件，与业务表同库可做事务性更新，契合单机部署目标 | 亿级向量时需迁移 |
| 5 | 中文分词第一期用应用层 bigram | 零依赖，纯 SQL；商品标题短、术语密集，bigram 够用 | 长尾查询效果弱于 jieba |
| 6 | AI 只做路由，写操作走 GUI 确认 | 规避 prompt injection 与误操作资损；结构化操作 GUI 本就更快 | 演示时少一个「全对话下单」噱头 |
| 7 | 商品理解不使用 dtmrs | 幂等可重试的异步任务，队列即可 | — |
| 8 | 库存用条件原子更新而非乐观锁 | 高争抢下乐观锁反复重试失败；`WHERE available>=n` 单语句原子 | 需配合 CHECK 约束兜底 |
| 9 | 代码英文、设计文档中文 | 代码/Issue/提交信息全英文，便于国际协作；设计文档用中文，因为作者与早期贡献者都在中文环境 | 国际贡献者暂时只能读 README |
| 10 | 不把「语义检索」作为首要卖点 | Medusa 已内置（托管版）；差异点应落在本地推理与全链路覆盖 | 需要更长的一句话解释定位 |
| 11 | 提供官方 MCP Server 与 Agent Skills | Medusa / Saleor 已成标配；成本低且与 AI 原生定位咬合 | 需随 API 演进维护 |

>
> 原先写的是「README/代码/Issue 全英文，中文作为翻译版」。方向没错——
> 开源项目要国际贡献者就得降低语言门槛。但四份长设计文档翻译加上后续双语维护
> 是持续成本，而项目现在连一行代码都没有。**为一个还不存在的贡献者群体先付这笔钱，

>
> 等真的出现国际贡献者，那时也更清楚该优先翻哪几份。代价是短期内他们只能读 README。

### ADR #1 补注：cgo 嵌入已实测通过

这条决策原先挂着一个未验证的前提——「放弃 dtmrs 嵌入式模式（除非 cgo 打通）」，
而形态 A 的全部叙事都建立在它之上。已做实测，结论如下。

**结论：cgo 不需要「打通」，它本来就是通的。** 编译出 `libdtmrs.so` 后，Go 经 cgo
成功驱动嵌入式协调器完成 SAGA 提交、逆序补偿、拉取式异步分支、进程崩溃后的跨进程恢复，
并验证了同一段编排代码只改分支地址一行、`local://` 与 `http://` 两种形态都成立。
`local://` 是引擎 `parse_target` 里的真实分支，不是设计设想。

> 原先的悲观判断很可能源于一处误读：dtmrs 文档里「Go structurally cannot do this」
> 说的是 **Go 没法把自己编成可被嵌入的 `.so`**（Go 当 guest），
> 不是「Go 没法调别人的 `.so`」（Go 当 host）。方向正好相反。

**真实代价只剩一条：**

**`CGO_ENABLED=0` 静态编译确定失去**（已实测）。静态链接 `libdtmrs.a` 可行，
单文件二进制约 15 MB。但 dtmrs 上游不提供预编译产物、CI 只跑 ubuntu-latest——
Keel 要么要求贡献者装 Rust 工具链，要么自建多平台预编译流水线，
等于替上游做发布工程。**这是形态 A 最大的真实成本，别低估。**

> **原先这里还写着第二条「FFI 层只有 SAGA，没有 TCC」。dtmrs 0.11 把它解决了。**
>
> 0.8 的 C ABI 导出 11 个符号，事务提交入口只有 `dtmrs_submit_saga`；
> 0.11 导出 22 个，**只增不减**，TCC / XA / 二阶段消息 / workflow 全部可用，
> 已从 Go 实测跑通（`examples/dtmrs-embedded/cmd/tcc`，正向 Confirm 与
> 失败后逆序 Cancel 两条路径都验过）。
>
> 这意味着 §7 里「TCC 留给预售定金 / 多仓调拨」那条路**现在就是通的**，
> 不再需要先给上游补导出。下单继续走 SAGA 不变——那是因为 SAGA 更合适，
> 不是因为 TCC 不可用。

**还有一条不是代价、是必须自己写的东西：子事务屏障。**

屏障不在 C ABI 里，**也不可能在**。dtmrs 的 `decide()` 签名是
`decide(&mut self, tx: &mut Transaction)`——它接收**调用方的事务**，
因为屏障记录必须与业务变更在同一个本地事务内提交，这正是屏障成立的前提。
Go 侧事务握在 pgx 手里，没法递过 C 边界。

所以任何非 Rust 宿主都要自己实现那三十行。好在算法很短，
且三种异常（重复请求 / 空回滚 / 悬挂）已在 Go 侧实测通过，
含 50 协程并发下「恰好一次 Execute」——见 `examples/dtmrs-embedded/barrier`。

**并发行为已实测，结论直接影响工程骨架：**

**每个阻塞的 cgo 调用占一个 OS 线程,线程数跟的是「同时卡在 cgo 里的调用数」,
不是总工作量。** 2000 笔 SAGA、handler 各阻塞 50ms,只改提交并发度:

| 提交并发 | 峰值 OS 线程 | 吞吐 |
|---|---|---|
| 不限制 | 1213 | 246.8 saga/s |
| 256 | 290 | 247.2 saga/s |
| 32 | 70 | 243.7 saga/s |

三者吞吐几乎相同——**限制并发不花代价,却省掉一千多个线程**。
超出 Go 的线程上限(默认 10000)不是返回错误,是 `fatal error: thread exhaustion`,
**进程直接死**。

因此定一条工程规矩:**所有进入 dtmrs 的调用都要过一个有界信号量**。
`SubmitSaga` 与 `WaitFinal` 都是阻塞 cgo 调用,后者尤其——它按设计就要等到终态。
下单链路的 worker 池大小据此设定,不能让它随请求数线性增长。

> 这条规矩在 M2 落到了 `internal/dtm`：信号量在 `TC` 里，`Start` / `SubmitSaga`
> / `WaitFinal` 三个阻塞调用都要先取一张通行证，默认上限 32（就是上表第三行）。
> 它由 `TestBlockingCallsAreBounded` 钉住——把取通行证那行删掉，峰值会冲过上限，
> 测试当场红。代价说清楚：一批长 `WaitFinal` 会占满额度把提交挡在外面，
> 所以 `WaitFinal` 必须带有界的 timeout。

**诚实边界**：仍未验证 macOS / arm64 构建（上游 CI 只跑 ubuntu-latest），
以及 Go panic 跨 C 栈的实际压测（目前只有理论分析与 `defer recover` 的写法约定）。
在这两项之前，形态 B（TC 作为同容器独立进程）应作为逃生舱保留——
两种形态共用同一套业务代码，不是二选一。
