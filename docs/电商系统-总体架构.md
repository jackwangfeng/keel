## 一、这个项目为什么存在

开源电商系统已经很多（mall、Saleor、Medusa、Shopware）。做第五十个没有意义。
本项目的存在理由是三条别人没有的东西：

**1. 自带分布式事务内核**
交易一致性由自研的 [dtmrs](https://github.com/jackwangfeng/dtmrs) 保障——
Rust 实现，支持 SAGA / TCC / 二阶段消息 / XA / workflow。
其他开源商城要么回避分布式事务（单体大事务），要么依赖外部 Seata / DTM。

**2. AI 贯穿经营全链路，且全部本地推理**
进货（商品结构化、同款归并、合规检查）、卖货（语义检索、对话导购、拍照搜同款）、
经营（销量预测、补货建议、自然语言查数据）、反馈（评价归因、退货归因）——
每个环节都有，且全部跑在自研推理引擎上。
**零外部 API 调用，商品数据与客户信息不出网，无按量计费。**

> **竞品现状（2026 年 9 月核实）**
> Medusa 已内置语义检索，但托管在 Medusa Cloud 上——自托管仍需自行接入
> MeiliSearch 或 Algolia。Saleor 是被第三方用作 AI 导购的后端，非内置能力。
> Shopware、Bagisto 的 AI 走插件，多为 OpenAI 接口封装。
>
> 因此「语义检索」本身**不再是独有卖点**，不应作为首要差异点宣传。
> 真正独有的是三条：本地推理、供给侧与经营侧的 AI（全行业空白）、以及覆盖面的完整性。

**3. 一套代码，从单机长到分布式**
借助 dtmrs 的嵌入式协调器，事务编排代码在单进程与多服务形态下完全一致。
小商家一台机器 `docker compose up` 即可跑通全流程；规模增长后拆分服务，
**业务代码不改**。

传统开源商城逼你在「单体好部署但难扩展」与「微服务能扩展但部署地狱」之间二选一。
本项目不需要选。

## 二、系统全景

```
┌──────────────────────────────────────────────────────────────┐
│  客户端                                                        │
│  Web 商城 (Next.js) │ 小程序 / H5 / App (uni-app) │ 后台 (React)│
└───────────────────────────┬──────────────────────────────────┘
                            │ OpenAPI 3.1 契约（codegen 双向）
┌───────────────────────────▼──────────────────────────────────┐
│  API 层   Go + Gin                                            │
│  handler：参数校验 / 响应封装 / 鉴权。无 SQL、无事务            │
└───────────────────────────┬──────────────────────────────────┘
┌───────────────────────────▼──────────────────────────────────┐
│  Service 层   业务逻辑 · 事务编排入口                          │
│  ┌────────┬────────┬────────┬────────┬────────┬────────┐     │
│  │ 商品   │ 库存   │ 订单   │ 支付   │ 营销   │ 检索   │     │
│  └────────┴────────┴────────┴────────┴────────┴────────┘     │
└──────┬──────────────────────────────┬─────────────────┬──────┘
       │                              │                 │
┌──────▼───────┐            ┌─────────▼────────┐  ┌─────▼──────┐
│   dtmrs      │            │  商品理解服务     │  │ Repository │
│ 事务协调器    │            │ (异步 worker 池)  │  │   sqlc     │
│ TCC/SAGA/2PM │            └─────────┬────────┘  └─────┬──────┘
└──────┬───────┘                      │                 │
       │                    ┌─────────▼────────┐        │
       │                    │   推理引擎        │        │
       │                    │ Rust / 本地 GPU   │        │
       │                    │ embed·rerank·gen │        │
       │                    └──────────────────┘        │
       └──────────────────────────┬────────────────────-┘
                        ┌─────────▼─────────┐
                        │   PostgreSQL 16+  │
                        │  业务表 + barrier  │
                        │  + pgvector       │
                        └───────────────────┘
```

**关键点：`barrier` 表与业务表同库。** 这是子事务屏障成立的前提——
屏障记录与业务变更必须在同一个本地事务内提交。该约束直接决定分库策略。

## 三、多租户：一套部署，多个商家

一套部署承载多个商家，**每个商家有自己独立的店铺前台，订单永远不跨商家**——
Shopify 那一类的多店模型，不是淘宝那类的集市模型。

**单机叙事不变。** 多租户是能力不是要求：小商家 `docker compose up` 起来就是
租户数为 1 的部署，感知不到任何多租户的存在；需要开第二家店时不用换架构。

三条硬规矩（细节见[数据模型](./电商系统-数据模型设计.md) §2）：

1. **每张业务表都带 `merchant_id`**，不靠 join 推导。`scripts/check_tenancy.py`
   机械检查这一条，新加表却忘了租户列会在提交前被拦下。
2. **父子关系用复合外键钉死**。把 A 商家的订单项挂到 B 商家的订单上，
   数据库直接拒绝——不是靠代码记得过滤。
3. **行级安全兜底**。repository 层强制注入租户条件是第一道防线，但它是人写的；
   PostgreSQL 的 RLS 是第二道——注意必须 `FORCE ROW LEVEL SECURITY`，
   只 `ENABLE` 的话表属主会绕过去，而迁移工具跑出来的表属主通常就是应用自己
   （已实测，见数据模型 §2）。

> **为什么值得付这个代价**：共享 schema 的多租户里，跨租户泄露不是「小概率 bug」，
> 而是「漏一次就是事故」——更麻烦的是，这类 bug 在单租户测试数据下**完全看不出来**，
> 加不加那个 `WHERE` 条件结果一模一样。所以必须把它从「记得写」变成「写不错」。

> **买家属于商家**。同一个人在 A 店和 B 店购物是两行 `users`，订单、地址、
> 优惠券互不相通。这是多店模型的定义，不是缺陷。想要「一次登录逛所有店」
> 就得是集市模型，整个订单域要重做。

## 四、模块边界

| 模块 | 职责 | 不负责 |
|---|---|---|
| handler | 参数校验、鉴权、响应封装 | 业务逻辑、SQL、事务 |
| service | 业务规则、事务编排、调用 AI 层 | 直接拼 SQL |
| repository | 数据访问（sqlc 生成） | 业务判断 |
| dtmrs | 跨分支一致性 | 业务语义 |
| 商品理解服务 | 商品的语义化 | 交易 |
| 推理引擎 | 模型推理 | 业务逻辑 |

**分层纪律**：handler 里出现 SQL 或事务，即为架构违规。
守住这条，将来换框架或拆服务只需改最外层。

## 五、核心链路：下单的端到端

```
① 用户点「提交订单」
       │
② POST /orders/preview  ── 试算金额与优惠分摊（无副作用）
       │                    前端展示应付金额
③ POST /orders  (Idempotency-Key + expected_payable_cents)
       │
④ service 层校验：幂等键、金额一致性、地址有效性
       │
⑤ 发起 dtmrs 全局事务  gid = order-{order_no}  (SAGA)
       │
   ┌───┴────────────────────────────────────────┐
   │ 正向阶段（任一失败则已执行分支全部补偿）      │
   │  ├ 库存：available_qty -= n                 │
   │  ├ 优惠券：status 1 未使用 → 3 已使用        │
   │  └ 订单：建单 status=10 待支付               │
   └───┬────────────────────────────────────────┘
       │ 全部成功
⑥ 返回订单号 + 应付金额 → 前端跳支付
       │
⑦ 用户支付 → 渠道异步回调 POST /webhooks/payments/{channel}
       │      幂等由 (channel, channel_txn_id) 唯一索引兜底
       │
⑧ 二阶段消息：订单 10→20 · 支付单落库 · 积分发放 · 触发履约
       │      库存与券在此步无动作（见下）
       │
⑨ 若超时未支付 → 定时任务扫 status=10 AND expire_at<now
       │           发起 SAGA 补偿：库存 available_qty += n
       │                          · 券 status 3 已使用 → 1 未使用 · 关单
```

> **第 ⑧ 步为什么没有「库存 Confirm」「券 Confirm」？**
> 因为下单走的是 SAGA，不是 TCC。库存在第 ⑤ 步的正向阶段就已经真实扣减、
> 优惠券也已真实核销——没有中间的预留态，自然也没有需要确认的东西。
> 支付成功只是让这些既成事实**不再可能被补偿掉**。
> 这正是 §7 所说「SAGA 比 TCC 少一半方法数」的具体体现：
> 库存分支只需写 `扣减` 与 `回补` 两个方法，而不是 `Try / Confirm / Cancel` 三个。
>
> 代价也要说清楚：SAGA 在正向阶段就改了「可售量」这个对外可见的量，
> 因此第 ⑤ 步到第 ⑦ 步之间，超卖风险为零、但**少卖风险存在**——
> 用户下单未付、订单关闭前，这批库存对其他人不可售。这是刻意接受的取舍，
> 换来的是少一半的方法数与少一个永远为 0 的预留字段。

每个分支内部用 `BranchBarrier::decide()` 保证幂等：

| Decision | 业务方动作 |
|---|---|
| `Execute` | 在**同一事务**内执行业务 SQL |
| `NullCompensation` | 什么都不做，**返回成功** |
| `Duplicated` | 什么都不做，**返回成功** |

> 最易踩的坑：后两者是正常路径。返回失败会让 TC 误判并无限重试。

## 六、部署演进：一套代码三种形态

### 形态 A · 单机（默认，面向小商家与演示）

```
docker compose up
  ├ app        (Go, 含 dtmrs 协调器)
  ├ postgres   (业务表 + barrier + pgvector)
  └ inference  (推理引擎, GPU 可选)
```

- 事务分支为进程内函数调用（`local://`），无网络开销
- 单机目标容量：商品 10 万、日订单 1 万、搜索 QPS 50
- 无 GPU 时降级为小模型 CPU 推理，搜索仍可用

### 形态 B · 读写分离

应用多实例无状态化；Postgres 主从；推理引擎独立部署到 GPU 机器。
事务编排代码不变。

### 形态 C · 服务拆分

按 dtmrs 的事务边界拆分：商品 / 库存 / 订单 / 支付各自独立服务与数据库。

**迁移工作量**：分支地址由 `local://deduct_stock` 改为
`http://inventory-svc/deduct`，dtmrs 转独立 TC 部署。
**业务逻辑代码零改动。** 每个服务的库各自建 `barrier` 表。

```
形态 A:  tc.saga(gid).step("local://deduct_stock", "local://restore_stock").submit()
形态 C:  tc.saga(gid).step("http://inv/deduct",    "http://inv/restore").submit()
                     ↑ 只有这一行变了
```

这是本项目最核心的架构主张——**部署形态是配置，不是重写**。

## 七、一致性策略：什么用 dtmrs，什么不用

| 场景 | 方案 | 理由 |
|---|---|---|
| 下单（库存+券+订单） | **SAGA** | 操作天然可逆，无需预留阶段；比 TCC 少一半方法数（无 Confirm 分支） |
| 支付回调 | **二阶段消息** | 外部单向触发，只需保证最终一致 |
| 退款 | **SAGA** | 补偿链清晰，无需预占；部分退款只推进 `orders.refund_status`，不动 `orders.status` |
| 超时关单 | **SAGA** | 同上 |
| 预售 / 多仓调拨（未来） | **TCC** | 需要区分「锁定量」与「真实销量」时才引入 |
| 商品理解 | **普通任务队列** | 幂等可重试的异步任务，不需要分布式事务；落地就是 `jobs` 表 + `FOR UPDATE SKIP LOCKED` 出队 |
| 搜索索引更新 | **普通任务队列** | 同上，与商品理解共用 `jobs` 表，靠 `queue` 字段分流 |
| 购物车操作 | **单库事务** | 不跨服务 |

> **克制原则**：分布式事务是有成本的（额外表、额外往返、更复杂的失败路径）。
> 只在真正跨资源且需要回滚的地方使用。为了展示而滥用，是架构上的减分项。

> **SAGA 的连带决定**：既然下单不走 TCC，库存表里就**不保留预留量字段**——
> 「可售量」即全部真相。等真正做预售定金或多仓调拨时再加列，加一列很便宜；
> 而一个永远为 0 的预留字段留在表里，后面接手的人一定会误用它。字段清单见数据模型文档。

> **退款为什么要两个维度**：订单状态管履约，售后状态管资金。买三件退一件时，
> 订单该继续走它的履约流程（已发货的照发），只有资金侧发生了变化。
> `orders.status` 的 `50 退款中` / `60 已退款` 因此收窄为**仅整单退款**，
> 部分退款由正交的 `orders.refund_status` 表达。压进一个字段的话，
> 「部分退款后订单还能不能确认收货」这类问题会无解。状态机见数据模型文档。

## 八、架构决策记录（ADR）

开源项目必须回答「为什么这么做」，否则每个贡献者都会重问一遍。

| # | 决策 | 理由 | 代价 |
|---|---|---|---|
| 1 | 后端用 Go 而非 Rust | 支付/短信/物流 SDK 生态成熟；迭代快；贡献者基数大十倍 | 失去 `CGO_ENABLED=0` 静态编译；需自建多平台预编译流水线（见下） |
| 2 | 不用 `{code,message,data}` 信封 | 信封让所有响应都是 200，破坏 HTTP 语义；codegen 客户端需手写拆包。改用 RFC 9457 | 与国内惯例不同，需在文档说明 |
| 3 | 金额用 `BIGINT` 存分 | 浮点在金额计算中必然产生舍入误差 | 展示层需除 100 |
| 4 | 向量用 pgvector，不引入专用向量库 | 少一个组件，与业务表同库可做事务性更新，契合单机部署目标 | 亿级向量时需迁移 |
| 5 | 中文分词第一期用应用层 bigram | 零依赖，纯 SQL；商品标题短、术语密集，bigram 够用 | 长尾查询效果弱于 jieba |
| 6 | AI 只做路由，写操作走 GUI 确认 | 规避 prompt injection 与误操作资损；结构化操作 GUI 本就更快 | 演示时少一个「全对话下单」噱头 |
| 7 | 商品理解不使用 dtmrs | 幂等可重试的异步任务，队列即可 | — |
| 8 | 库存用条件原子更新而非乐观锁 | 高争抢下乐观锁反复重试失败；`WHERE available>=n` 单语句原子 | 需配合 CHECK 约束兜底 |
| 9 | 代码英文、设计文档中文 | 代码/Issue/提交信息全英文，便于国际协作；设计文档用中文，因为作者与早期贡献者都在中文环境 | 国际贡献者暂时只能读 README |
| 10 | 不把「语义检索」作为首要卖点 | Medusa 已内置（托管版）；差异点应落在本地推理与全链路覆盖 | 需要更长的一句话解释定位 |
| 11 | 提供官方 MCP Server 与 Agent Skills | Medusa / Saleor 已成标配；成本低且与 AI 原生定位咬合 | 需随 API 演进维护 |

> **ADR #9 为什么从「英文优先」改成现在这样**
>
> 原先写的是「README/代码/Issue 全英文，中文作为翻译版」。方向没错——
> 开源项目要国际贡献者就得降低语言门槛。但四份长设计文档翻译加上后续双语维护
> 是持续成本，而项目现在连一行代码都没有。**为一个还不存在的贡献者群体先付这笔钱，
> 顺序反了。**
>
> 等真的出现国际贡献者，那时也更清楚该优先翻哪几份。代价是短期内他们只能读 README。

### ADR #1 补注：cgo 嵌入已实测通过

这条决策原先挂着一个未验证的前提——「放弃 dtmrs 嵌入式模式（除非 cgo 打通）」，
而形态 A 的全部叙事都建立在它之上。已做实测，结论如下。

**结论：cgo 不需要「打通」，它本来就是通的。** 编译出 `libdtmrs.so` 后，Go 经 cgo
成功驱动嵌入式协调器完成 SAGA 提交、逆序补偿、拉取式异步分支、进程崩溃后的跨进程恢复，
并验证了同一段编排代码只改分支地址一行、`local://` 与 `http://` 两种形态都成立。
`local://` 是引擎 `parse_target` 里的真实分支，不是设计设想。

> 原先的悲观判断很可能源于一处误读：dtmrs 文档里「Go structurally cannot do this」
> 说的是 **Go 没法把自己编成可被嵌入的 `.so`**（Go 当 guest），
> 不是「Go 没法调别人的 `.so`」（Go 当 host）。方向正好相反。

**但有两条真实代价，比原先写的那条更要紧：**

1. **FFI 层只有 SAGA，没有 TCC。** C ABI 导出的 11 个符号里，事务提交入口只有
   `dtmrs_submit_saga`；Rust 侧的 `Embedded` 也只有 `saga()` / `submit_workflow()`。
   **换 Rust 也解决不了**——嵌入式 TCC 根本不存在。
   好在引擎层 TCC 与 SAGA 共用同一条分支调用路径，缺的只是提交 API。
   §7 把下单定为 SAGA 本就是对的；等真要做预售定金 / 多仓调拨时，
   得先给 dtmrs 补一个 `dtmrs_submit_tcc` 导出。
2. **`CGO_ENABLED=0` 静态编译确定失去**（已实测）。静态链接 `libdtmrs.a` 可行，
   单文件二进制约 15 MB。但 dtmrs 上游不提供预编译产物、CI 只跑 ubuntu-latest——
   Keel 要么要求贡献者装 Rust 工具链，要么自建多平台预编译流水线，
   等于替上游做发布工程。**这是形态 A 最大的真实成本，别低估。**

**诚实边界**：本次验证约 5 小时，证明的是「demo 能跑通」，不是「能上生产」。
尚未验证：高并发下的 OS 线程行为（最高优先级剩余风险）、barrier 三种异常的端到端表现、
macOS / arm64 构建。预计还需 5–7 人日。在此之前，形态 B（TC 作为同容器独立进程）
应作为逃生舱保留——两种形态共用同一套业务代码，不是二选一。

## 九、性能与容量目标

| 指标 | 目标 | 说明 |
|---|---|---|
| 搜索 P95 | < 300 ms | 含 reranker；超时降级见检索文档 |
| 下单 P95 | < 500 ms | 含 SAGA 三分支正向操作 |
| 支付回调处理 | < 200 ms | 渠道通常要求 5 s 内响应 |
| 商品详情 P95 | < 100 ms | 冗余字段避免 join |
| 单机容量 | 10 万 SKU / 1 万单日 | 形态 A |
| 理解服务吞吐 | 10 万商品文本向量 ≈ 5 分钟 | 批大小 64 |

## 十、安全

| 面 | 措施 |
|---|---|
| 支付回调 | 强制验签；失败返回 401 且不泄露内部状态 |
| 重复下单 | 强制 `Idempotency-Key`；落地为 `idempotency_keys` 表，唯一约束即锁，并存请求指纹与存档响应——同键不同体要拒绝，而不是静默吞掉 |
| 价格篡改 | 下单携带 `expected_payable_cents`，服务端复算不符则 409 |
| Prompt injection | 商品文本为第三方可控输入，进入 LLM 上下文前仅取结构化字段；所有写操作不由 LLM 执行 |
| 越权 | 订单/地址/券按 `user_id` 强制过滤，不信任前端传入 ID |
| 广告法合规 | 发布时同步拦截违禁词 |
| 资金安全 | 金额恒等式写入数据库 `CHECK` 约束 |

## 十一、工程规范（决定「精品」还是「demo」）

- `docker compose up` 一条命令起全栈，含种子数据
- CI：lint + test + build，绿标挂 README
- 核心逻辑必须有测试：**库存扣减、优惠计算、订单状态机**
- OpenAPI 为唯一接口真相源，前后端均由其生成代码
- 数据库变更走迁移工具（goose / atlas），禁止手改
- 语义化版本 + CHANGELOG + Release
- 独立文档站，在线 Demo 永久可用
- 结构化日志 + trace_id 贯穿全链路

## 十二、AI 能力全景

完整清单（37 项，含价值 / 难度 / 依赖 / 是否需数据积累）见
[AI 能力全景](./ai-capabilities.md)。此处只记核心判断：

**成本极不均匀，先铺底座再铺功能。** 三个底座——推理服务
（embed / rerank / generate / forecast）、商品理解服务、数据智能层——
建成后，清单中约三分之二的功能退化为「调两个接口 + 一段 prompt + 一个页面」。

**五项功能在早期做不出效果**（个性化推荐、尺码推荐、个性化排序、促销预测、
刷单识别），因其依赖用户行为数据积累。预留接口，不前期投入。
对应清单第 33–37 项（清单「需积累」列标**行为**的那五项）。

**三条纪律**：每个 AI 功能必须有评测方式；写操作永不由模型执行；
AI 故障不得阻塞交易主链路。
