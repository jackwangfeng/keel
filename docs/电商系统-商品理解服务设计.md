# 商品理解服务设计

## 定位

传统电商系统里，商品是**一堆字段**：标题、价格、库存、图片 URL。
系统只负责存取，不负责理解。

本服务把商品转换成**可被机器理解的对象**：向量、标准化属性、类目、
质量评分、合规状态、同款簇。所有 AI 功能消费同一份理解结果，
而不是各自重新处理一遍商品数据。

```
                        ┌──────────────────────────┐
  商家后台 ────────────►│                          │
  供应商导入 ──────────►│    商品理解服务           │
  批量回填 ────────────►│  Product Understanding   │
                        └────────────┬─────────────┘
                                     │ 统一理解结果
        ┌──────────────┬─────────────┼─────────────┬──────────────┐
        ▼              ▼             ▼             ▼              ▼
    语义搜索       拍照搜同款      对话导购      合规风控      同款比价
```

**架构对称性**：`dtmrs` 保障交易的一致性，本服务保障商品的语义。
两个自研内核，一左一右，各自可独立开源。

## 一、能力清单（可插拔 Processor）

每个能力是一个独立 processor，实现统一接口，可单独开关、单独重跑。

| Processor | 输入 | 输出 | 路径 |
|---|---|---|---|
| `text_embedding` | 标题/属性/类目 | 1024 维向量 | 慢 |
| `image_embedding` | 主图 | 768 维向量 | 慢 |
| `category_classify` | 标题 + 图 | 类目 ID + 置信度 | 慢 |
| `attribute_extract` | 标题 + 详情 | 标准化属性 KV | 慢 |
| `selling_points` | 标题 + 详情 | 卖点短语 ≤5 条 | 慢 |
| `image_quality` | 主图 | 清晰度/白底/占比评分 | 慢 |
| `compliance_check` | 全部文本 | 违禁词命中 + 风险等级 | **快** |
| `dedup_cluster` | 文本向量 + 图向量 | 同款簇 ID | 慢 |

```go
type Processor interface {
    Name() string
    // 该 processor 关心哪些字段 —— 决定增量重算的粒度
    InputFields() []string
    Process(ctx context.Context, in *ProductInput) (*ProcessorResult, error)
}
```

## 二、快慢路径分层

商品发布不能被 AI 阻塞，但合规又必须前置。因此拆两条路径：

### 快路径（同步，预算 < 200 ms）

只跑 `compliance_check`。命中「最」「第一」「国家级」这类广告法违禁词、
或类目资质缺失时**直接拒绝发布**并返回具体位置。

> 广告法违禁词在中国是硬约束，单次处罚起点二十万。这一步必须同步阻塞，
> 不能放异步。规则词表打底 + 小模型兜底变体（"蕞""No.1""巅峰之作"）。

#### 实现状态（M4 阶段 2）：落地了规则词表，**没有小模型兜底**

上面那段话描述的是目标形态。代码里今天真正存在的是它的前半句，
三条缺口写在明面上：

1. **小模型兜底变体没有做。** 上面点名的三个例子（"蕞" "No.1" "巅峰之作"）
   是被**列进词表**的，所以它们拦得住 —— 但那是枚举，不是识别。
   词表之外的新变体（"冣好"、"zui 好"、拆字、谐音、"最·好"
   这种用标点隔开的写法）今天一个也拦不住。
   没做的理由不是来不及：快路径预算是 200 ms，而一次生成式调用在共享 GPU 上
   远超这个数；按下面 §七「超时即拒绝」那条规矩，把它放进同步路径的效果是
   「引擎忙」直接变成「商家发不了货」。真要做，它得先有一条不在同步路径上的
   落点（比如上架后异步复查 + 命中则下架并通知），那是一次独立的设计。
2. **类目资质缺失拦不了，因为库里没有那个东西。** §三的商品域只有
   `categories` / `products` / `skus` / `product_images`，没有任何一张表记录
   商家资质。没有数据就没有判据。这条直接决定了词表的边界：医疗/保健用语
   （治疗、疗效、根治、特效）**刻意不在词表里** —— 它们的合法性取决于类目与
   资质，一家卖血压计的店说「用于高血压治疗」是合规的，而在没有资质数据的
   前提下列进词表，等于让那家店永远发不出商品且没有豁免出口。
3. **词表里没有裸的「最」和「第一」**（「国家级」本身是完整的绝对化用语，
   它在词表里）。上面正文那句
   「命中「最」「第一」「国家级」这类……」如果照字面实现，全站商家的标题会
   成片被拒：「最近」「最后」「最多可放 5 件」「第一次」「第一天」全是正常中文。
   《广告法》第九条禁的是**绝对化用语**，不是那两个字。所以词表里每一条都是
   短语（「最佳」「全网第一」「国家级」），代价是「本店第一」「价格最低哦」
   这类没被枚举到的说法漏得掉 —— 那正是第 1 条说的小模型该补的那一半。

合规结论**不落库**（不写 `product_understanding.results`），理由是一条实测过的
连锁反应：那张表上挂着 `touch_product_understanding_updated_at`，任何一次 UPDATE
都会把 `updated_at` 推到 now()，而那一列是索引触发点的水位线 ——
「发布时顺手记一条合规结论」会让刚上架的商品静默退出索引候选集，
症状是新品搜不到而且不报错。后果诚实说一条：后台看不到「这件商品上次因为
什么被拒」，商家只在那一次响应里见过它。

挂载点是两条路：`POST /admin/products/{id}/publication` 的 publish，
以及 `PATCH /admin/products/{id}` **当商品已经在架时**。判据是「这段文字会不会
出现在买家面前」—— 草稿不查（拦它只是在商家写到一半时打断人，而它一个买家
也看不到），下架与软删不查（它们只让文案消失）。在架时的 PATCH 必须查，
否则「先用干净标题上架、再 PATCH 成违禁标题」是一条两步都返回 200 的
完整绕过路径。存量商品（这一轮之前就在架的）不会被回头检查。

### 慢路径（异步，秒级）

其余全部进队列。商品先以 `understanding_status = pending` 上架，
理解结果陆续回填。搜索侧对 pending 商品降权但不隐藏。

```
发布请求 → 合规检查(同步) → 落库 → 入队 → 返回成功
                                   ↓
                          worker 池并行跑 processors
                                   ↓
                          结果回填 + 状态推进
```

## 三、数据模型

> **全部表结构见 `电商系统-数据模型设计.md` §8「语义检索与 AI 层」。**
> 本文档只讲这些表为什么长这样，不再重复 DDL——
> 数据模型文档是业务表的唯一真相源，两处各写一份必然漂移。

本服务落地依赖四张表，分三类：状态表、向量表（按模态两张）、同款簇表。

| 表 | 职责 | 关键点 |
|---|---|---|
| `product_understanding` | 每个商品的处理状态、各能力的输入指纹、非向量类结果 | `status`（0 待处理 / 1 部分完成 / 2 完成 / 3 失败）、`input_hashes` JSONB、`results` JSONB、`pipeline_version`、`last_error` / `retry_count` |
| `product_text_vectors` | 文本向量，`vector(1024)` | Qwen3-Embedding-0.6B 输出（M3 时是 BGE-M3，同为 1024 维），HNSW + cosine |
| `product_image_vectors` | 主图向量，`vector(768)` | clip-vit-l 输出，HNSW + cosine |
| `product_clusters` | 同款簇归属 | `cluster_id` + `confidence` + `method`（1 自动 / 2 人工确认 / 3 人工拆分） |

`results` 只放非向量结果（标准化属性、卖点、类目预测、质量分、合规结论）——
这些是变长的半结构化数据，JSONB 正合适；向量则不能塞进 JSONB，
它需要的是 HNSW 索引，只能作为 `vector` 列独立存放。

### 为什么向量按模态拆成两张表

一个很容易掉进去的坑：把两种向量塞进同一张表，
用 `(product_id, vector_type)` 做复合主键，`embedding` 一列通吃。
**这个写法在 pgvector 上根本跑不起来。**

`vector(N)` 的维度写在**列类型**上，同一列里所有行的维度必须一致。
而看 §1 的能力清单就知道，本服务的两种向量维度不同：

- `text_embedding` → **1024 维**（BGE-M3 / Qwen3-Embedding）
- `image_embedding` → **768 维**（clip-vit-l）

768 维的图像向量写不进 `vector(1024)` 的列，插入直接报错。
靠 `WHERE vector_type = 1` 这样的部分索引也救不了——
问题出在列类型上，不在索引上。

因此拆成 `product_text_vectors` 与 `product_image_vectors` 两张表，
各自 `PRIMARY KEY (product_id)`，各自建 HNSW 索引。

> **代价。** 多一张表；跨模态召回要自己 `UNION`（同款归并 §5 正是这种场景），
> 没有一条 SQL 通吃的写法。
> **换来的。** 除了「能跑」这个前提之外，两张表的 HNSW 参数可以分别调优——
> 文本向量和图像向量的分布本来就不一样，用同一组 `m` / `ef_construction`
> 只是凑合；换模型换维度时，也只影响单一模态那张表。
>
> 一期只嵌入主图，所以图像表主键是 `product_id`。
> 将来要做多图检索，主键改为 `(product_id, image_url)` 即可，
> 这个演进方向不会波及文本向量。

### 为什么按能力分别记 hash

单一 `content_hash` 太粗：改一张图，文本向量也会被判定为「需重算」。
按 processor 的 `InputFields()` 分别计算指纹，只重跑真正受影响的能力。

```
标题变更   → 仅重跑 text_embedding / category_classify / compliance_check
主图更换   → 仅重跑 image_embedding / image_quality
价格变更   → 不触发任何 processor
```

`input_hashes` 是**全系统判断「要不要重算」的唯一归口**：
两张向量表都不带 `content_hash` 列，语义检索层的增量更新
（`电商系统-语义检索层设计.md` §2.2）也查这里的
`input_hashes ->> 'text_embedding'`。

> 指纹如果跟着向量走，就得每张向量表各存一份，两处写同一件事，迟早对不上；
> 更要命的是粒度会退回到「整个商品的内容 hash」，改一张图连带触发
> 十万商品级别的文本向量重算。指纹的语义是「某个 processor 的输入变没变」，
> 它天然属于 processor 的状态表，不属于结果表。
> 代价：判断是否重算要多查一次 `product_understanding`，
> 但这条路径本来就是异步的，一次主键查询可以忽略。

## 四、版本管理与模型升级

每条结果携带 `model_name` + `model_version` + `pipeline_version`。

**升级策略：影子表 + 原子切换**，禁止原地更新。

```
1. 新模型写入影子表（如 product_text_vectors_v2），老表继续服务线上
2. 用离线评测集对比 v1 / v2 的 NDCG@10
3. 指标不劣化 → 改配置切读 → 观察 24 小时 → 删旧表
4. 任何时刻可回滚
```

影子表是**按模态各自升级**的：换文本模型只新建
`product_text_vectors_v2`，图像那张表不动，反之亦然。
这也是 §3 拆表的一个附带好处。

> 换模型经常同时换维度（1024 → 1536 之类）。`vector(N)` 的 N 是列级固定的，
> 所以即便没有灰度需求，升级也不可能原地 `UPDATE`——必须新建表。
> 这不是保守，是 pgvector 的物理约束。

灰度期间两套并存，按 `product_id % 100 < N` 分流，
`search_logs` 记录实际使用的版本以便归因。

## 五、同款归并（本服务最难的一块）

多供应商同款商品，标题写法千差万别：

```
"Apple iPhone 15 Pro 256GB 原色钛金属 国行"
"苹果15Pro 256G 原色 全网通5G 正品行货"
"iPhone15 Pro（256G/原色钛金属）官方标配"
```

传统规则（标题相似度、型号正则）做不好，向量匹配天然适配。

### 三阶段流程

**阶段 1 · 向量粗召回**
禁止全量两两比对（O(n²)，十万商品即百亿次）。
分别在 `product_text_vectors` 和 `product_image_vectors` 上各召回 top-20 候选，
把两个结果集按 `product_id` 取并集。

> 这是 §3 拆表的直接代价：两张表维度不同，不存在一条 SQL 同时扫两种向量的写法，
> 必须发两次查询再在应用层（或 `UNION`）合并。
> 好在这正是我们想要的行为——两路召回本来就该独立：
> 标题写法差异大但图一样的、图拍得不同但型号文本一致的，
> 各由一路兜住，取并集才不漏。若压进一张表用 `vector_type` 过滤，
> HNSW 反而要在混合空间里做带过滤的近似检索，召回质量更差。

**阶段 2 · 精判**
候选对送入判别逻辑：

```
必要条件（硬规则，任一不满足直接否决）：
  · 品牌一致（或一方为空）
  · 型号/货号一致（提取自标题的字母数字串）
  · 核心规格一致（容量/尺码/颜色）

充分条件（软信号，加权打分）：
  · 文本向量 cosine > 0.92
  · 图像向量 cosine > 0.88
  · Reranker 判定分 > 0.85
```

**阶段 3 · 聚类**
精判通过的边构成图，取连通分量作为同款簇。
增量场景下用「新商品挂靠到已有簇」而非全量重聚类。

### 阈值必须保守

**错误合并的代价远高于漏合并。**
两个不同商品被归为同款 → 比价页展示错误 → 用户按 A 的价格买到 B → 客诉与资损。
而漏合并只是少一个功能。

因此：
- 阈值宁高勿低
- 置信度 < 0.95 的合并进**人工审核队列**，不自动生效
- 提供人工「确认 / 拆分」操作，且人工结果优先级最高（`method = 2/3` 不被自动逻辑覆盖）

## 六、与推理引擎的接口

在已有 `/v1/embeddings`、`/v1/rerank` 之外，新增两个：

```
POST /v1/embeddings
  { "model": "Qwen3-Embedding-0", "texts":  [...],               "normalize": true }
    → { "embeddings": [[...]], "dim": 1024 }
  { "model": "clip-vit-l",        "images": ["<base64 或 url>"], "normalize": true }
    → { "embeddings": [[...]], "dim": 768 }

POST /v1/generate
  { "model": "qwen3-27b", "prompt": "...", "schema": {...}, "max_tokens": 512 }
  → { "text": "...", "json": {...} }
```

`schema` 参数用于**结构化输出约束**（属性抽取、卖点提取必须返回固定 JSON 结构）。
引擎侧用约束解码保证输出合法，避免解析失败重试——这是自建引擎相对通用 API
的一个实打实的优势。

**批处理要求**：索引侧批大小 32–64；禁止循环单条调用。

**`dim` 必须校验，不能只读不看**：响应里的 `dim` 要与目标向量表的列维度一致
（文本 1024 / 图像 768，见 §3），不一致时**拒绝写入并告警**，不要交给 Postgres 报错。
换模型或配错 `model` 名时，这是第一道也是唯一一道能给出可读原因的关卡。

`normalize: true` 对两个模型都必须传——向量表上的 HNSW 索引按
`vector_cosine_ops` 建立，写入未归一化的向量不会报错，只会悄悄拉低召回质量。

## 七、降级与容错

| 故障 | 行为 |
|---|---|
| 单个 processor 失败 | 标记该能力失败，其余继续，`status = 1` 部分完成 |
| 推理引擎不可用 | 任务留在队列，指数退避重试，商品照常上架 |
| 合规检查超时 | **保守拒绝**（唯一一处宁可误拒的地方） |
| 向量写入失败 | 搜索侧降级为纯关键词召回 |

重试策略：指数退避，最多 5 次，超限进死信队列并告警。
`retry_count` 和 `last_error` 落库，后台可见可手动重跑。

**原则：AI 层的任何故障都不得阻塞交易主链路。**

## 八、冷启动与批量回填

首次部署或模型升级时需全量处理存量商品。

- 按销量/浏览量降序处理，热门商品优先生效
- 全局限流（令牌桶），避免打满 GPU 影响线上查询
- 断点续传：以 `product_id` 游标记录进度
- 与线上查询共享推理引擎时，回填任务设低优先级

十万商品的文本 embedding，批大小 64、单批 200 ms，约 5 分钟可完成。
图像 embedding 慢一个量级，需预留一小时。

> **多租户下，「低优先级」不足以保护其他商家。**
>
> `priority` 只在租户内排序（见数据模型 §12）——A 商家把回填标成最低优先级，
> 也不妨碍这十万条任务占满整个 worker 池，而 B 商家的一条商品发布就卡在后面。
> **一个新商家导入一次商品目录，就能让所有其他店铺的搜索索引停止更新几小时。**
>
> 真正起作用的是队列的每租户在途上限：回填再多也只能占住有限几个 worker。
> 上面那条「低优先级」因此只解决**同一个商家内部**的先后——
> 他自己的回填不该挡住他自己的新品上架。
>
> 这也意味着：**大规模回填的实际完成时间取决于同时有多少租户在抢**，
> 上面那个「十万商品约 5 分钟」是独占推理引擎时的数字。

## 九、用户可感知的差异

技术设计最终要落到体验上。有了这层，App 相对传统电商的差别：

| 传统电商 | 本系统 |
|---|---|
| 搜「行李箱」，再自己筛尺寸材质 | 搜「适合出差带的轻便行李箱」直接出结果 |
| 搜不到 → 空白页 | 搜不到 → 给相近替代 + 澄清追问 |
| 想找同款只能自己翻 | 拍照搜同款 |
| 同一商品多个卖家各自独立 | 自动归并，一页比价 |
| 商品详情靠人工写 | 属性自动补全、卖点自动提炼 |
| 评价几千条只能自己翻 | 自动归纳「主要反馈：偏小半码、鞋底偏硬」 |
| 违禁词靠人工审 | 发布时同步拦截并指出位置 |

## 十、一个克制的说明：这里不用 dtmrs

商品理解是**幂等可重试的异步任务**，不是跨服务的强一致事务。
用普通任务队列 + 幂等键即可，强行套分布式事务只会增加复杂度。

`dtmrs` 的战场是交易链路（下单、支付、退款），不是这里。
**两个自研内核各守各的边界，不为了用而用。**

## 十一、实施顺序

| 阶段 | 内容 | 依赖 |
|---|---|---|
| 1 | 服务骨架 + 队列 + `text_embedding` | 推理引擎 `/v1/embeddings` |
| 2 | `compliance_check`（快路径） | 违禁词表 |
| 3 | `attribute_extract` + `selling_points` | `/v1/generate` + schema 约束 |
| 4 | `image_embedding` → 拍照搜同款 | 多模态模型 |
| 5 | `dedup_cluster` + 人工审核后台 | 阶段 1、4 |
| 6 | `image_quality` / `category_classify` | — |

阶段 1–2 是最小可用集：有向量就能搜，有合规就敢让商家自助发布。

> 阶段 6 的 `category_classify` 先落地了一个**零样本、只看文本**的版本，挂在批量导入的
> 预检上（标题向量 vs 类目路径名向量），实际做了什么、评测数字与阈值见 §十二。
> 阶段 3 仍然等 `/v1/generate`。
阶段 4 的拍照搜同款，边际成本最低而展示效果最强，建议优先于阶段 3。

## 十二、批量导入：这一步实际落地了什么

§一开头那张图里的「供应商导入」入口，第一版是**后台批量导入**
（契约 `/admin/product-imports`，后台「商品 → 批量导入」）。这一节记录它**实际**
用上了本服务的哪几样能力、哪几样没用上，免得读者按上面的目标形态以为都有了。

| 能力 | 状态 | 说明 |
|---|---|---|
| `compliance_check` | ✅ 用上了 | 预检里逐件跑同一张违禁词表，命中标到行与码点位置上。**只提示不阻断**：导入的是草稿，草稿不拦（§二实现状态那一节的判据），上架时照旧拦 |
| `category_classify` | ⚠️ 落地了一半 | 只有文本、只有零样本：标题向量 vs 类目路径名向量，见下 |
| `attribute_extract` | ❌ 没做 | 要 `/v1/generate`（带 schema 约束的结构化输出），infero 今天只有 `/v1/embeddings`。模板因此是**固定列**的——「从杂乱的供应商表格里抽 SKU 与属性」（ai-capabilities 第 1、2 项）仍然等生成接口 |
| `selling_points` | ❌ 没做 | 同上 |
| `text_embedding` 入库 | 照旧 | 导入建出的是草稿，派生数据索引任务（`internal/service/index.go`）按它原来的规则处理，导入这一步不另算商品向量 |
| 图片 | ❌ 只记录 | 图片 URL 原样留在导入回执里，不下载（SSRF，见 `internal/service/product_import.go` 文件头第四节），`image_embedding` 也就无从谈起 |

### 类目推荐怎么做的

- **输入**：商品的「标题 + 副标题」，前面加一句 Qwen3-Embedding 的任务指令
  （`Instruct: 给定一个电商商品标题，找出它所属的商品类目\nQuery: …`）；
  类目这一侧是每个**叶子**类目（启用中、没有启用中的子类目）的路径名
  （「服装 > 女装 > 连衣裙」），不带指令——这是该模型推荐的非对称检索用法。
- **打分**：余弦，取 Top 3。一次预检里全部商品与缺缓存的类目**合成一批**送去嵌入
  （§六「禁止循环单条调用」）。
- **类目向量缓存**：进程内，以路径名文本为键——改名、移动之后键就变了，旧向量自然不命中；
  每条缓存记着 `model_version`，引擎换了模型时整个缓存作废重算。
- **自动选中要过两道门**：Top-1 余弦 ≥ 0.50，且比 Top-2 高出 ≥ 0.03。过不了门的给候选、
  不替商家选，界面标「需人工确认」。
- **降级**：没配引擎（`not_configured`）或引擎不可用 / 超过 15 秒预算（`unavailable`）时，
  需要推荐的商品一律「需手选」，预检照常返回，导入不受影响（§七最后那条原则）。
- **确认导入这一步不调引擎**：推荐的类目由界面显式带回，服务端不会自动采用推荐——
  否则同一份预检结果可能因为确认时引擎一抖而导出不同的类目，事务也要为一次网络调用持锁。

在 §一的清单里它是「标题 + 图 → 类目 ID + 置信度」的慢路径能力；这里落地的是一个
**同步、零样本、只看文本**的版本，挂在预检这一步上。「拿店里已归好类的商品做近邻投票」
（`product_text_vectors` 里现成就有向量）会更准，但冷启动恰恰没有已归类的商品——
两路融合留给以后。

### 离线评测：数据、结果、阈值怎么定的

评测集在 `internal/understanding/testdata/category_eval/`，三份：

- `tree.txt`：一棵综合店的类目树，41 个叶子，刻意留了几组名字相近的同级类目
  （女装 / 男装各有「外套」、零食下的巧克力与坚果、咖啡机与咖啡豆与手冲壶）；
- `titles.txt`：123 条人工标注的商品标题（每个叶子 3 条，淘宝 / 京东式写法，
  每个类目至少一条不含类目名里的字）；
- `demo_seed.txt`：演示栈种子的 5 个类目与 23 件商品。

评测集的完整性（标注的类目在不在树里、每个叶子够不够 3 条）与算分逻辑在每一次
`make test-db` 里跑；对真引擎的那一半要 GPU，手动跑：

```bash
KEEL_EMBED_ENDPOINT=http://127.0.0.1:18081 make category-eval
```

2026-09-26 对 infero（Qwen3-Embedding-0.6B，F16）实测：

| 评测组 | 查询写法 | Top-1 | Top-3 |
|---|---|---:|---:|
| 综合店 41 叶子 × 123 条 | **带指令（线上用的）** | **83.7%** | **95.9%** |
| 同上 | 不带指令 | 83.7% | 96.7% |
| 演示种子 5 类目 × 23 件 | 带指令 | 60.9% | 78.3% |
| 同上 | 不带指令 | 56.5% | 78.3% |
| 演示种子去掉「默认分类」4 类目 × 16 件 | 带指令 | 87.5% | 100% |
| 同上 | 不带指令 | 81.2% | 100% |

演示种子那一组低，是因为七件咖啡器具挂在「默认分类」下——这四个字不描述商品，
向量上与咖啡毫无关系，它们**按构造**推不中。这正是零样本做法的边界：类目名得描述商品。

**阈值**。先试了只按 Top-1 余弦卡（综合店 × 带指令）：

| 余弦 ≥ | 自动选中 | precision |
|---:|---:|---:|
| 0.60 | 80.5% | 85.9% |
| 0.65 | 55.3% | 89.7% |
| 0.70 | 22.8% | 100% |

要 precision 过 95% 得卡到 0.70，那时只剩 23% 的商品被自动选中——余弦的绝对值更多反映
「标题写得像不像类目名」，而不是「分得清分不清」。推错的 20 条几乎都是 Top-1 与 Top-2
挤在一起的（「百褶裙」在连衣裙与半身裙之间只差 0.02，「双肩背包电脑包」在双肩包与行李箱
之间只差 0.003）。改按分差卡：

| 分差 ≥ | 自动选中 | precision |
|---:|---:|---:|
| 0.02 | 75.6% | 95.7% |
| **0.03** | **74.0%** | **96.7%** |
| 0.04 | 66.7% | 97.6% |
| 0.05 | 61.0% | 97.3% |

取 **分差 ≥ 0.03，另加余弦 ≥ 0.50 的底线**：底线在综合店这组上一条都不多挡
（数字与上表同一行），它防的是「店里没有一个类目对得上」时矮子里拔将军
（演示种子只有「默认分类」可选之类）。在这组判据下，综合店那组自动选中 91 / 123，
其中 88 条选对（precision 96.7%）；演示种子去掉「默认分类」后自动选中 13 / 16，对 12 条。
选带指令而不是不带：两者 Top-1 相同，但带指令时分差更有区分力（同样卡 0.03，
不带指令的 precision 只有 92.6%），而且在演示种子两组上 Top-1 都更高。

**这组数字要打折扣看**，说清楚三条：阈值是在同一份 123 条上挑的（没有独立的验证集，
数字偏乐观）；样本是按真实写法编的，不是从真实商家的导入里采的；类目树也是编的。
所以 `category_eval_realengine_test.go` 只断言两条底线（Top-3 ≥ 85%、当前判据下
precision ≥ 95%），守的是「换了模型或改了拼法之后没有塌掉」。**换模型必须重跑评测、
重定这两个数**——余弦的尺度是模型相关的，失效时不会报错。攒到真实导入数据之后，
应当用「商家最终选定的类目」做标注，拆出验证集再定一次。
