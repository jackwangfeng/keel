## 一、目标

把 Keel 从「设计基本成型、但对外承诺与实际内容对不上」推进到
**「文档自洽、承诺兑现、可以开始写代码」**。

这一轮不写业务代码。产出全部是文档与契约。

### 为什么先做这个

上一轮评审把设计本身的硬伤修掉了（向量表维度冲突、失效索引、SAGA/TCC 措辞混用、
缺失的六类表）。剩下的债不在设计质量，而在**完整性与诚实度**：

- README 链接的 `CONTRIBUTING.md`、`LICENSE` 不存在
- 架构文档链接的四份子文档路径全错，`ai-capabilities.md` 从未写过
- README 挂着 `CI-passing` 徽章，链接是 `(#)`，而 CI 并不存在
- 契约要求客户端提供 `evidence_urls` / `avatar_url`，却没有任何上传接口

这些对一个尚未开工的项目不致命，但对一个**准备公开的开源项目**是硬伤：
第一个点进来的人看到的就是坏链接和虚标徽章。而且这批债越往后拖越贵——
等代码写起来，改契约就要动已生成的客户端。

## 二、已确认的决策

### 决策 1 · 文档以中文为准，改链接就近

四份设计文档保持中文文件名与中文内容，移入 `docs/`，把 README 与架构文档里的
链接改成实际路径。

ADR #9「英文优先」改写为诚实表述：**代码、Issue、提交信息用英文，设计文档用中文**。

> **为什么不翻成英文**：ADR #9 的原意是降低国际贡献者门槛，方向没错，但四份长文档
> 翻译加后续双语维护是持续成本，而项目现在连代码都没有——为一个还不存在的贡献者
> 群体先付这笔成本，顺序反了。等真有国际贡献者出现再翻，那时也更清楚该翻哪几份。
>
> 代价：短期内国际贡献者只能读 README。接受。

### 决策 2 · 文件存储：接口抽象 + 一期本地磁盘

定义 Storage 接口（put / delete / 签名 URL），一期只实现本地磁盘 driver，
预留 S3 driver 位置。

> **为什么不直接上 MinIO**：README 的核心卖点之一是「只有一个数据库，
> 不需要 Redis / RabbitMQ / ES」。加对象存储要么破坏这句话，要么逼着改写卖点。
> 而本地磁盘 driver 不是新增组件——它就是容器的一个卷。
>
> 更重要的是，这与 dtmrs 那套「部署形态是配置，不是重写」的主张**同构**：
> 形态 A 用本地磁盘，形态 B/C 换 S3 driver，业务代码不改。项目的架构主张
> 应当在每一处都成立，而不只在事务层成立。
>
> 代价：形态 A 多实例部署时要共享卷；换 S3 时多一个组件（届时 README 措辞需调整）。

### 决策 3 · AI 能力清单由推导产出，人工审定

从 README 四栏、架构 §11、商品理解服务的 processor 清单、检索层设计中抽取能力项，
逐项标注价值 / 难度 / 依赖 / 是否需数据积累，成稿后人工增删。

**若推导结果不是 37 项，改架构 §11 里的数字，不凑数。**

## 三、两个实现层面的判断

### 3.1 `uploads` 建表，不是只写磁盘返回 URL

**需要表的三个理由**：

1. **归属校验**。退款凭证是隐私内容，只写磁盘意味着任何人拿到 URL 就能看别人的
   退货照片。必须能查「这个文件属于谁」。
2. **孤儿回收**。用户上传了凭证但没提交退款申请，文件就永远留在磁盘上。
   要能扫出未被引用的文件并清理。
3. **迁移能力**。将来换 S3 driver 需要批量搬运存量文件，没有清单就搬不了。

清理任务挂在已有的 `jobs` 表上，**不引入新机制**。

### 3.2 README「只有一个数据库」保留，加脚注

这句话的实质承诺是「不用额外起服务」，本地磁盘卷没有破坏它。
但要诚实标注：换 S3 形态时会多一个组件。

## 五、并行与串行

先把文件占用摊开看：

| commit | 写入的文件 |
|---|---|
| 1 | 总体架构、README ×2、四份文档（路径变更） |
| 2 | README ×2、LICENSE（新）、CONTRIBUTING.md（新） |
| 3 | 数据模型、OpenAPI、README ×2 |
| 4 | OpenAPI |
| 5 | ai-capabilities.md（新）、总体架构 |

**结论：五组几乎全部串行，真实并行度接近 1。**

- README ×2 被 commit 1、2、3 共同写入
- 总体架构被 commit 1、5 共同写入
- OpenAPI 被 commit 3、4 共同写入

> 初稿里我写的是「并行度为 2，commit 5 可与 1–2 并行」，**那是错的**——
> 漏看了 commit 5 要改架构 §11，而 commit 1 也在改同一份文件的 ADR #9 与链接。
> 这正是上一轮靠「文件独占」才避免掉的冲突类型，在计划阶段就该算清楚。

**唯一真正可并行的部分**：`ai-capabilities.md` 是新建文件，它的**内容起草**
不碰任何既有文件，可以与 commit 1–2 同时进行；只有最后「架构 §11 对齐」那一步
需要排到 commit 1 之后。因此 commit 5 拆成两步：

- 5a 起草 `docs/ai-capabilities.md`（可并行）
- 5b 架构 §11 数字与链接对齐（须在 commit 1 之后）

## 七、明确不做

- **不写业务代码**。本轮产出全部是文档与契约。
- **不翻译设计文档**（决策 1）。
- **不实现 Storage 的 S3 driver**，只留接口位置。
- **不建 CI**。摘掉虚标徽章即可；真做 CI 属于 M1 工程骨架，不在本轮。
- **不碰 dtmrs 上生产前的 5–7 人日验证**（高并发线程行为、barrier 端到端、
  多平台构建）。那是独立议题，且需要先有代码。
