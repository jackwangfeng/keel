## 开工前定下的四件事

### 一、RLS 让 pgvector 的 post-filter 陷阱从「可能」变成「必然」，而且应用绕不开

语义检索层 §2.4 讲了这个陷阱：HNSW 是近似索引，规划器可能先取向量最近的 N 条
再过滤，类目稀疏时最终返回远少于 N 条、甚至为空。文档已经指出多租户把它从
「偶尔踩」变成「每个查询都踩」。

**但实际情况比文档写的更棘手一层。** `product_text_vectors` 带 `merchant_id`，
是 tenant 类，策略是 `merchant_id = current_merchant()`——**那个过滤条件不是
应用写在 SQL 里的 `WHERE`，是数据库注入的**。也就是说：

- 应用**看不见**它，也**改不掉**它
- 「过量召回再过滤」这个降级方案（§2.4 方案 2）在应用层**根本实现不了**——
  应用拿到的已经是被过滤过的结果，它不知道自己少拿了多少
- 小商家几百个商品，而 HNSW 先在全库几十万条向量里取最近的 N 条：
  **一条都不剩是正常结果，不是异常**

所以迭代扫描（`hnsw.iterative_scan`）不是优化项，是能用的前提；它是会话级 GUC，
必须设在**检索用的那条连接**上——也就是 `repository.WithTenant` 那一层，
和 `SET LOCAL app.merchant_id` 同一个地方。

**这一条必须用实验定下来，不许照抄文档的推荐值。** 要造出的场景是：
一个大库（几十家商家、几万条向量）里，一家只有几百个商品的小商家去搜索。
先证明不设迭代扫描时**真的召回不足或为空**，再证明设了之后召回正常。
没有前半段，后半段证明不了任何事。

如果实测发现迭代扫描不够，第二方案是按 `merchant_id` 做分区索引
（§2.4 方案 3，文档说「租户数不多时这是最干净的解法」）。

### 二、推理引擎必须是真的

验收标准是「搜『连衣裙』能返回相关商品」。一个哈希凑出来的伪 embedding 能让
所有测试变绿，而搜索结果毫无意义——那正是这个仓库一直在消灭的那类东西。

约束：

- 走语义检索层 §10 定的接口（`POST /v1/embed`，批量，`normalize: true`），
  这是 AI 层与引擎的**唯一耦合点**
- 向量**必须 L2 归一化**后写入，配合 `vector_cosine_ops`。§2.3 写明了：
  写入未归一化的向量**不会报错，只会悄悄拉低召回质量**——所以要有一条测试
  真的去验归一化，而不是相信 `normalize: true` 传过去了
- 模型与维度由数据模型定死：`vector(1024)`，BGE-M3。换模型等于改 DDL
- 测试里可以用确定性的替身，但**替身不许能在生产路径上被默认选中**，
  而且要有一条测试证明「替身跑不出真实的语义相关性」——否则替身会悄悄变成事实

引擎跑不动或太重时，**说出来并给出证据**（镜像体积、CPU 单次耗时、内存），
不要默默换一个小模型然后让 DDL 和文档对不上。

### 三、compose 要换 pgvector 底座

现在是官方 `postgres:16`，`\dx` 只有 plpgsql。README 的「还没在盒子里的」
那一节列着 pgvector 与推理引擎——M3 把它们放进盒子，那一节要跟着改。

注意 `scripts/check_promises.py` 有一条：README 快速开始里出现的 localhost
端口必须在 compose 里真的映射。

### 四、增量更新的触发点

§2.2 讲了增量更新。商品标题、副标题、类目变了，向量就该重算。**这件事要么
有机制，要么有闸门**——不能靠「记得调一下」。现在库里有 `touch_updated_at`
触发器，`product_text_vectors.updated_at` 与 `products.updated_at` 的先后关系
是一个现成的、可机械检查的判据。

## 关于「CPU 单条 62ms vs §8 预算 15ms」：M3 不需要为它做任何事

推理引擎落地后实测:CPU(20 核,无 GPU)单条 embedding **62ms**,批量
31–35ms/条。而语义检索层 §8 给 query embedding 的预算是 **15ms**——超了 4 倍。

**但那是单项预算,不是总预算,而总预算没超。** §8 的链路是 query embedding 与
关键词召回**并行取 max**,之后串行:

| 阶段 | §8 预算 | M3 实际 |
|---|---|---|
| Query embedding ∥ 关键词召回 | max(15, 20) = 20 | **max(62, 20) = 62** |
| 向量召回(HNSW,`ef_search=100`) | 30 | 30 |
| RRF 融合 | 1 | 1 |
| ~~Reranker top-50~~ | ~~80~~ | **M3 不含**(§11 阶段 3,路线图 M5) |
| 业务重排 + 结果组装 | 15 | 15 |
| **合计** | ~66 | **~108** |

目标是 **P95 < 300ms**,108ms 有三倍余量。

**所以 M3 不换模型、不上 GPU、不加 query 缓存。** 三者都是真实可选项,但现在做
等于为一个不存在的问题付代价:换模型要连 DDL 一起改(维度 1024 是写在列类型上的),
上 GPU 要改部署形态,而缓存会在还没有离线评测集(§9.1)的时候引入一层
「结果为什么变了」的不确定性。

**要重算这笔账的时点是 Reranker 落地那一轮**(188ms,仍在 300 以内,但那时
真正的问题不是单次延迟而是并发下的 CPU 争抢)。谁做到那一步,回来看这一节。

> 顺带:索引侧完全不受影响(批 32 时 33ms/条),而 M3 的大头是索引侧。

### 第三次修正:这笔账在长查询上不成立

上面那张表算的是**短**查询。实测 embedding 耗时随长度线性涨,而超时是个常数:

```
3 字   → 0.048s      60 字  → 0.125s
150 字 → 0.258s      200 字 → 0.424s      600 字 → 0.980s
```

契约允许 `maxLength: 200`,所以在**契约允许长度的 75%** 处(150 字)就已经越过
当时那个 250ms 的常数超时,向量路整个没了、只剩关键词——而客户端看到的是一个
正常的 200,`strategy` 照样回 `rrf-v1`。M3 独立验收实测复现过。

修法是让等待上限随长度走,代价是**200 字查询现在要 548ms,超出 P95 < 300ms
的目标**。这是刻意的取舍:宁可慢,也不要静默少做。真要把它压回去有三条路,
都不在 M3 范围内:

- 给引擎调用加**全局并发上限**(信号量)——让前 N 个跑满速、其余立刻降级,
  而不是让所有人一起慢。这是洪水复测量出来的那条:限流把爆炸半径从 20 缩到 8,
  但放行的 8 个仍然一起压在 CPU 上,同时的短查询照样降级
- 上 GPU(架构 §6 形态 B/C)
- 换更小的 embedding 模型(要连 DDL 一起改,维度写在列类型上)

**这笔账已经错过三次**,每次都是同一个毛病:拿一个场景的数字当成全部场景的。
第一次把单项预算当成总预算,第二次没算 Reranker 不在 M3 里,第三次拿短查询的
62ms 当成 query embedding 的耗时。下一个动这段的人请先问:**这个数字是在什么
输入上量的?**

## 每个任务的硬性要求（沿用 M1/M2）

1. **变异验证**：删掉被守护的那段逻辑（只改语义、不破坏可编译性），确认真的红，
   而且**红的是它**。M2 期间抓到四次「断言存在但没有因果关系」，其中两次是
   实现者自查出来的——这是本仓库的常见失败，不是假想。
2. 冷库 `make test-db` 全绿、`./scripts/check-all.sh` 全绿且跑完 `git status` 干净。
3. 新表必须在设计文档里有 DDL（`TestEveryTableInTheDatabaseIsDocumented` 会查），
   并在 `db/tenancy.json` 里归好类（不需要豁免就别加条目）。
4. 本机验证不了的**如实标注**，不要用「应该可以」蒙混。
5. 发现计划自相矛盾或与仓库既有决定冲突，**先说出来再动手**。M2 期间计划被
   实测推翻过四次（barrier 谁建、Rust 下限、`/etc/passwd`、二阶段消息存不存在），
   每一次都是实现者先说出来的。

## M2 收口还欠两笔，M3 期间要还

M2 验收提的 Critical（webhook 的错误日志是个黑洞）与 I2/I3 已经修完，剩两条：

- **I4：`scripts/smoke.sh` 对下单/支付零覆盖。** `grep -c "orders\|webhooks\|payments"`
  = 0。M2 主链路完全靠 `internal/handler` 的 httptest 撑着——那些测试不经过真实
  HTTP server、不经过 compose 起来的那个镜像。镜像里 `libdtmrs.so` 链接坏了、
  `KEEL_DTM_DSN` 指到不可写的路径、webhook 路由忘了挂进 v1 组，smoke 照样全绿。
  M3 加完检索之后，进程外唯一的验证仍然只看 `/products`。
- **I5：支付回调密钥住在 `shop_settings.extra`，而那是全库唯一一张刻意没有 RLS
  的表**（tenant-root 类，理由正当：租户解析要在 `SET LOCAL` 之前读它）。实测以
  `keel_app` 带着租户 2 的上下文能读出租户 1 的 `notify_secret`——全仓库唯一一份
  「拿到就能伪造一笔支付」的数据没有数据库层兜底，只剩一道应用层防线（那道防线
  有测试盯着，所以是「只有一层」不是「没有」）。
  最便宜的止血在 `db/queries` 里加 merchant_id 复核——**但那条路被
  `check_query_tenancy.py` 堵死了**（应用层不许写租户过滤）。所以正解是把密钥挪进
  一张有 RLS 的表，那要动数据模型 §8 与种子。
