# 语义检索层设计

本文档描述电商系统的检索与推荐层。核心主张：**语义相关 ≠ 应该卖**。
通用向量检索只解决前者，电商必须同时解决后者。这一层的差异化全在于此。

所有模型（Embedding / Reranker / LLM）**本地推理**：embedding 这一半从 M4 起
跑在自研的 [infero](https://github.com/jackwangfeng/infero) 上
（Qwen3-Embedding-0.6B，1024 维），rerank 与 LLM 那几半在 M5 之后陆续接。
**零外部 API、数据不出网。**

> infero 只有 CUDA / Metal 后端，**今天没有 CPU 后端**。所以没有 GPU 的部署
> 不配 `KEEL_EMBED_ENDPOINT`，`/search` 走 §8 的纯关键词降级链 —— 那是一条
> 设计好的、有执行者的路径，不是故障。详见[总体架构](./电商系统-总体架构.md) §6 形态 A。

> **实现状态（M5）**：双路召回 → RRF 融合 → **业务重排**（仅库存因子）已上线；
> **cross-encoder 精排仍未实现**——infero 还没有 `/v1/rerank`（§10），这一层没有可调的东西。
> 默认策略 `rrf-biz-v1`，`rrf-v1`（不做业务重排）可显式请求作对照（§9.3）；
> 每次检索写一行 `search_logs`（§9，数据模型 §8），`/search` 回 `trace_id`，
> 点击 / 加购 / 下单经 `POST /search/events` 回填到同一行（§9.2）。
> `explain: true` 只列出这一次真正跑过的阶段：`scores.rerank` 永远不出现，
> 向量路没跑成时 `scores.vector` 也不出现。

## 一、总体流水线

```
                          ┌─ 查询理解 (可选 LLM) ─┐
   用户 query ────────────►│  纠错 / 意图抽取      │
                          └──────────┬───────────┘
                                     │
                 ┌───────────────────┴───────────────────┐
                 ▼                                       ▼
        向量召回 top-100                         关键词召回 top-100
     (pgvector HNSW, cosine)                   (bigram tsvector)
                 └───────────────────┬───────────────────┘
                                     ▼
                            RRF 融合 → top-50
                                     ▼
                     Reranker 精排 (cross-encoder) → top-30
                                     ▼
                   业务重排 (库存 × 活动 × 口碑 × 时效)
                                     ▼
                                 最终 top-N
```

**为什么必须两路召回**

| 场景 | 纯向量 | 纯关键词 |
|---|---|---|
| "适合送长辈的保暖礼物" | ✅ | ❌ 无法理解意图 |
| "iPhone 15 Pro 256G 原色" | ⚠️ 易串型号 | ✅ 精确 |
| "A4 打印纸 70g" | ⚠️ 规格易漂移 | ✅ |
| "夏天穿着不闷的鞋" | ✅ | ❌ |

精确型号、规格、货号必须靠关键词兜底；模糊意图必须靠向量。
少任何一路，都有一整类查询失效。

## 二、索引侧：Embedding 的生成与维护

### 2.1 参与 Embedding 的文本（最影响效果的一步）

不是简单把标题加描述拼起来。按结构化模板组织，并**刻意排除高频变动字段**：

```
{标题}
{标题}                      ← 重复一次，提升标题权重
类目：{一级} > {二级} > {三级}
品牌：{品牌名}
规格：{颜色} {尺码} {材质} {规格值...}
适用：{适用人群} {适用场景} {适用季节}
卖点：{卖点短语，最多 5 条}
```

**必须排除的字段**

| 字段 | 排除理由 |
|---|---|
| 价格、库存 | 高频变动 → `text_embedding` 指纹天天变 → 天天重算 |
| 促销文案（"限时秒杀""买二送一"） | 与商品语义无关，且频繁变动 |
| SEO 关键词堆砌 | 稀释语义，拉低向量质量 |
| 详情富文本 HTML | 噪声极大，长度爆炸 |

> 这条是工程与效果的交点：把变动字段放进 embedding，会让增量更新机制
> 完全失效——每天全量重算 10 万商品，成本和延迟都不可接受。

### 2.2 增量更新

```sql
-- 商品变更后，仅当 text_embedding 这一能力的输入指纹改变才重算
SELECT product_id FROM product_understanding
WHERE product_id = $1
  AND input_hashes ->> 'text_embedding' = $2;
-- 命中 → 跳过；未命中 → 调推理引擎生成 → UPSERT product_text_vectors
```

> **指纹为什么不放在向量表里。** 指纹的语义是「某个 processor 的输入有没有变」，
> 而不是「某张向量表里存的是什么」。放进向量表就必须每张表各存一份，
> 两处写同一件事，迟早漂移。统一归口到
> `product_understanding.input_hashes`（商品理解服务 §3）后，
> 指纹还能按 processor 分别记：改一张主图只让 `image_embedding` 失效，
> 文本向量不必重算；改标题反过来。这比单一 `content_hash` 严格更优——
> 粒度更细，且不会漏判。
> 代价：检索侧判断是否重算要多查一张表。但这条路径本来就是异步的，
> 一次主键查询的开销可以忽略。

**更新触发时机**

| 触发 | 处理方式 | 时效要求 |
|---|---|---|
| 商品新建/上架 | 同步生成（阻塞上架完成） | 立即 |
| 标题/属性/类目变更 | 异步队列 | < 1 分钟 |
| 价格/库存变更 | **不触发**（不在嵌入文本内） | — |
| 模型版本升级 | 全量重建到新表，双写后原子切换 | 离线 |

> **落地位置（M3 Task 3）**：判定在 `internal/service/index.go` 的 `decide`，
> 触发点在 `db/queries/semantic.sql` 的 `ListStaleProductsForIndex`。
> 两段判据为什么必须分开（时间戳只能当触发点、判定只能看指纹），
> 论证与实测写在 `db/migrations/00016_semantic_layer.sql` 的文件头第四节。
> 上表里「模型版本升级」那一行的影子表方案**本轮没有实现**，当前的人工杠杆是
> `go run ./cmd/keel-index -force`（无条件重算，维度不变时够用）。

模型升级必须用**影子表 + 切换**，不能原地更新：
`product_text_vectors_v2` 建完并验证后，改配置切读，保留 v1 可回滚。
换模型往往同时换维度（`vector(N)` 的 N 是列级固定的），
这本身也决定了升级只能新建表，不可能原地 `UPDATE`。

### 2.3 向量存储

> **表结构见 `电商系统-数据模型设计.md` §8「语义检索与 AI 层」。**
> 本文档不再重复 DDL——全部业务表以数据模型文档为唯一真相源，
> 两处各写一份的结果一定是两处不一致。

需要知道的只有一件事：向量表**按模态拆成了两张**，
`product_text_vectors`（`vector(1024)`，Qwen3-Embedding-0.6B）与
`product_image_vectors`（`vector(768)`，clip-vit-l），
均以 `product_id` 为主键。原因是 pgvector 的维度写在列类型上，
文本 1024 与图像 768 无法共存于同一列（详见商品理解服务 §3）。
本文档的向量召回只查 `product_text_vectors`；
图像那张表服务于拍照搜同款与同款归并。

拆表对检索侧的实际影响：跨模态召回要自己 `UNION`，没有一条 SQL 通吃的写法。
换来的好处是 HNSW 参数可以按模态分别调——两种向量的分布并不一样。

**HNSW 参数与写入约定**（这几条属于检索侧的工程决策，留在本文档）

- `m = 16` / `ef_construction = 64`：十万到百万量级商品的通用起点。
  提高 `m` 提升召回率但索引变大、构建变慢；
  `ef_construction` 只影响建索引时的质量与耗时，不影响查询开销。
  在有离线评测集（§9.1）之前不要凭感觉调这两个值。
- 查询时 `SET hnsw.ef_search = 100;`。pgvector 默认 40 偏低，
  召回 top-100 时候选池本身还不够 100 条，召回率会明显掉。
  这是会话级参数，在检索连接上设置，不必改索引。
- 向量**必须 L2 归一化**后写入，配合 `vector_cosine_ops` 使用。
  推理引擎的 `/v1/embeddings` 带 `normalize: true` 参数（§10），
  归一化在引擎侧完成；归一化之后余弦距离与内积等价，
  但索引一旦按 `vector_cosine_ops` 建好，写入未归一化的向量会让距离计算失真，
  且这种错误不会报错、只会悄悄拉低召回质量。

### 2.4 pgvector 的一个真实陷阱：带过滤的向量检索

```sql
-- ❌ 危险写法
SELECT product_id FROM product_text_vectors tv
JOIN products p ON p.id = tv.product_id
WHERE p.category_id = 123 AND p.status = 1
ORDER BY tv.embedding <=> $1 LIMIT 100;
```

HNSW 是近似索引，规划器可能先取向量最近的 N 条再过滤（post-filter），
若该类目商品稀疏，**最终返回远少于 100 条，甚至为空**。

**三种对策**

1. **pgvector 0.8+ 的迭代扫描**（推荐）
   ```sql
   SET hnsw.iterative_scan = relaxed_order;
   SET hnsw.max_scan_tuples = 20000;
   ```
2. **过量召回再过滤**：取 top-500 后在应用层过滤到 100，简单粗暴但可控
3. **分区索引**：按大类目分区建索引，过滤条件转为分区裁剪

第一期用方案 1，降级方案用 2。

> **多租户把这件事从「可选」变成了「必须」。** 每一次检索都带
> `WHERE merchant_id = ?`，也就是说**每个查询都会踩上面那个 post-filter 陷阱**，
> 不再只是「类目稀疏时偶尔踩」。
>
> 小商家的商品数可能只有几百，而 HNSW 会先在全库几十万条向量里取最近的 N 条
> 再过滤——结果很可能一条都不剩。**这不是性能问题，是功能直接失效。**
>
> 所以迭代扫描不是优化项，是能用的前提。另一个值得认真考虑的方案是按
> `merchant_id` 做分区索引，让过滤变成分区裁剪——租户数不多时这是最干净的解法。

## 三、关键词召回：中文分词的务实选择

PostgreSQL 的 `to_tsvector('simple', ...)` 对中文会把整句当成一个 token，**完全不可用**。

| 方案 | 部署成本 | 效果 | 结论 |
|---|---|---|---|
| `pg_jieba` / `zhparser` | 需编译扩展，自打 Docker 镜像 | 好 | 第二期 |
| Meilisearch | 单二进制，自带中文分词 | 好 | 备选 |
| **应用层 bigram + simple 配置** | **零成本，纯 SQL** | 够用 | **第一期** |

### bigram 方案

应用层把中文切成二元组写入独立列：

```
"红色连衣裙" → "红色 色连 连衣 衣裙"
```

落库结构是 `products` 上的两列：应用层写入的 `search_text`（bigram 串），
以及由它生成的 `search_vector`（`tsvector`，GIN 索引）。
**列定义与索引见 `电商系统-数据模型设计.md` §8「语义检索与 AI 层」的「关键词召回」小节**，
本文档不重复 DDL。

> 关键点是分词发生在**应用层**，不在数据库里：`search_vector` 由 `search_text`
> 生成而不是由 `title` 生成。`to_tsvector('simple', title)` 会把整句中文当成一个
> token，这正是本节开头说的「完全不可用」。切好词再交给 Postgres，
> `simple` 配置就够了，不需要任何扩展。
> 代价：`search_text` 由应用层维护，标题变更时必须同步重写，
> 忘了写就等于这条商品从关键词路消失了——这条写入必须和商品更新在同一个事务里。

查询时对 query 做同样的 bigram 切分，用 `websearch_to_tsquery` 或手工构造。
英文和数字（型号、规格）按空格与边界正常切词，不做 bigram。

bigram 对商品搜索意外地够用——商品标题短、术语密集，恰好是 bigram 的舒适区。
效果不足时再上 pg_jieba，索引结构不用改。

## 四、融合：RRF

```
RRF(d) = Σ_i  1 / (k + rank_i(d))       k = 60
```

对每个文档，累加它在各路召回中排名的倒数。

**为什么用 RRF 而不是加权分数融合**

- 向量的 cosine 相似度与 BM25 分数**量纲完全不同**，归一化后仍不可比
- 加权融合需要调 `α`，而最优 `α` 随查询类型变化，无法用单一常数覆盖
- RRF 只用排名，对分数分布免疫，无需调参，工程上最省心

`k = 60` 是文献通用默认值，直接用，不必调。

## 五、精排：Cross-Encoder Reranker

> **未实现（M5 时点）。** 推理引擎 infero 目前只提供 `/v1/embeddings`，
> §10 的 `/v1/rerank` 还只在纸上，所以这一层没有东西可调。代码里没有任何
> 「精排」的占位：`internal/service/search.go` 不声称做了它，`explain` 里
> `scores.rerank` 永远缺席，`search_logs.stages` 里也不会出现它；契约描述里的
> 「Reranker 精排」挂在 `handler/contract_test.go` 的 `NotYetImplementedStage` 上。
> 精排落地时要同时重算 §8 的延迟账，并重新审视 §6 里被推迟的时效 / 销量因子。

```
输入：(query, doc_text) 成对
模型：bge-reranker-v2-m3（或同级）
输入量：top-50 → 输出 top-30
```

与双塔 embedding 的区别：cross-encoder 让 query 与文档做**全交互注意力**，
精度显著高于向量相似度，代价是无法预计算，只能在线推理。

**这一步是延迟大头，也是自研推理引擎的价值所在。**
50 个 pair 的批量推理，在本地引擎上可控制在几十毫秒；
若走外部 API，网络往返就已经超预算，且每次搜索都产生费用。

工程要点：

- 送入 reranker 的文档文本要**截断**（标题 + 核心属性，控制在 128 token 内），
  过长会线性拉高延迟且收益递减
- 批量一次送入，不要循环单条调用
- 设置超时（如 80ms），超时则降级为「跳过精排，直接用 RRF 结果」

## 六、业务重排：本系统与通用向量检索的分界线

语义最相关的商品，**不一定是应该展示的商品**。缺货的、活动已结束的、
差评如潮的商品排在首位，是搜索体验的灾难。

### 采用乘性衰减，而非加性扣分

```
final_score = rerank_score
            × w_stock        // 库存
            × w_promo        // 活动有效性
            × w_quality      // 口碑
            × w_freshness    // 时效
```

硬约束应当接近归零而非扣几分——加性扣分在高相关度下仍可能排到前面。

| 因子 | 取值 |
|---|---|
| `w_stock` | 有货 `1.0`；预售 `0.85`；缺货 `0.05` |
| `w_promo` | 活动进行中 `1.10`；无活动 `1.0`；活动已结束 `0.90` |
| `w_quality` | `0.8 + 0.4 × 好评率` |
| `w_freshness` | 新品 30 天内 `1.05`；一年以上 `0.95` |

销量用对数缩放叠加，避免头部商品垄断：
```
w_sales = 1 + 0.1 × log10(1 + sales_count)
```

**硬过滤**（不参与打分，直接剔除）：下架、删除、区域不可售、黑名单。

### M5 落地了什么、没落地什么

实现在 `internal/search/business.go`，接在 RRF 融合之后、截断到 `size` **之前**
（作用在融合出的全部候选上——否则缺货商品只会在第一页里往下挪几位，
而不是让出位置给第一页之外的有货商品）。

**因为精排还没有，乘子乘在 RRF 分上**：`final = rrf × business`。

| 因子 | 状态 | 说明 |
|---|---|---|
| `w_stock` | **已实现** | 有货 `1.0`；缺货 `0.05`。RRF 分的值域极窄（两路第一 2/61，单路第 300 名 1/360），0.05 恰好把最好的缺货候选压到最差的有货候选之下：缺货一律排在有货之后，缺货之间保持相关度先后。「预售 0.85」那一档没有——没有预售状态 |
| `w_promo` | 未实现 | 活动表 00044 起才有（数据模型 §7·二，商品标签已在用）；检索路径没接，「活动失效」的口径（结束的活动算失效，还是等同于从没参加过）要先定 |
| `w_quality` | 未实现 | 没有评价数据 |
| `w_freshness` / `w_sales` | **刻意推迟** | 数据都在（`published_at` / `sales_count`）。但上面的系数是对着精排分定的，而 RRF 分同一路里第 1 名与第 2 名只差 1.6%、与第 20 名只差 31%：±5% 的时效会让相邻五六名按上架时间重排，999 销量的 1.3 倍会把第 20 名推到第 1 名前面——排序主体从相关度换成了销量。等精排落地、有 §9.1 评测集之后再定 |
| 毛利 | 不做 | 照下一节的建议默认关闭；连开关都没做——没有调用方会打开的开关是没有执行者的代码。另外 `skus.cost_cents` 默认 0，「成本未知」与「零成本」分不开 |

硬过滤（下架、删除、区域 / 门店不可售）仍在两条召回 SQL 的 `WHERE` 里，到不了这一层。

**`in_stock_only` 与降权的关系**：契约把 `filters.in_stock_only` 的默认值定成 `false`，
正是为了让「缺货降权」被执行而不是被过滤抢先（M3 独立验收 I10）。实现此前一直按 `true`
在跑，M5 一并改正：缺货商品默认出现、排在最后；显式传 `true` 才删掉。

### 关于毛利权重的诚实建议

技术上可以把毛利放进排序（`skus.cost_cents` 字段已预留）。
**但默认应当关闭。**

把毛利排进搜索结果，短期 GMV 上升，长期结果是：用户发现搜不到想要的东西 →
搜索使用率下降 → 整体转化下降。这是所有电商平台都踩过的坑。

若确需使用，建议：仅作为**同分时的 tiebreaker**，且权重上限 ±3%，
并通过配置开关控制、记录到 `search_logs` 以便回溯分析。

## 七、查询理解

### 7.1 按查询长度分流（无需模型，规则即可）

| 查询特征 | 策略 |
|---|---|
| ≤ 3 字，或含数字/字母型号 | 关键词路权重优先，向量路作补充 |
| ≥ 8 字，自然语言句式 | 向量路优先，并触发 LLM 意图抽取 |
| 中间长度 | 两路等权（默认 RRF） |

### 7.2 LLM 意图抽取（仅长查询触发）

```json
{
  "keywords": ["保暖", "礼物"],
  "category_hint": "服饰/围巾",
  "attributes": { "适用人群": "中老年", "季节": "冬" },
  "price_max_cents": 30000,
  "scene": "送礼"
}
```

抽取结果转为 `SearchFilters` 的过滤条件与向量查询文本。
**约束**：抽取失败或超时（> 150ms）时静默降级为纯检索，绝不阻塞主流程。

### 7.3 Query Rewrite

- 错别字纠正（基于历史高频查询词表做编辑距离匹配）
- 同义词/缩写展开（"笔电" → "笔记本电脑"，"AJ" → "Air Jordan"）
- 词表从 `search_logs` 中挖掘，不写死在代码里

## 八、延迟预算

目标：**P95 < 300 ms**（不含网络）

| 阶段 | 预算 | 备注 |
|---|---|---|
| Query embedding | 15 ms | 短文本，可与关键词召回并行 |
| 向量召回 | 30 ms | HNSW，`ef_search=100` |
| 关键词召回 | 20 ms | 与上并行，取 max 而非 sum |
| RRF 融合 | 1 ms | |
| **Reranker top-50** | **80 ms** | 大头，可降级 |
| 业务重排 | 5 ms | 需要库存/活动数据，建议缓存 |
| 结果组装 | 10 ms | |
| **合计** | **~160 ms** | 留一倍余量 |

> M5 的实际链路没有 Reranker 那 80 ms；业务重排是内存里对几百条候选的一次乘法与排序，
> 另加一次写 `search_logs` 的单行 INSERT（同步，上限 200 ms，失败不阻塞检索）。

**并行化**：query embedding 与关键词召回同时发起。
**降级链**：reranker 超时 → 用 RRF 结果；向量服务不可用 → 纯关键词 + 业务重排。
任何一环故障，搜索都必须仍能返回结果。

## 九、效果评估体系

没有评估体系的检索优化等于盲调。这一节的优先级**高于任何算法优化**。

### 9.1 离线评测集

从 `search_logs` 中采样 200–500 条真实高频查询，人工标注相关商品，
构建 `(query, relevant_product_ids)` 集合。

指标：**NDCG@10**（主）、**Recall@50**（召回层）、**MRR**（首位命中）

### 9.2 在线指标

| 指标 | 含义 |
|---|---|
| 搜索无结果率 | 最刺眼的问题，优先归零 |
| 首屏点击率 CTR@10 | 排序质量 |
| 搜索→加购率 | 真实意图匹配度 |
| 搜索→下单转化率 | 最终目标 |
| 二次搜索率 | 高 = 首次没搜到，负向指标 |

> **落地状态**：前四项算得出来了，第五项还不行。
>
> - **回传**：`/search` 响应带 `trace_id`（`search_logs` 那一行的定位键；日志没写进去时缺席），
>   客户端在点击 / 加购 / 下单**这次检索返回的商品**时调 `POST /search/events`
>   （`{trace_id, event, product_id}`，event ∈ `click` / `add_cart` / `order`），
>   服务端回填 `clicked_id` / `carted_id` / `ordered_id`。实现在 `service/search_event.go`。
> - **三条防护**：`product_id` 必须在这次的 `ranked_ids` 里，否则 422 一列不写
>   ——接口是公开的（与 `/search` 一样，访客也在点），不设这道闸门任何人都能拿一个
>   `trace_id` 刷某件商品的点击；每一列**首次为准**，重复回传 204 不覆盖，所以
>   天然幂等、不收 `Idempotency-Key`；租户隔离靠 RLS，别家店的 `trace_id` 与
>   不存在的是同一个 404。另有一只独立的按 IP 限流桶（默认 36/s，`/search` 的三倍：
>   一次检索至多三次有效回传），挡的是写放大而不是刷指标。
> - **统计**：`make search-metrics`（`scripts/search_metrics.sql`）按
>   店铺 × strategy × stages 输出无结果率、CTR@10、加购率、下单率与首次点击名次倒数的均值
>   （MRR 的在线近似）。后三个率的分母是「有结果的检索」。口径由
>   `handler/search_metrics_test.go` 用手算数据逐格锁住。
> - **二次搜索率还算不出来**：它要「同一个人的相邻两次检索」，而 `/search` 是公开接口，
>   `search_logs.session_id` 恒为 NULL。要它得先让客户端在 `/search` 上带一个会话标识——
>   那是一次契约变更，本轮没做。

### 9.3 可切换的排序策略

排序策略必须**可配置、可切换、可对比**：

```
strategy_id 写入 search_logs → 按策略分组对比线上指标
```

第一期不必做完整 A/B 分流，但接口层要预留 `strategy` 参数，
否则后续每次改排序都是不可逆的「拍脑袋上线」。

M5 的现状：认得两条策略——`rrf-biz-v1`（默认，含业务重排）与 `rrf-v1`（不含，
留作对照）。**一个策略名只指一条流水线**：业务重排上线时默认策略换了名字，
而不是让 `rrf-v1` 悄悄多做一层。`search_logs` 另记 `stages`（这一次真正跑过的阶段），
因为降级时 `strategy` 不变、向量那一路却没跑——只按 `strategy` 分组会把两种结果混进一桶。

## 十、与推理引擎的接口

```
POST /v1/embeddings
  { "model": "Qwen3-Embedding-0", "texts": ["..."], "normalize": true }
  → { "embeddings": [[...]], "dim": 1024,
      "model": "Qwen3-Embedding-0", "model_version": "..." }

POST /v1/rerank
  { "model": "bge-reranker-v2-m3",
    "query": "...", "documents": ["...", "..."], "top_k": 30 }
  → { "results": [{ "index": 3, "score": 0.91 }, ...] }
```

约定：

- 批量接口，禁止循环单条调用
- 索引侧批大小 32–64；查询侧一次一批
- 服务端超时后立刻返回，由调用方走降级链
- 模型名与版本随响应返回，写入 `search_logs` 以便归因

> 这两个接口是整个 AI 层与推理引擎的唯一耦合点。
> 保持接口稳定，引擎可独立演进（换模型、换量化、换硬件）而不动业务代码。

### 路径这一行改过一次，而改它的那次说明了「唯一耦合点」值多少钱

这一节原本写的是 `POST /v1/embed`，请求体里的 model 是 `bge-m3` —— 那是 M3
的实现（一个跑 BGE-M3 的 Python 服务）。M4 换成 infero 之后路径变成 OpenAI
风格的 `/v1/embeddings`，模型名变成引擎自报的 `Qwen3-Embedding-0`。

值得记下来的是**换引擎在代码里有多小**：请求体与响应体逐字段一致
（`{model, texts, normalize}` → `{embeddings, dim, model, model_version}`），
所以业务侧一行没动，动的只有 `internal/inference` 里的两个字符串。
keel-integration.md 那句「路径名可以谈，请求体形状不能谈」，说的就是这件事
——真正贵的是形状，不是名字。

两处**没有**跟着一起省下来的代价，写在这里免得下次低估：

- `model` 那个字符串是 `product_text_vectors.model_name` 的来源，它一变，
  库里全部存量行就该重算（§2.2）。这次靠的是增量任务按 model_name 逐轮追，
  外加一次 `keel-index -force`。
- `Qwen3-Embedding-0` 这个名字看着像被截断了，因为它确实是
  （infero 的 `derive_model_id` 用 `Path::file_stem()`，把 `.6B` 当扩展名丢了）。
  这里照抄引擎真的说出口的那个字符串，而不是好看的那个 ——
  完整论证在 `internal/inference/client.go`。

## 十一、实施顺序

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| 1 | Embedding 入库 + 向量召回 | 搜"连衣裙"能返回相关商品 |
| 2 | bigram 关键词召回 + RRF | 精确型号查询命中率 > 95% |
| 3 | Reranker 精排 | 离线 NDCG@10 相对阶段 2 提升 |
| 4 | 业务重排 | 缺货商品不再出现在首屏 |
| 5 | `search_logs` + 离线评测集 | 可量化对比策略优劣 |

> **M5 时点的状态**：阶段 1、2 已完成；阶段 4 完成库存因子（验收标准由
> `handler/search_test.go` 的 `TestOutOfStockIsDemotedNotDropped` 守着）；
> 阶段 5 的在线那一半已完成（`search_logs` + 行为回传 + `make search-metrics`，§9.2），
> 离线评测集还没有；阶段 3（精排）未开始，卡在推理引擎。
> 顺序因此与本表不同：阶段 4 先于 3 落地，而它能先落地正是因为只做了不依赖分数动态范围的那一个因子。
| 6 | 查询理解 + 对话导购 | 自然语言长查询可用 |

**阶段 5 可以提前，但绝不能省略。**
没有评测集，阶段 3、4 的所有调整都无法判断是变好还是变坏。
