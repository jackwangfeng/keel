# 性能压测摸底（2026-10-01）

一轮在私有测试栈上的性能摸底：拆分形态（core + 库存两进程两库），照[总体架构「九、性能与容量目标」](./电商系统-总体架构.md#九性能与容量目标)造了 10 万商品量级的数据，
压了买家读、搜索、购物车 / 试算、下单（含热点与秒杀）、后台和混合负载。**没有改任何业务代码**；
压测器、造数脚本和复现命令在 [scripts/loadtest](../scripts/loadtest/README.md)。

> **同机同跑，是下限。** 压测机就是被测机：20 核 61G，同时跑着公开演示站、推理引擎和别的项目的库。
> 压测开始前 load average 2.15，读场景压满时到 18，收尾时 14.2。所有数字（尤其 PG 吃满后的吞吐）都应当按「至少这么多」理解。

## 一、结论

1. **读侧的瓶颈是 PG CPU，而且几乎全花在「数总数」上。** 商品列表每个请求都对全店 10 万商品跑一次 `count(*)`（41 ms），
   只看有货再跑一次带 JOIN 的计数（110 ms）；取那一页本身只要 0.75 ms。于是默认列表在 PG 吃满 18 核时只有 **≈230 req/s**。
2. **小类目在大目录里最慢**：种子里只有几件商品的类目，列表要沿发布时间索引把 10 万行逐行过滤一遍（估 2.5 万行、实际 4 行），**67 req/s、p95 280 ms**。
3. **关键词搜索不达标**：长尾词（品牌 + 修饰 + 品类）的二元组 OR 召回命中近 1 万件，价格 / 图片 / 排序分对全部命中都算一遍再取前 N，
   单条 217 ms；16 并发时搜索整体 **p95 483 ms**（目标 < 300 ms），长尾 p95 747 ms。
4. **下单吞吐天花板 ≈150–160 单/s，与 CPU 无关**（app 2.4 核、PG 2.2 核）。采样里 78% 的活跃会话停在 `LWLock:WALWrite`：
   这台机器的盘 fdatasync 只有 330 次/s，而一单在 core 库要 ≈12.4 次提交、库存库 ≈3.7 次；协调器只有 32 张通行证，SAGA 时延直接换算成上限。
   实验：两库 `synchronous_commit = off` 吞吐翻倍到 282–307 单/s。下单 p95 在 16 / 32 / 64 并发是 172 / 267 / 466 ms，**仍在 500 ms 目标内**。
5. **付款后的通知外发会积压**：每付一单写 2 条通知 × 3 个渠道 = 6 行投递记录 + 2 个任务，渠道一个没配也照写。高峰积压 **5.2 万个待办、最老 239 s**，停压后约 10 分钟排空。
6. **后台每个请求都是一次写事务**（会话续活 `UPDATE staff_tokens ... RETURNING`），同一会话的并发请求排在同一行锁上：后台读接口 16 并发时平均 12–15 个会话在等锁。
7. 达标的：**商品详情 p95 3–11 ms（7900 req/s）**、门店解析 / 地址簿 16k req/s、购物车 p95 18 ms、试算 p95 12 ms、支付回调 p95 16–19 ms；
   全程 **0 个 5xx、0 次 lock_timeout、0 个 503 busy**；热点和秒杀都没有出现行锁排队（被协调器的通行证挡在前面了）。
8. 对比上次（列表 6300 req/s、下单 650 单/s）：列表的差距主要是**数据规模**（这次 10 万商品，`count(*)` 随商品数线性变慢），
   下单的差距主要是**部署形态与盘**（上次 3 实例 + Postgres 协调器、这次单 core + sqlite 协调器；每单的写也比当时多了通知投递、二阶段消息）。详见第五节。

## 六、发现的问题（按收益排序，只建议，未改代码）

### ① 列表每个请求都全量 `count(*)`（收益最大）

- **现象**：默认列表 227 req/s 吃掉 PG 16–18 核；p95 随并发线性涨。混合负载的拐点也是它。
- **证据**：`EXPLAIN ANALYZE`（keel_app、带租户上下文）——`CountProducts` 走 `idx_products_listing_published` 仅索引扫描 100023 行 + 两个对空覆盖表的 anti join，**41 ms**；
  `CountProductsInStock` 再对 `product_store_stock` 做 bitmap heap scan（4.9 万行）+ hash join，**110 ms**；同一请求里取第一页的 `ListProductsByStock` 只要 **0.75 ms**。
- **建议**：`total` 不必每次精确算。可选：按（门店, 类目, 只看有货）缓存 30–60 s，有货标记消息到达时失效；或只在第 1 页算、翻页沿用客户端带回的值；
  或契约加 `has_more`、`total` 改成「约」（`EXPLAIN` 估算 / `reltuples`）。
- **预计收益**：列表 PG 时间降一个数量级以上，默认列表从 ≈230 到数千 req/s；混合负载的拐点同步右移。
- **已改（2026-10-01）**：service 按（商户, 门店, 大区, 类目, 只看有货）进程内缓存 total 30 秒、上限 1 万个键（`internal/service/product_total_cache.go`，契约不动、仍是精确计数）。命中时一个请求不再数全店。

### ② 小类目在大目录里逐行过滤整张表

- **现象**：只有几件商品的类目，列表 67 req/s、p95 280 ms，比 2 万件的大类目还慢 6 倍。
- **证据**：`ListProductsByStock`（类目 2，有货段）沿 `idx_products_listing_published` 扫描，`Filter: (hashed SubPlan 3) AND COALESCE((SubPlan 4), false)`，
  `Rows Removed by Filter: 100019`，估 25006 行、实际 4 行，38.9 ms；无货段再来一遍 27.8 ms。类目过滤是 `category_id IN (按 path 前缀取子树)`，规划器只能猜选择率。
- **建议**：先把子树解析成 id 数组（同一事务里一条小查询），主查询写 `p.category_id = ANY($ids)`；
  加索引 `(merchant_id, category_id, published_at DESC, id DESC) WHERE deleted_at IS NULL AND status = 1`，叶子类目直接按序取前 N。
- **预计收益**：小类目列表从 60+ ms 到 1 ms 以内（PG 侧）。
- **已改（2026-10-01）**：照建议先取子树 id 数组；索引 `idx_products_listing_category`（00200）。按类目取页写成 `unnest(数组) × LATERAL` 每个类目按序取前 offset+limit 行（通用计划里也只能这么走），类目多、占比大时改走上架时间索引（`repository.perCategoryCheaper` 按缓存的件数选）。同一份 10 万商品数据：小类目有货段 37 → 0.29 ms、无货段 35 → 0.24 ms，小类目计数 18.6 → 0.14 ms；大类目第一页 1.2 → 1.1 ms（不退化）。

### ③ 搜索对全部命中算价格、图片和排序分再取前 N

- **现象**：长尾词 p50 378 ms / p95 747 ms（16 并发），是搜索不达标的全部原因。
- **证据**：「栖木复古地毯」切成 `栖木 | 木复 | 复古 | 古地 | 地毯`，OR 召回 **9980** 件；计划里价格 LATERAL `loops=9980`，执行 **217 ms**；
  常见词「连衣裙」命中 1996 件，29 ms；无结果 3–6 ms。`keyword_hit_products` 本身只占 25 ms。
- **建议**：内层只按 `ts_rank_cd` 排序取 `recall` 个 id，外层再 JOIN 价格与图片；召回先 AND（全部二元组）、不够再 OR 兜底；给 OR 召回设上限。
- **预计收益**：长尾 5–10 倍；搜索 p95 回到 300 ms 以内（关键词路径）。

### ④ 下单被 WAL 刷盘和协调器通行证限住

- **现象**：下单 ≈160 单/s 封顶，CPU 闲着（app 2.4 核、PG 2.2 核）。
- **证据**：32 并发下单时每 0.5 s 采样 `pg_stat_activity` 共 25 次，core 库活跃会话 **311 / ≈400 次停在 `LWLock:WALWrite` + 23 次 `IO:WALSync`**，库存库同样；
  `pg_test_fsync`：fdatasync 330 次/s（3 ms）；`pg_stat_database` 计数：每单 core ≈12.4 次提交、库存 ≈3.7 次；`pg_stat_wal` 20 s 内 2968 次 sync。
  对照：`synchronous_commit = off` → 282–307 单/s；协调器换 Postgres 存储（同一个 PG）→ 更差（又多一路刷盘）。
- **建议**：减少每单提交数（⑤ 是现成的一大块；SAGA 分支能合并的合并）；生产盘用低延迟 SSD / NVMe，协调器的 sqlite 放独立快盘；
  试 `commit_delay`（让组提交多攒几个）；`DefaultMaxInflight` 做成可配，盘快了之后它就是下一道闸。
- **预计收益**：每单少 ⅓ 提交约 +30–50%；盘换成 NVMe 估计 2–4 倍（未实测）。

### ⑤ 通知外发：没配渠道也每单写 6 行投递 + 2 个任务

- **现象**：下单高峰时 `notification.deliver` 积压到 **51,819 个待办、最老 239 s**，停压后约 10 分钟排空。
- **证据**：每付一单产生 `order_paid` + `merchant_order_paid` 两条通知，每条对 email / sms / wechat_subscribe 各写一行投递（全部 status 2 跳过，因为一个渠道都没配）；
  共 23.7 万条通知、71 万行投递记录对应 11.8 万笔已付订单。投递任务每次最多 20 个在途。
- **建议**：渠道未配置时不入队、不写投递行（或只写一行汇总）；投递任务批量认领；或通知本身合并到订单事务的 outbox 里一次写。
- **预计收益**：每单少 ≈8 行写和若干次提交，直接叠加到 ④；高峰不再积压。

### ⑥ 后台每个请求都是一次写事务，同会话并发排在一行锁上

- **现象**：后台读接口单请求 ≈8 ms，16 并发 p50 ≈50 ms、p95 ≈180 ms；改库存同一 SKU 与不同 SKU 的吞吐几乎一样（193 / 199）。
- **证据**：采样里后台场景平均 12–17 个会话处于等锁（`wait_event_type = Lock`），而 PG CPU 只有 1–3 核；会话校验是 `UPDATE staff_tokens SET last_seen_at = now() ... RETURNING`
  （db/queries/staff.sql，注释里写明了「每一个后台请求因此都是一次写事务」）。压测共用一个会话放大了它，但店员开多个标签页、批量导出、AI 员工并发调用都会走到同一行。
- **建议**：`last_seen_at` 节流——只在距上次超过 1 分钟时才写（校验仍用同一条带条件的语句保证「此刻仍有效」），或者校验走只读、续活异步批量写。
- **预计收益**：后台接口时延回到单请求水平，吞吐数倍；顺带少一路 WAL。

### ⑦ 深分页在 OFFSET 之前对所有跳过的行算价格

- **证据**：page=50（OFFSET 980）计划里价格聚合 `loops=1000`、图片 `loops=1000`，21.5 ms；第一页 0.75 ms。
- **建议**：先取这一页的 id（只用排序列与过滤列），再 JOIN 价格与图片；或改游标分页（`published_at, id` 之后）。
- **预计收益**：深分页 PG 时间降 ≈20 倍（再叠加 ① 的计数）。
- **已改（2026-10-01）**：列表先在子查询里定页（只用排序列与过滤列），价格与主图的 LATERAL 挂在那一页上：不筛类目 page=50 13.4 → 6.5 ms，价格 / 主图 loops 1000 → 20。另一个坑：深页、按类目筛时估算代价越过 `jit_above_cost`（58 万），每次先花 ≈200 ms 做 JIT 编译而执行只要 12 ms —— offset+limit > 100 时事务里 `set_config('jit', 'off', true)`（`repository.jitOffWindow`）。

### ⑧ 只看有货的计数走 bitmap heap scan

- **证据**：`CountProductsInStock` 110 ms，`product_store_stock` 按 `(store_id, product_id)` 主键位图扫描后回表取 `in_stock`。
  （造数时有货标记按随机顺序写入，物理分布比真实数据更散，这一项可能偏悲观。）
- **建议**：部分索引 `(store_id, product_id) WHERE in_stock`（或主键 INCLUDE `in_stock`）让它变仅索引扫描；根本解决仍是 ①。
- **已改（2026-10-01）**：部分索引 `idx_product_store_stock_in_stock (merchant_id, store_id, product_id) WHERE in_stock`（00200），计数改写成从它出发的内连接（原来的 `LEFT JOIN … COALESCE(in_stock, FALSE)` 让规划器没法化简外连接）：默认店 196 → 64 ms、30% 铺货的店 125 → 34 ms。它仍是 O(有货件数)，total 靠 ① 的缓存；只剩「整页落在无货段」时为算起点精确数一次。

### ⑨ 风险项：后台订单计数的「可空参数 + OR」写法在 generic plan 下会退化

- **证据**：`AdminCountOrders` 按手机号 / 单号，custom plan 0.08 / 0.02 ms；强制 generic plan 时都变成沿 `idx_orders_receiver_phone_col` 全扫，**58–77 ms**（12 万单）。
  这次压测里看到的是 custom plan（单请求 7.5 ms），但 pgx 的语句缓存一旦被规划器切到 generic，就是上千倍的差。
- **建议**：按有无筛选条件拆成几条语句，或对这类语句 `SET plan_cache_mode = force_custom_plan`。

### ⑩ 小项

- 进程重启时对账与有货标记全量刷新扫库存 260 万行，几秒内吃 1–1.5 核（启动后 10 s 内结束），多实例滚动重启时会叠加。
- core 业务池 20 条在读压满时全占满（`active` 峰 20–21），但瓶颈在 PG CPU，加池子没用；库存库连接全程空闲。

| 下单阶段后 12:24 | notification.deliver 27,287（116 s）| 0 | 28,406 成功 / 203 失败 | 22 / 21 |

- 协调器里「失败」的全局事务都是库存不足被补偿的订单（订单关到 90），没有卡住的事务。

- 积压只出现在通知投递（⑤）。

## 八、复现

工具与用法见 [scripts/loadtest/README.md](../scripts/loadtest/README.md)。这一轮的完整命令：

```bash
# 起栈（拆分形态，项目名 / 卷名独立）后造数据
go run ./scripts/loadtest/seed -core-dsn ... -inv-dsn ... -out /tmp/lt/fixture.json
# 拿后台令牌（引导 token 换会话）后整轮跑
PROJECT=<项目名> FIXTURE=/tmp/lt/fixture.json OUT=/tmp/lt/results KEEL_LT_ADMIN_TOKEN=... scripts/loadtest/run-all.sh
python3 scripts/loadtest/summarize.py /tmp/lt/results/results.jsonl --labels
scripts/loadtest/backlog.sh                      # 后台积压
# 对照：小类目列表
keel-loadtest -fixture /tmp/lt/fixture.json -scenario list-category -categories 1,2,3,4,5 -c 16,32 -d 30s
```

`EXPLAIN` 用应用账号、带租户上下文跑：`docker exec -i <pg> psql -U keel_app -d keel`，事务里先 `SET LOCAL app.merchant_id = '1'`。

## 九、这轮没覆盖的

- 语义检索与 reranker（会打到共享推理引擎，刻意没接）；搜索目标里「含 reranker」的那部分没量。
- 多实例、PgBouncer、只读副本；独立的压测机（这次压测器和被测栈抢同一台机器的 CPU）。
- 盘：只在这台共享机器的盘上测过，没有 NVMe 对照。
- 秒杀配额卖完那一刻的行为（配额 5 万、只卖出 9199）；退款、售后路径。
