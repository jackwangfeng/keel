## 一、发现的问题

### P0：SAGA 超时后幂等键永久锁死，客户必然重复下单（重复收款）

**触发条件**：下单的 SAGA 超过 `sagaWaitTimeout = 15s`（`internal/service/order.go:148`）未到终态。
C 档物理拆分后，下单要跨进程调库存服务与协调器，任何一侧抖动都会踩到。

**实测链（三条记录同一毫秒）**：

| 证据 | 值 |
|---|---|
| SAGA `order-1-202610080657236c7bac24bca66dbe0b` | create 06:57:23 → update 06:57:53，status=**succeed** |
| 订单 `202610080657236c7bac24bca66dbe0b`（id 50022）| created 06:57:23.224，status=**10（已支付）** |
| 幂等键 `chaos-e3-1791442643` | created 06:57:23.224，status=**0（in-flight）**，expire_at +24h |

操作过程：停掉 inventory 进程 → 下单 → 客户端在第 15 秒拿到
`409 idempotency-key-in-flight` → 恢复 inventory → dtm 重试分支成功，订单真实存在且已支付。
**但请求早已返回，没有任何人在等那个结果，幂等键再也没被回填。**

**后果（实测）**：

- 用同一把 key 重试 → 恒定 409。**把 `expire_at` 提前到过去模拟 24 小时后，仍是 409**
  （`order.go:704-705` 对 InFlight 只有 409 这一个出口，而 `admin_idempotency.go:221-225`
  对「记录刚好过期被清理」也返回同一个 409）。**这把钥匙永久锁死。**
- 客户换一把新 key 重试 → `201`，订单 50025 → **50026**。第一单已存在且已支付，
  于是**重复下单 + 重复收款 + 重复发货**，而客户从头到尾不知道第一单存在。

**代码根因**：`internal/service/order.go:704` 只处理「键在处理中」这个当下状态，没有任何路径在
SAGA 到达终态之后回填这条记录。`internal/service/admin_idempotency.go:237-239` 的注释写着
「0 处理中：单事务形态下按构造不可达，但『不可达』依赖的是一个会变的前提」——C 档把这个前提变成了现实，
而没有配套的回填。

**离触发有多近**：本次压测 `order-hot` c=256 一档的 `max` 延迟是 **12505 ms**，
距 15 秒阈值只差 2.5 秒。压测还没开始就出现 258 次 `503 inventory-unavailable`（同样没有人为停服务）。

**建议**：在 SAGA 分支回调里回填键（终态时把 `status` 写成 succeeded 并存下订单号），
或加一个后台 reconciler 按 gid 扫 `status=0` 的行、与 `trans_global` 比对后修正。
前者更准——回调本来就在 app 进程里，ctx 里已经有 trace 和订单上下文。

### P1：协调器不可用返回裸 500，没有 Retry-After

停掉 `dtmrs` 后下单：

```json
{"status":500,"title":"服务内部错误","type":"https://keel.dev/problems/internal"}
```

响应里**没有 `Retry-After` 头**（已 grep 确认）。

契约（OpenAPI 第 44–52 行）把结果分成三态：确定生效 / 确定没生效 / **无法判定 → 退避重试**。
协调器挂掉属于第三态，应该给一个可区分的 problem type 加重试提示，而不是 generic internal。
现在同一个故障域里两种不可用给了互斥语义：库存服务挂 → `409 in-flight`，协调器挂 → `500`。

附带一个可观测现象：这次 500 发生的同时，订单行 `50024` 已经建出来（status=0 待支付），
但客户端拿不到订单号，这单会变成僵尸待支付单直到 30 分钟超时关闭。

**规律很清楚：不查库的接口全部持平（差 <10%），查库的快了 3–32 倍。** 这排除了「机器变快」这个解释。

**根因查到迁移 `00200_product_listing_category_stock_indexes.sql`（2026-10-01 提交）** ——
它新建了 `idx_products_listing_category` 与 `idx_product_store_stock_in_stock`，
迁移注释直接点名要修基线报告的「六 ② ⑧」两条。所以基线里的 227 RPS 是**修复前**的数字，
而报告的「发现的问题」一节至今仍把这两条列为未修。

### 由此引出的两个文档/运维问题

1. **`docs/性能压测-2026-10.md` 已经不能作为容量依据** —— 核心数字差了 15 倍，且报告自称的瓶颈已被修掉。
2. **迁移 00200 自己写着那个隐患**：「CONCURRENTLY 失败会留下一条 INVALID 索引，IF NOT EXISTS 会把它当成已存在跳过」。
   本次实测三条相关索引 `indisvalid = true`（安全），但迁移里**没有任何存在性断言**——
   下次再失败仍然是静默的。只有 `scripts/check_migrations.py` 覆盖不到这一类。

### 与基线不可比的一处

基线是「协调器 sqlite」（进程内嵌入式），本次是独立 `dtmrs` 容器 + Postgres 后端。
下单吞吐 136.9 单/s（基线 160 单/s，慢 15%）、p95 109 ms（基线 267 ms，快一半）——
两个变量混在一起了，这组对比不干净。要严格对比得把 sqlite 形态再跑一遍。

## 三、没发现问题的部分（省得下次重复怀疑）

- **幂等并发**：同一把 key 并发 20 次 → 恰好 1 单（16 个 201 + 4 个 409 in-flight，15 个 `Idempotency-Replayed`）。正确。
- **库存行锁**：20 个并发订单打同一个 SKU，流水 `before_available` 严格递减无交错（72→49），
  `min(after_available) = 49`，无负库存。锁粒度正确。
- **统一 traceid**：机制齐全（HTTP 入口/RPC/SAGA query/自动注入 slog），但**请求路径基本不打日志** ——
  打一次真实搜索（200）之后 app 日志零新增，所以号统一了却看不到。这次没深挖。

## 四、我自己的判据错误（记录下来）

E2「超卖」**误报**了：查库存行时没按 `store_id` 限定，`limit 1` 取到了另一个门店的行（那行库存是 1），
而 20 个订单全落在 store 1（库存 72）。真实数据是流水 72→49 严格递减，没有超卖。
**取单行的查询不带 store_id 就得出「库存=1」的结论，是错的数据源支撑对的逻辑。**

另一个：我一度怀疑压测期间出现的 981 条 `status=2` 幂等键是 bug，读了买家侧代码后确认是对的
（`order.go:712-713` 明确处理 Failed，回放存档里的失败原因）。admin 侧那条注释不适用于买家侧。
