# AI 经营：规划（M9–M11）

> 2026-09-28 定稿。M9 的详细设计见 [AI经营-M9设计](./AI经营-M9设计.md)。

## 一句话

**Keel 不内置模型。商家把自己的 agent（Claude Code、Codex 或任何支持 MCP 的 harness）接进来，
Keel 给它一个员工账号、一套工具、一本手册、一个审批队列和一本账 —— AI 是店里的一名员工。**

## 为什么这是 Keel 最值得讲的事

- 主流开源电商（mall、Saleor、Medusa、Shopware）的 AI 几乎全在**卖货**一侧：搜索、推荐、客服。
  **进货、补货、定价、营销、售后** —— 商家每天花时间最多的地方 —— 没有人让 AI 去做。
- 让 agent 真正动手经营，难点不在「接一个模型」，而在**敢不敢把钥匙交出去**。
  Keel 在这件事上的底子是别人没有的，而这些底子原本只是「基础设施」：
  - 每个写接口**幂等**（Idempotency-Key / biz_id）：agent 重试不会重复扣、重复发；
  - **分级权限与管辖范围**（管理员 / 操作员 / 大区 / 门店）：AI 员工越权被拒，和人一样；
  - **行级安全**：agent 自己写的查询也查不到别家店；
  - **试算接口**（下单试算、活动预览）：动手之前先预演；
  - **分布式事务**：下单链路改一半不会留下脏数据；
  - **审计**：每一步可追溯。
- 于是对外的说法是：**第一个可以放心交给 agent 经营的开源电商系统**。

## 设计原则

1. **Keel 是手脚、规矩和账本，不是脑子。** 智能来自外部 harness，可替换；Keel 只提供能力与约束。
2. **AI 就是一名员工。** 它有自己的员工账号与角色，走和人完全一样的权限判定；没有「AI 专用后门」。
3. **写操作默认走提案。** agent 提出「证据 + 动作 + 预计影响」，人在后台一键批准或驳回；
   批准后由 Keel 执行（幂等）。按类别开放自动执行放到 M11。
4. **数字由 Keel 算。** 补货量、卖断日、活动测算这些由确定性代码作为「计算工具」提供；
   agent 负责判断、解释、取舍，不自己编数字。
5. **效果由系统量。** 每条执行过的提案自动复盘（执行前后的指标），
   「AI 员工本月带来了什么」是系统算出来的，不是宣传页写的。
6. **与 harness 无关。** 工具走 MCP，手册是 Markdown，触发靠事件 + 一个参考运行器；
   换一个 harness 不需要改 Keel。

## 里程碑

### M9 能接上（详见 M9 设计）

- AI 员工账号与接入密钥；MCP 服务（读工具、计算工具；写工具一律生成提案）；
- 提案队列与后台审批页；调用审计；
- 两本手册：巡店日报、补货；Claude Code 的参考运行器；
- 演示站：模拟经营数据 + 每天定时跑的 AI 员工。
- **验收**：演示站上 AI 每天发一份简报和若干补货提案，人批准后库存自动加上，提案页能看到执行结果。

### M10 能经营

- 事件触发（库存跌破预警线、无结果搜索激增、新售后单、每日定时）→ 唤醒 agent；
- 手册：滞销清仓、搜索缺口、售后审核、活动复盘；对应的写工具（都走提案）；
- 复盘：执行后 N 天自动对比指标，后台「AI 员工成绩单」。

### M11 能放手

- 自动授权策略：按工具类别开放自动执行，带单笔 / 每日上限；
- 只读 SQL 工具；
- 用第二个 harness（Codex 等）实测同一套接入，写进文档；
- 演示站公开的「AI 经营日志」页面。
