# 我给自己的电商系统做了故障注入，压测把它打出一个 P0：同一把幂等键永久锁死，客户必然重复下单

> 这不是一篇「我们做了很多测试」的博客。这是一篇**测试打穿了生产代码**的复盘，
> 里面有一条真实的 P0、一个我一开始判错的误报，以及一个至今仍未根治的边界。
> 全文的数字都来自隔离环境实测，报告原文在仓库里。

## 一、起因：为什么有人会去停掉自己的库存服务

因为我的压测数据全是绿的。

14 天里提交了 885 次，CI 全绿，`scripts/check-all.sh` 全通过，全量测试 26 个包通过。
然后我架了一个隔离栈（`keelchaos`，端口 38180，与演示环境完全隔离），灌了同量级的数据：
10 万商品 / 20 万 SKU / 260 万库存行 / 40 门店 / 5000 买家 / 5 万历史订单。

第一轮压测一切正常。`order-hot` 峰值 492RPS，p95 1378ms，压测自身触发了 258 次
`503 inventory-unavailable`——注意，**没有人停过任何服务**，这是高并发下的正常背压。

于是我做了这件此前从没做过的事：故障注入。

```bash
# 第一个动作就出事了
docker stop keelchaos-inventory-1
# 然后下一个请求
```

下单。15 秒后客户端拿到：

```http
HTTP/1.1 409
{"type":"https://keel.dev/problems/idempotency-key-in-flight"}
```

**这看起来是正确行为**——幂等键处理中，拒绝重复请求，天经地义。

然后我把 inventory 启回去，等待 SAGA 完成。数据库里的结果是：

| 证据 | 值 |
|---|---|
| SAGA `order-1-202610080657236c7bac24bca66dbe0b` | create 06:57:23 → update 06:57:53，status=**succeed** |
| 订单 `202610080657236c7bac24bca66dbe0b` | created 06:57:23.224，status=**10（已支付）** |
| 幂等键 `chaos-e3-1791442643` | created 06:57:23.224，status=**0（处理中）** |

**订单真实存在、客户真的付了钱，而那把幂等键还在「处理中」。**

## 二、P0：一把永远不会翻面的钥匙

我做了两个验证。

**第一个**：用同一把key 重试。

```http
HTTP/1.1 409 idempotency-key-in-flight
```

再试一次，还是 409。

**第二个**：我怀疑是 24 小时过期时间没到，于是手工把 `expire_at` 改到过去，模拟 24 小时后。

```http
HTTP/1.1 409 idempotency-key-in-flight
```

**这把钥匙永久锁死了。**

原因在代码里只有几行。`replay()` 处理「键在处理中」这个状态时，**只有一个出口**：
返回 409。它不检查订单到底怎么样了。而 `admin_idempotency.go` 里那行注释写着：

> 「0 处理中：单事务形态下按构造不可达，但『不可达』依赖的是一个会变的前提」

这句话是对的，但**它只保护了管理员后台那条路径**。买家侧那条路径上，
"SAGA 超时后请求已返回、而 SAGA 之后可能成功"这件事，从来没有任何地方记下来过。

于是链路变成这样：

1. SAGA 卡在库存服务调用上，超过 `sagaWaitTimeout = 15s`
2. 请求带着 409 返回给客户端 —— **客户端此时完全不知道订单可能已经在推进**
3. SAGA 重试成功，订单变成 status=10（已支付）
4. **但没有任何人在等那个结果，幂等记录再也没被回填**

而幂等协议给客户端的唯一出路就是「用同一把key 重试」。重试得到的是 409。
于是理性的客户端只能换一把新钥匙：

```http
POST /orders   Idempotency-Key: chaos-e3-1791442643   →  409  （第一单已存在且已支付）
POST /orders   Idempotency-Key: chaos-e3-1791442644   →  201  （第二单）
```

**重复下单、重复收款、重复发货，而客户从头到尾不知道第一单存在。**

### 离触发有多近

这次压测 `order-hot` c=256 那一档的最大延迟是 **12505ms**，距 15 秒阈值只差 2.5 秒。

**它不需要有人停掉服务，只需要一次稍微慢一点的请求。** 我是在手动停掉一个服务之后
才把它稳定复现出来的——那个更容易触发的版本，恰好在正常压测里擦着边过去了。

## 三、这不是新代码引入的

收到反馈的第一反应是「最近改坏了」。查下来不是：

- 处理逻辑和 `sagaWaitTimeout = 15s` 来自 **2026-09-26** 的设计；
- **2026-10-02** 把事务协调器从内嵌 SQLite 改成独立 `dtmrs` 容器，跨进程 HTTP 调用
  带来了新的抖动，把这条路径从「几乎踩不到」推成「一压就踩到」。

**放大器是新的，被放大的那个洞是三个月前的。**

而原来的测试为什么没抓到？因为**没有一条测试覆盖「等待超时之后 SAGA 反而成功」**——
所有幂等测试都在测「真正并发」和「真正失败」，没人测过「请求走了、事情后来成了」。
这条路径在设计上就存在，只是一直需要一次特定时序才被触发。

## 四、修法：不追那个已经返回的请求，让重试自己查库

第一个念头是在 SAGA 分支回调里回填幂等键。**这是错的**：回调可能永远不来
（进程重启、协调器落库后连接断开），而客户端已经拿到 409 在重试了——
**修一个可能不发生的路径，不如修一个一定发生的路径**。

最终的做法是把「结果判定」从「等待那个请求」换成「重试方自己查库定论」：

**第一步：落草稿时，在同一个事务里把单号记进幂等行。**

```sql
-- name: MarkIdempotencyInFlightOrder :execrows
-- 它写的是 response_body，但 status 仍是 0：那一列在这里临时当
-- 「还没最终」的暂存位用，与存档是两件事。
UPDATE idempotency_keys
   SET response_body = $5::jsonb, updated_at = now()
 WHERE scope = $1 AND subject_kind = $2 AND subject_id = $3 AND idem_key = $4
   AND status = 0;
```

**第二步：重试时按订单的真实状态分派。**

```
读到 status = 0（处理中）
├── 没有暂存单号    → 409 处理中（真在跑）
├── 单号查不到      → 释放这把钥匙，409（下次重试是全新尝试）
├── 订单 status = 0 → 409 处理中（SAGA 真在推动这一单）
├── 订单 status = 90 → 存失败存档，报业务失败（不再是 409）
└── 订单 status = 10/20 → 补成功存档并回放该订单
```

最后一条是关键：**补上成功存档，这把钥匙才真正回到「成功」档**，从此同键重试走回放。
而且这个办法**不依赖当时那个请求还活着**——进程崩了、SAGA 还在跑、客户端隔天才重试，
都能自愈。

顺带在 `ON CONFLICT` 上加了回收条件（原来只有 `DO NOTHING`）：

```sql
ON CONFLICT (scope, subject_kind, subject_id, idem_key) DO UPDATE
   SET request_hash = EXCLUDED.request_hash, expire_at = EXCLUDED.expire_at
 WHERE idempotency_keys.status = 0 AND idempotency_keys.expire_at < now();
```

只回收「处理中**且**已过期」那一行，不会抢走真正在跑的请求。

### 一个只有自己会撞上的坑

写完第一版测试直接 panic：`reportSecondConn`。

原因是我在 `replay()` 里调了 `archiveSuccess()`，而那个函数走
`finishKey → s.repo.WithTenant` —— **在已经是事务的上下文里又开了一个事务**，
同一个连接上嵌套开事务会死锁自己。

修法是加事务内版本 `archiveSuccessTx` / `archiveFailureTx`。这类「开事务的函数不能
在事务里调」的约束在代码里没有任何语言级保障，只能靠写的时候记得——**这条我记在了
函数注释里，因为下一个读到这里的人就是我**。

## 五、P1 顺手也修了：协调器不可达不该是 500

停掉 `dtmrs` 再下单，得到：

```json
{"status":500,"title":"服务内部错误","type":"https://keel.dev/problems/internal"}
```

**没有 `Retry-After`。**

500 的 `internal` type 在客户端读作「服务端写错了代码，重试也不会好」；
而协调器挂掉会自己恢复，退避后原样重试才是对的处置。更糟的是同一个故障域里
库存服务不可用回的是 409/503，**两种同样会自愈的依赖给出互斥语义**。

改法是在网络层分类，而不是在 handler 里猜：

```go
// 判据是 net.Error 与 context 的两类超时，外加一条明确标记。
// **故意不解析错误字符串** —— 那是最容易在重构时静默失效的做法。
func IsUnavailable(err error) bool {
    if err == nil { return false }
    if errors.Is(err, ErrUnavailable) { return true }
    var netErr net.Error
    if errors.As(err, &netErr) { return true }
    return errors.Is(err, context.DeadlineExceeded)
}
```

现在返回 `503 coordinator-unavailable` + `Retry-After: 10`。

**细节在于这个 503 不保证「这笔一定没下」**——协调器可能落库之后才断的连接。
所以 detail 里明确写「用同一个 `Idempotency-Key` 原样重试即可，服务端保证不会重复下单」。
让客户端以为「这次一定没下」而换一把新钥匙，那才是**把一个 503 变成一次重复下单**。

`Retry-After` 是 10 秒而不是幂等那档的 2 秒：协调器重启通常要十几秒，
客户端拿到钥匙重试时还会先撞一次「处理中」，退太快只是白跑一趟。

## 六、收尾：一个我一开始想错的地方

自愈时如果订单被补偿关掉了（status=90），需要给客户端一个失败原因。
我第一版直接返回了 `ErrOrderSagaFailed`——那是 500。

**但它本来是个 500 的东西被用错了地方。** 那一单是被库存不足正常补偿掉的，
业务上完全正常，却因为报告成了「服务端状态异常」。

顺着查下去发现更麻烦：补偿失败的原因**存在进程内的 map 里**，而原始请求返回时
`defer s.notes.drop(gid)` 就把它删了。自愈发生在之后，所以**原因本来就查不到，
这是常态不是异常**。

最后没有编一个业务原因，而是新增一个诚实的类型：

```
503 order-outcome-unknown
「结果确定不成功（商品没售出，库存已回补，没有重复下单），但具体原因暂时无法查证。」
```

**查不到原因，不等于「原因是什么」，也不等于「服务端坏了」。**
编一个业务原因报出去更糟——那会让客户端显示一条它无法处理的错误。

（顺带记一笔：`replayableFailures` 那个编码表必须加 `outcome_unknown` 条目，
不加会被兜底写成 `saga_failed`，回放时又变回 500。这个兜底很值钱，也很容易忘。）

## 七、我自己判错的一次：超卖是误报

压测里我一度报了「20 个并发订单打出超卖」。
查库存流水时看到 `after_available` 出现负数，第一反应就是锁粒度错了。

再查，发现**我的判据查询漏了 `store_id`**：`limit 1` 取到了另一个门店的库存行，
那行库存是 1，而 20 个订单全落在库存 72 的那个门店。

纠正后的数据是：流水严格递减 `72 → 49`，`min(after_available) = 49`，无负库存。

**锁是对的。我那条「取单行不带 store_id」的查询才是错的。**

记这一笔是因为：**错的数据源能支撑出完全正确的逻辑，而且看起来毫无破绽。**
如果我少查一步，这个「发现」会带着一份看起来很严谨的证据进到 CHANGELOG 里。

## 八、验证：两个自己会红的判据

改完之后我做了两件事，都刻意构造了「必然失败」的情形。

**第一，把测试的 SKIP 变成真 PASS。** 过期键回收那条测试最初是**静默跳过**的——
夹具造的两单选中了同一个 SKU，业务上提前失败，根本走不到过期回收那一步。
报告里它显示为「跳过」，不在失败列表里。改成不同数量之后才是真的跑过。

**这里有个通用教训**：跳过不等于通过。我后来的验收脚本里，任何 `skip` 都单列在
汇总外面，绝不混进「全绿」。

**第二，故意让一条判据红。** 我不想让「验收脚本自己错了」变成下一个 P0，
所以先构造了一个必然失败的场景，确认闸门真的会红。

最终验收：

```
scripts/check-all.sh          → GATE_EXIT=0
go test ./... -count=1 -p 4   → TEST_EXIT=0，24 个包通过
```

## 九、至今没修的三件事

1. **失败原因没有持久化字段。** 要让「库存不足」在自愈时也能原样回放，
   得给订单表或协调器结果加一列。库存侧的 `inventory_logs.reason` 是有的
   （跨进程持久化），订单侧没有。这次没做，是设计取舍。
2. **没有后台 reconciler。** 纯靠客户端重试来自愈，那客户端再也不来的遗留行
   （`status = 0` 且没有任何 SAGA 会再推进它）要靠后台扫。
3. **基线压测报告已经过时。** 本次测出查询类接口比基线快 3–32 倍，
   根因是 `00200` 迁移新建的索引——而那份报告的「发现的问题」一节至今
   仍把这两条列为未修。

## 结语

我没有一次「读代码读出来的 bug」。这三个问题全部是**跑出来和打出来**的：
停掉一个服务、把 `expire_at` 改到过去、漏掉一个 `store_id`、造一个必然失败的场景。

**测试的价值不在于「覆盖了多少」，在于「有没有构造过那个会红的时刻」。**
我原来的 26 个包全绿，覆盖率 respectable，但它们测的全是「事情按设计走」。
而这三个问题，全部发生在「事情没按设计走」的缝里——那缝只有故障注入能照到。
