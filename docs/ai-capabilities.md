> 召回。实测表与完整的后果见[总体架构](./电商系统-总体架构.md) §1「那个缺口」与 §6 形态 A。

## 一、三个底座

清单里三分之二的功能，在底座建成后退化为「调两个接口 + 一段 prompt + 一个页面」。
先铺底座再铺功能，顺序反了会重复造轮子。

### 底座 A · 推理服务

四个接口撑起全部 AI 能力：

| 接口 | 用途 | 对应里程碑 |
|---|---|---|
| `POST /v1/embeddings` | 文本 / 图像向量 | M3 / M8（文本那一半 M4 起跑在 infero 上） |
| `POST /v1/rerank` | cross-encoder 精排 | M5 |
| `POST /v1/generate` | 带 schema 约束的结构化生成 | 远期（2026-09-26 路线图重排） |
| `POST /v1/forecast` | 时序预测（Chronos-2） | 远期（2026-09-26 路线图重排） |

> **`generate` 的 schema 约束是自建引擎相对通用 API 的实打实优势**：
> 引擎侧用约束解码保证输出合法，避免「解析失败→重试→再失败」的循环。
> 属性抽取、卖点提炼、评价归因全部依赖它。

### 底座 B · 商品理解服务

把商品从「一堆字段」变成「可被机器理解的对象」。所有消费侧（搜索、导购、
拍照搜同款、风控、比价）共用同一份理解结果，而不是各自重新处理一遍。

### 底座 C · 数据智能层

指标语义层 + Text-to-SQL。让商家用大白话查自己的数据，而不是学会写 SQL 或
等运营出报表。

## 二、能力清单

价值 / 难度用 高·中·低。「依赖」列填底座代号或其他能力编号。

「需积累」分三档，这个区分很要紧——把两类混为一谈会导致排期错判：

| 取值 | 含义 |
|---|---|
| **否** | 冷启动即可有效果 |
| **业务** | 需要订单 / 评价 / 查询日志攒够，但不涉及个人画像。**开店几周即可**|
| **行为** | 需要**用户行为画像**积累。这一档在冷启动阶段无论投入多少都做不出效果 |

架构文档 §12 说的「五项早期做不出效果」，指的是**行为**这一档。

## 三、早期做不出效果的五项

第 33–37 项（「需积累」列标 **行为** 的那五项）**依赖用户行为画像积累**，
冷启动阶段无论投入多少都做不出效果。

注意与标 **业务** 的那几项（20、25、28、29、31、32）区分：那些只要开店几周、
订单与日志攒起来就能做，不该被一并推迟。

处理方式：**预留接口，不前期投入。** 具体地说——
`search_logs` 从第一天就埋（第 23 项），订单与退货数据本来就在库里，
等数据够了再开这五项，那时是「调两个接口」而不是「从头设计」。

把它们排进早期里程碑是典型的资源错配：花最大的力气，得到最差的效果，
还会让人误以为「AI 推荐没用」。

## 四、三条纪律

**一、每个 AI 功能必须有评测方式。**
说不出「怎么判断它变好还是变坏」的功能不要做。检索侧的评测体系（第 23 项）
优先级高于任何算法优化。

**二、写操作永不由模型执行。**
模型只做理解与路由，所有写操作走 GUI 确认。这规避了 prompt injection
与误操作资损——商品文本是第三方可控输入，它会进入 LLM 上下文。

**三、AI 故障不得阻塞交易主链路。**
推理引擎挂了，搜索降级为纯关键词，商品照常上架，下单支付完全不受影响。
唯一的例外是第 6 项合规检查——那里宁可误拒。
