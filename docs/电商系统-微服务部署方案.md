# 微服务部署方案：协调器独立、依赖单向

> 状态：**已施工（2026-10-02，用户拍板「直接上独立的 dtmrs 协调器」）**，代码 dccb49a 起；演示站切换记在 PROGRESS。上一期把库存拆成了独立进程（[微服务拆分方案](./电商系统-微服务拆分方案.md)），
> 这份文档回头审视「拆开之后怎么部署」，起因是用户指出的两件事：**嵌入式协调器在多实例下反而成了累赘**；
> **服务之间互相调用，方向乱**。

## 一、结论

1. **两种形态，协调器跟着形态走，不混用。**
   - 单体（一个进程，`KEEL_ROLE=all`）：协调器**嵌入**进程，零运维，分支全是 `local://`。不变。
   - 微服务（`core` + `inventory` + 以后的服务，各自多实例）：协调器**独立部署**成 dtmrs 集群，所有服务都只是它的客户端，
     **任何服务进程里都不再嵌协调器**。
2. **同步调用只许向下。** core 依赖库存，所以只有 core → 库存的同步调用；库存不知道 core 的存在（代码里不出现、配置里也不出现）。
3. **向上只发事件。** 底层的变化发到**主题**（dtmrs 0.12 的 topic，与 DTM 同协议），谁关心谁在协调器上订阅；
   二阶段消息「本地事务与消息原子提交 + 回查」的语义不变，只是投递目标从写死的地址变成主题。
4. **商家后台、后台任务都不拆成独立服务**，用同一份程序的不同实例做隔离（第七节）。

## 二、现状（2026-10-02，拆分部署 C 档）

| 进程 | 嵌入的协调器 | 存储 | 它推进的事务 |
|---|---|---|---|
| core | 有 | `sqlite:/var/lib/keel/dtm.db` | 下单 SAGA；活动配额同步消息（core → 库存） |
| inventory | 有（配了 `KEEL_CORE_URL` 才起） | `sqlite:/var/lib/keel/inventory-dtm.db` | 有货标记消息（库存 → core） |

服务间调用：

| 方向 | 调用 | 性质 |
|---|---|---|
| core → 库存 | 查水位、SAGA 扣减 / 回补、配额同步投递 | 正常（上层用下层） |
| 库存 → core | 有货标记消息投递到 core 的 `stock_changed` | **反向** |
| 库存 → core | 配额同步收到后，回 core 读配额定义（`RemoteQuotaSource`，`KEEL_CORE_URL`） | **反向** |

## 三、问题

1. **多实例时嵌入式没有省事。** 3 个库存实例 = 3 个嵌入的协调器，必须共用一个 Postgres 当存储（sqlite 跨容器不能共享），
   效果等于一个协调器集群，却散落在业务进程里：连接池按「实例数 × (业务池 + 协调器池)」涨，协调器的升级跟着业务发版走，
   排查要先找「这笔事务在哪个服务的协调器里」。
2. **发布方一多，订阅就碎了。** 每个发事件的服务各有一个协调器、各存一份订阅表。库存、营销、商品都发事件时，
   订阅方要记住每一家的协调器地址、各订一遍；主题也没有全局视图。
3. **依赖成环。** 两处反向调用让库存必须配 `KEEL_CORE_URL`：库存起不来不影响 core，但 core 起不来，库存的配额同步会一直重试，
   而且库存的部署配置里写着上层的地址——再加服务，就是面条。

## 四、目标形态

```
                ┌────────────── dtmrs 集群（≥2 实例，独立 Postgres 库，Bearer 令牌）──────────────┐
                │  事务表 / 租约 / 主题订阅表（全局唯一一份）                                        │
                └──────▲──────────────────────▲──────────────────────────┬──────────────────────┘
          提交 SAGA / 发消息│            发消息（topic）│                  调分支（HTTP，分支令牌）│
                ┌───────┴──────┐      ┌───────┴──────┐                    ▼
                │  core × N    │─同步─▶│ inventory × M│        各服务 /internal/v1/saga/<分支>
                └──────────────┘ 向下  └──────────────┘        屏障记在分支所在服务自己的库里
```

- **dtmrs 集群**：独立容器，≥2 实例（租约选主、崩溃接管已有），存储用专用的 Postgres 库（可以和业务库同一台机器，
  不同库、不同账号）。服务调它带 `DTMRS_AUTH_TOKEN`（dtmrs 已有，`Authorization: Bearer`）。
- **服务**：只认 `KEEL_DTM_SERVER`（协调器地址）+ `KEEL_DTM_TOKEN`；不再有 `KEEL_DTM_DSN`。
- **分支**：全部是 `http://<服务内网地址>/internal/v1/saga/<名字>?bt=<分支令牌>`，包括 core 自己的步骤
  （核销券、建单）——微服务形态下这几步多一次本机回环，换来协调器与业务进程解耦。分支体是同一个函数，不改。
- **回查**：二阶段消息的回查分支也变成发送方自己的 HTTP 地址（查的仍是发送方库里那行屏障）。

### 4.1 依赖规则与两条消息的新接法

**规则**：同步调用只能从上往下；下层要告诉上层「我变了」，发到主题，自己不知道谁在听。上层收到后可以**向下**回源读。

| 消息 | 现在 | 改成 |
|---|---|---|
| 有货标记（库存跨 0） | 库存的协调器投递到 core 的 `stock_changed` 地址 | 库存发到 `topic://stock.zero_crossing`，载荷 `{"store_id", "sku_ids"}`（只有键），打开 `allow_empty_topic`；core 启动时订阅；core 收到后**向下**回库存读水位重算（不变） |
| 活动配额同步（core 改配额） | core 投递给库存，库存**向上**回 core 读定义 | core 把**完整的配额定义 + 版本号**放进载荷投递给库存（定义是 core 自己刚写进去的数据，和消息同一个本地事务提交）；库存按版本号只接受更新的那份，不再回 core 读——反向调用消失 |

配额那条不再「回源」是有意的：「接收方回源读最新」这条约定，前提是源头在接收方的**下游**或同级。
这里源头在上游，回源就是反向依赖；而载荷来自发送方同一个本地事务、带单调版本号，乱序、重复都由版本号挡住，
可靠性与回源等价。总体架构 §7 的约定要补这一条（见第八节）。

改完之后库存服务不需要 `KEEL_CORE_URL`，也不需要任何协调器配置以外的上游地址。

### 4.2 订阅怎么登记

- core 启动时调协调器的 `subscribe?topic=stock.zero_crossing&url=<core 自己的分支地址>`；返回「this url exists」当成功（幂等），
  失败退避重试，**不阻塞启动**（没订上之前，库存那边 `allow_empty_topic` 让消息直接完成，靠每小时对账兜住）。
- core 有 N 个实例时，订阅的 URL 是 core 的**服务地址**（负载均衡后的那个），不是某个实例的地址——所以 N 个实例订的是同一行，
  重复订阅幂等。
- 下线 / 改地址：先订新地址，再退订旧地址（先扩后收）。

## 五、Keel 要改的代码

调用面不大：业务代码只用到 `SubmitSaga / WaitFinal / PrepareMsg / SubmitMsg / AbortMsg / Status` 六个方法
（`service/order.go`、`service/promotion_quota_msg.go`、`inventory/stock_msg.go`）。

1. **`internal/dtm` 抽一层接口**（`Coordinator`），两个实现：
   - `embedded`：现在的 FFI 实现，原样。
   - `remote`：dtmrs HTTP API 的客户端（`/api/dtmsvr/submit`、`prepare`、`abort`、`query`），带 Bearer 令牌；
     `WaitFinal` 用 `query` 轮询（现在嵌入式也是等终态，语义一致）；每实例在途上限（`maxInflight`）留在客户端这一侧。
   - `PrepareMsg` 加主题、载荷、`allow_empty_topic`（dtmrs 0.12）。
2. **配置**：`KEEL_DTM_SERVER` / `KEEL_DTM_TOKEN` 与 `KEEL_DTM_DSN` 二选一，都配或都不配拒绝启动；
   `KEEL_ROLE=core|inventory` 时必须用 `KEEL_DTM_SERVER`（微服务不许嵌入），`all` 时两种都行。
3. **分支地址**：`BranchResolver` 加「本服务自己」的地址（`KEEL_SELF_URL`），远程协调器模式下 core 自己的分支、
   回查分支都解析成 HTTP；core 的内网路由挂上这些分支（`dtm.MountBranches`，机制已有）。
4. **消息改造**：有货标记改发主题 + 载荷（顺带去掉「把门店和 SKU 编进 gid、超长拆条」的绕法）；配额同步改成载荷带定义 + 版本，
   删掉 `RemoteQuotaSource` 与 core 上的 `MountQuotaSource`。
5. **启动订阅**：core 启动后台订阅（第 4.2 节）。
6. **部署文件**：`compose.split.yaml` 加 `dtmrs` 服务（官方镜像或从源码构建）与它的 Postgres 库；库存与 core 都去掉 `KEEL_DTM_DSN`
   和协调器卷；库存去掉 `KEEL_CORE_URL`。
7. **测试**：下单 SAGA、两条消息、补偿、崩溃恢复这几组在 CI 里各跑两遍——嵌入式一遍、真起一个 dtmrs 容器再跑一遍。

### 5.1 独立部署 dtmrs 与嵌入式的差别（dtmrs-db 对着 0.12.0 代码核过，2026-10-02）

- **鉴权只有一种令牌、不分权限**：设了 `DTMRS_AUTH_TOKEN`（或管理台密码）后，除 `/health` 外全部接口都要 `Authorization: Bearer`，
  能 subscribe 的令牌也能 prepare / abort。嵌入式的订阅端口（`serve_topic_api`）用单独的共享密钥、只开订阅接口。
  独立后「订阅方只有订阅权限」这层隔离没有了；要的话 dtmrs 可以做按令牌分权限，接入前决定。
- **gRPC 只认环境变量里的令牌**：管理台签发的托管令牌只在 HTTP 上认（已知问题，待 dtmrs 修）。Keel 走 HTTP，不受影响。
- **订阅者地址只能是 `http(s)://` 或 `grpc://`**：`local://` 在独立部署下不会被拒，但永远投不出去、一直重试——Keel 的配置校验要挡住。
  独立部署没有静态登记，只能调 `subscribe`（4.2 本来就是这么设计的）。
- **空主题计数只有嵌入式能读**：独立部署时只有一条 WARN 日志（「主题没有订阅者，按 allow_empty_topic 放行」），没有指标接口，先按日志告警。
- **多实例一致**：订阅存在共享存储里，每次 prepare 直接读库、不缓存，集群各实例看到的订阅关系一致。

## 六、演示站切换步骤

1. 先发 dtmrs 0.12，Keel 接好接口层，嵌入式回归通过（行为不变）。
2. 起 dtmrs 集群与它的库；core / 库存仍是旧版，**先把两个嵌入式协调器里的在途事务排空**：停止接新单（维护页）→
   等两个 sqlite 里没有未终结的事务（`Status` 查不到 prepared / submitted）→ 切新版配置 → 恢复。
   在途事务不迁移：两个存储格式虽然一样，跨存储搬事务没有必要，排空几十秒就完。
3. 验收：下单、取消、退款回补、改库存跨 0、改活动配额各走一遍，管理台里能看到事务；停一个 dtmrs 实例，另一个接手。

## 七、后台要不要单独拆

- **商家后台接口**：不拆成独立服务。它和买家接口是同一份数据、同一套业务规则，拆开只是多一层调用。
  真要隔离（买家流量高峰不拖慢后台），用**同一份程序多部署一组实例**，网关按路径（`/api/v1/admin/*`）分流到这组即可，代码不动。
- **后台任务**：不拆。`KEEL_BACKGROUND=off` 已经能让接请求的实例不跑任务，单独留一两个实例跑（扫描类任务本来就选主）。
- 判断标准与拆库存时一样：**有独立的数据、独立的扩容理由、边界清楚**才拆。后台和任务都不满足第一条。

## 七之一、服务发现：交给平台，Keel 只认服务名

**不做服务发现模块，也不接注册中心 SDK。** 服务地址都是配置项，配的是**服务名**而不是 IP：
`KEEL_INVENTORY_URL=http://inventory:8090`、`KEEL_DTM_SERVER=http://dtmrs:36789`。名字由部署平台解析——
docker compose 用内置 DNS，k8s 用 Service（后面几个实例、谁挂了、负载均衡都是平台的事）。代码不知道有几个实例、各在哪。

唯一的规矩：**凡是写进别处的地址，都写服务名**。主题订阅登记的 URL（4.2）、SAGA 分支地址、回查地址，一律是经过负载均衡的
服务地址，不是某个实例的 IP——实例增减、重启换 IP 都不影响已经登记的东西。

什么时候才接注册中心（Consul / Nacos / etcd）：没有容器编排、服务直接跑在虚拟机上；要客户端侧负载均衡（按权重、就近、按版本灰度）；
跨机房多集群；服务几十上百个、频繁上下线。Keel 今天一条都不满足。真要接也只动一处：把「配置里的服务名」换成「启动时向注册中心
解析出的地址」，或者让注册中心提供 DNS（Consul、Nacos 都支持）——后者连代码都不用改。

## 七之二、Serverless 部署（方案，暂不实施）

**结论：容器型 serverless（Cloud Run、Knative、阿里云函数计算容器模式）能用；函数型（AWS Lambda、传统云函数）不建议。**
前提就是本文的微服务形态：协调器独立、服务只认服务名。嵌入式协调器在 serverless 下不成立——实例没请求时被冻结或回收，
没人推进在途事务；独立之后协调器经 HTTP 调分支，serverless 按请求拉起实例，正好对上。

### 要补的四样

| 项 | 现状 | serverless 下的问题 | 做法 |
|---|---|---|---|
| 后台任务 | 每个实例按 `KEEL_BACKGROUND` 跑常驻循环（超时关单、对账、通知投递、相关度预判……），扫描类选主 | 实例会被冻结，循环跑不了；选主连接被掐断 | serverless 实例一律 `KEEL_BACKGROUND=off`，另留**一个常驻的普通实例**专跑后台任务。不把任务逐个改成平台定时触发——十几个任务逐个改造，收益只是省一台小机器 |
| 数据库连接 | 每实例一个业务池 + 一个库存池 | 一扩容就是几十上百个实例，连接数打爆 Postgres | 前面加连接池代理（PgBouncer，事务模式；或云厂商的 RDS Proxy），每实例池上限调到 2–4。注意事务模式下不能用会话级状态——Keel 的租户是 `SET LOCAL`（事务级），选主用的 advisory lock 只在常驻的后台实例上，不受影响 |
| 上传文件 | 本地磁盘 driver（`KEEL_UPLOAD_ROOT`，compose 里的 `uploads` 卷） | 实例没有持久磁盘 | **已落地（2026-10-02）**：`KEEL_UPLOAD_DRIVER=s3`（OSS / COS / S3 / SeaweedFS），存量用 `cmd/keel-uploads migrate` 搬 |
| 进程内状态 | 按 IP 限流、列表总数缓存（30 s）、地图瓦片缓存都在进程内存里 | 实例多了：缓存命中率下降（只影响性能）；限流变成每实例各算各的，等于放宽 | 限流挪到网关（或接 Redis）；缓存保持进程内即可，必要时瓦片缓存交给 CDN |

### 其他要知道的

- **同步等待的请求**：下单要等 SAGA 到终态（几百毫秒到几秒），商品导入、报表导出是长请求。容器型 serverless 的请求时长上限一般够
  （分钟级），按请求时长计费会贵一点；函数型的上限与冷启动叠起来不合适，这是不建议函数型的主要原因——Keel 是一个完整的 Web 服务，
  硬拆成函数等于重写路由层。
- **冷启动**：Go 程序本身启动快；微服务形态下不再需要 dtmrs 的动态库，镜像可以更小（远程协调器模式下用编译标签去掉 cgo，
  第五节的接口层顺带做）。迁移不能在实例启动时跑，由发版流程单独跑一次 `migrate`。
- **协调器与推理服务不上 serverless**：dtmrs 要常驻推进事务（无状态、可多实例，但不能被冻结）；infero / Kev 要 GPU，
  常驻部署，或用 GPU serverless（冷启动要加载模型，几秒到几十秒）。
- **最小实例数**：买家接口设 1–2 个常驻实例，避免流量低谷后第一个请求吃冷启动。

### 改动清单（实施时）

1. ~~对象存储 driver~~（已落地，2026-10-02）。
2. 限流配置改成可以关掉（交给网关），或接 Redis。
3. 远程协调器模式下的无 cgo 构建。
4. 部署文件：serverless 服务定义（买家 / 后台 / 库存各一组）+ 一个常驻后台任务实例 + dtmrs 集群 + PgBouncer。

前三项都是在已有接口上加实现，不动业务代码。

## 八、要同步修改的约定

- 总体架构 §7「派生数据同步约定」补两条：
  ① 下层通知上层用**主题**，发布方不知道订阅方；
  ② 「接收方回源读最新」只在源头位于接收方下游或同级时成立；源头在上游时，由发送方把数据和单调版本号放进载荷，接收方按版本号接受。
- 微服务拆分方案「服务间调用」一节改成指向本文。
- 部署指南：环境变量表加 `KEEL_DTM_SERVER` / `KEEL_DTM_TOKEN` / `KEEL_SELF_URL`，删去拆分形态下的 `KEEL_CORE_URL`。

## 九、代价与风险

| 项 | 说明 | 怎么兜 |
|---|---|---|
| 协调器成了下单的必经之路 | dtmrs 集群整体不可用 → 下单全停 | 协调器无状态，挂了重启即可，没推完的事务租约到期后接着推；真正要保的是它的库：放在业务库同一套 Postgres 主备上（不同库、不同账号），主库挂了切备库、协调器重连即恢复。≥2 实例主要为了滚动升级不停服 |
| 每个分支多一跳网络 | core 自己的步骤从函数调用变成本机 HTTP | 同机房 1 ms 量级；下单的瓶颈在 WAL 落盘（压测报告 ④），这点不改变结论 |
| 多一个要运维的组件 | 升级、监控、令牌轮换 | dtmrs 自带管理台与 `/health`；令牌按 `DTMRS_AUTH_TOKEN` 文档轮换 |
| dtmrs 版本与 Keel 绑定 | 主题、载荷、`allow_empty_topic` 要 0.12 | Keel 启动时检查协调器版本，低于要求拒绝启动 |

## 十、工作量与顺序
