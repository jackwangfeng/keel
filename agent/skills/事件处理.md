# 手册：事件处理

**什么时候**：被事件唤醒时（运行器轮询 `agent/runner/claude-events.sh`，或 AI 员工配了 webhook 被推送叫醒），
而不是每天定时全量巡一遍。

## 看哪些工具

- `list_events`（拉事件）、`ack_events`（确认处理到哪条）。
- 按事件类型分派到对应手册（见下）；`list_my_proposals`（读 `proposal_decided` 事件时用）。
- `post_brief`（只在有值得播报的情况时用）。

## 步骤

1. `list_events()`：不传 `after_id`，从上次 `ack_events` 的位置接着读。`limit` 用默认（50）即可。
2. 按 `id` 升序逐条处理，按 `type` 分派（见下表）。
3. 处理完这一页，`ack_events(up_to_id = next_after_id)` 确认；如果 `has_more` 为真，接着
   `list_events(after_id = next_after_id)` 读下一页，重复到读完。
4. **游标只进不退**：确认过的事件下次不会再来（webhook 是至少一次，重复的按 `id` 去重就好，不用当新事件重处理）。
5. 只有出现值得播报的情况（新提案、需要店长决定的事、从驳回里学到的教训）才 `post_brief`；纯粹「事件正常执行
   成功、没什么好说」的不必发简报，省得刷屏。

## 按类型分派

| type | 怎么处理 |
|---|---|
| `stock_low` | 对 `payload` 里的 `store_id` + `sku_id` 跑一遍 [补货.md](./补货.md) 里同样的判断：`restock_plan`
  算这一个（门店，SKU），满足条件就 `propose_inventory_adjust`，不满足就记进简报。 |
| `refund_created` | 按 [售后审核.md](./售后审核.md)：`list_refunds`（`status: 10`，可以按 `store_id` 缩小范围）
  找到 `payload.refund_no` 对应的这条，走同样的同意 / 驳回 / 只写简报判断。 |
| `search_zero_spike` | 按 [搜索缺口.md](./搜索缺口.md)：针对 `payload.query` 这个词，`list_products` /
  `get_product` 看有没有匹配商品，决定改标题还是只报「上新机会」。 |
| `proposal_decided` | 不是让你重新提案，是让你**学**：`list_my_proposals` 读这条提案的最新状态与
  `reject_reason` / `outcome.verdict`。被驳回的记住理由，下次同类情况别再犯一样的错；`verdict` 是
  `negative` 的记进这周对 `my_scorecard` 的判断（要不要收着提这一种）。 |

## 什么时候提案 vs 只写简报

跟着分派到的那本手册的判断规则走；事件处理本身不改变判断，只是换了个「怎么知道该看哪儿」的入口——
不要因为「被事件叫醒了」就降低证据要求或者跳过查重。

## 证据怎么写

跟分派到的那本手册一致；额外在 `evidence` 或简报里注明是被哪个事件触发的（比如「由 stock_low 事件
触发（event_id=1234）」），方便店长追溯。

## 上限

- 各事件类型分派后遵守各自手册的上限（补货 ≤10 条/次、`flash_price` ≤20 SKU 等）；
- 一次唤醒把 `list_events` 能读到的都处理完再 `ack_events`，不要处理一半就确认导致漏事件；
- `proposal_decided` 事件不产生新提案，只用来调整判断，不占提案上限。
