# 手册：售后审核

**目的**：帮店长把简单明确的售后申请先审一遍——该同意的不要拖，说不清楚的留给人。
**这个种类永远不会被自动执行**：`refund_decision` 不进 M11 的自动执行策略（资金动作，库里 CHECK 挡住），
提了之后一定要等人批准才会真的执行。

## 看哪些工具

- `list_refunds`（`status: 10` 待审核）。
- `list_my_proposals`（查重：同一 `refund_no` 是否已有待处理提案）。
- `propose_refund_decision`（提案：`action: approve` / `reject`）。

## 判断规则

对每一条待审核售后单，看 `order_status`（订单履约状态）与 `refund_type`（1 仅退款 / 2 退货退款）：

- **同意（approve）**：订单还没发货（`order_status` 是 10 待支付或 20 已支付，都属于「未发货」）——这种情况下
  不管仅退款还是退货退款，货本来就没寄出去，同意退款没有额外风险；
- **驳回（reject）**：只在有具体、买家能看懂的理由时才驳回，比如金额与订单实付不符、同一笔已经有一条待处理
  的售后在走、或者明显不满足店铺售后政策里写死的条件。驳回理由 `reject_reason`（≤200 字）要让买家读得懂
  「为什么」，不要写「不符合规定」这种模板话——写不出具体理由就不要驳回，留给人审；
- **不确定就只写进简报，不提案**：订单已经发货（`order_status >= 30`）之后的售后，是否需要等买家寄回、
  货有没有问题、金额算得对不对，这些判断超出「确定性计算」的范围，交给店长自己审，简报里列出来提醒
  「已发货订单的售后，等店长处理」即可。

## 什么时候提案 vs 只写简报

- 未发货 + 理由清楚 → 提 `approve`；
- 有具体、可复现的驳回理由 → 提 `reject`；
- 已发货、金额存疑、理由含糊、或者拿不准 → 写进简报，不提案；
- 同一 `refund_no` 已有待处理提案 → 跳过。

## 证据怎么写

`evidence` 里写清楚：`list_refunds` 的调用参数（`status`、`store_id` 如果有）、这条售后单的
`refund_no`、`order_no`、`order_status`、`refund_type`、`amount_cents`（同时写元）、`reason_code` /
`reason_text`、`created_at`，以及判断依据，例如：

> list_refunds（status=10）：售后单 RF20260928001，订单 ORD20260920003，order_status=20（已支付未发货），
> refund_type=1（仅退款），金额 4900 分（¥49.00），reason_text「拍错了不想要了」。订单未发货，同意退款
> 不影响履约。

驳回同理，把「为什么」写进 `evidence`，`reject_reason` 是给买家看的那句话，两者可以不同（`evidence` 给店长看
判断依据，`reject_reason` 给买家看结论）。

## 上限

- 没有金额 / 数量上限（工具本身不限），但**永远不能自动执行**——即使店长以后给别的种类配了自动执行策略，
  `refund_decision` 也不受影响，提了照样要等人批；
- 判权按订单的履约门店：门店范围的 AI 员工只能审自己店履约的订单；
- 同一 `refund_no` 已有待处理提案会被拒；
- 拿不准就写简报，不要为了「清空待审核列表」硬审。
